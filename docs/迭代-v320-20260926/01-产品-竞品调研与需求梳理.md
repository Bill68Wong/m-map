## 1. 调研范围与方法

- **直接竞品（4）**：面向「轻轨 / 地铁实时报时与月台信息」场景。
  1. 港铁 MTR Mobile（含轻铁 PIDS 月台屏 / Next Train）
  2. 深圳地铁 App（+ 广州地铁微信小程序「列车到站查询」作同源参照）
  3. Moovit（已收录澳门轻轨氹仔线）
  4. 官方基线：澳门轻轨官网（mlm.com.mo）· 澳门交通事务局 DSAT「巴士报站」与 data.gov.mo 开放数据
- **替代方案（3）**：面向「地图导航 · 用户位置体系」场景（用户本次多条需求明确以谷歌 / 高德为参照）。
  1. Google Maps（蓝点 / 回中按钮 / 双钉 / 公交导航 / 下车提醒）
  2. 高德地图（蓝点 / 回中 / 公交模式 / 定位省电策略）
  3. Citymapper（GO 模式 + 下车提醒，作为「流程化导航」参照）
- **局限性**（须向用户说明）：澳门轻轨与 DSAT **均无面向第三方的分钟级实时到站 API**（DSAT 报站数据自带短时预测；轻轨官网仅提供**静态发车时刻表**）。因此本项目的「秒级读秒」本质是**「官方时刻表 + 自采样偏差」派生值**，与竞品的「官方实时流」不在同一数据层——这一点决定了免责声明与降级策略的写法。

## 3. 关键机制提炼（竞品怎么做 → 我们能学什么）

### 3.1 倒计时粒度：秒级 vs 分钟级
- **行业事实**：几乎所有地铁 / 轻轨 App 与月台屏都是**分钟级**。原因有二——① 官方数据流本身是分钟级；② 分钟级天然「容错」，1 分钟误差不会显得刺眼。[港铁轻铁 PIDS](https://hkrail.fandom.com/wiki/%E4%B9%98%E5%AE%A2%E8%B3%87%E8%A8%8A%E9%A1%AF%E7%A4%BA%E5%B1%8F) · [广州地铁](https://news.qq.com/rain/a/20251028A043YK00)
- **秒级只在「已知绝对时刻」时才有意义**：即「一个确定的发车时间戳 + 本地时钟倒数」，本质是**秒表**，而非「实时流推断」。港铁月台屏采用「一边显示当前时钟、一边显示到达时间」也是同一思路。
- **对本项目的启发**：我们的 `depMs + 设备本地时钟倒计时` 与「秒表」机理一致——**不受网络 / 获取延迟影响**，这是**机制上的正确解**。风险不在机制，而在「我们承诺的秒级精度，与派生值的真实误差是否匹配」。

### 3.2 「现正到达 / 即将到站」状态与阈值
- **行业惯例窗口**：福州「即将到站 = 60s 内」；港铁月台「5 分钟内广播」。**结论：秒级窗口是行业通行的「到达态」触发带**。
- **归零后行为**：竞品普遍在「到达」态**驻留一小段时间再滚下一班**（避免班次切换过快导致误读）；本项目「读秒班次驻留 10s、无读秒班次驻留 30s」属同类设计。
- **对本项目的启发**：阈值按线路区间时长差异化（石排湾全线约 2 分钟 → 2:00 进「现正到达」合理）**符合逻辑**；核心缺陷是**站台报时卡与推荐卡两处口径不一致**——行业做法是「同一状态在任何入口表现一致」。

### 3.3 免责声明与可信度标注
- **Moovit 是最佳范式**：不只写免责，还**用颜色/图标让用户一眼看出「这条时间有多可信」**（绿 / 黄 / 红 / 黑，黑=无实时）。[来源](https://support.moovitapp.com/hc/en-us/articles/13145331853842-Ver-5-125-Arrival-Time-Accuracy-Guide)
- **国内惯例**：「仅供规划参考，以实际为准」几乎逐字一致（福州、广州、武汉、Delhi Metro 均如此）。
- **对本项目的启发**：00 文档定稿的「报时数据通过澳门轻轨时刻表推算，仅供参考，请以实际为准」**方向完全正确且合规吻合**（对应铁律 9「派生值须说明算法」）。建议进一步**在 UI 层体现数据来源差异**——读秒班次（四大模式）与不读秒班次在视觉上可留一个极轻的区分（如小角标），让用户知道「哪些是真读秒」。**但注意**：不要引入与项目 Token 体系冲突的硬编码色值；区分应走既有 Token。

### 3.4 蓝点：更新频率 · 平滑 · 置信圈 · 回中按钮
- **更新频率**：Google「每几秒一次」；高德**正常约 1s、省电模式 3~5s**（并明确因此产生漂移）。→ **本项目「1~3s 高频 + 浏览态降频」与行业一致**。[Google](https://techyorker.com?p=166813/) · [高德省电](https://m.toutiao.com/article/7675511688577204759)
- **平滑**：Google 靠**地图匹配**让蓝点「吸附 / 滑行」到路网，而非硬跳。→ 本项目「平滑移动动画」等价实现，且设计规格（doc 12 §B.3）已改用 `transform/opacity` 保证合成层性能，**方向正确**。
- **置信圈**：半透明圈 = 误差半径，圈大=不准。→ 本项目可**低优先级**考虑（个人项目可先不做，或仅在精度差时提示）。
- **回中按钮状态语义**：Google「拖走后按钮呈未居中态，点击回中并恢复跟随」；近期还用**上下文浮动按钮**（缩放到自身位置 / 操作罗盘时出现，探索远处时隐藏）。→ **本项目合并为右侧栏单一图标时，务必保留「跟随 / 未居中」两态反馈**，否则用户不知当前是否在跟随。

### 3.5 起终点钉的全程显示策略
- **Google 惯例**：路线预览显示「起点钉 + 终点钉 + 路线」；进入导航后仍保留终点钉（+ 当前箭头）。→ **本项目「红钉起点 / 绿钉终点」全程显示 = 行业惯例**。
- **潜在坑（技术）**：本项目终点钉通过 **CSS `background: url("/pin-destination.svg")`** 引入，**CSS 自定义属性不会穿透到外部 SVG 文档**；若 SVG 内 `fill` 写成 `var(--x, fallback)`，**部分 Android WebView 会因解析不到 `var()` 而使整张外部 SVG 渲染失败（整图不显示）**——这与用户「Android 全程没见过钉」的现象高度吻合，而桌面可能因浏览器容错而正常。→ **零风险修复 = SVG 内写死颜色**（与 doc 12 §B.1 结论一致）。

### 3.6 公交模式「下车提醒」的位置与形态
- **Google / Citymapper 一致**：**顶部横幅 / 粘性通知**，措辞「该下车了 / 该换乘了」，且**即便切到别的 App 也能在通知栏看到**。理由——公交乘客容易「睡着 / 走神」，顶部是最不挡地图、最醒目的位置。[Google 公交导航](https://arstechnica.com/gadgets/2017/12/google-maps-finally-gets-step-by-step-transit-navigation/) · [The Verge](https://www.theverge.com/2017/12/15/16763340/google-maps-train-bus-stop-transfer-alerts)
- **对本项目的启发**：需求 8「横幅移到页面最顶部」= 行业标准做法。设计需处理：**系统状态栏安全区（safe-area-inset-top）**、与品牌栏 / 头部按钮的层级、以及与需求 12「右上刷新按钮」的**同屏共存不遮挡**。

### 3.7 线路标签（route badge）形态
- **Google Maps 惯例**：每条线路一个**圆角药丸块**，用**线路主题色**，**白字**；多条线并列时块间留**浅缝**。
- **本项目特有形态**：00 文档定稿目标 = **v0.19.1「谷歌地图风格」**（整组圆角外框 + 块间「右上→左下」**斜切留白缝** + 白字），且明确「不是 `/` 字符」。→ 形态本身是行业惯例的**本地化变体**，合理。
- **历史缺陷提醒**：v2.2.1 时代「overflow 改 visible 导致容器圆角碎裂」；v3.1.1 白字丢失。→ 实现须解决「组级圆角 + 块间留白缝 + 白字不被遮挡」三者的兼容。

### 3.8 纵轴 / 流程图的离散进度表达
- **行业事实**：Google 等主流采用**连续**进度（蓝点沿路线滑动）。**离散进度（点的位置跳变）**多见于**站条 / 流程条**这类抽象视图（如深铁 App「剩余站数」）。
- **对本项目的启发**：需求 6「停站离站后点瞬移到两站中点并驻留」是**为可读性服务的主动量化**（点不与站点节点堆叠）。建议**加一段很短的缓动（约 200~300ms）**替代「硬瞬移」，避免被误读为卡顿 / 故障；并明确「中点驻留不随进度微动」的边界（何时才更新）。

## 4. 13 项需求逐项建议

> 格式：**行业最佳实践** → **用户真实期望（挖掘）** → **我们的取舍建议** → **风险 / 验收点**

### 需求 1 · 轻轨偏差值入库 + 氹仔线读秒
- **最佳实践**：主流 App 均分钟级；秒级仅在「已知绝对发车时刻」时成立（本质是秒表）；且行业普遍区分「实时 / 计划 / 推算」数据可信度并显式免责。
- **用户期望**：不是「要精确到秒」本身，而是**「车快到的那几秒要可信、不要跳来跳去」**——用户原话「趟次波动是可以被精确的」说明其真正诉求是**模式判定正确后的稳定读数**。
- **取舍建议**：① 秒级读秒**仅覆盖四大主力模式**（≈98%），深夜零星变体保持分钟级——同意；② `depMs + 本地时钟` 机制**保留**（不受获取延迟影响，机制正确）；③ 免责句按 00 文档「站台报时卡放完整句 / 紧凑处放『推算』小角标、字小不换行」执行；④ **建议在 UI 加极轻的来源区分**（读秒 vs 推算），但**必须走既有 Token、禁硬编码色**。
- **风险 / 验收**：模式判定错 → 用错偏差 → 秒级错得更显眼（比分钟级更伤信任）。**验收**：四大模式逐站抽样比对；模式判定边界（相邻模式切换时刻）专项复验。

### 需求 2 · 「现正到达」显示策略
- **最佳实践**：秒级「到达态」窗口（福州 60s / 港铁 5 分钟广播）；到达态驻留后再滚下一班；同一状态在任意入口表现一致。
- **用户期望**：**「两处不一致」是本次真正的痛点**——用户要的是「同一个班次，站台卡和推荐卡看到的是同一件事」。
- **取舍建议**：① 阈值按线路差异化（氹仔 0:30 / 石排湾 2:00 / 横琴 1:00）**符合区间时长逻辑**，保留；② 归零后驻留（读秒 10s / 无读秒 30s）**保留**；③ **核心动作 = 统一站台报时卡与推荐卡的判定与文案**（同一条计算函数产出）。
- **风险 / 验收**：读秒归零与「下一班开始读秒」之间可能出现**短暂空档或双态重叠**。**验收**：跨归零时刻连续录像，确认无闪烁 / 无「回退」。

### 需求 3 · 导航模型轻轨时间精细化
- **最佳实践**：Google 等用 GTFS `stop_times` 的**逐段运行时间**（每段独立），而非「站数 × 常数」。
- **用户期望**：推荐卡总用时**不准**（媽閣↔海洋跨海段被少算）。→ 用户要的是**「排序和时间可信」**。
- **取舍建议**：① 用**实测区间用时（发→发）**替换「跳数 × 2 分」**= GTFS 逐段模型，方向正确**；② 石排湾 100s / 横琴 135s 保持并复核；③ 统一 `model.ts`/`score.ts`、站条换乘行、in-line 读秒**同一口径**。
- **风险 / 验收**：单次样本 ≠ 常数（铁律 33 / 14 号文档）。**验收**：跨海段（媽閣→海洋）单独实测；总用时与真机实测误差目标 ≤ 1 分钟。

### 需求 4 · 蓝点任何时候显示
- **最佳实践**：Google 在授权后即显示蓝点；未授权时地图仍可用（渐进增强）。
- **用户期望**：**「打开地图就想看到我在哪」**——即时反馈。
- **取舍建议**：① 打开地图页即请求定位（用户已确认）——同意；② **必须有「拒绝 / 失败」兜底**（不空白、显示默认视野 + 可手动搜索）；③ 显示条件 = 「只要有一次有效定位就常显」。
- **风险 / 验收**：部分浏览器 / WebView 要求**用户手势**才弹权限，自动弹可能被拒；Android 可能弹「精确 / 约略」。**验收**：真机三种授权结果（允许精确 / 允许约略 / 拒绝）各跑一遍。

### 需求 5 · 起终点钉全程显示（+ 排查）
- **最佳实践**：Google 在预览与导航全程显示起点 + 终点钉。
- **用户期望**：**红起点 / 绿终点要「看得见、认得出」**。用户 Android「全程没见过」→ 说明**当前实现对其机型完全失效**（非样式偏好问题）。
- **取舍建议**：① 定位根因（见 §3.5）：**外部 SVG + `var()` 在部分 Android WebView 整图失败**；② **零风险修复** = `pin-destination.svg` / 新增 `pin-origin.svg` 内**写死颜色**（`#0B6E4F` 绿 / `#B4342A` 红），不依赖 CSS 变量穿透；③ **必须真机（Android）复现定位**，不能只看桌面 / Playwright。
- **风险 / 验收**：钉可能被蓝点（z128）/ 车辆（z130）覆盖，或被面板遮挡。**验收**：Android 真机「选起终点 → 选路线 → 导航全程」逐帧确认双钉可见。

### 需求 6 · 纵轴用户点（站点流程图）
- **最佳实践**：连续进度为主流；离散进度用于站条类抽象视图，目标是**可读性**。
- **用户期望**：**点要清晰、不与站点节点堆叠**（可读性 > 位置精度）。
- **取舍建议**：① 「停站离站后瞬移到中点并驻留」**方向合理**；② **建议加 200~300ms 缓动**替代硬瞬移，避免误判为卡顿；③ 明确「何谓『接近下一站 / 新数据到达』」的触发边界，防止抖动。
- **风险 / 验收**：频繁触发会显得「跳」。**验收**：连续多站运行，观察点是否单调推进、无来回抖动。

### 需求 7 · 定位更新频率（行程体感）
- **最佳实践**：Google「每几秒」+ 地图匹配平滑；高德正常约 1s、省电 3~5s（无隐患时可用高频）。
- **用户期望**：**「跟着我走」的手感**——不是要绝对精度，是要**跟手、不滞后、不跳**。
- **取舍建议**：① 行程态 1~3s 高频 + 平滑动画**同意**（手机 GPS 不经高德 / DSAT，配额无隐患）；② 浏览态降频省电（阈值由设计师 / 架构师定，建议 5~10s 或按需）；③ **动画走 `transform/opacity` 合成层**（延续 doc 12 §B.3 性能结论），避免高频下掉帧。
- **风险 / 验收**：高频 + 重绘会导致移动端掉帧 / 发热。**验收**：真机导航 10 分钟，确认蓝点跟手且无明显卡顿 / 发热。

### 需求 8 · 下车横幅位置
- **最佳实践**：Google / Citymapper = **顶部横幅 / 粘性通知**，最醒目且不挡地图。
- **用户期望**：**「要下车时一眼看到」**——顶部最符合（导航模式无搜索条，顶部本就空）。
- **取舍建议**：① 移到页面最顶部**同意**；② 规格需含**系统安全区**、与品牌栏关系、与需求 12 头部按钮**不遮挡**、非阻塞 + 可自动消失 / 手动关闭。
- **风险 / 验收**：遮挡左上返回 / 右上刷新。**验收**：横幅显形时，返回、刷新、地图关键信息均可见可点。

### 需求 9 · 「回到我的位置」按钮处置
- **最佳实践**：Google = **单一**定位控件（避免重复入口）。
- **用户期望**：**不要两个「回到我」**（左下按钮 + 右侧定位图标功能重叠，反造成困惑）。
- **取舍建议**：① 导航模式去掉左下角按钮**同意**；② 能力由右侧栏定位图标承担**同意**；③ 首页默认地图也不加该按钮**同意**（右侧栏已覆盖）。
- **风险 / 验收**：右侧图标需**保留「跟随 / 未居中」两态反馈**（承接 §3.4），否则用户不知是否在跟随。

### 需求 10 · 导航模式右侧栏精简
- **最佳实践**：按模式隐藏无关控件，减少遮挡。
- **用户期望**：**导航时界面干净**——只看需要的。
- **取舍建议**：导航模式隐藏「查看路线」图标与「M Map logo」，仅留定位**同意**；过渡时避免布局跳动。
- **风险 / 验收**：隐藏后相关能力入口是否彻底不可达（查看路线仅首页可用——确认无导航内路径依赖）。**验收**：导航模式右侧栏只剩定位图标。

### 需求 11 · 右侧栏随弹窗避让
- **最佳实践**：Google 用 **map padding** 让控件始终位于 sheet 之上，随 sheet 移动。
- **用户期望**：定位图标**永远不被弹窗盖住**。
- **取舍建议**：① 图标底距**绑定弹窗当前档位高度**（peek80 / half50 / full96-128），始终在弹窗上沿「上方一点点」**同意**；② 随拖动**同步动画**；③ **须定义 full 档行为**——面板近乎全屏时图标如何处置（建议：full 档时吸附到面板上沿之上角落或临时隐藏）。
- **风险 / 验收**：档位切换时若计算滞后会「穿帮」。**验收**：三档 drag 来回，图标始终不重叠。

### 需求 12 · 导航弹窗头部按钮重构
- **最佳实践**：Google 公交导航用**情境相关动作**（该步才出现对应操作）。
- **用户期望**：**叉 = 关闭**带来「会退出导航」的担忧；改成**刷新**更贴合「我想让数据更新」的诉求（用户真正想要的是「数据刷新」）。
- **取舍建议**：① 左上返回保留、右上叉改刷新**同意**；② 刷新情境化（recommend 刷路线 / detail + riding 刷巴士数据）**同意**；③ 刷新时给**加载反馈**、不适用时禁用；④ **须确认「结束导航」仍有出口**（去掉叉后，返回键或其它控件需能结束导航）。
- **风险 / 验收**：删除叉后结束导航路径丢失 = 严重问题。**验收**：各态下刷新行为正确 + 结束导航可达。

### 需求 13 · 线路标签形态修正
- **最佳实践**：Google = 每线一圆角药丸块 + 主题色 + 白字，多块间浅缝。
- **用户期望**：**「文字在正中、不被遮挡、不跑位」+ 恢复白字**——比形态更重要的其实是**可读性**。
- **取舍建议**：① 目标形态以 00 文档为准（**v0.19.1 谷歌地图风格**：组级圆角 + 块间「右上→左下」斜切留白缝 + 白字，**非 `/` 字符**）；② 实现须解决历史「圆角碎裂」与「白字丢失」；③ 覆盖单块 / 多块 / 多段（`→`）/ `+N` / `size="sm"` / 深色主题。
- **风险 / 验收**：某些线路主题色偏浅 → 白字对比不足。**验收**：全部线路（含浅色线）截图确认白字可读、缝为「留白」非字符。

## 5. 风险与边界（个人项目 / 数据受限场景）

| # | 风险 | 影响 | 建议边界 |
|---|---|---|---|
| R1 | **秒级读秒放大派生值误差** | 模式判定或偏差值漂移 → 读秒明显出错，信任受损 | 仅四大模式读秒；判定边界专项复验；UI 区分「读秒 / 推算」 |
| R2 | **外部 SVG + CSS 变量不穿透（Android WebView）** | 钉整图不显示 | SVG 内写死颜色；Android 真机验证（非桌面 / Playwright 代替） |
| R3 | **无官方实时流** | 无法做到竞品级实时 | 明确「推算」定位；免责句常驻；不承诺「实时」（用「推算 / 参考」措辞） |
| R4 | **高频定位耗电 / 掉帧** | 移动端发热、卡顿 | 行程态高频、浏览态降频；动画走合成层 |
| R5 | **删「叉」后结束导航入口丢失** | 用户被困在导航 | 需求 12 实施前先确认结束导航出口 |
| R6 | **弹窗 full 档遮挡定位图标** | 控件不可达 | 定义 full 档处置（吸附 / 隐藏） |
| R7 | **数据样本量不足**（铁律 33 / 14 号文档） | 常数化误判 | 标注 `measured_on`；新样本按同口径增量；禁单次记录当常数 |
| R8 | **视觉硬编码色值**（P0 红线） | 违反项目 Token 体系 | 一律走既有 Token；唯一例外 `#fff`/`#000` |

**不适合个人项目 / 数据受限场景的做法（明确「不做」）**
- 不做「精度置信圈」的复杂可视化（Google 级多源融合）——个人项目无多源数据，先不引入。
- 不做「地图匹配（map-matching）吸附路网」——需路网几何 + 算法投入，MVP 用「平滑动画」替代。
- 不做「锁屏 / 通知栏级下车提醒」——PWA 能力受限，用页面内顶部横幅替代。
- 不引入「Moovit 式四色可信度」完整体系——可用「读秒 / 推算」二元轻量区分替代。
