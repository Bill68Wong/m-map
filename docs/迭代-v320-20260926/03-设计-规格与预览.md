## 1. 需求 13 · 线路标签「v0.19.1 谷歌地图风格」精确设计稿（最高优先）

### 1.1 考古结论（本批已二次核实）

| 版本 | 形态 | 判定 |
|---|---|---|
| **v0.19.1（`7842648` 内 `globals.css:716-790`）** | 容器 `border-radius:6px; overflow:hidden`；块 = 平行四边形 `clip-path: polygon(8px 0,100% 0,calc(100%-8px) 100%,0 100%)` + `margin-right:-5px` 咬合；首块左端竖直、尾块右端竖直；白字 13px/700、`padding:4px 14px`、`line-height:1.15` | [通过] **目标形态**（用户对比图确认 C） |
| v2.4.0（同提交另一处 `.route-stack`） | 每块独立圆角 + 白斜杠 `/` + 四向黑描边 | [否] v3.1.1 走过的路（用户判「形态错 + 白字丢失」） |
| v2.4.1（现线上 v3.1.1） | 斜切直角（无圆角）+ 无缝（斜杠被删） | [否] 现状抱怨对象 |

> 关键判据：本项目 `00` 文件 §三「目标形态 = v0.19.1」**推翻**了上一批 12 文档「正确版 = v2.4.0 白斜杠」的结论。本批以 `00` 为唯一口径源。

### 1.2 历史缺陷与**现代方案**（核心设计决策）

**历史缺陷（v2.2.1）**：为支持「多段换行」把**顶层容器** `.route-stack` 的 `overflow` 改为 `visible` ⇒ 容器的 `border-radius` 失去裁剪对象 ⇒ **容器圆角碎裂**（首尾块不再被圆角外框裁成圆角矩形）。

**现代方案（本批采用）：把「圆角外框 + 裁剪」从容器**下沉**到每个 `__group`（逐组裁剪）。**

```
DOM（已存在，无需改结构）：
.route-stack                 ← 顶层：只换行/段间距，overflow:visible（不裁剪）
  ├─ .route-stack__group     ← ①「段」= 一个自足圆角外框（border-radius + overflow:hidden）
  │    ├─ .route-stack__seg  ← 块（平行四边形 · 右倾）
  │    └─ .route-stack__seg
  ├─ .route-stack__arrow     ← 段间换乘箭头 →
  └─ .route-stack__group     ← ② 另一段 = 另一个独立圆角外框
```

**为什么不是 mask / clip 方案（对比与理由）**

| 候选方案 | 多段换行表现 | 代价 | 评价 |
|---|---|---|---|
| **组级 `overflow:hidden`（采用）** | 每组独立裁剪，各组换行互不影响，**每组各自保留完整圆角外框** | 0 额外几何、0 结构改动（DOM 已有 `__group`），纯 CSS | [通过] **采用** |
| 顶层容器 `mask` / `clip-path` | 换行后整体变成「两行并集」，**不是**简单圆角矩形 ⇒ 需**逐行**再算 mask | 需 JS 测行高/分段、SwiftUI 式复杂逻辑，且高德/浏览器兼容性风险 | [否] |
| 顶层容器 `overflow:hidden`（v0.19.1 原法） | 换行时**整块被裁**（第二行块丢角 / 被切边） | 即历史缺陷 | [否] |

**收益**：一次性同时满足 ① 单段 = 一个连续圆角外框（谷歌地图风格）；② 多段换行时每组各自成框、组间由箭头 `→` 分隔 —— 语义更清晰（「每段一个框」比「所有段共用一个框」更符合「换乘 = 换段」的心智）。

### 1.4 文字「不切、不跑位」的关系式与临界值

设：块高 `H = padT + fs·lh + padB`；斜切水平跨度 `S`；文字带（text band）从 `y = padT` 到 `y = padT + fs·lh`。

**斜边侵入量**（左侧斜边从 `(S,0)` 到 `(0,H)`，即 `x_intrude(y) = S·(1 − y/H)`）。文字带内**最大**侵入发生在文字带**顶端**：

```
intrude_max = S · (1 − padT / H)

安全条件：  斜边侧 padding ≥ intrude_max + 1px（缓冲）
保守规则：  斜边侧 padding ≥ S        ← 简单、永远安全
```

| 变体 | S | H | intrude_max | 设计 padding（斜边侧） | 余量 |
|---|---|---|---|---|---|
| md | 8px | 23px | `8·(1−4/23)` = **6.6px** | **14px** | +7.4px [通过] |
| sm | 6px | 20px | `6·(1−3/20)` = **5.1px** | **12px** | +6.9px [通过] |
| 首块左端 | — | — | `0`（竖直边） | 10px | [通过] |
| 尾块右端 | — | — | `0`（竖直边） | 11px | [通过] |

**最长码压力测试（`white-space: nowrap` ⇒ 必不折行）**

| 码 | 字形 | 字宽估算 | 块宽 = 字宽 + 2×14 | 判定 |
|---|---|---|---|---|
| `MT4` | 3 拉丁 | ≈ 3×8.2 = 24.6px | ≈ 52.6px | [通过] |
| `AP1` | 3 拉丁 | ≈ 24.6px | ≈ 52.6px | [通过] |
| `21A` | 3 拉丁 | ≈ 24.6px | ≈ 52.6px | [通过] |
| `MT1` | 3 拉丁 | ≈ 24.6px | ≈ 52.6px | [通过] |
| `氹仔线` | 3 CJK | ≈ 3×13 = 39px | ≈ 67px | [通过] |
| `協和醫院` | 4 CJK（极端） | ≈ 52px | ≈ 80px | [通过]（可容纳，超出上限即换行） |

> 结论：**最长的 3 字码（含 CJK）在 md/sm 两档均远小于可用宽度，既不折行也不被斜边切到**。左右 `padding` 与斜切 `S` 的关系锁定为 `padding ≥ S`（md 14≥8、sm 12≥6），任何未来新增的 2~3 字码自动安全。

### 1.5 「不跑位」的居中口径

- **水平居中**：`justify-content: center` + `text-align` 居中；`white-space: nowrap` 保证单行。首/尾块两侧 `padding` 不对称（10 vs 14）时，文字相对**边界盒**略偏 —— 但相对**可见（斜切）形状**的视觉重心居中，观感更稳（谷歌地图同款）。**建议 md 首块 `padding-left: 10px` 保持不变**（v0.19.1 生效值），如需「严格边界盒居中」把首块改为 `12px`（与尾块 11 对称化），属局部微调，默认不改。
- **垂直居中**：组 `align-items: stretch` ⇒ 块等高；块内 `align-items: center` + `line-height: 1.15` ⇒ 字形完整落在实色区内（`1.15` 而非 `1` 的理由见 v0.19.1 原注释：CJK 字形略高于 em 框，`1` 会切上下缘）。

### 1.6 `+N` 折叠块（第 4 条起）

v0.19.1 时代尚无 `+N`（后加）。为了不让 `+N` 成为「第二个视觉语汇」，本批把 `+N` 设计为**中性色尾块、落在组外框内**：

| 维度 | 值 |
|---|---|
| 形态 | 同高同形；**左端斜切**（延续「/」节奏）、**右端竖直**（收进组圆角） |
| `clip-path` | `polygon(8px 0, 100% 0, 100% 100%, 0 100%)` |
| 底色 | `var(--surface-2)`（次表面 · 既有 Token；**不新增 Token**） |
| 文字 | `var(--muted)`（= 既有 `--muted`；解决 v2.4.0 白字白底不可见的老问题） |
| 内边距 / 字号 | `padding: 4px 10px` / 13px·700 |
| sm | 斜切 6px / `padding: 3px 9px` / 12px |

⇒ 整组读作 `[56｜AP1｜26A｜+1]` 一个连续圆角外框，尾块中性收口。

### 3.3 位置公式推导（与 `--sheet-y-layout` / `--sheet-y-anim` 的联动）

| 变量 | 含义 | 本按钮用哪个 |
|---|---|---|
| `--sheet-y-anim` | 面板**每帧**位移（拖动中命令式写、落定时 React 写；已镜像到 `<html>`） | [通过] **用这个** —— 拖动/落定都同步，恒贴合 |
| `--sheet-y-layout` | **仅档位落定**同步（喂滚动容器 padding，拖动中不动） | [否] 不用（拖动期会不同步 ⇒ 跑位） |

- `--sheet-y-anim = sheetY` ⇒ 面板顶边（视口 y）= `sheetY` ⇒ 按钮底边落在 `sheetY − 12px` ⇒ CSS `bottom = 100dvh − (sheetY − 12) = 100dvh − sheetY + 12`。
- **三档表现**：`full`（sheetY≈96~128）⇒ 按钮浮在面板框上方；`half`（0.5h）⇒ 随之下移；`peek`（0.8h）⇒ 继续下移；**面板关闭**（`100dvh`）⇒ `max()` 兜到「底导 + safe + 12px」，仍在拇指区。
- **12px 偏移** = 「上方一点点」；与面板圆角(14px)视觉呼吸一致。
- **与 recenter 动画的关系**：`--nav-map__recenter` 原用**同一条公式**与**同一缓动**（`bottom` + `var(--sheet-dur-settle) var(--sheet-ease)`）。本批删除 recenter，公式/缓动**原样由定位浮层继承** ⇒ 「随面板浮动」既有手感不变（无缝迁移；架构师 `02 §8.3` 亦定「复用 recenter 的 bottom 公式与过渡」）。

**两版等价写法（按架构师最终挂载点二选一，结果完全一致）**：

```css

.nav-locate-fab--inmap {
  position: absolute;
  bottom: max(
    calc(100dvh - var(--tabbar-h) - var(--safe-bottom) - var(--sheet-y-anim, 100dvh) + 12px),
    12px
  );
}
```

> 两版在**视口坐标**下等价（都令按钮底边 = `100dvh − sheetY + 12`，且面板关闭时都不越过底导）。版 A 更简单、不受 `.nav-map` 层叠上下文影响（避免 `nav-card-overlay z90` 之类夹层）；**建议版 A**。

## 4. 需求 6 · 纵轴用户点：离站「瞬移两站正中间」+ 中点驻留

### 4.1 语义定义（口径）

| 状态 | 点位置 | 动作 |
|---|---|---|
| **停靠中**（`atIdx !== null`） | 贴该站节点中心（`frac = 0`） | 与现状一致 |
| **离站后（行驶中）** | **锁两站正中间**（`frac = 0.5`），**驻留不动** | **新口径**：不再随进度插值微动 |
| 接近下一站 / 新数据到达 | 到达即 `atIdx` ⇒ 贴下一站节点 | 离散更新 |

> 目标（用户原话）：点永远清晰可读、不与站点节点堆叠。**`frac = 0.5` 恒为两节点正中间 ⇒ 数学上保证与两端节点等距，永不重叠。**

### 4.2 视觉规格

| 项 | 值 |
|---|---|
| 载体 | `.navstrip__youmark`（既有骑线浮标） |
| 位置 | `left: calc(9px + var(--track-rail-w)/2)`（纵条中线，**不变**）；`top: calc(50% + var(--you-frac) × 100%)` |
| `--you-frac` 取值 | **只有 0 与 0.5 两个离散值**（停靠=0；行驶=0.5）。**移除 `fracBetween` 连续插值**（`useRideTracking` §youAt 计算改「行驶 ⇒ `frac:0.5`」） |
| 尺寸 | `12px`（`--track-you-dot-w`，**不变**） |
| 颜色 | `--track-you`（= `--accent` 青花蓝） |
| 描边 | `2.5px solid var(--surface)`（把点从纵条上"拔"出来） |
| 光圈 | `box-shadow: 0 0 0 var(--you-ring-0, 4px) var(--track-you-ring)` |
| 呼吸 | `animation: navYouPulse 1.6s ease-in-out infinite`（**保留**；驻留时靠它保持「活着」的观感） |
| 层级 | `z-index: 3`（浮标压在纵条之上，与节点同级不遮字） |
| 与节点的关系 | 停靠时=节点位置（复用 `is-at` 的纯 CSS 节点态）；行驶时=中点（浮标），**二者互斥**（`atIdx === null` 才渲染浮标，现有逻辑） |

### 4.3 「瞬移」的过渡处理

- 默认 **`--you-jump-dur: 0ms`（瞬移，零过渡）** —— 严格照用户原话「瞬移」。
- **建议值（可切换）**：若真机观感过硬，改 `150ms`（项目动效收敛值）`--ease-standard` —— 感知上仍是「瞬间到位」，但避免硬切。**请用户在真机上二选一**。


## 5. 需求 7 · 蓝点平滑（定位改高频 1~3s）

### 5.1 采样频率（◆ 以架构师 `02-技术-调研与方案.md` §6.2 为准）

| 场景 | 现状 `intervalMs` | **本批（架构师定）** | 说明 |
|---|---|---|---|
| **导航中（riding）** | 30 000 | **1 500** | 需求 1~3s 级；与站点判定 / 蓝点随动 |
| **导航候车（detail 非 riding）** | 30 000 | **3 000** | 兼顾灵敏度与耗电 |
| **浏览地图（首页）** | 15 000 | **10 000** | 低频省电 |

```ts
// NavShell.tsx（架构师 02 §6.2）：riding 1500 / detail 非 riding 3000 / 浏览 10000
const intervalMs = ridePhase === "riding" ? 1_500 : detailActive ? 3_000 : 10_000;
```

- 配套（架构师 02 §6.2）：`maximumAge: 5000 → 0`（导航态，避免陈旧坐标导致读数跳变）；精度门沿用 `YOU_ACC_MAX_M = 150`。
- **设计联动**：移动过渡时长 `--you-move-dur` **= 当前 `intervalMs`**（riding 1500ms / 候车 3000ms）⇒ 匀速插值刚好在两帧间走完，视觉连续。**仅当 `intervalMs ≤ 5s` 才启用插值**；浏览态（10s）不插值（否则把 GPS 抖动放大成缓慢漂移）。

### 5.2 平滑移动动画规格

蓝点 = `AMap.Marker`（DOM content）⇒ `setPosition` **瞬跳**。为平滑，对**被 AMap 施加 `translate3d` 定位的那个节点**加 `transform` 过渡。

> **[注意] 关键前提（架构师 02 §6.3 已列为首要验证项）**：AMap 4.x marker 的 DOM 结构 —— 定位 transform 施加在**外层容器**还是 **content 元素**。
> · 若为 **content 元素**（= `.user-dot`）⇒ 直接给 `.user-dot` 加过渡；
> · 若为**外层**（`.amap-marker`）⇒ 由 `UserDotLayer` 在创建后给外层加类（`marker.getContentDom()?.parentElement?.classList.add(...)`）。
> 真机/DevTools 确认后再定；两种落点**互斥**，不要同时加。

```css
/* 蓝点移动层（类名落到「AMap 实际 transform 的节点」；下面以 content 落点为例） */
.user-dot {
  /* 时长 = 采样间隔 ⇒ 匀速直线插值；◆ linear，非 ease */
  transition: transform var(--you-move-dur, 0ms) linear;
}
body[data-nav-phase] .user-dot { will-change: transform; }  /* 仅导航期挂载，避免常态吃显存 */
@media (prefers-reduced-motion: reduce) { .user-dot { transition: none; } }
```

| 参数 | 值 | 说明 |
|---|---|---|
| 缓动 | **`linear`（匀速）** | [注意] **关键设计判断**：高频离散采样下，`ease` 会让点在**每个定位点减速** ⇒ 看起来「一顿一顿」。`linear` = 恒速直线插值，才是谷歌地图的观感 |
| 时长 | `--you-move-dur` = **1500ms**（riding）/ 3000ms（候车） | = 采样间隔 ⇒ 到达下一帧时刚好走完，视觉连续 |
| 浏览态 | `--you-move-dur` = **0ms** | 10s 采样下若仍插值 ⇒ 把 GPS 抖动放大成「缓慢漂移」⇒ **必须关掉**（阈值：仅当采样 ≤ 5s 才插值） |
| **必须抑制过渡的情形**（架构师 02 §6.3） | 冻结（投影失败 / 精度差）· 单帧位移超阈值 · 首次出现 · 换乘/换段跳变 | 这些场景**临时关掉 transition 瞬移**，否则会出现「横跨全屏的一秒钟缓滑」 |
| 与冻结逻辑隔离 | 插值只作用于**渲染层**，不改 `youDot` 投影与 `passedIdx/atIdx` 判定 | 位置序列不被破坏（AC-60） |
| 回退方案 | 若 AMap marker DOM 不可控 ⇒ 架构师 **方案 3**（rAF 插值 + 逐帧 `setPosition`） | 观感目标不变（匀速直线） |

### 5.3 与 ping 呼吸（2.4s）的关系（风险隔离）

| 动画 | 宿主元素 | 属性 | 结论 |
|---|---|---|---|
| **移动插值** | 被 AMap 施加 `translate3d` 的节点（content `.user-dot` **或** 外层 `.amap-marker`，真机确认） | `transform: translate3d(...)` | 外层 |
| **ping 呼吸** | `.user-dot__ping`（`.user-dot` 的**子元素**，永不动） | `transform: scale(0.6→2.2)` + `opacity` | 内层 |

⇒ **两者永不在同一元素**（移动在祖辈、ping 在子孙）⇒ 各自独立合成、互不干扰。

**实现纪律（唯一红线）**：
- **绝不**把 `transition: transform` 加到 **`.user-dot__ping`** 本身（那会与 `navYouPing` 的 `scale` 抢 `transform`）。
- 若过渡落在 `.user-dot`（父）上 ⇒ 安全（父做 `translate`、子做 `scale`，元素不同）。
- 若 AMap 的定位 transform 恰好在 `.user-dot` 上，而 ping 的 `scale` 在其子元素上 ⇒ 同样安全。
- 二者都不成立时才需要回退到方案 3（rAF 插值）。

- ping 周期 **2.4s** 保持不变（刻意与到站 1.2s 错频，避免全屏共振）。
- 移动（1.5s）与 ping（2.4s）是两个正交运动 ⇒ 观感 = 「一边匀速漂移、一边水波扩散」，与谷歌地图一致。

### 5.4 调研参考（简要，供文档留档）

- **谷歌地图**：定位高频（约 1s）+ 蓝点位置**平滑插值**（近似匀速），方向锥随方位角平滑旋转；静止时靠精度光圈半径收敛表达置信度。
- **高德地图**：定位约 2~3s 一次 + 「位置平滑」算法（点不瞬跳）；静止时用漂移抑制。
- **本规格**：按架构师定频（riding 1.5s / 候车 3s）+ `linear` 同长插值（观感贴近谷歌、成本更低；浏览态 10s 低频省电）。**真机复验项**（`00` §四「真浏览器跑用户流程不可省」）。

### 8.3 红钉「另有原因」——◆ 架构师已定位根因

**架构师 `02-技术-调研与方案.md` §7 结论（首选根因）**：
> **起点为「我的位置」时 `originArg = null` ⇒ 不画红钉**（`from` 为空时 origin 传 null）。
> 已定（P4）：**要画红钉** ⇒ `originArg` 不再因 `from = null` 而为 null，组合形态由设计师定（本规格 §8.1 已给：红钉 = 与终点钉同款几何、z110）。

⇒ 因此两颗钉的「全程见过 / 没见过」是两个不同根因，须**分别修**：

| 钉 | 根因 | 修复 |
|---|---|---|
| **终点钉（绿）** | `pin-destination.svg` 的 `fill="var(--pin-dest, #0b6e4f)"` 在部分 WebView 判无效 ⇒ 不绘制（§8.2） | 改**字面量** `fill="#0b6e4f"` |
| **起点钉（红）** | 起点为「我的位置」时 `originArg = null` ⇒ **标记从未创建**（架构师 §7） | `originArg` 不再为 null（P4）；并保证全程保活（§8.4） |

**设计侧补充排查清单**（与架构师真机取证配合）：

1. **标记是否被销毁**：`NavMap` 的 `origin` effect 依赖 `[origin, phase]` —— 换阶段时 `origin` 是否被置 `null`（`null` ⇒ remove 标记）？须全程非 null（= 架构师 P4）。
2. **取景是否把钉移出视口**：`setBounds` / `--sheet-y` 让位后，起点可能落在被面板遮住的下半屏 ⇒ 用既有 `fit-two` 把两点收进上半屏。
3. **`offset` 是否生效**：`new AMap.Pixel(-10, -26)` 与钉形底边中点对齐；错则钉尖偏出视口边缘。
4. **CSS 是否被覆盖**：`.nav-map__originpin` 的 `background: url("/pin-origin.svg")` + `width/height` 是否被其他规则覆盖。
5. **middleware 白名单**：`/pin-origin.svg` 已在 `PUBLIC_FILES`（`middleware.ts:86`）[通过] —— 线上（配口令）可取到。
6. **真机取证**：Android + DevTools 看 marker DOM 是否创建、`.nav-map__originpin` 的 computed `width/height` 是否 20×26、`background-image` 是否加载。
