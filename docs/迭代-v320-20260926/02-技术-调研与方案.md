## 1. 轻轨「模式判定」链路（核心难题）

正式裁决见 `docs/decisions/ADR-101-氹仔线偏差模式判定.md`。此处给出**面向实现**的补充。

### 1.1 问题本质

`lrt_timetables` 无「班次 / 趟次」标识，只有「本站发车时刻」序列。要回答「站在 X 站、方向 D、下一班 T 属于哪一种模式」，
必须**由站间时序链式反推**出该班所属的 11 位间隔序列。原型算法（**修正版** `.verify/lrt-tpl-chain2.mjs`）已验证可复刻：
从起点站一趟发车 t0 出发，逐站取「首个满足 `arr[i] − t ≥ minGap[hop]` 的发车时刻」（**首跳跨海段 min-gap ≥ 4 分**，其余 ≥ 1），
得 11 位间隔序列；naive「仅取 > 当前」会产出伪模式 `12322213132`（1 分钟跨海，物理不可能）。详见 §1.1 更新版与 `06` §1.1。

### 1.2 候选方案对比矩阵

| 维度（权重） | A 离线预计算表 | B 运行时内存链式反推 | C 混合（推荐） | D 全表灌预载（否决） |
|---|---|---|---|---|
| 串行 DB 往返（红线） | 直连路由 1 次按站查；预载若不优化则负载偏重 | 0（复用已加载 tt） | 直连 1 次按站查；预载 0 | 预载负载 0.3~0.6MB（偏重） |
| 预载负载 | 若整表灌入偏重 | 同今日（72 行） | 同今日（72 行） | 偏重（逼近 230ms） |
| 可审计 / 可复核 | 强（冻结表 + 分布报表） | 弱（算法在请求路径） | 强（表 + 一致性测试） | 强 |
| 抗「沉默逻辑错误」 | 强（离线可审、可与 A2 对照） | 中（纯函数可单测，但无中间产物） | 强 | 强 |
| 刷新维护 | 需重跑脚本（运维耦合） | 自动跟随 | 自动跟随（预载） + 需重跑（表） | 需重跑 |
| 显式降级 | 强（查不到→分钟级） | 中（链断→无模式） | 强 | 强 |
| 实现复杂度 | 中 | 中 | 中高（两处复用） | 低 |
| **综合** | 备选 | 备选（预算紧时首选落地） | **推荐** | 否决 |

### 1.3 推荐方案的数据流（方案 C）

```
离线（npm run，db-guard）
  lrt_timetables ──pattern.ts#deriveStationPatterns──▶ lrt_station_patterns（权威表）
                                         │
                                         └─ 打印分布报表（对照 14 号 A2）

运行时
  直连路由 /api/lrt/eta、/api/station/eta
    └─ 按站查 lrt_station_patterns（站×向×班别） + lrt_station_biases（逐站偏差，小查询）
  推荐预载 buildLrtPreload（loadStatics 并行窗口内）
    └─ 内存跑 pattern.ts（复用已加载 tt 行，0 额外 RTT） + 预载偏差小表
  统一出口 apply-bias.ts#fixDeparture → { depMs(已修正), biasSec, secPrecise, pattern }
```

### 1.4 边界与降级（必须写进实现的硬约束）

| 情形 | 处理 |
|---|---|
| 模式命中四大主力 | `secPrecise=true`，叠该模式逐站 `dep_bias_sec` 读秒 |
| 模式未命中（变体，约 2%） | `secPrecise=false`，**分钟级**（正好对应需求 1 的「其余变体不读秒」） |
| 链被收班截断 / 缺站行 / 某站班次被 0 或多条链覆盖 | 视为无模式 → `secPrecise=false` |
| 跨午夜班（hour>23；前一日行 offset≥1440） | 复用现有 `rowOffsetsOf` / `rowCandidateSec` 的「D 00:00 起秒」单轴，**不得**引入新日期口径 |
| 终点站氹仔碼頭（无时刻表行） | 只作起点用（方向→BAR）；末段不参与 11 位模式串 |

### 1.5 验证方法

- `pattern.ts` 纯函数单测：给定人造时刻表，断言链式产物与手工推演一致。
- 离线脚本分布报表：四大模式占比须落在 `14` 号 A2 区间（62.8~73.8% / 23.0~29.7%；反向 56.6~73.8% / 20.3~30.7%）。
- 一致性测试：表派生 == 内存派生（同一快照逐行相等）。

## 2. 偏差数据表设计

### 2.1 新表 `lrt_station_biases`（逐站 / 逐模式偏差）

```
lrt_station_biases (
  id            serial        PRIMARY KEY,
  route_code    text          NOT NULL,   -- 本库线码 'LRT-氹仔线'（与 lrt_route_params.route_code 同口径）
  direction     text          NOT NULL,   -- 乘车方向 = 终点站 api 码 'BAR'|'TFT'（与 lrt_timetables.direction 同口径）
  pattern       text          NOT NULL,   -- 站间间隔模式 '52222222222' 等；线路级线（石排湾/横琴）填 'default'
  api_station   text          NOT NULL,   -- lrt_api_stations.api_id（'BAR'/'OCE'/…）
  arr_bias_sec  integer       NULL,       -- 到站（开门）偏差；起点站/无到站语义为 NULL
  dep_bias_sec  integer       NULL,       -- 出发（关门）偏差；读秒取**本列**
  source        text          NOT NULL,   -- '手记实测 2026-09-26' | '打点实测 2026-09-08~15' | '线路级'
  measured_on   date          NOT NULL,   -- 取得日期（合规：派生值须可溯源）
  note          text,                     -- 口径/勘误说明（如 132 路氹東 −10/+20）
  updated_at    timestamptz   NOT NULL DEFAULT now(),
  UNIQUE (route_code, direction, pattern, api_station)
)
```

- 行数预期（**2026-09-26 更正**）：氹仔线 4 模式 × 13 站 = 52 行 + 石排湾/横琴 2 线 × 2 站 = 4 行 ⇒ **共 56 行**
  （原「112 行」系把「方向」与「模式」重复相乘所致 —— 四模式本就方向专属，不应再乘方向；详见 `06-技术-实施规格.md` §6）。
- 数值来源：`15-轻轨偏差值-数值汇总-20260926.md` §一（逐站 到/发）+ §二（打点）。`13222222222` 路氹東取**勘误后** `−10 / +20`。
  横琴线 `+40s` 关门 / 石排湾线 `−05s` 关门（按需求 1：两站各登记一行，`pattern='default'`）。
- 读秒只取 `dep_bias_sec`（出发/关门口径，与 `depMs` 语义一致）；`arr_bias_sec` 仅存档，供后续「现正到达」到站口径细化。

### 2.2 与 `lrt_route_params` 的关系（推荐：保留 + 分职，偏差读口迁移）

| 表 | 现有内容 | 本批处置 |
|---|---|---|
| `lrt_route_params` | `dep_bias_sec`(石排湾 -5 / 横琴 +40) · `ride_sec`(100/135) · `stops` | **保留**：`ride_sec`/`stops` 供 item 5 使用；`dep_bias_sec` **退役为历史兜底** |
| `lrt_station_biases`（新） | 逐站/逐模式偏差 | **读秒偏差唯一真源**（含石排湾/横琴 `pattern='default'` 两站行） |

- 推荐「读口迁移」而非「数据迁移」：代码层把读偏差统一改为读 `lrt_station_biases`；`lrt_route_params.dep_bias_sec` 保留现状不再被 `src/` 读取。
- 加一条一致性断言（脚本或测试）：石排湾/横琴在 `lrt_station_biases` 的 `dep_bias_sec` 须与 `lrt_route_params.dep_bias_sec` 相等 ⇒ 防双真源漂移。
- **备选（待拍板）**：若认为双表冗余，可把 `dep_bias_sec` 列从 `lrt_route_params` 彻底移除；但会触碰既有迁移脚本，风险略高，不推荐本批做。

### 2.3 入库脚本设计（走 `npm run` · db-guard · 先 dry-run）

沿用 `db/migrate-v2150.ts` 的「DRY-RUN 默认 / `--apply` / `--rollback`」范式：

- **建表**：`db/migrate-v3200.ts`（`CREATE TABLE IF NOT EXISTS` + 注释；幂等）→ `npm run db:migrate-v3200 -- cloud --allow-prod`。
- **写值**：`scripts/seed-lrt-biases.ts`：
  - 默认 DRY-RUN：打印将 upsert 的全部行 + 校验（行数、pattern 长度=11、`dep_bias_sec` 落在 −35~90s、覆盖四大模式与两线）；
  - `--apply`：单事务 `ON CONFLICT ... DO UPDATE` 幂等写入（照 `migrate-v2100.ts` 写法）；
  - `--rollback`：按 `source`/`measured_on` 定位并删除本批写入（谨慎，默认不执行）。
- package.json 新增：`"db:migrate-v3200"`、`"db:seed-lrt-biases"`、`"db:build-lrt-patterns"`，均以 `tsx scripts/db-guard.ts run …` 包装（铁律 12）。
- 模式映射表 `lrt_station_patterns`（ADR-101 方案 C · 已裁定）：`db/migrate-v3200.ts` 一并建表；写值走 `scripts/build-lrt-patterns.ts`（同 DRY-RUN 范式）。

### 2.4 时刻表刷新链路（team-lead 裁定追加 · 硬要求）

模式映射是时刻表的**派生数据** ⇒ 时刻表刷新后必须**同批重建**，否则派生漂移。落地为一条 npm 命令链：

```
"lrt:fetch"            // 既有：抓取时刻表（scripts/fetch-lrt-timetable.ts）
"db:build-lrt-patterns" // 新增：由 pattern.ts 重建 lrt_station_patterns（DRY-RUN/--apply）
"lrt:refresh": "npm run lrt:fetch -- cloud --allow-prod && npm run db:build-lrt-patterns -- cloud --allow-prod"
```

- 约定：**刷新时刻表一律走 `lrt:refresh`**，不得只跑 `lrt:fetch`（防漏重建）。
- 记账：`lrt_station_patterns` 增 `src`（'chain-expand'）与 `built_at` 列，便于判断映射新旧；重建时按 `src` 覆盖。
- 复核：重建后打印分布报表（对照 `14` 号 A2），并跑「表派生 == 内存派生」一致性测试。
- 链路本身写入本批 Spec 与发版清单（发版前若刷新过时刻表 → 必须已跑 `lrt:refresh`）。

## 3. 读秒 API 双链路统一

### 3.1 现状（口径不一）

| 链路 | 文件 | 偏差处理 | 下发字段 |
|---|---|---|---|
| `/api/lrt/eta` | `src/lib/lrt/next-departures.ts` | **纯表定**（不叠 bias） | `departures:[{clock, depMs}]`（depMs=表定） |
| `/api/station/eta`（轻轨分支 `lrtItems`） | `src/app/api/station/eta/route.ts` | 叠**线路级** bias（`lrt_route_params.dep_bias_sec`） | `nextAt`/`etaSec`/`depMs`(含bias)/`biasSec` |

同一站同一班，两链路给出的时刻可能不同 ⇒ 站台卡与推荐卡表现不一致（需求 2 要修）。

### 3.2 统一方案

新增纯模块 `src/lib/lrt/apply-bias.ts`，两路由共用「唯一实现」：

```
fixDeparture({
  lineCode, routeNo, directionApi, apiStation, dayType,
  tableMin,            // 表定当日分钟偏移（可 >1440）
  dayStartMs,          // 澳门当日 00:00（UTC ms）
  patternOf,           // (station,route,dir,day,depMin) => pattern | null
  biasIndex,           // lrt_station_biases + lrt_route_params 合并后的索引
}) → { depMs, biasSec, secPrecise, pattern }
```

判定：氹仔线取「模式命中 → 该模式逐站 bias」；石排湾/横琴取线路级 bias（`secPrecise=true`）；
模式未命中 → `biasSec=0, secPrecise=false`（分钟级）。

### 3.3 字段契约（两链路一致）

- 逐班次增设：`secPrecise: boolean`（有无秒级偏差数据）、`pattern: string | null`、`biasSec: number`。
- `depMs` 一律为**已叠偏差的绝对发车时刻**（沿用 v2.10.1/v2.14 机制，前端用设备时钟倒计时）。
- 向后兼容：现有 `clock` / `etaSec` / `etaMin` / `nextAt` 保留；`/api/lrt/eta` 仅**新增**字段，旧前端忽略即无感。
- `middleware.ts`：两路由已在白名单（`/api/*`），无新增。

### 3.4 影响面与原因

- `LrtEta.tsx` 倒计时当前直接吃 `depMs` ⇒ 服务端改下发修正后的 `depMs` 后，站台卡**自动**用上偏差，前端改动最小；
  仅需新增「按 `secPrecise` 选择窗口/文案」（见 §4）。
- `LrtEtaInline` 消费的是推荐卡下发的 `liveDepartures`（`model.ts` 经 `LrtLive` 产出）⇒ 需在 `LrtLive`/`RideLegView`
  增设每班 `secPrecise`（如 `livePrecise?: boolean[]`），供窗口与文案选择。

## 4. 「现正到达」窗口重构

### 4.1 现状

`LrtEta.tsx` 的 `LRT_ARRIVAL_WINDOW`（按线路码）：氹仔 `{pre:30s, post:30s}` · 石排湾 `{pre:5s, post:45s}` · 横琴 `{pre:0, post:40s}`；
`pickNext`（取窗未结束的班次）+ `inArrivalWindow`（闭区间）两卡共用同一实现（同文件）。

### 4.2 目标口径（需求 2）

| 班次类型 | pre（进入「现正到达」） | post（归零后保持） |
|---|---|---|
| 有精准读秒 · 氹仔 | 30s | 10s |
| 有精准读秒 · 石排湾 | 120s | 10s |
| 有精准读秒 · 横琴 | 60s | 10s |
| 无读秒 · 氹仔（变体，约 2%） | 30s | 30s |

实现要点：

- `post` 由**班次级** `secPrecise` 决定（非线路级）⇒ `pickNext` / `inArrivalWindow` 须接收该班次的 `post`。
  即：`postOf(departure) = departure.secPrecise ? 10_000 : 30_000`；`pre` 仍按线路（`LRT_PRE_SEC`）。
- 站卡 `LrtEta` 与推荐卡 `LrtEtaInline` **共用同一** `windowOf/pre` 与 `postOf` ⇒ 两处天然统一（需求 2 的「两处口径统一」）。

### 4.3 缓存 / TTL / 滚动（`pickNext`）影响评估

- **服务端缓存**：`/api/station/eta` 已对轻轨**跳过**内存缓存（保证 `depMs` 新鲜）；`/api/lrt/eta` 无服务端缓存 ⇒ 无新增影响。
- **客户端**：`LrtEta` 有 10s 冷却 + 每秒 tick；末班重拉判据现为 `dep[last].depMs - now ≤ 0`，
  引入 post 后应改为 `dep[last].depMs + post ≤ 0` 再重拉（否则 10s 保持期内会过早重拉，属小瑕疵）。
- **滚动**：窗口结束即滚下一班，逻辑不变；仅 `post` 随班次变化 ⇒ 无结构性风险。
- **风险点**：`secPrecise` 为 `undefined`（旧数据/旧字段）时应**安全回落**为 `false`（分钟级 30s），不得当作 `true`。

## 5. 乘车时间精细化

### 5.1 现状

`model.ts`：轻轨 `ride.minutes = (LRT_RIDE_SEC_FIXED[route] ?? hops.length × LRT_MIN_PER_HOP×60)/60`，
`LRT_MIN_PER_HOP=2.0` ⇒ 氹仔线「跳数 × 120s」；已知低估（媽閣→海洋跨海段被按 2 分计，全线少算约 2~3 分钟）。

### 5.2 方案

## 6. 定位高频 + 平滑动画

### 6.1 现状

`useUserFix.ts`：`watchPosition({ enableHighAccuracy: true, timeout: 10000, maximumAge: 5000 })`，
采纳节流由 `intervalMs` 决定（`NavShell` 传 `ridePhase==='riding' ? 30_000 : 15_000`），
`enabled = navActive`（仅 detail pane）；页面隐藏停订阅、可见重订阅（已实现）。

### 6.2 频率目标（需求 7）

| 场景 | 建议 `intervalMs` | 说明 |
|---|---|---|
| 导航中（riding） | 1500ms | 需求 1~3s 级；与站点判定 / 蓝点随动 |
| 导航候车（detail 非 riding） | 3000ms | 兼顾灵敏度与耗电 |
| 浏览地图（首页 map/panel） | 10000ms | 低频省电 |

- `maximumAge: 5000 → 0`（导航态），避免浏览器回传陈旧坐标导致读数跳变。
- **页面可见性策略**：保留现有（隐藏停、可见重置节流并重订阅）。
- **耗电评估**：`enableHighAccuracy` 下 1.5s 连读在 Android WebView 属显著耗电项；
  缓解手段 = 仅导航态高频 + 浏览低频 + 后台暂停（均已具备）；建议再加**精度门**（`accuracy` 超阈值不采纳推进，已有 `YOU_ACC_MAX_M=150`）。

### 6.3 蓝点平滑动画方案对比

| 方案 | 做法 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| 1 AMap `Marker.moveTo` | 引擎内置路径动画 | 引擎驱动、拖拽期零 JS | 是「路径动画」，连续 1~3s 调用行为不保证；与 `setPosition` 混用语义不清 | 备选 |
| 2 `setPosition` + content 内层 CSS transition | 给 marker content 的 DOM 加 `transition: transform 1s linear` | 改动最小、GPU 合成、与现 `UserDotLayer` 定位方式最兼容 | 需真机确认 AMap 4.x marker 的 DOM 结构（外层定位 / 内层可 transform） | **首选** |
| 3 rAF 插值 + 逐帧 `setPosition` | 在两帧 fix 之间 rAF 插值坐标 | 完全可控、与冻结逻辑解耦 | 代码量最大；需处理与拖拽/缩放并发 | 回退方案 |
| 4 `AMap.CustomLayer` 自绘 | 自绘 canvas 覆盖 | 最灵活 | 最重 | 否决 |

- **推荐**：方案 2 为首选，方案 3 作为真机不合格时的回退。前提验证项：AMap 4.x 蓝点 marker 的 DOM 层级。
- **与 `youDot` 冻结逻辑兼容**：`useRideTracking` 的 `youDot` 在每帧 fix 上做投影；插值只作用于**渲染层**，
  不改判定；冻结（投影失败/精度差）时给出 frozen 点，需**抑制大跳变的过渡**（例如 frozen 或位移超阈值时不启用 transition，瞬移）。

### 6.4 与需求 4（蓝点任何时候显示）的关系（P6 · 已决）

用户已确认需求 4（`00` 文档 §二）：「打开地图页即请求定位权限；浏览/选点/导航全程有定位就显示蓝点」。
→ **已决：`enabled` 覆盖地图页浏览态**，浏览态低频（10s）、蓝点常显（只要已授权且有定位）。

- 权限申请时机：受浏览器约束，`watchPosition`/`getCurrentPosition` 需用户手势触发或产品认可的入口；
  需与设计师/前端确认「打开地图页即申请」的落地方式（如首页首次交互触发），**不得**用不可靠的自动弹权路径。
- 落地后 `useUserFix.enabled` 不再仅绑 `navActive`；浏览态与导航态共用同一订阅，靠 `intervalMs` 分档调频。
- 与既有 `data-userdot`（`none|blue`）观测钩子一致，QA 可断言。

### 7.4 结论（P4 · 已决）

### 9.2 回滚总原则

- 数据侧：迁移脚本均**幂等 + DRY-RUN + `--rollback`**（照 `migrate-v2150.ts`）；建表类 `CREATE TABLE IF NOT EXISTS` 天然可留。
- 代码侧：优先用**常量/开关集中**（如 `LRT_HOP_SEC`、频率常量、窗口常量、`navMode` prop），便于单点回退。
