## 0. TL;DR —— 参数建议表（含置信度）

> 前提认知（务必先读）：我方 `model.ts` 的 `T_total = walkOut + Σ[wait_k + ride_k + transfer_k] + walkIn`，**已经包含真实等待与真实步行分钟**。因此本表的惩罚项**只表达"额外心理/不便成本"，不得重复计等待或步行本身**。

| 参数 | 含义 | 建议值 | 依据 | 置信度 |
|------|------|--------|------|--------|
| **模型结构** | 默认"综合"＝多因子效用最优（非纯时间） | `cost = totalMin + α×换乘次数 + (β−1)×步行分钟 + 紧接换乘风险惩罚`；**cost 升序** | 谷歌 Route options 默认"Best route＝各变量甜蜜点"；高德 `BUS_DEFAULT＝综合权重`；OTP 广义成本 | **高**（结构）/ 低（精确权重） |
| **α 换乘惩罚** | 每次换乘的**纯额外**不便成本（**不含**已计的等待/步行） | **8 ~ 12 分钟/次，默认 10** | 文献"pure transfer penalty"：马德里 15.2~17.7／爱尔兰 12.73~24.32／西安 9.93~12.13（均为"额外"口径）；澳门行程短、取偏保守中值 | **中** |
| **β 步行惩罚** | 步行 1 分钟折合综合成本 | **总权重 1.5 ~ 2.0，默认 1.8**（即额外项 ＝(β−1)×步行分钟 ≈ 0.5~1.0 倍） | OTP `walk.reluctance` 默认 **2.0**（步行痛苦度＝乘车 2 倍） | **中高** |
| **等待是否额外惩罚** | 等待分钟**不**再加线性惩罚（已计入 totalMin）；**仅对"紧接换乘"加风险惩罚** | 对 `slack < 安全余量` 的换乘：**判不可用 → 顺延下一班**（需求 7）。可选轻微风险惩罚 | OTP `minSafeWaitTimeFactor=5.0`（对逼近 0 的换乘给对数惩罚，**防极限换乘**，非惩罚普通等待） | **中** |
| **换乘安全余量** | min-safe-transfer | **2 ~ 3 分钟，默认 3** | OTP transferOptimization"避免过短换乘 + 最大化可用等待"；谷歌"1 分钟换乘易在延误时崩塌" | **中** |
| **三档主判据** | 见 §4.5 | 综合＝cost↑；少换乘＝换乘次数↑（tie-break cost↑）；少步行＝步行量↑（tie-break cost↑） | 谷歌 Route options：**Best route / Fewest transfers / Least walking**；高德 `BUS_LEASE_CHANGE`/`BUS_LEASE_WALK` | **高** |

★ **最强新证据（对齐谷歌原话）**：谷歌地图公交的 **Route options** 菜单**默认＝"Best route"（各变量甜蜜点）**，可选 **"Fewest transfers"（最少换乘）/ "Least walking"（最少步行）/ "Wheelchair accessible" / "Lowest cost"**。这与我方"综合 / 少换乘 / 少步行"三档**一一对应**，档位命名与取舍逻辑据此对齐（我方暂不做"无障碍/最低票价"，理由见 §4.6）。

## 2. 谷歌地图公交推荐排序机制

### 2.1 官方可查证口径（一手，置信度：高）

| 证据 | 内容 | 对结论的意义 |
|------|------|--------------|
| 谷歌支持页《在 Google 地圖中規劃路線》 | 交通工具排名"**基于一组客观因素**：持续时间、距离、价格、**你的模式偏好**、查询相关性。通常**最重要的因素是模式偏好、行程时长，有时是价格**"。并声明"商业合作不影响排名"。 | ★ 谷歌**公开承认多因子**，但**不公开权重** ⇒ 精确公式不可得（§5）。 |
| 谷歌公交 **Route options** 菜单（Popular Science / How-To Geek 描述） | 选项：**Best route（默认）/ Fewest transfers / Least walking / Wheelchair accessible / Lowest cost**。官方口径："Best route 默认提供一个**在各变量间取得甜蜜点（sweet spot between all variables）**的行程"；"首条建议不总是你要的，Maps 会同时给出**更少换乘 / 更少步行 / 不同出发到达时间**的备选"。 | ★★ **需求 8 的直接对标**：默认＝综合最优；偏好＝少换乘/少步行（+无障碍/低成本）。 |
| 谷歌公交提示（Komarilab / PositionIsEverything） | "选**更稳定**而非理论最快；**1 分钟换乘**在延误时会崩塌"；"在同等条件下**保留换乘更少或步行更短**的方案"。 | 支持"可靠性/紧接换乘风险"进入默认模型（§4.4）。 |

### 2.2 算法层：RAPTOR / McRAPTOR 多准则 Pareto（一手论文，置信度：中高）

- **RAPTOR**（Delling, Pajor, Werneck，ALENEX'12）：轮次法公交路由，基础版同时优化 **最早到达时间 + 换乘次数**，可算出**全部 Pareto 最优行程**。
- **McRAPTOR**（同团队）：在 RAPTOR 上扩展 **步行时长、费用** 等额外准则；行程 J **支配** J′ ⇔ J 在任一准则上都不差。研究与工程实践中常取**三准则：到达时间 + 换乘次数 + 步行时长**，再按用户偏好排序选择。
- **"谷歌采用"的证据强度**：RAPTOR 由**时任微软研究院**团队提出，该团队后转入 Google；二手资料（kindatechnical 综述）称 "Google Maps Transit 使用 RAPTOR"。⚠ 具体产品实现为**二手信息**（一手论文确认算法与多准则扩展存在，但未确认谷歌线上恰好跑 McRAPTOR）。

★ 结论：谷歌"推荐"在**结构上**＝**多准则（时间+换乘+步行+…）取 Pareto 集 → 按效用/偏好排序**；这与"单一 totalMin 升序"有本质差别，是我方需求 8 要对齐的方向。

### 2.3 小结（谷歌）

1. **默认"Best route"＝多因子综合的"甜蜜点"**，不是纯最快；显式提供 **Fewest transfers / Least walking** 备选。
2. 权重**不公开**；可确证的是"**时长 + 换乘 + 步行 + 可靠性**"进入默认排序，**模式偏好**居首（对公交场景即"公交优先"）。
3. 算法层最可能为**多准则 Pareto（RAPTOR 系）+ 效用排序**。

## 3. 高德地图公交推荐排序机制

### 3.1 官方定义（一手 SDK 文档，置信度：高）

`RouteSearchV2.BusMode`（高德鸿蒙/Android SDK 文档一致）：

| 常量 | 值 | 官方中文 | 官方英文 |
|------|----|----------|----------|
| `BUS_DEFAULT` | 0 | **推荐模式，综合权重，同高德 APP 默认** | Recommended mode, comprehensive weighting, same as Amap APP default |
| `BUS_LEASE_CHANGE` | 2 | **最少换乘模式，换乘次数少** | Least transfer mode, fewer transfers |
| `BUS_LEASE_WALK` | 3 | **最少步行模式，尽可能减少步行距离** | Least walking mode, minimize walking distance |
| `BUS_WASTE_LESS` | — | **时间短模式，方案花费总时间最少** | Shortest time mode |

老接口 `m` 参数：`0` 最快捷 / `2` 最少换乘 / `3` 最少步行 / `8` 时间短。

★ 关键：**`BUS_DEFAULT` 明确是"综合权重"**，且"同高德 APP 默认"；**"时间短"是独立档**（≠默认）⇒ 进一步印证**高德默认不是纯时间**，与谷歌一致。

### 3.2 官方引擎描述（高德，置信度：中）

高德"新公交引擎"官方通稿（太平洋电脑网转载）：设定 **N 个影响因子（总里程、时间、票价、步行距离、换乘次数等）**，用**机器学习按用户画像调整各因子权重**；并"**删除存在明显劣势的垃圾方案**，展示 **1~5 条**"。
⇒ 与我方既有口径（"sortCards 取前 5""候选变多不挤掉更优"）方向一致。

### 3.3 第三方逆向（可信度评估，置信度：低~中）

| 来源 | 内容 | 可信度评估 |
|------|------|------------|
| 简书《百度地图公交推荐路线策略分析》 | 线性加权评分：`得分 = 时间×w_t + 步行距离×w_d + 换乘次数×w_r + 出行方式×w_m`，**分低者优**；叠加"停运置底/高峰偏好直达/堵车风险前调" | **中**：为**百度**（非高德）逆向，方法是"猜权重+样本反推"，未公开原始数据；**结构可参考，数值不可采信**。 |
| CSDN 问答"高德为什么…" | 列"总得分 = −w1×耗时 −w2×换乘 −w3×步行 −w4×等待 −w5×风险"，并称"高德按综合成功率最高排序" | **低**：CSDN 问答，疑 AI 生成，**无出处**；仅"综合成功率/风险惩罚"的**定性方向**与他处一致，**公式与系数不可引用**。 |

### 3.4 小结（高德）

1. 默认 `BUS_DEFAULT`＝**综合权重**（多因子），**"时间短/少换乘/少步行"为独立偏好档**。
2. 官方承认"**N 因子 + 机器学习调权 + 剔除劣势方案 + 1~5 条**"。
3. 精确权重**不公开**；第三方公式**仅结构可参考**。

## 4. 三方推导：最接近业界口径的默认模型与参数

> 推导三支柱：**产品行为观测（谷歌 Route options / 高德 BusMode）＋ 学术文献（transfer penalty）＋ 开源实现（OTP 默认参数）**。

### 4.1 结构（置信度：高）

```
综合成本 cost(方案) =
    totalMin                        // 已含 walkOut + Σ wait_k + ride_k + transfer_k + walkIn
  + α × 换乘次数                     // α＝纯换乘不便（不含等待/步行，避免重复计）
  + (β − 1) × 步行分钟               // β＝步行总权重（步行的"额外痛苦"部分）
  + [可选] 紧接换乘风险惩罚           // 仅当 slack < 安全余量
```

- 排序：`cost` 升序。
- **为什么不把 α 直接加到"显示的总时长"**：`totalMin` 是对用户**显示的时间**；α/β 是**排序用的效用成本**（业界 generalized cost），**二者分离**，避免"显示时间对不上明细"。

### 4.2 换乘惩罚 α（置信度：中）

| 来源 | 数值（换算为等效车内分钟） | 口径 |
|------|-----------------------------|------|
| Garcia-Martinez et al., 2018（马德里） | **15.2 ~ 17.7** | **纯换乘惩罚**（**不含**额外步行/等待） |
| National Transport Authority, 2024（爱尔兰） | **12.73 ~ 24.32**（常客 12.73~15.79；偶乘 14.87~24.32） | 巴士-巴士换乘惩罚 |
| 西安（Atlantis Press） | **9.93 ~ 12.13** | 换乘惩罚（步行/等待另有独立项） |
| Han, 1987（台北） | ≈ **30 分钟车内** 或 10 分钟等待 | 含更广的不便 |
| OTP | 不设单一 α；用 board/alight cost + transfer optimization | 工程近似 |

★ **建议 α = 8 ~ 12 分钟/次，默认 10**。理由：文献主流"纯换乘"落在 10~18；澳门网络**线路少、站距短、行程总时长短**，直接套用欧美 15+ 会让"多一次换乘"过度主导排序 ⇒ 取**偏保守中值**。置信度**中**（文献强，跨地域迁移是主要不确定项）。

### 4.3 步行惩罚 β（置信度：中高）

- **OTP `walk.reluctance` 默认 2.0**：同样耗时，步行的"痛苦"≈乘车的 **2 倍**（一手文档）。
- 我方 `totalMin` 已把步行分钟按 1:1 计入 ⇒ 额外项取 **(β−1)×步行分钟**，`β ∈ [1.5, 2.0]`。
- ★ **建议 β = 1.8（额外 0.8 倍），区间 1.5~2.0**。理由：OTP 2.0 是国际默认；考虑到澳门夏季炎热/多坡道，"步行更痛"合理，但不宜过高（避免"步行 3 分钟"的短接驳被过度惩罚）。置信度**中高**。

### 4.4 等待时间是否额外惩罚（置信度：中）

- **结论：不给"普通等待"加线性惩罚**。因为 `totalMin` 已把等待计为真实分钟，再加线性惩罚＝**重复计**，且会让"总时长"与"成本排序"脱节（用户会困惑"为什么更快的反而排后面"）。
- **要对"紧接换乘"加风险项**：OTP `minSafeWaitTimeFactor=5.0` 的实质是**对逼近 0 的换乘时间给对数型惩罚，抑制"极限换乘"**（可靠性语义），**不是**惩罚一般等待。
- ★ **落地**：换乘以 `slack = 下一班发车时刻 −（到达换乘站时刻 + 换乘步行 + 安全余量）`；`slack < 0` → **判不可用，顺延下一班并计入等待**（需求 7 闸门）；`slack` 很小（0~安全余量）→ 可给**轻微风险惩罚**或标记"偏紧"。置信度**中**。

### 4.5 三档主判据定义（置信度：高）

| 档 | 主判据 | tie-break 顺序 | 行业锚 |
|----|--------|----------------|--------|
| **综合**（默认） | `cost` **升序** | ①换乘次数↑ ②步行量↑ ③来源（高德优先）④planId | 谷歌 **Best route**；高德 `BUS_DEFAULT` |
| **少换乘** | **换乘次数升序** | ①`cost`↑ ②步行量↑ ③来源 ④planId | 谷歌 **Fewest transfers**；高德 `BUS_LEASE_CHANGE` |
| **少步行** | **步行量（米/分钟）升序** | ①`cost`↑ ②换乘次数↑ ③来源 ④planId | 谷歌 **Least walking**；高德 `BUS_LEASE_WALK` |

- 说明：tie-break 均**回收 `cost` 作次级判据**（保证"同换乘数/同步行时仍选更优总体验"），末位保留既有"来源/planId"稳定序（对齐 `rank.ts`）。
- **为什么不设"时间短"第四档**：澳门无地铁、行程短，"时间短"与"综合"高度重合；高德/谷歌也把"时间短"作为**独立但非默认**档。若用户坚持可加，但**默认仍为综合**。

### 4.6 与谷歌/高德档位的取舍（置信度：高，决策性）

| 行业档 | 我方是否做 | 理由 |
|--------|------------|------|
| Best route / 综合权重 | ✅ 做（默认） | 直接对标 |
| Fewest transfers / 少换乘 | ✅ 做 | 直接对标 |
| Least walking / 少步行 | ✅ 做 | 直接对标 |
| Shortest time / 时间短 | ⚠ 暂不做 | 与"综合"重合度高；可作 Backlog |
| Lowest cost / 最低票价 | ⚠ 暂不做 | 我方票价数据未完整接入；个人工具优先级低 |
| Wheelchair accessible / 无障碍 | ⚠ 暂不做 | 澳门无障碍数据不完整，做易误导 |

## 6. 对需求 8 的落地建议（对齐 AC-52~54）

1. **默认档 = "综合"**，按 §4.1 的 `cost` 升序；`cost` 为**内部排序量**，**不直接展示为"总时长"**（展示仍用 `totalMin`）。
2. **三档快捷标签**：`综合`（默认）/ `少换乘` / `少步行`；命名与判据对齐谷歌 Route options（§4.5）。
3. **参数可配置**：α、β、安全余量集中为常量/配置，便于后续按实测调参（Phase 2 架构师落为纯函数参数）。
4. **联动需求 7**：换乘可行性闸门（slack ≥ 安全余量）与安全余量**共用同一参数**，避免两处口径分叉。
5. **AC 补齐**：在既有 AC-52~54 基础上，建议架构师补一条"**α/β/安全余量可核对**"的断言（cost 明细可对账），确保排序**可解释、可回归**。
