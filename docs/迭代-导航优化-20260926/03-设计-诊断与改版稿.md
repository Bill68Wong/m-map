## 2. 逐项现状诊断（截图为证 + 量化）

### 2.1 需求 ② 站点全量渲染 —— **量化最硬的一条**

| 场景 | `.nav-map__station` 总数 | 本线 `--onroute` | 非本线 `--dim` |
|---|---|---|---|
| 首页（未选线） | **192** | 0 | 0（全部按线路色实心渲染） |
| 路线查看「51」 | **425** | 19 | **406** |

**判读**：线上已经做了「本线放大 / 非本线缩小转灰」，但用户要的是**隐藏**。406 个灰点虽降到 `opacity .45`，在 390px 宽的屏幕上依然是密集噪点 —— 尤其轻轨站为了保留线路色，`--dim` 下仍是**彩色小方点**（`globals.css:4954-4966`），比灰点更抢眼。

> 证据截图：`13-route-view.png`（选线后）、`14-route-view-zoomout.png`（缩到全市，点数不变 ⇒ 数据层无剔除）、`00-home.png`（首页 192 点）。
> 取证打印：`stationAll 425 / stationOn 19 / stationDim 406`（脚本 07）。

**竞品印证**：Google Maps 地图上公交站「At wider zoom levels, many bus stops disappear to reduce clutter and improve readability」；选中某条线时该线高亮、其余「recede into context」。也就是说**业界做法就是按当前焦点过滤掉无关站点**，与本需求完全一致。

### 2.2 需求 ⑤ 用户位置标点 —— **两个点，中心重合**（本文件最关键实证）

**线上实拍（等车态 boarding）**：

| 元素 | 类名 | 实测框 `[x, y, w, h]` | 中心 | 外观 | 动画 | z-index |
|---|---|---|---|---|---|---|
| ① 定位蓝圆 | `.nav-map__mepin` | `[113, 404, 18, 18]` | (122, 413) | Ø18 实心青花蓝 + `0 0 0 4px rgba(11,87,208,.25)` 光环 | **none（静止）** | 110 |
| ② 实时蓝点 | `.user-dot` → `__core` | `[114, 405, 16, 16]`（core 12×12） | (122, 413) | Ø12 青花蓝 + 2.5px 白边 + 呼吸光圈 | `navYouPulse 1.6s` | 128 |
| ② 附标签 | `.user-dot__label` | — | — | 胶囊，**文字 = 「您」** | 无 | — |

**判读（明确）**：用户看到的「两个用户点」= **① `.nav-map__mepin`（单次定位的蓝圆，不随移动）+ ② `.user-dot`（实时蓝点，呼吸 + 「您」字胶囊）**。两者中心**完全重合**在同一坐标，因此视觉上是「一个蓝圆里面套着一个带字的呼吸点」，比两个分开的点更难看。

**成因（源码定位）**：
- `.nav-map__mepin`：`NavMap.tsx:317-325`，由 `runLocate()`（`AMap.Geolocation` 一次性定位）创建并缓存于 `userMarkerRef`，**只在用户点「定位」按钮时 `setPosition`** ⇒ 天然不随移动；
- `.user-dot`：`UserDotLayer.tsx` + `useUserFix.ts`（`watchPosition` 实时定位），文案硬编码 `label.textContent = "您"`；
- **乘车中更糟**：`NavShell.tsx:329-331` 的 `userFix = (!detailActive || (ride.phase === "riding" && ride.plate)) ? null : userFixR.fix` ⇒ 一旦判定上车且锁定车牌，**实时蓝点被隐藏，只剩静止的 mepin**。

**实测补充（riding 态）**：`.nav-map__mepin [125,414,18,18]`，`.user-dot: null`（不存在）。即：
- 等车态 → 两个点（重合）；
- 乘车态 → 一个点，但它是**停在出发地不动**的那个 ⇒ 与用户「希望它随线路轨迹移动」的诉求完全相反。

> 证据截图：`20-userdot-zoom.png`（以蓝点为中心放大 150×130 的裁剪图）、`06-nav-boarding.png`、`10-nav-riding.png`。
> 取证打印：`mepin [113,404,18,18] / userDot [114,405,16,16] / userLabelText "您"`（脚本 10）。

### 2.3 需求 ③-1/2 「顶部时间区灰框紧紧框住」+ 「线路标签放到总用时同一行右侧」

**实测几何（390×844，half 档，详情面板）**：

| 元素 | 框 `[x, y, w, h]` | 说明 |
|---|---|---|
| `.rc-detail__head` | `[16, 498, 358, 80]` | 头部容器 |
| `.rc-detail__head .rc-head__main`（总用时 22 分） | `[17, 499, **356**, 34]` | **宽度 356 ≈ 整行** ⇒ 独占第一行 |
| `.rc-detail__head .rc-arrive`（预计到达） | `[17, 550, 93, 19]` | 落到**第二行** |
| `.rc-detail__head .route-stack`（线路标签） | `[110, 550, 37, 20]` | 同样在**第二行** |
| `.rc-detail__head .fav-btn__btn`（收藏） | `[146, 533, 66, 44]` | 第三层错位 |

**根因（决定性）**：全仓 `grep -rn "rc-detail__head" src/` **只有 1 处**，且是 JSX 引用（`NavDetailBody.tsx:141`）——**`globals.css` 里没有任何 `.rc-detail__head` 规则**。CSS 里存在的是旧类名 `.rc-head`（`globals.css:1274`，`display:flex; gap:12px; flex-wrap:wrap`），但**类名改了、规则没跟着改**。

于是头部只吃到 `.card`：
```
background: var(--surface); border: 1px solid var(--stroke);
border-radius: var(--r-card);  /* 10px */
/* 关键：display 默认 block、padding 0 */
```
实测计算值复核：`display: block`、`padding: 0px`、`border-top 1px rgb(220,220,223)`、`border-radius 10px`、`font-size 15px`。

**这就是用户说的「一个灰框紧紧框住时间区域」**：一个 1px 灰边 + 10px 圆角的白卡片，里面文字**零内边距、直接顶到边框**，而且因为不是 flex，`margin-left:auto` 的到达时刻也没能靠右，只能被挤到第二行。

> 证据截图：`21-head-frame-zoom.png`（头部裁剪放大）、`09-detail-half.png`、`05-detail-pane.png`。

### 2.4 需求 ③-3/4/5/6 「窗格乱跑位 / 去掉估算 / 车辆信息重复下一站 / 横幅超长」

#### (a) 吸底条「乱跑位」—— **已用多帧采样复现**

对 `.route-sheet__handle` 做拖拽（每 20–25ms 采样一次），记录吸底操作条 `.nav-actions` 的 `y` 与面板上缘：

**half → full（上拖，松手后）**

| t (ms) | `.nav-actions` y | 面板上缘 |
|---|---|---|
| 14 | 447 | 359 |
| 61 | 383 | 295 |
| 111 | 320 | 232 |
| 151 | 257 | 169 |
| 182 | 193 | 105 |
| 213（松手瞬间） | **170** | 82 |
| 263 | **321** | 83 |
| 334 | **591** | 98 |
| 412 | 634 | 101 |
| 490+ | **642**（落定） | 101 |

**full → peek（下拖，松手后）**：`736 → 829 → 922 → 1016 → 1109 → **1202** → 682 → 693 → 695`（落定）。
其中 `1202 > 844`（视口高）⇒ **操作条先被甩到屏幕外，再弹回来**。

**判读**：拖动过程中操作条**跟手**（与面板同步移动，这没问题）；**松手瞬间开始一段约 300ms 的「横跨 470px」的自动滑动**（170 → 321 → 591 → 642），期间它停在面板中部、**盖住正文内容**。这正是用户描述的「窗格会乱跑位，导致其他内容被遮挡」。

**成因（源码定位）**：`.nav-actions` 是 `position: sticky; bottom: calc(var(--sheet-y-layout, 0px))`，并在 2026-09-25 被加上了 `transition: bottom var(--sheet-dur-settle)`（`globals.css:6195-6198`，注释说明是为修「换档时跑位」）。但根问题是**布局通道**：面板位移走 `transform: translateY(--sheet-y-anim)`（GPU 合成、不动布局），而操作条的 `bottom` 是**布局属性**，且同时受「滚动容器高度变化」影响 ⇒ 两者永远不在同一时基上，只要 `bottom` 参与过渡就会「先跑后归」。**单纯加 transition 治不好。**

> 证据截图：`07-detent-full.png` / `08-detent-peek.png` / `09-detent-half.png`。

#### (b) 吸底条**压住头部**（遮挡的另一处实证）

half 档同帧实测：`.rc-detail__head [16, 498, 358, 80]`（占 498–578）与 `.nav-actions [16, 510, 358, 85]`（占 510–595）**横向同宽、纵向重叠 68px**。且 `.nav-actions` 在后、`z-index:20` ⇒ 头部内容被操作条盖住。

#### (c)「估算」徽标

`NavDetailBody.tsx:151`：`{degraded && <span className="nav-degraded nav-degraded--inline t-label">估算</span>}` —— 就渲染在头部行内（与线路标签同排）。样式见 `globals.css:2430-2438`（错误色系胶囊）。用户要求去掉 ⇒ 见 §4.2。

#### (d) 车辆信息重复「下一站」—— 两处同屏

| 位置 | 源码 | 文案 |
|---|---|---|
| 吸底条状态行右侧 | `NavTrackBar.tsx:121` `right = nextLabel ? \`下一站 ${nextLabel}\` : null` | `下一站 T354 北安出入境事務大樓` |
| 面板中部提示 | `NavDetailBody.tsx:202-208` `.nav-note-neutral` | `距下车站还有 N 站 · 下一站 T354 …` |

再加上纵轴 `.navstrip__badge`「下一站」胶囊 —— **同屏最多 3 处「下一站」**。用户要求车辆信息行不重复 ⇒ 见 §4.3。

#### (e) 下车横幅超长溢出 —— **实测溢出 66px，且含开发提示**

`.nav-alarm` 为 `white-space: nowrap`（`globals.css:6259`）。以真实容器宽 358px 注入实测：

| 变体 | 文案 | `scrollWidth` | `clientWidth` | 溢出 |
|---|---|---|---|---|
| soon | `下一站就是下车站：T345 氹仔客運碼頭 · 准备下车 横幅 + 震动` | **424** | 358 | **是（+66px）** |
| now | `到站了：T345 氹仔客運碼頭 · 请下车 横幅 + 震动` | 358 | 358 | 否（已贴满） |

**两个问题**：① 文案结构冗长（"下一站就是下车站"）；② `AlightBanner.tsx:32` 里的 `<span className="nav-alarm__hint">横幅 + 震动</span>` 是**开发期说明，直接暴露给用户**（现在还在线上）。`now` 之所以没溢出，只是因为「请下车」比「准备下车」短 —— 已经贴到 358px 边缘，任何更长的站名都会溢出。

### 2.5 需求 ④ 线路标签不统一 —— **实际是 3 种形态并存**

| # | 形态 | 选择器 | 实测 `border-radius` | 出现在 |
|---|---|---|---|---|
| ① | 圆角矩形 | `.route-stack__seg:only-child` | `6px`（`--radius-chip`）| 头部（单码）、站条、多数单码处 |
| ② | **斜切直角**（`clip-path` 削掉圆角）| `.route-stack__group--multi .route-stack__seg` | **`0px`**，`clip-path: polygon(0 0,100% 0,calc(100% - 7px) 100%,0 100%)` | 推荐卡「51 51B 59」、导航头部多码、卡片页 |
| ③ | 胶囊 | `.nav-linechip` | `999px` | 地图品牌栏「当前查看线路」+ `×` 退出键 |
| （④ 历史遗留）| 胶囊 | `.route-chip` | `var(--r-pill)` = 8px | 其它页面（卡片/免费乘坐等） |

**归因**：`globals.css` 里有**两套** `.route-stack` 规则：旧段 `785-857`（v0.19.1，斜切平行四边形）与新段 `3209-3301`（v2.4.1，「空白斜间隙」）。新段覆盖大部分属性，但多码组仍是 `border-radius:0` + `clip-path` ⇒ 圆角被几何裁掉。这正是用户「部分没做圆角」的来源。

**实测复核**：推荐卡内多码 `.route-stack__seg` 计算值 `borderRadius: 0px`、`clipPath: polygon(...)`。

> 证据截图：`04-recommend-list.png`（卡内「51 51B 59」）、`13-route-view.png`（品牌栏胶囊）。

### 2.6 需求 ⑥ 点击车/站图标导致导航中断 —— **复现成功**

| 时点 | `body[data-nav]` | `.nav-actions` | `data-nav-phase` | 详情面板 | 面板上缘 y |
|---|---|---|---|---|---|
| 点击前（面板 peek 档，看着地图） | — | 存在 | （`off`/`boarding` 视帧） | 存在 | 675 |
| **点击地图上的巴士图标后** | — | **null（从 DOM 消失）** | **null** | **false（卸载）** | **844（面板全关）** |

**判读**：点击巴士 / 站点图标后，面板被强制收起、吸底操作条整体消失、页面退回纯地图舞台 —— 与用户描述「导致导航中断回到首页地图界面」一致。

**成因（源码定位，与架构师结论一致）**：`NavShell.tsx:273-292` 的 `onStationClick` / `onVehicleClick` 在 `rsOpenRef.current` 为真时执行 `setRsOpen(false); setStage("map")` ⇒ 打开站点卡/车辆卡的同时**把导航面板关掉**。

> 证据截图：`16-after-vehicle-click.png`。

| **地图稳定感** | 导航中用户手动缩放后，**系统刷新绝不重置 zoom/center**；只有「重新居中」按钮或 `re-center` 超时（约 30s 无操作）才回收视角 | 同理；刷新只更新图层不碰 viewport | 现状：数据刷新触发 `frame()` 重取景 ⇒ 比例尺归位 | **铁律：刷新只更新数据层，不改 `zoom/center`**；视角只由「显式意图」（打开面板/换档落定/点定位）改变 |
| **主/备路线线型** | 选中路线 = 亮蓝粗线；备选 = 灰线（只在地图上，不带站点） | 选中 = 主题色粗线；备选 = 灰 | 选中 = 线路色；总览灰底线 + 彩段 | 沿用（已合规），并**备选路线不渲染站点** |
| **站点密度** | 广域缩放下**大量公交站直接消失**；选中某线后该线高亮、其余「recede into context」 | 同：默认隐藏公交站，选中线路才画站 | 现状：425 点全画（406 灰点） | **只画本线站点**（换乘站保留）+ 可选「显示周边站点」开关 |
| **用户点** | 导航中是**一个**蓝点/蓝箭头（带方向），**没有文字**；已走过路段变灰，蓝点骑在灰/彩交界 | 一个蓝点，无文字，带方向扇形 | 现状：两个点重合；带「您」字；乘车时只剩静止点 | **单点、无字、呼吸、随移动、沿线推进、身后变灰** |
| **站点节点** | 站 = 小圆点/图标**压在线上**；换乘站 = 更大的多层圆 | 站 = 圆点，换乘站加粗 | 已实现（空心圆 / 已过灰 / 停靠蓝环） | 沿用，仅把「用户点」并入节点（不再单独一行） |
| **线路标签** | 官方线路色**色块/胶囊**，浅色线路用深字，深色用白字；换乘用图标序列 | 线路色**圆角矩形**，并列用「/」或并列排布 | 现状：三种形态混用 | **统一 6px 圆角**；并列用 2px 白色斜间隙；换乘用箭头 |
| **信息层级** | 顶部一条**指令横幅**（下一步动作 + 距离），信息高度收敛；详情面板只留决策必需 | 顶部指令条 + 卡片 | 头部 + 步行/等车 + 纵轴 + 折叠 + 脚注 + 吸底条，**信息较密** | 头部收敛为「总用时 / 到达 / 线路」三件事；其余下沉 |
| **动效** | 极少：位置平滑插值、面板弹性、无装饰动画 | 极少 | 呼吸 2 处 + 到站脉动 + toast | 收敛为 **1 处常驻呼吸（用户点）+ 1 处紧急脉动（到站）** |

**可迁移的三条结论**：
1. **「稳定感」不是靠动效，而是靠「不打断」**：不重置 zoom、不因刷新重取景、点击信息卡不退出导航。
2. **地图的清晰度来自「减法」**：非焦点站点直接不画，而不是画淡一点。
3. **一个语义只用一个形状**：线路标签要么全圆角、要么全斜间隙；并列与换乘必须用不同语汇。

### 4.6 吸底操作条「防跑位」设计约束（对应需求 ③-1）

问题不在动画时长，而在**通道**。给出两条可选实现（推荐 ②）：

**① 最小改动（保留 sticky）**：把 `bottom` 的过渡**去掉**（`transition: none`），并让 `--sheet-y-layout` 与 `--sheet-y-anim` **同帧写入**；操作条的跟手完全交给「滚动容器高度变化」自然重排。
风险：`bottom` 突变仍可能与面板 `transform` 不同步 ⇒ 视觉上仍是「瞬跳」。

**② 推荐（换通道）**：把 `.nav-actions` **移出滚动容器**，挂到面板根（`.route-sheet`）作为 `position: absolute; bottom: 0` 的直接子元素，与面板**同属一个 `transform` 上下文** ⇒ 面板怎么动，操作条怎么动，**物理上不可能跑位**。滚动容器底部留出 `padding-bottom: calc(操作条高 + safe-area)`（现状已有 `padding-bottom: 96px` 类似做法）。

```css
/* ② 推荐 */
.route-sheet { position: absolute; /* 既有 */ }
.route-sheet__actions-slot {           /* 新增：操作条挂载点（不随滚动） */
  position: absolute; left: 0; right: 0; bottom: 0; z-index: 20;
  background: var(--surface);
  border-top: var(--frame-w) solid var(--border);
  padding: 10px var(--space-4) max(10px, env(safe-area-inset-bottom));
}
.route-sheet__scroll { padding-bottom: calc(96px + env(safe-area-inset-bottom)); }
```

**视觉验收项（写入 Spec 的 AC）**：拖动面板在 `full ↔ half ↔ peek` 之间往返各 3 次，采样 `nav-actions` 的 `y`：
- 拖动中：与面板上缘的相对距离变化 ≤ 2px；
- 松手后：从松手帧到落定帧，`y` 的**单调**变化且总位移 ≤ （面板位移 + 2px），**不得出现反向移动**；落定后立即稳定（后 300ms 内 `y` 变化 ≤ 1px）。

> 现状实测值供对照：松手后 `170 → 321 → 591 → 642`（含反向与超调），`peek` 档甚至到 `1202`（越出视口）。

   `换乘 T354 · 步行 3 分 · 等车约 6 分`
   （现文案只有 `换乘步行 N 分（atLabel）`，等车被隐藏 ⇒ 用户看到换乘方案「更快」却不理解为什么实际赶不上）。
2. **总用时口径统一**：卡片总用时 = 步行 + 乘车 + **换乘步行 + 换乘等车** + 步行（进站）。若某段等车仍为估算，用 `rc-val--est` 灰字标注，但**不隐藏数值**。
3. **「能不能赶上」只用文字表达，不用颜色**：`正常走能赶上`（`--fg-2`，中性）/ `需快走`（`--warn`）/ `可能赶不上`（`--danger`）。避免新增第 3 种彩色徽标。
4. 已过/未过、上车站、下车站的口径不变（沿用上轮：已过灰 / 下车站绿仅站名 / 到站砖红脉动）。

### 4.8 需求 ⑧ 用户偏好模型 UI（`04-pref-model-v2.html`，待拍板）

**形态：推荐列表顶部一行三档快捷切换（segmented control），不引入设置页。**

```
┌───────────────────────────────────────────────┐
│ [  推荐  ] [ 少换乘 ] [ 少步行 ]               │  ← 36px 高，圆角 10px 外框，选中 = --accent 底白字
└───────────────────────────────────────────────┘
  排序依据 总用时 60% · 换乘 25% · 步行 15%        ← 一行小字，解释「为什么这样排」
```

| 档 | 第一排序键 | 并列时 | 建议参数 |
|---|---|---|---|
| **推荐**（默认） | 综合分 `Score` | — | `Score = 0.60·totalMin + 0.25·(transferCount·8) + 0.15·walkMin + waitPenalty`；`waitPenalty` = 换乘等车超 10 分后每分钟 0.5 分 |
| **少换乘** | `transferCount` 升序 | 综合分升序 | 换乘次数为硬第一键 |
| **少步行** | `walkMin` 升序 | 综合分升序 | 步行 = 出站 + 换乘 + 进站总和 |

- 徽标只用三种语义：`推荐`（综合第一）/ `更快`（总用时最短，沿用 `--brand-green`）/ `含等车 N 分`（换乘方案诚实披露）；
- 选择写入本地偏好，下次直达；默认「推荐」；
- 三档都**不得出现不可行方案**（赶不上换乘的班次必须先剔除，见需求 ⑦）；
- 参数落在 Service 层常量，前端只读。

**待用户拍板 4 问**：① 三档形态？② 默认档 + 是否记忆？③ 权重 `0.60/0.25/0.15` 与 `K_t = 8 分/次`？④ 「含等车 N 分」徽标要不要？

### 4.9 需求 ⑨ / ⑩：设计侧验收项

**⑨ 上车判定灵敏度 / 下车自动化** —— 设计侧只关心「状态是否可见、能否纠错」：
- 上车自动判定成功后：**瞬态反馈（2.5s toast，现有）+ 常驻纠错入口**（`不是这辆`）保留；
- 上车判定失败 / 低置信：`等待上车` 态下保留 `手动标记上车`（弱样式），并显示原因（`这条线现在查不到车 · 稍后再试，或直接点「我已上车」`，现有文案 OK）；
- 下车自动化后：`我已下车` 主按钮降级为**纠错**语义（自动完成时不再需要用户点），但**按钮必须常驻**（防误判）；
- 新增规范：**任何自动判定都必须有 ≤1 个纠错出口，且出口在 44×44 触摸区内**。
- 全屏化：`body[data-nav="riding"]` 隐藏底导（现有）—— 但**必须保证**面板关闭时用户仍能看到「正在导航」的持续指示（建议：品牌栏保留线路标签 + 蓝点呼吸），否则「自动」会让用户以为导航结束了。

**⑩ 去除高德底图自带站点** —— 设计侧验收项：
- 底图上**不得**出现高德的公交站标 / 站名（现有自定义 `--onroute/--dim` 站点图标是我们自己的）；
- 若因 `AMAP_MAP_STYLE_ID` 未配置而降级到默认样式（`technique`：`技术方案-隐藏底图公交站点方案-20260923.md` 已给出链路，缺 Vercel env），则该环境**视为不通过验收**（因为会出现双层站点）；
- 视觉验收：随机 3 个缩放级别截图，站标总数 = 我们图层的 marker 数（无重复、无多出来的底图站名）。
