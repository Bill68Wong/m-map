## 1. ① 色值：为什么是 `#FFD400`

### 1.1 硬约束回顾
澳门第 5/2002 号法律《机动车辆税规章》：免税车辆（含 ≥15 座载客巴士）车牌 **底色黑、字与横划为黄色**。法规只钉死「黄」，未指定色号 ⇒ 色号由设计定。

### 1.2 候选与实测对比度（黑底 `#0C0F14`）

| 候选 | 颜色语义 | 对比度 vs `#0C0F14` | 判定 |
|---|---|---|---|
| `#FFFF00` | 纯黄 / 屏幕高亮色 | 17.87:1 | ✗ 过亮：OLED 全黑面上产生溢光（halation），小字发糊；且纯黄在本项目里是「选中/警告」语汇 |
| `#FFDE33` | 浅黄 | 14.39:1 | ✗ 偏白，像褪色贴纸，失去「反光黄」的饱和感 |
| **`#FFD400`** | **交通信号黄（H50 S100 L50）** | **13.41:1** | **✓ 采用** |
| `#FFCC00` | ≈ PMS 116 C | 12.70:1 | △ 可用，比采用值略偏橙 |
| `#F0C000` | 深黄 | 11.19:1 | △ 备用降档值（仅当夜间眩光实测不通过时启用，见 A1） |

**取舍理由**：`#FFD400` 落在「交通反光膜黄」同族区间（与 PMS 116 C ≈ `#FFCD00` 相邻），色相不偏橙也不偏绿；感知明度 L\* = 86（纯黄 L\* = 100，低 14%）、对比度由 17.87:1 降到 13.41:1 —— 这 25% 的对比度让出量，换来的正是「小字号在深底上不溢光」；即便让出后仍有 91% 的 AAA 余量，是纯赚的交易。**不照搬户外过曝后的发白黄** —— 屏幕 UI 的对比度预算与反光膜不同：反光膜靠外部光源提亮，屏幕只能靠自发光，把亮度顶到 `#FFFF00` 换来的是眩光而不是可读性。

### 1.3 三个必须校验的对比度（全部实测）

| 对 | 数值 | 标准 | 结果 |
|---|---|---|---|
| 牌号字 `#FFD400` × 牌底 `#0C0F14` | **13.41:1** | AAA 正文 7:1 | ✓ 通过（余量 91%） |
| 牌底 `#0C0F14` × 浅色卡片 `#FFFFFF` | **19.19:1** | 非文本 3:1 | ✓ 通过（浅色主题无需框线） |
| 牌底 `#0C0F14` × 深色卡片 `#1C1E24` | **1.15:1** | 非文本 3:1 | ✗ **不通过** ⇒ 这就是深色主题必须补框线的原因 |
| 框线（`rgba(226,226,233,.45)` 合成 ≈ `#6C6E74`）× 深色卡片 | **3.27:1** | 非文本 3:1 | ✓ 通过 |

> 复算脚本：WCAG 2.x 相对亮度公式（sRGB 线性化 → `0.2126R+0.7152G+0.0722B`）。上表数值可复现。

### 1.4 为什么字色不随主题变

1. **车牌是物理对象**，黄色不因天色而改；主题切换若让牌子变色，会削弱「这是同一块牌子」的认知。
2. 更要紧的是任务场景：本 App 大量在**夜间行驶的车厢里**使用，车牌是「车快到了，核对是不是这辆」的唯一锚点。压暗字色省下的一点眩光，换来的是核对失败率上升 —— 这笔交易不划算。
3. 真正的暗色适配需求（牌子在深底上"消失"）由**框线**解决，不是由改字色解决。

**唯一例外（不默认启用）**：若真机夜间实测确认 13px 档有眩光，把 `--plate-ink` 换成 `#F0C000`（11.19:1，仍 AAA），只改这一个 token。见 A1。

## 2. ② 组件规格

### 2.1 字体：必须先修一个坑（本次最关键的发现）

现状 `src/app/globals.css:58`：

```css
--font-mono: "JetBrains Mono", "Barlow", monospace;
```

**全仓没有任何一处加载字体文件** —— `src/` 与 `public/` 中不存在 `@font-face`、`next/font`、`fonts.googleapis`、`.woff*`（已全量 grep）。设计文档里规划的 Barlow / Noto Sans SC / JetBrains Mono **一个字都没真正加载**，因此：

```
--font-mono  →  "JetBrains Mono"(无) → "Barlow"(无) → generic monospace
```

- iOS / Safari：generic `monospace` 默认解析为 **Courier** —— 一种**衬线**打字机体。
- 结果：车主在 iPhone 上看到的「等宽车牌」是衬线打字机字体，与澳门车牌「**统一正体无衬线**」的法规要求**视觉相悖**，也完全不像车牌。

⇒ 车牌**必须**用自己的字体 token（`--plate-font`），不能复用 `--font-mono`。本规格只新增 token，不动 `globals.css` 既有行；`--font-mono` 的修复另案（A3）。

```css
--plate-font: ui-monospace, SFMono-Regular, "SF Mono", Menlo, Consolas,
              "Roboto Mono", "Droid Sans Mono", "DejaVu Sans Mono",
              "Liberation Mono", monospace;
```

覆盖 Apple（SF Mono，无衬线）/ Windows（Consolas）/ Android（Roboto Mono、Droid Sans Mono）/ Linux（DejaVu Sans Mono），**全部为无衬线等宽**。不引入 Web Font ⇒ 零下载、零 FOUT，代价是字宽跨平台有差（0.55em–0.60em，见 §2.3），已用 `ch` 单位吸收。

**已实测验证（Windows Chrome / Consolas）**：`ch` = 0.55em，`AA7312` 墨迹完美垂直居中于标签盒，无裁切。

**字体规则（法规约束）**：
- 用等宽 ✔（真实车牌字符等宽，且防伪；等宽 ≠ 艺术字）
- 字重固定 **700**（黄字黑底属「亮字暗底」，光渗会让笔画显粗，但 13px 档更需要笔画厚度；Android 无真粗体时浏览器合成加粗，1px 级，可接受）
- **禁止**：`font-style: italic`、`text-shadow`、`-webkit-text-stroke`、艺术字/描边/渐变填充、`text-transform` 之外的任何字形修饰 —— 法规「统一正体无衬线，禁止斜体或艺术字体」
- 牌号内容**不得**插入分隔符或空格（不做 `AA 73 12`），数据给什么就渲染什么

### 2.2 左上「澳門」二字：**不加**

真实澳门车牌左上角有繁体「澳門」+ 区徽。UI 标签里**一律不加**，理由四条（第 1 条是否决性的）：

1. **字号纪律冲突（否决项）**：sm 档牌号 13px，「澳門」若要不抢主号、只作牌面元数据，需 ≤9px。而项目在 v2.4.1 因「禁止整页缩放」把最小字号下限抬到了 13px（`globals.css:62-65`、`layout.tsx:56-73` 有完整决策记录）。加「澳門」= 逼出一个 9px 的字号，直接违反既有可读性纪律。
2. **零信息增益**：整个 App 就是澳门导航、用户人在澳门、页面标题写着 M Map。牌子再说一次「澳門」是纯装饰。
3. **横向预算**：`VehicleCard` 标题行（`globals.css:5129-5134`）已有「线路标签 + 车牌 + 末班」三个 flex 项、`gap:8px`。md 档再加两字 ≈ +22px，375px 屏下长线路名会被挤到省略。
4. **符号已自足**：黑底黄字这个**颜色组合本身**就是澳门车牌的能指，不需要文字注解。

> 若未来确实要做「品牌化车牌」，正确做法是 lg 档以上的**独立牌面组件**（真比例、带区徽与冲压凹槽），而不是往 20px 的 UI 标签里塞字。届时应另立规格。

### 2.3 三档规格

| 档位 | 用途 | 字号 | 内边距 (y / x) | 圆角 | 字距 | 字重 | 实测尺寸 W×H* |
|---|---|---|---|---|---|---|---|
| `sm` | 状态行 / 列表行 / 行内独立值槽 | **13px** (`--text-sm`) | **2px / 6px** | 4px | 0.08em | 700 | 60×18.3 |
| `md` | 车辆信息弹窗标题行（**主场景**） | **15px** (`--text-md`) | **3px / 8px** | 4px | 0.08em | 700 | 71.5×22.5 |
| `lg` | 详情页 / 大卡 | **20px** (`--text-xl`) | **4px / 12px** | 4px | 0.08em | 700 | 98×30 |

\* Windows/Consolas 实测。iOS/Android（0.60em 字宽）预估：`sm` ≈62、`md` ≈76、`lg` ≈104 宽；**高度跨平台一致**（只由 fontSize × 1.1 + padding 决定）。

- **不新增字号**：13/15/20 全在既有 `--text-*` 阶梯内（`--text-sm`/`--text-md`/`--text-xl`），零冲突。
- **sm 不得再往下**：11px（`--text-2xs`）虽然存在，但因「禁缩放 ⇒ 小字无法放大」，车牌这种「核对用」信息绝不能是站内最小字号。
- **字距统一 0.08em**，跨档不变：字距是车牌识别特征（字符间留白），不该随尺寸漂移；0.08em 在 13/15/20px 分别 ≈1.0/1.2/1.6px，均落在可读区间。
- **字距补偿（必做）**：`letter-spacing` 会在**末字之后**也追加一份空白，右侧视觉边距会莫名变宽 1.0–1.6px。故 `padding-right` 必须减去一个字距：
  `padding: var(--_py) calc(var(--_px) - var(--plate-tracking)) var(--_py) var(--_px);`
  已实测：补偿后左右光学等距（8.00px / 8.00px）。
- **等宽定宽**：`min-width: calc(6ch + 2 * var(--_px))`。澳门巴士牌号为 2 字母 + 4 数字 = 6 位（DSAT `busPlate` 如 `AA7312`/`MY9362`，无分隔符）。
  ⚠️ **更正（实测）**：`min-width` 目前**并未生效** —— 字距 0.08em 让文字 advance 达 `6ch + 6×tracking`（md 档 56.7px），加 padding 后盒宽 71.5px，已大于 `min-width` 的 65.5px。所以「换车不跳动」**真正靠的是「等宽字体 + 全库牌号恒为 6 字符」这两件事**，`min-width` 只是兜底。⇒ **任何人不得以「有 min-width 兜着」为由去掉 `--plate-font`** —— 一旦换成比例字体，字符宽度随内容变化，宽度立刻开始抖。
  `min-width` 的价值在**未来**：若出现 7 位牌号，它是下限、内容自然撑开，**不裁切**（已删 `text-overflow:ellipsis`）。UI 会**如实显示**格式变化，而不是静默截断 —— 这对及早发现 DSAT 数据格式变动是好事。
- **禁止省略号**：现 `.nav-vehicle-card__plate` 带 `overflow:hidden; text-overflow:ellipsis`（`globals.css:5148-5154`），牌号被截成 `AA7…` 比不显示更糟。改为 `flex:none`。
- **空值不渲染**：`.plate:empty { display:none }` 是硬防线 —— 牌号为空时若照常渲染，会留下一个 6ch 宽的黑方块（比不显示更像 bug）。

### 2.4 数据契约（与后端对齐，2026-09-30 实测确认）

我的尺寸假设依赖「牌号恒为 6 字符大写」，已由 `mvp-dev-expert-team-backend-2` 用真实库数据核验，**不是推测**：

| 检查项 | 实测结果 |
|---|---|
| `vehicle_plates` 行数 | 514 行，**全部长度为 6** |
| 含空格/连字符/小写/全角 | **0** |
| 不符合 `^[A-Z]{2}[0-9]{4}$` | **0 行**（514/514 全符合） |
| 源表 `bus_snapshots` 原始 `bus_plate` 脏值 | 4080 行中**与 `upper(trim())` 不一致的为 0** |

⇒ 写入清洗（`src/lib/dsat/vehicle-plates.ts:54` `normalizePlate`）= `toUpperCase() + replace(/\s+/g,"")`，**无分隔符插入**，与 §2.1「数据给什么渲染什么」一致。DSAT 源头本身即规范 6 位，清洗是防未来的保险。
⇒ **无 `raw_plate` 列**（后端决定不加，避免双真身）。设计侧按「不存在该列」处理，不需要任何降级分支。

**对我方规格的连带结论**：
1. 宽度稳定性的**真正承重件是等宽字体 + 6 字符保证**（见 §2.3 更正），数据侧已锁死。
2. 若 DSAT 某天改格式（如 7 位），标签会**自然撑开而非截断** ⇒ 从 UI 一眼可见；此时无需改 CSS，只需复核 375px 下的横向预算。
3. `plate` 在 `/api/route-vehicles` 侧已过滤空值（`route.ts:197,217` `if (!plate) continue`），故 `VehicleLite.plate` 实际恒非空；`.plate:empty` 属额外防线，不影响正常渲染。

> ⚠️ **跨端契约（务必记入）**：「6 字符」是**写入侧 `normalizePlate` 的保证，不是天然属性**（`mvp-dev-expert-team-backend-2` 明确指出）。该函数是唯一关口，若哪天为兼容 7 位牌号而放宽为「原样存」，**等宽假设会先在后端层破，再在 UI 上显形**。改动前需通知设计侧复核预算。同理 §2.5.5.1 的 `5ch` 也依赖「编号最长 5 字符」这条数据事实 —— 若出现 6 字符编号，角标会自然变宽（**不截断**），无碍渲染，但需重跑 320px 预算。

### 2.5 车队编号角标（Fleet Code Badge）—— 与车牌同行的第二枚标识

车主本轮需求原文：「**在巴士车牌那一行居右制作车牌对应的巴士的车型标签，如标签 HE380**」。

#### 2.5.1 术语裁定：它叫「车队编号」，不叫「车型」

**这是一处必须先说清的措辞风险。** 车主说的是「車型標籤」，但举的例子 `HE380` 是 **DSAT 的 `busCode`（车队编号/车隊編號）**，不是车型型号（车型是 `KLQ6116GHEV2` 这类）。

- 事实依据：`src/lib/dsat/vehicle-models.ts:12-13` 已记录「**UI 只显车队编号（如 `HE380`），不显长型号名（主人 2026-10-30 拍板）**」。型号四列（`model` / `model_category` / `model_source` / `model_confidence`）入库**只作校准用，不是给人看的**。
- ⇒ 即车主的**既定决定**与「UI 只显示 HE380」一致，本轮需求只是给这个字段**安排位置**，不是新增数据需求。
- ⚠️ 但措辞仍不一致：车主心里可能想的是「这辆车是什么型号」。**若他真想要型号名，本规格不覆盖**（型号名更长、置信度有 high/medium/low、且 120 台 `HE81-200` 刻意留空）—— 需另立规格。**建议 PM 在交付时用一句「这行显示的是车队编号 HE380」确认口径**，避免验收时出现"这不是车型"的失望。这是**需求侧风险，不阻塞实现**。

⇒ 结论：**可见文字只显 `HE380`**（车主原话），**不写「车型」「编号」等前缀字**（见 §2.5.5 宽度账）。

#### 2.5.2 位置与顺序：`[线路 chip] [车牌] [HE380] [末班]`

顺序理由（不是随手排的）：
1. 车牌与车队编号**同指一台车**，是「身份数据」，应相邻；`末班` 是「状态」，应处最外。
2. 车主原话「车牌那一行**居右**」⇒ 编号在车牌右侧。
3. **不做 `space-between` 把它推到行尾**：一旦推远，编号与它所注解的车牌失去视觉邻近（Gestalt 接近律），会读成"另一个独立信息"。保持**同一 flex 组 + 8px 网关**（`.nav-vehicle-card__title` 已有 `gap: 8px`，`globals.css:5130-5133`，**无需改**）。

#### 2.5.3 视觉降权：四个独立通道同时降，不靠字号硬压

车主的要求其实是「主次一眼可分」。层级**不能只靠字号**（只靠字号会导致"想更弱就再缩小"的死循环，最终不可读）。这里四个通道同时工作：

| 通道 | 车牌 | 车队编号 | 效果 |
|---|---|---|---|
| 底色 | 实心黑 `#0C0F14` | **透明** | 最强的分离信号：一块有实体、一枚只是线框 |
| 文字色 | 黄 `#FFD400`（13.41:1） | `--muted` 灰（浅 6.0:1 / 深 9.79:1） | 饱和 vs 中性 |
| 字重 | 700 | **500** | 笔画厚度 |
| 字号 | 15px | 11px | 最后一档辅助 |

⇒ 即便把编号提到 13px，车牌依然压倒性主导（实心黑块 + 饱和黄）；11px 的选择与"层级"无关，纯粹是**宽度预算**决定的（见下）。

#### 2.5.4 字号定 11px（`--text-2xs`）—— 由最坏情况实测决定

**可用宽度先修正**：卡片是 `left/right: 8px` + `padding: 10px 12px` + 1px 边框 ⇒ 375px 屏下标题行 `head` 宽 **333px**；减去关闭按钮 28px 与 `gap: 8px` ⇒ **标题行真实可用 297px**（team-lead 估的 307px 略高，此处以实测为准）。320px 屏 ⇒ **242px**。

四件套全长 = `线路 chip + 8 + 车牌 71.5 + 8 + 编号 + 8 + 末班 34`。线路 chip 实测：`25X` 36.8 / `MT4` 40.1 / `氹仔线` 52 / **`石排湾线` 64**（轻轨真实线路，4 汉字）。

| 视口 | 线路 | 编号 11px 全长 | 余量 | 编号 13px 全长 | 余量 |
|---|---|---|---|---|---|
| 375px (avail 297) | 石排湾线 | 236.8 | +60.2 | 244.5 | +52.5 |
| 360px (avail 282) | 石排湾线 | 236.8 | +45.2 | 244.5 | +37.5 |
| **320px (avail 242)** | **石排湾线** | **237.0** | **+5.0** ✅ **单行** | 244.5 | **−2.5** ❌ **溢出 → 被迫折成两行**（实测 `titleH` 22.6 → **45.6px**） |

**实测复核（headless Chrome，真实 `globals.css`）**：

| 组合（320px） | 11px | 13px |
|---|---|---|
| 「石排湾线」+ 末班 | `need=237 ≤ 242`，`titleH=22.6`（**单行**） | `need=245 > 242` ⇒ `titleH=45.6`（**两行**） |

⇒ **定 11px**。三条理由：
1. **最坏真实组合下仍是单行**：iPhone SE(320) + 轻轨「石排湾线」+ 末班，11px 恰好通过（余 5px），13px 会把标题行顶成两行、卡片高度 +23px。
2. **不发明第三层字号**：11px(`--text-2xs`) 在本系统就是「徽标/元信息」层 —— `末班` 是 11px（`globals.css:5162`）、来源标签 `.nav-actions__src` 是 11px。给编号用 13px 会让它比 `末班` 更大，同一行出现「编号 > 状态」的怪阶梯。
3. **可读性达标**：`--muted` 11px 在浅色卡 6.0:1、深色卡 9.79:1（11px 正文需 4.5:1，均通过）。大写等宽字母数字在 11px 下辨识度高于同字号中文。

**升级条件（写清，避免以后反复争）**：若真机验收判定 11px 读不清，升到 13px（`--text-vcode: var(--text-xs)`，一行改动），**代价是接受 320px 下折行**。二者不可兼得 —— 除非把 `末班` 移出标题行（那是另一个交互决策，不在本规格）。

#### 2.5.5.1 编号长度不固定（4–5 字符）—— **最终决定：不定宽，随内容收缩**

> **本节结论改过一次，这里是终版。** 详见文末「决策变更记录」—— 我们先后拿到两版错误的分布数据，最终以 `67/532` 重算后**推翻了「加 `min-width` 定宽」的方案**。

**数据快照**（**2026-10-30，532 台样本**；来源 `mvp-dev-expert-team-backend-2` 全量实测）：

| 长度 | 台数 | 占比 | 构成 |
|---|---|---|---|
| **5 字符** | **465** | **约 87%** | `HE380` / `E1154` 这类 |
| **4 字符** | **67** | **约 1/8（12%~13%）** | `HE05` 等 49 台 + 纯数字 11 台（`2107`/`6009`）+ `ZE` 3 + `YE` 2 + `HL` 2 |
| 6 字符及以上 | **0** | — | 不存在（**这是约束，不是快照**，见下） |

> ⚠️ **比例是快照，不是常量。** 表是采集驱动的（当天已从 526 涨到 532 台），百分比会漂。
> 故此处一律写「**约**」+ **日期** + **样本量**，绝不写成固定值 —— 否则过几天没人能复现，后人会以为是错的。
> 复现方法（任何人可重跑）：
> ```sql
> SELECT length(bus_code) AS len, count(*)::int AS n
>   FROM vehicle_plates WHERE bus_code IS NOT NULL
>   GROUP BY 1 ORDER BY 1;
> -- 2026-10-30：长度4 = 67 · 长度5 = 465（总 532）
> ```

⇒ 编号是 **4–5 字符**，最长 5。（4 字符里最大的一类是 **`HE01`–`HE12` 这类小号段，49 台** —— 容易漏，我第一版按抽样归类就是漏了这批，把占比算成 3.4%，差 3.7 倍。）

**「约束」与「快照」要分清**（`backend-2` 提出，已确认为准则）：

| 类型 | 例子 | 能否当常量引用 |
|---|---|---|
| **约束**（写入侧保证，不随行数变） | `plate` 恒 6 字符（`normalizePlate` 强制）；编号最长 5 字符 | ✅ 可直接引用，**不需标日期** |
| **快照**（统计结果，随采集漂移） | 4 字符编号占 ~1/8；某线路覆盖率 | ✅ 必须标**日期 + 样本量 + 「约」** |

⇒ 本文档中 `plate` 的 `6ch` 假设属**约束**（见 §2.3/§2.4），可放心引用；编号长度分布属**快照**，故上面标了日期。

**宽度实测**（11px 等宽，无定宽）：

| 内容 | 盒宽 | 文字宽 | 单侧内边距 |
|---|---|---|---|
| 5 字符 `HE380` | **43.34px** | 31.34px | 6.00px |
| 4 字符 `HE05` | **37.08px** | 25.08px | 6.00px |
| 极差 | **6.26px** | — | — |

**我曾提出加 `min-width: calc(5ch + 12px)` 把它定宽，现已撤回。** 四条理由，**第 1 条最硬**（内部一致性，不依赖对用户感知的判断）：

**先分清两种位移** —— 它们量级差 8 倍、机制完全不同，混为一谈会得出错误结论：

| | A 型位移 | B 型位移 |
|---|---|---|
| 触发 | 4 字符 ↔ 5 字符 | 编号「有 ↔ 无」 |
| 何时发生 | **只在换车时**（一辆车的编号固定，不会变长度） | **同一辆车、相邻两帧**（瞬时缺失后恢复） |
| 卡片其余内容 | 全部同 commit 替换 | **不变**（车牌/状态/当前站可能完全一样） |
| 位移量 | **6.26px** | **51.34px**（角标 43.34 + gap 8） |
| `min-width` 能否治 | ✅ 能 | ❌ **不能**（`display:none` 的元素无盒子，`min-width` 不生效） |

**下面 4 条理由针对的是 A 型（`min-width` 要解决的问题）**；B 型另见 §2.5.5.2。

1. ★ **自相矛盾：已接受 B 型的 51.34px，却在为 A 型的 6.26px 付代价。**
   ⇒ 若 51px 的跳动能被接受（§2.5.5.2 已明确接受），那么 51.34 / 6.26 = **8.2 倍**小的 6.26px 更能接受。再为它付 43% 内边距代价**逻辑上不自洽**。
   这条优于"用户感知不到"，因为它不依赖我的感知判断，而是**决策与决策之间的冲突**，可被他人独立复核。
   ⚠️ 措辞更正：这两种位移**不是"同类"** —— A 型可被 `min-width` 治、B 型不能。此处论证成立靠的是**量级对比**（大的都接受了，小的更该接受），不是机制相同。
2. **A 型位移确实不可感知。** 编号与车牌 1:1 绑定，一辆车的编号固定 ⇒ **A 型（长度变化）只可能在换车时发生**。
   **已核实 DOM 层事实**（team-lead）：`NavShell.tsx:1154` 挂载 `<VehicleCard>` 时**没有传 `key`** ⇒ 换车是**同组件原地更新、DOM 复用**，不存在"旧卡片→新卡片"的过渡。整卡同一 commit 刷新，`末班` 横移 6.26px **没有可参照的静止元素**。
   ⚠️ **本条只覆盖 A 型。B 型（51.34px）是"卡片其余内容不变、仅角标消失"，reference 完整，位移恰恰可感知** —— 不要用本条去论证 B 型（`backend-2` 实测反例见 §2.5.5.2）。

   > 📌 **这条的来历与教训（重要，勿删）**：本条即我**最初版本的理由①**，当时的措辞是**全称否定**——
   > 「**抖动场景根本不成立**：看到不同编号必然是因为换了一辆车」。
   > 它只枚举了「编号 A → 编号 B」（换车），**漏了「编号 A → 无编号」（瞬时缺失，B 型）**。
   > `backend-2` 用 3 例实测击倒它 —— **一条存在性反例就足以推翻全称否定**。
   > ⇒ 真实教训**不是「措辞要小心」**（表述层），而是「**下全称否定前没穷举分支**」（推理层）。
   > 两者防法不同：前者靠改字句，后者靠**先列出所有子情况再逐个否掉**。详见附录 A2 形态 6。
3. **代价比我原先说的大 3.7 倍，且视觉代价不是"略松"。** 若定宽，4 字符单侧内边距 6px → **8.58px（+43%）**。这不是"稍微宽松"，而是**同一组件出现两种视觉密度**：4 字符角标明显更空，5 字符更紧。而这批车**约占 1/8**（约数，见上），不是边缘情况 —— 用户会在同一条线上频繁遇到两种长相。
4. **与系统既有惯例冲突。** 同行的 `末班` chip 是内容宽（`padding: 1px 6px`，`globals.css:5156-5164`），其它元信息 chip 也是内容宽。给车队编号定宽会让它成为这一排里**唯一的定宽元素**，需要额外理由 —— 而它没有。

**关于"不跳动"的正确判断**：真正需要防抖的是**车牌**（恒 6 字符，靠等宽字体保证，见 §2.3）；编号是可变长元数据，**内容宽才是语义正确的呈现**（多一位就该宽一点）。

**若真机验收后车主认为 4 字符角标"看着不一致"**，可逆的一行改动是：`min-width: calc(5ch + 12px)`。但**默认不做**，理由如上；且一旦加上，就要接受**约 1/8 的车**角标变空 43%。

- **320px 预算**：最坏值仍是 5 字符的 43.34px（237 ≤ 242 单行，已验）。4 字符更窄，**不定宽只会更安全**。
- ⚠️ 与车牌的 `min-width: 6ch` 是两件事：车牌那个是 **no-op**（字距使文字已超 6ch），靠等宽字体本身保证；编号这里**不需要**定宽，理由如上。

**纯数字编号不做任何特殊处理**（11 台 `2107`/`6009`/`6015` 等）：等宽字体下数字与字母 advance 相同，居中后左右对称，**不需另设样式**。数据侧已确认**不是脏数据**（源表 4080 行历史零纯数字，是 DSAT 现采现状；澳巴确有纯数字旧编号，如三菱 Rosa 那批）。UI 只负责原样显示。

#### 2.5.5.2 编号缺失：约 0.4%，且**单帧瞬时**（B 型位移的代价核算）

**数据快照**（**2026-10-30，743 车次 / 两轮全量扫描，117 个「线路×方向」帧**；`backend-2` 实测）：

| 轮次 | 车次 | 缺编号 | 该轮缺失率 |
|---|---|---|---|
| 第 1 轮 | 370 | **3** | 0.81% |
| 第 2 轮 | 373 | **0** | 0.00% |
| **合计** | **743** | **3** | **约 0.4%** |

**三例缺失明细 —— 全部是瞬时、下一轮即恢复**：

| 线路/方向 | 车牌 | 第 1 轮 | 第 2 轮 |
|---|---|---|---|
| 30/0 | `AA5837` | 缺 | **有** |
| 32/0 | `MZ7305` | 缺 | **有** |
| 51A/0 | `AA7248` | 缺 | **有** |

> ⚠️ **两轮差异大（0.81% → 0%）说明这是突发型、非稳态**，不宜当常量。引用请带分母与日期：**约 0.4%（2026-10-30，743 车次）**。
> 注意与早前口径的差别：先前报 **99.7%**（362 台）是同一现象在更小样本上的值；样本涨到 743 后为 **99.6%**。**两个数都对，只是分母不同** —— 这正是「比例必须带分母」的原因。

**机制**：位置接口与报站接口**独立并行**。某台车恰在「位置已上报、报站尚未挂上」的一瞬 ⇒ 有坐标没编号；**下一帧（12s）通常补齐**。

##### B 型位移：真实存在，且**可感知**

同一辆车、相邻两帧，卡片其余内容（车牌/状态/当前站）可能**完全不变**，只有角标消失 ⇒ `末班` 左移 **51.34px**，且 reference 完整、**位移可感知**。
（这是 `backend-2` 提出的反例，成立。§2.5.5.1 理由 2 的"不可感知"只对 A 型 6.26px 有效，**不可外推到 B 型**。）

**`min-width` 治不了它**：`display:none` 的元素没有盒子，`min-width` 无从生效。所以这与撤回 `min-width` **无关** —— 它从来不是 B 型的解。

##### 在「不留位 / 留位」之间的取舍（结论：不留位）

| 方案 | 代价 | 频率 | 总量 |
|---|---|---|---|
| **不留位**（采用） | 缺失那帧，`末班` 跳 **51.34px** | **约 0.4%**，且下一帧即恢复 | 0.4% × 单帧 |
| 留位（占位空框） | 常态下多一块**永久空白** | **约 99.6%** | 99.6% × 全程 |

⇒ **理由不是"抖动不可感知"**（B 型恰恰可感知），而是：
> **瞬时缺失频率极低（约 0.4%，单帧即恢复），接受其瞬跳代价，换取 99.6% 常态下无多余空白。**

这才是可以写进规格、且将来被真机撞见那 51px 跳动时**不会自相矛盾**的表述。

##### 三条实现结论

1. **缺失 ⇒ 整枚不渲染**（`{vehicle.busCode ? … : null}` + `.vcode:empty{display:none}`），不留占位。理由见上表。
2. **角标可能"晚一帧出现"**：首次渲染可能无编号，12s 后补上。**不加动效/占位/骨架/淡入** —— 静态徽标静默出现即可（§3.2 已禁动效，正好覆盖）。
3. **判断用真值检查，不要 `!== null`**：键缺失时 `'busCode' in v === false`、`v.busCode === undefined`（**不是 `null`**）。故 `{vehicle.busCode ? … : null}` 正确；`vehicle.busCode !== null` 会把 `undefined` 误判为「有值」。

#### 2.5.6 无障碍

- **可见文字只有 `HE380`**（车主原话），但单纯 `HE380` 对读屏/新用户是无语义的字母串 ⇒ 语义放在**容器**上，不靠额外可见字：
  - 角标自身加 `title="车队编号"`（桌面端悬浮提示）；
  - **必须同步改车辆卡根节点的 aria-label**（`VehicleCard.tsx:122`）：
    `aria-label={`车辆 ${vehicle.plate}${vehicle.busCode ? `，车队编号 ${vehicle.busCode}` : ""}`}`
- 不加 `role`：它是纯文本标签，不需要控件语义。
- 对比度：文字 6.0:1 / 9.79:1 均 ≥ 4.5:1（11px 属正文，非大字豁免）。边框 1.63:1 / 2.53:1 —— **它不是控件、也不是唯一识别手段**（文字才是），故不受 WCAG 1.4.11 的 3:1 约束；深色取 2.53:1 是为了满足"深色卡面上看得见"的视觉要求。

#### 2.5.7 换行安全阀（防未来，不是防现在）

`11px` 在最坏真实组合下只余 5px。为防将来出现更长线路名（如 5 汉字新线）或更长编号，标题行加折行阀：

```css
.nav-vehicle-card__title {
  flex-wrap: wrap;                 /* ★ 安全阀：宁可折行，绝不横向溢出 */
  row-gap: var(--space-1);         /* 4px */
}
```
- 实测：加阀后 320px + 13px 的溢出组合**折成两行、零横向溢出**（`titleH 45.6`），而不是把关闭按钮挤出视口。
- 375px 下**不触发**（余量 60px），零视觉变化。

#### 2.5.8 一处真实风险：末班 11px 与编号 11px 同级

两者同为 11px 且相邻 ⇒ 可能被读成"一对并列小标签"。当前靠「`末班` 是软黄底 + 中文 / 编号是线框 + 等宽」区分。若真机验收觉得二者过于相似，**不要在本次给编号加底色**（那会抢车牌），而应**把 `末班` 的字重提到 600** 或前移位置 —— 记入 advisory，不阻塞。

### 3.3 别名 token：可用，但本组件不用（附一次自我更正）

**结论**：`.vcode` 直接 `color: var(--muted)`，不设 `--vcode-ink` 别名。理由是**少一层间接**，且为将来留余地（见下）。**这不是"否则会冻结"。**

> ⚠️ 本节上一版曾断言「`--x: var(--y)` 一律冻结」，并建议排查项目 token。**该结论已被实测推翻，勿据此改动任何既有 token。**

**实测（真实 `globals.css`，light/dark 各跑一遍）**：

| 结构 | 深色下别名值 | 结果 |
|---|---|---|
| **A. 别名与覆写同在 `:root`**（项目现行 `@media` + `:root`） | `--info` = `#a8c7fa` | ✅ **正常跟随** |
| **B. 别名在 `:root`、覆写在后代元素**（我当时的预览台 `.theme--dark`） | `--vcode-ink` = `#5a6472` | ❌ 才冻结 |

项目现行的 8 个别名（`--info` / `--card` / `--text` / `--track-*` 等）**均正常跟随** —— 因为覆写点与声明点同为 `:root`。**我看到的"冻结"是预览台结构造成的假象。**

**判据**：别名安全 ⇔ **覆写点与声明点在同一元素**。项目用 `@media (prefers-color-scheme: dark) { :root { … } }` ⇒ 满足。

**面向将来的推论**（team-lead 补）：若引入「后代元素换肤」（`<div class="theme-dark">`），**所有依赖主题的别名会集体失效**。两条出路：① 别名改直接引用；② 换肤也做在 `:root`（`html[data-theme="dark"]`）。
⇒ 所以直接引用不仅少一层间接，**还为后代换肤留了余地** —— 这是它的实质优势。

**对设计原型的提示**：用 `.theme--dark` 这类后代 class 模拟深色时，不能照抄项目的别名 token，会看到假的"冻结"。

### 4.3 关于「地图 marker 用 sm」—— 明确否定

team-lead 的档位表把「地图 marker」列为 sm 用途。**不可行，且不应做**：

- 车标是 `32×32` 的 SVG（`VehicleMarker.tsx:151` `viewBox="0 0 32 32"`）。sm 标签实测宽 60px（iOS ≈62px），是图标的近 2 倍宽，塞进去必然要么压扁字形、要么把 marker 做成一个横向胶囊 —— 后者会破坏「车头朝上」的方向语义与聚合布局。
- marker 已有数量角标（`VehicleMarker.tsx:186`）承担「这里几辆车」；牌号属于**点击后的详情**，不属于地图视觉层。
- 若将来一定要「地图上直接看牌号」：技术上需要放大 marker 命中盒 + 引入 marker 放大态（点击后浮出 sm 标签），这是**另一条交互规格**，不在本次范围。

### 4.4 关于「合并显示 N 辆车」里出现车牌

- **只有计数**（「共 3 辆」/ 角标 `3`）⇒ **不用**标签（R4）。

- 目前代码里没有这种并列场景（`merge-cards.ts` 不涉及 plate），此条为**前瞻规则**。

## 附录 A2 · 决策变更记录（编号宽度，共改两次判断）

> 留档原因：这条决策在一天内被推翻两次，且两次都是**数据错误**导致。写清过程，避免后来者复用已作废的依据。

| 阶段 | 依据 | 结论 | 作废原因 |
|---|---|---|---|
| 初版 | 以为编号恒 5 字符 | 不设定位，内容宽 | — |
| 第二轮 | 后端报「4–6 位」；我抽样 `2107`/`ZE01`/`HL12` 归出 4 字符 18 台（3.4%） | **加** `min-width: calc(5ch + 12px)` 防「末班」抖动 | ① 抽样漏掉 `HE01`–`HE12`（49 台）；② 后端首版分布 78/448 本身写错 |
| 第三轮（终版） | 后端复测 **67/532 ≈ 12.6%（2026-10-30，532 台）**（`HE` 49 + 纯数字 11 + `ZE` 3 + `YE` 2 + `HL` 2） | **撤回** min-width，改回内容宽 | — |

**促使撤回的三条实质理由**（不是"数字变小了所以算了"）：
1. **抖动场景不成立**：编号与车牌 1:1，看到不同编号必因换车；而换车时整卡内容全替换，`末班` 横移 6.26px 无参照物，不可感知。
2. **定宽的视觉代价不是"略松"**：4 字符单侧内边距 6px → 8.58px（**+43%**），同一组件出现两种密度，且这批车约占 1/8，不罕见。
3. **与系统惯例冲突**：同行 `末班` chip 与其它元信息 chip 都是内容宽，定宽会让编号成为唯一特例。

**方法论教训**：
- 我犯的错是**用抽样当全量**（18 台来自"我见过的样例"，不是查询结果）。
- 后端犯的错是**转述数字而非贴脚本输出**（78/448 应为 66/460）。
- ⇒ 约定：**凡涉及分布/比例，一律贴原始查询输出**；引用他人数据时标明「抽样/全量」。此条已写入 §2.5.5.1 正文。

**第 6、7 条要单列，因为它们与 1–5 的防法不同**：

- 1–5 是**取样偏差** —— 防线是「多测 / 回指原始证据 / 带分母」，靠**更严格的取证**能防。
- 6 是**枚举偏差** —— 再多次实测也防不住，只能靠「**下全称否定前，先列出所有分支并逐个否掉**」。
- 7 是**传播偏差** —— 与推理无关，是**工程纪律**问题：结论一旦写出去，副本就不受你控制。
  ⇒ 防线：**撤回一个结论时，先列出它已经扩散到的所有位置**（文档正文 / 附录 / 代码注释 / 设计稿 / 口头转述 / 别人的笔记），逐一清理；否则「错的版本」会比「对的版本」活得更久 —— 因为它进入了必经路径（代码文件），而更正只停在对话里。
- 8 是**时序偏差** —— 与推理无关，与取证也无关，是**状态验证**问题：读到的内容在"读"与"用"之间可能已变。
  ⇒ 防线：**任何"某处有问题"的断言，落笔前重跑一次 `grep`/`stat` 确认它现在仍然成立。**

> **8 为什么比"漏报"更危险**：错误方向不对称 ——
> **假阳性**（报了不存在的问题）的默认动作是**动手改**，会主动破坏已经正确的状态；
> **假阴性**（漏报真问题）只是留存，还有下一次机会发现。
>
> **破坏力分级**（`backend-2` 补）：**假阳性的严重等级 = 误告警 × 目标对象的不可逆性**。
> 本迭代误报落在 `globals.css` —— 纯 CSS，改坏了浏览器静默忽略无效声明，不会崩，故损失有限。
> 但同样的误报若指向**数据库迁移**或**已上线 API 契约**，一次基于过时快照的"修复"就是生产事故。
> ⇒ **对不可逆对象，验证门槛必须更高**（不是"改完能回滚"就够，而是"改前必须自证前提"）。

> **8 的根因不是粗心**：`backend-2` 指出 —— 假阳性往往源于**从有效快照推出了已失效的结论**，而非疏忽。
> 本迭代 `globals.css` 在 5 分钟内被改了 3 次（22:25、22:29、22:30），我们两人的读取分散在这三次之间，**各自在读取当刻都判断正确**。
> ⇒ **并发编辑期间，「当前状态」是一个正在移动的对象，快照保质期可能只有约 1 分钟。**
> ⇒ 纪律精化：**讨论阶段用快照可以（成本低、错了再改）；下「应改 X」的结论前必须重跑验证命令。**
> 且命令要同时覆盖两件事 —— **「我发现的旧问题是否还存在」+「我的修复是否已被他人做过」**（判断"缺失"和判断"已被覆盖"需要不同的 grep）。
> ⇒ 更严格的做法：**执行型建议必须附一条可复现的验证命令**，让对方能先自证前提，而不是相信"我看到了"。

> **8 的镜像面：假通过比假警报更隐蔽。**
> 本迭代实例：我一直用「` ``` ` 出现次数为偶数」判断本文件的代码围栏是否配对，每次都"通过"。
> 但该文件有 **17 个代码块**，其中 1 个在引用块内（`> ```sql`，行首不是围栏）。
> **计数法碰巧得到 34（偶数）→ 通过**；而正确方法（剥掉 `>` 前缀后跑状态机）才确认「17 块全闭合、无块内裸围栏」。
> ⇒ **通过的依据错，与报警的依据错同样危险** —— 只是没人会去复查一个"通过"的检查，所以它可能长期静默失效。
> **通用规则：「计数法忽略上下文」——凡"配对/平衡"类检查，用状态机而非计数。**
> 根因：**计数法假设"所有标记同等"，而同一标记在不同上下文里含义不同。** 同类项：
> `/*` 在 CSS 注释内不是注释开始（`*.svg`）· ` ``` ` 在引用块内行首不是围栏（`> ``` `）·
> HTML 的 `<!-- -->` 内 `<div>` 不是标签 · JSON 字符串 `"}"` 里的 `}` 不是括号 · 正则 `/[/]/` 里的 `/` 不是分隔符 · SQL `'--'` 里的 `--` 不是注释。
>
> ⇒ 这同时解释了"假通过"为何难防：**计数法会给出一个看起来合理的数字**（偶数/平衡/差值小），
> 人看到就通过，而不会问"这个数字是怎么数出来的"。
>
> **同一根因的另一个变体：「grep 为空 ≠ 对象不存在」。** 本迭代实测：
> ```
> $ git status --porcelain | grep "车牌"                → 空（exit 1）
> $ git -c core.quotepath=false status --porcelain | grep "车牌" → ?? …/08-设计-车牌标签规格.md（exit 0）
> ```
> ⚠️ **上面输出里的 `08-` 是历史真实值，勿改成 `17-`** —— 该文件其后被重命名，此处记录的是**当时那条命令原样返回的结果**。
> 改它等于篡改证据：后人会以为当时文件就叫 `17-`，从而无法理解「为什么 grep `08-` 会成功」。
> ⇒ **历史记录里的旧名是数据，不是笔误**（同 §2.5.5.1「快照保留原值、新增不覆盖」）。
> 文件一直存在，只是 git 默认把非 ASCII 路径转义成八进制。⇒ **"搜不到"可能是编码/转义/上下文造成的，
> 不能反推"不存在"** —— 与"计数法忽略上下文"是同一条：匹配工具给出的否定结果，同样需要验证方法。
> （出处：`backend-2` 数 `/*` 567 vs `*/` 566 报"未闭合"，实为 `*.svg` 被误判；我数 ` ``` ` 得 34（偶数）通过，实为混了两层上下文。）

**「否定结果」的六项排查清单**（下"不存在/没有/通过"结论前逐项排除，`backend-2` 与 team-lead 各补一层）：

| # | 层 | 本迭代实例 |
|---|---|---|
| 1 | **编码 / 转义** | `git status` 默认把中文路径转义成八进制 ⇒ grep 为空。**本仓库 14 条路径受影响**（`docs/迭代-*`、`docs/改版-*` 全中文）⇒ 应**默认**加 `git -c core.quotepath=false` |
| 2 | **上下文差异** | `/*` 在注释内、` ``` ` 在引用块内、`<div>` 在 `<!-- -->` 内 —— 含义都不同 |
| 3 | **搜索粒度** | 关键词 vs 语义：用「全称否定」搜不到，用「后被实测推翻」就搜到 |
| 4 | **快照过期** | 文件 mtime 比读取时刻更新（本迭代 5 分钟内被改 3 次） |
| 5 | **工具作用域 / 裁剪** | `git status` 不显示已 ignore 的文件（`.next/`、`*.tsbuildinfo`）；`grep -r` 跳过二进制；`find` 默认不跟符号链接；**`cut -c` 按字符截断中文输出会切断多字节字符 ⇒ 路径显示成乱码**（应用 `cut -b` 或干脆不截）⇒ **工具替你决定了看什么，且不告诉你裁掉了什么** |
| 6 | **工具语义（"没有"时会不会说"没有"）** | `grep -c` 匹配 0 行时**退出码是 1** ⇒ 用 `&&` 串联会短路，`$?` 让人误以为 tsc 失败；`dispatchEvent` 绕过命中测试 ⇒ 永远"成功"，无法验证"能不能点到" |

> 第 6 层是本轮最隐蔽的一类：**工具在"没有"的时候，未必会告诉你"没有"** —— 它可能报错、可能静默、可能给出一个看起来正常的值。
> ⇒ 所以「否定结果」的最后一道检查不是"我搜对了吗"，而是"**这个工具在目标缺失时，行为是什么？**"

> 写「这种情况不会发生」时，必须能**枚举完所有子情况**。
> 本迭代的真实教训不是"措辞要小心"（那是表述层），而是"**下全称否定前没穷举分支**"（那是推理层）—— 两者防法完全不同，记错会让人学错。

**共同点**：中间隔着**算术 / 预览台 / 抽样 / 转述 / 单次观测 / 我自己的枚举**，而那一层没被验证。
⇒ **防线**：任何结论都要能回指到**可复现的原始证据**（SQL 输出 / 真机截图 / 项目真实 DOM）。回指不到，就还只是推理。

**关于「用绝对数校验」的修正**（`backend-2` 实证）：
> 三组错数 **66/460、78/448、18/508 的总和全都是 526** —— ⇒ **「求和自洽」一个错都抓不出来**。
> 必须**逐项比同项分子**（66 / 78 / 18 三个值互不相同）才露馅。
> ⇒ 单看一组绝对数也判断不了对错，**要横向对比另一组数据的同项**。只说「带分子分母」还不够。

**为什么这类错误危险**：它**不报错**。测量成功、数值合理、结论自洽，只是对象不是真的。所以"测试通过"发现不了，必须额外问：
> 我测的这个东西，和上线跑的那个东西，是同一个东西吗？我引的这个数，和脚本原样输出，是同一个数吗？

**另一条**：**感官类判断（"看不出来"）必须绑定量级与场景。** 我曾写"末班横移不可感知"，只对 6.26px 成立；51.34px 的同车缺失场景下可感知。一旦被反例击中，**整份规格的可信度会被连带质疑** —— 能换成数字的就换成数字（"13.41:1"不会被推翻，"足够醒目"会）。
