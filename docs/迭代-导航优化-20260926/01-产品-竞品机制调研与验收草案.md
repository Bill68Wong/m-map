## 0. 执行摘要（先看这段）

1. 10 项需求里，**7 项是既有机制的行为偏差/缺失**（抖动、站点混杂、窗格跑位、双标记、车图标不刷新、点击中断、上下车判定），**3 项是新增能力**（换乘用时口径、偏好模型、底图站点隐藏）。
2. **需求 1（抖动/比例尺归位）的业界正解已被谷歌官方文档明确**：导航取景有 **Following / Overview / Free 三态**；用户拖动或缩放即进入 **Free**，**相机保持不动**，只有用户**点「重新居中」**（或有超时的自动回中）才回 **Following**。后台刷新**绝不允许**重置用户的手动缩放/平移。本项目当前是"指令化取景"（拖动不动），但**未隔离后台刷新与相机状态**，这正是抖动根因方向。
3. **需求 7（换乘用时）需要纠正一个认知**：现有 `model.ts` 的 `T_total` **已经包含 `wait_k`**（换乘等车），并非没算。真正的偏差在于 —— 换乘段等车用「**班距 ÷ 2**」估（下限口径），且**不校验"能否赶上"**，加上同场换乘步行记 0 ⇒ 换乘方案被**系统性低估**。修法对齐业界：**按"到达换乘站的时刻"查真实下一班次** + **可行性闸门（赶不上顺延并计入等待）** + **换乘惩罚项**。
4. **需求 10（隐藏高德底图站点）在 v3.0.0 代码里已经接通**（`AMAP_MAP_STYLE_ID` → `page.tsx` → `NavShell` → `NavMap`）。它**不需要开发**，只等**用户在控制台创建"关公交站"自定义样式并回填样式 ID**。详见 §4.10 与 `docs/技术方案-隐藏底图公交站点方案-20260923.md`。
5. ★⚠ **反面清单（严禁采信）**：网上（含 AI 生成内容）流传 `map.setFeatures(['bg','road','point:none','text:none'])` 可隐藏 POI —— 这是**幻觉接口**；高德 JS API 2.0 的 `setFeatures` **只接受** `'bg'|'point'|'road'|'building'`，无 `:none` 后缀、无 `text` 项。`showLabel:false` 会连街道名一起关，**过度**。详见 §4.10。
6. 验收标准草案共 **33 条（AC-25 ~ AC-57）**，全部 EARS 格式、引用/新增观测钩子，可被 QA 机器断言。

## 2. 竞品导航机制调研

> 关注点＝**机制**（何时回中、蓝点怎么走、已走过怎么画、下车怎么提醒、换乘怎么算），不做商业分析。

### 2.1 谷歌地图公交导航（机制维度表）

| 机制 | 谷歌地图的做法 | 对本项目的启示 |
|------|----------------|----------------|
| **① 地图跟随 / 回中** | 官方 Navigation SDK 定义**三种相机模式**：`Following`（默认，相机贴住车辆/用户、朝向行进方向；**此时不显示"重新居中"按钮**）、`Overview`（缩放以容纳整条路线，显示"重新居中"按钮）、`Free`（用户手指平移/缩放即自动进入，**相机就地固定不动**，显示"重新居中"按钮）。**用户移动地图 → 从 Following 切到 Free；只有用户点「重新居中」才回 Following**；也可用定时器实现"Free 停留 N 秒后自动回中"（官方示例给的是 5s）。 | ★ **需求 1 正解**：取景是**显式状态机**，用户手势是唯一"离开跟随"的入口，**后台数据刷新不得改动相机**。本项目应引入等价的 `follow | free` 状态；拖动中与拖动后（未点回中）一律不动比例尺/中心。 |
| **② 蓝点数据与视觉** | 蓝点是设备估位；外圈**浅蓝圆＝精度不确定性半径**（越小越可信）；行进时蓝点变**箭头/方向锥**表示朝向；精度差或丢失时变**灰点/旧位置**。 | 需求 5：本项目**只保留一个蓝点**，加**呼吸**（脉动）动效、去"您"字；可参考"精度圈"表达不确定性（选做）。 |
| **③ 已走过路段** | 主路线＝亮蓝粗线；**已走过部分**在导航中向后"吃掉"，未走部分保持蓝色；备选路线＝灰线。 | 需求 5：本项目口径已是「已驶过＝灰实线」，与谷歌"蓝线向前推进"不同但语义等价、且已获用户拍板（上轮 Spec §2.2）。保持灰实线。 |
| **④ 下车提醒** | 公交导航中开启"Start"后即进入**逐步导航**：顶部条给出**换乘/下车提醒**，并在**接近下车站时推送通知**（可震动），且像驾车一样**沿路线追踪进度**。业界普遍为"**提前一站**提醒 + 到站二次提醒"。 | 需求 3：本项目已有"下一站＝下车站→横幅＋震动（禁声音）"。方向一致；本轮只做**文案简化 + 排版不溢出**，**提前量维持 1 站**（澳门站距短，上轮已排除"提前 2 站"）。 |
| **⑤ 换乘方案总时长口径** | 公交 ETA **包含**：到站步行 + **等下一班** + 乘车 + **换乘步行** + 到目的地步行；会横向比较"多走一点赶更快的车"与"少走但多等"两类方案。**下一段等车按"到达换乘站的时刻能赶上的那一班"计**，而非泛化的"平均班距"。 | 需求 7：对齐"按到达时刻的真实下一班"，本项目当前用"班距÷2"是**近似下限**，需改为**真实班次 + 可行性闸门**。 |
| **⑥ 排序** | 公交默认给"**推荐**"（综合时间/换乘/步行/可靠性），并可切"少换乘/少步行"等偏好；用 RAPTOR 类算法在**多目标（Pareto）**上取候选。 | 需求 8：给用户**三档快捷切换**（综合推荐 / 少换乘 / 少步行），默认综合。 |

来源：Google Navigation SDK（`camera` 页，Android/iOS）、Google 公交导航官方博客（Sucheta Kulkarni）、Google 支持文档。

### 2.2 高德地图 + 百度地图（机制维度表）

| 机制 | 高德地图 | 百度地图 | 对本项目的启示 |
|------|----------|----------|----------------|
| **公交偏好档位** | `RouteSearchV2.BusMode`：`BUS_DEFAULT`（**推荐/综合权重，同高德 App 默认**）、`BUS_LEASE_CHANGE`（**最少换乘**）、`BUS_LEASE_WALK`（**最少步行**）、`BUS_WASTE_LESS`（**时间短**）、`BUS_COMFORTABLE`（最舒适）、`BUS_SAVE_MONEY`（最经济）。老接口 `m` 参数：`0` 最快捷 / `2` 最少换乘 / `3` 最少步行 / `8` 时间短。 | 公交检索 `sy`：`0` 推荐 / `2` 少换乘 / `3` 少步行 / `5` 时间短 / `6` 地铁优先 / `4` 不坐地铁。 | ★ **需求 8 直接对标**：两家都是"**默认综合 + 若干偏好快捷档**"的形态。本项目沿用：**综合（默认）/ 少换乘 / 少步行**三档（澳门无地铁，不设地铁档）。 |
| **推荐默认排序口径** | 综合权重（时间/换乘/步行/等待/可靠性），**非纯时间**。 | 逆向分析（简书）给出**线性加权评分**：`得分 = 时间×w_t + 步行距离×w_d + 换乘次数×w_r + 出行方式×w_m`，**分越低越优**；并叠加"停运方案置底""高峰偏好快速直达""堵车风险前调"等修正。 | 需求 8：默认模型＝**广义成本（generalized cost）最小**：`cost = totalMin + α×换乘次数 + β×步行分钟`，并保留既有"不可用方案置底/剔除"口径。 |
| **可靠性/可靠性因子** | 对新站/低可靠接驳给"风险惩罚"（用户感知：新线短期不易被推荐）。 | "堵车风险前调"。 | ⚠ 本项目数据量小（个人工具），**不引入风险惩罚**（易过拟合）；仅在文档记录"为什么不做"。 |
| **换乘等待估计** | 实时公交到站 + 班次间隔；未接入实时时按**最大间隔**估算。 | 实时到站 + 时刻表。 | 需求 7：本项目巴士用 `route_frequency` 班距、轻轨用 `lrt_timetables` 时刻表（已有），**正是业界做法**，只是"取班"逻辑要从"班距÷2"升级为"按到达时刻的真实下一班"。 |

来源：高德开放平台 `RouteSearchV2.BusMode` 文档 + 移动端路线规划文档；百度开放平台 uri 模板（`sy`）+ 百度用户服务中心说明 + 简书逆向分析。

### 2.3 换乘等待估计与"能否赶上"判定（业界做法）

| 产品/算法 | 做法 | 对本项目的启示 |
|-----------|------|----------------|
| **Citymapper** | 行程时长**实时、每分钟重算**（基于当前城市与网络状态，而非静态时刻表）；出行详情给"**tight transfer**"标签，提示换乘时间紧（按平均步速算，提醒用户按自己步速权衡）。 | ★ **需求 7**：换乘等待应基于**当前实况**（本项目＝车辆通道/时刻表），并对**紧接的换乘**给出"赶得上/偏紧/赶不上"表达（可用颜色/文案，不必弹窗）。 |
| **Transit App** | 实时到站 + 在图上**跟随车辆逼近**；乘车中提示下车。 | 与既有 AC 一致，无新增。 |
| **日本 乘换案内** | 按**时刻表逐班匹配**（発車/着時刻 + 乗換時間），"**間に合う/間に合わない**"是核心语义；检索条件含"乗換回数/料金/時間"。 | ★ **需求 7 的正解范式**：换乘以"**能否接上指定班次**"为核心；本项目应把"到换乘站时刻 vs 下一班发车时刻 + 换乘步行"做成**显式可行性判定**。 |
| **OpenTripPlanner（OTP，业界开源标准）** | ① **transfer optimization**：优先"**稳妥/保底换乘**（guaranteed/stay-seated）"，**避免过短换乘**，并**最大化可用等待**；② `walk reluctance` 默认 **2.0**（同样时间，步行"痛苦度"＝乘车的 2 倍）；③ `minSafeWaitTimeFactor` 默认 **5.0**（等待逼近 0 时给**对数型惩罚**，防"极限换乘"）；④ 支持 `unpreferred` 线路/公司惩罚。 | ★★ **需求 7/8 的工程范式**：可行性闸门 + 最短安全换乘时间（min-safe-transfer）+ 步行权重。本项目可设一个**最小换乘/安全余量**参数（如 ≥2~3 分钟），低于则视为"赶不上"顺延。 |

来源：Citymapper 官网/官方 News；OTP RouteRequest 文档（transferOptimization / walk.reluctance / minSafeWaitTimeFactor）；GTFS/RAPTOR 综述（Google 公交用 RAPTOR）。

## 3. 偏好模型调研（需求 8 专用）

### 3.1 主流产品如何让用户表达偏好

| 产品 | 表达方式 | 档位 |
|------|----------|------|
| 高德地图 | 结果页顶部**快捷标签组**（无需进设置） | 综合（默认）/ 少换乘 / 少步行 / 时间短 / 不坐地铁… |
| 百度地图 | 结果页顶部**筛选标签**（Web 4 档 / App 6 档） | 推荐（默认）/ 时间短 / 少换乘 / 少步行 / 地铁优先 / 不坐地铁 |
| 谷歌地图 | 默认"推荐"，偏好多内化进算法，少量可在设置调整 | 推荐为主 |
| Citymapper | 以"具体行程候选"表达（next hour 多趟对比 + tight transfer 标签） | 不强调全局偏好档 |

★ 结论：**澳门场景（无地铁）取"综合 / 少换乘 / 少步行"三档快捷标签**最贴合。默认档＝综合，符合两家主流默认。

### 3.2 换乘惩罚 / 步行惩罚的行业数值（供参数定稿参考）

| 研究 | 场景 | 换乘惩罚（换算为"等效车内分钟"） | 步行/等待惩罚 |
|------|------|-----------------------------------|----------------|
| Garcia-Martinez et al., 2018（马德里） | 多模式网络 | **纯换乘惩罚 ≈ 15.2 ~ 17.7 分钟** | 另有步行/等待/拥挤/习惯项 |
| Han, 1987（台北） | 巴士-巴士 | 一次换乘 ≈ **30 分钟车内时间** 或 **10 分钟等车**（≈4.5 NTD） | — |
| National Transport Authority, 2024（爱尔兰） | 巴士-巴士 | **12.73 ~ 24.32 分钟**（常客 12.73~15.79；偶乘 14.87~24.32） | 步行项 ≈ €1.96 |
| 西安（Atlantis Press） | 巴士网络 | 换乘惩罚 **9.93 ~ 12.13 分钟** | 步行时间惩罚 1.09~1.43；等待时间惩罚 1.04~1.34（每分钟的相对权重） |
| OTP 默认 | 通用 | — | `walk.reluctance = 2.0`（步行 1 分钟的"痛苦"≈乘车 1 分钟的 2 倍）；`minSafeWaitTimeFactor = 5.0`（对超短换乘给二次惩罚） |

★ **建议区间（待用户拍板）**：
- **换乘惩罚 α**：文献区间大（10~32 分钟）。考虑**澳门站距短、整体行程短**，取**偏保守中值 ≈ 8 ~ 12 分钟/次**（低于欧美长距离网络的 15+，避免把小城市的短换乘方案"误杀"）。
- **步行惩罚 β**：以"步行分钟 × 系数"并入，参考 OTP `reluctance=2.0`，可设 **步行 1 分钟 ≈ 综合成本 1.5 ~ 2.0 分钟**。
- **安全余量（min-safe-transfer）**：≥ **2 ~ 3 分钟**（低于视为"赶不上"，顺延到下一班并计入等待）。
- ⚠ 以上均为**待定参数**，Phase 2 由架构师结合本项目实测（`walk_times`/`route_frequency`/`lrt_timetables`）标定；Phase 1 只给区间与依据。

### 3.3 推荐默认模型（形态，非最终数值）

```
综合成本 cost(方案) =
    totalMin                      // 已含 walkOut + Σ wait_k + ride_k + transfer_k + walkIn
  + α × 换乘次数                  // α ∈ [8,12] 分钟/次（待定）
  + (β − 1) × 步行分钟            // β ∈ [1.5,2.0]；仅把"步行的额外痛苦"加进成本
  // 约束：换乘可行性（到站时刻 + 安全余量 ≤ 下一班发车）不满足则该换乘不可用（顺延或剔除）
```

- **综合（默认）**：按 `cost` 升序。
- **少换乘**：按 `换乘次数` 升序为主判据（tie-break：`cost`）——对齐高德 `BUS_LEASE_CHANGE` / 百度"少换乘"。
- **少步行**：按 `步行分钟/距离` 升序为主判据（tie-break：`cost`）——对齐 `BUS_LEASE_WALK` / "少步行"。

## 4. 10 项需求 → 现状代码事实 → 竞品机制 → 修改方向 映射

> 每项给出：**用户原话要点 / 现状（读码事实）/ 业界参照 / 修改方向（what，不下技术方案）**。

### 4.1 需求 1：导航弹窗时地图抖动 + 后台刷新致比例尺归位

- **现状（读码）**：`NavMap.tsx` 有 `mapStyleId`、取景段、`data-map-mask` 等；上轮 Spec §2.2-⑥ 已定"拖动中绝不动；落定后仅被遮挡时微调"。但用户观察到**弹窗（面板）操作时地图抖动**、**后台刷新（12s 轮询等）导致刚放大的比例尺被"归位"**。
- **业界参照（M1/M2）**：谷歌 **Free 模式相机就地固定**，后台刷新**不改相机**；回中只能由用户点按钮（或超时）触发。
- **修改方向**：
  1. 引入显式取景状态 `follow | free`；**用户任何手势（pan/zoom）→ free**，此后**所有后台刷新一律不得改动 zoom/center**（含"仅被遮挡时微调"也须在新 state 下重新裁决）。
  2. 提供**「重新居中」**入口（free 态可见），点击 → `follow`。
  3. 抖动治理：面板拖动/开合期间，地图容器与取景更新**解耦**（不在拖动帧内触发相机 effect）；与上轮 v2.15"拖动抖动修复"（`useSnapSheet` 命令式）方向一致，本轮补**相机侧**。

### 4.2 需求 2：路线查看 + 导航中，地图只显示选中线路的站点

- **现状（读码）**：`NavMap.tsx` 有站点图层（`AMap.Marker`，约 line 740）与 `data-overview-legs`；`lib/nav/map-stations.ts` 负责站码映射。当前地图按已有逻辑展示站点，**未按"选中线路/在乘线路"过滤**。
- **业界参照**：导航态"只显示相关要素"是通用原则（谷歌导航态弱化无关 POI/线路）。
- **修改方向**：
  1. **路线查看模式**：地图**仅渲染被选中线路的站点**，其余隐藏。
  2. **导航模式**：**仅渲染当前方案所属线路的站点**（因换乘可能不止一条线 → 渲染**方案涉及的全部线路站点**；含换乘站点）。
  3. 保留"我们自己的站点图层"语义（与需求 10 的底图 POI 相互独立）。

### 4.3 需求 3：导航界面优化（窗格跑位 / 灰框 / 标签归位 / 去"估算" / 车辆信息去重 / 提醒文案）

- **现状（读码）**：
  - "准备出发/车辆信息"窗格＝`NavDetailBody` 头部 + `NavTrackBar`（`data-nav-phase`）等；布局随内容/阶段变化 → 用户感知"乱跑位、遮挡"。
  - 顶部时间区有"灰框紧框"（视觉问题）。
  - 线路标签总览位置待调整（用户要求：**总用时左上，线路标签总览右上同一行**）。
  - "估算"标签需去除（★ 注意：上轮 Spec AC-21/23 已把"估算"列**禁用词**；本轮需核查是否仍有残留入口）。
  - 车辆信息**重复显示"下一站"**（纵轴已明确下一站）→ 去重。
  - 下车提醒文案过长溢出横幅（`AlightBanner.tsx`：现文案「下一站就是下车站：{dest} · 准备下车」+ 右侧还渲染了"横幅 + 震动"提示 `<span class="nav-alarm__hint">横幅 + 震动</span>` —— **该 hint 是开发占位文案，正是"过长/多余"的可疑来源**）。
- **修改方向**：
  1. 窗格定位**稳定化**（不因阶段切换/内容多少而位移或遮挡）；相关块**固定占位/固定锚点**。
  2. 顶部时间区**去灰框**；**总用时左上 + 线路标签总览右上（同一行）**。
  3. **去掉"估算"标签**（全链路扫描）。
  4. **车辆信息不再重复"下一站"**（纵轴已表达）。
  5. **简化下车提醒文案**；**站号 + 站名保持原样**（繁简/格式不变），并**确保单行不溢出**（呼应上轮"单行完整显示"口径）。

### 4.4 需求 4：线路标签统一圆角

- **现状（读码）**：线路标签散布多处（`RoutePieces.tsx`、`RecommendCard.tsx`、`StationReachFold.tsx`、`RouteStack.tsx`、`RoutePlanList.tsx` 等），样式未统一（部分无圆角）。
- **业界参照**：谷歌公交"彩色线路徽章与运营方官方色一致"；统一圆角徽章是通行做法。
- **修改方向**：**统一为圆角线路主题色标签**（或"带白色斜间隙的线路主题色标签"，二选一待拍板）；**颜色取 `routes.color`（数据，禁硬编码）**；across 全部使用点一致。

### 4.5 需求 5：用户位置标点（蓝点合并 + 呼吸 + 随程移动 + 已走过变灰 + 纵轴去"您在这里"）

- **现状（读码 + 总监摸底，对齐）**：地图上实际有**三个"人味"标记**：① `nav-map__mepin`（**蓝色圆、单次定位、不动**）；② `nav-map__originpin`（出发地钉）；③ `UserDotLayer` 蓝点（**实时更新、DOM 含 `user-dot__label` 文案"您"**、带呼吸感、z128；**riding 且锁车牌时被隐藏** —— `NavShell.tsx` L329-331）。
  - 用户看到的"两个用户点"＝ **① `mepin`（蓝色圆）** 与 **③ `UserDotLayer`（呼吸"您"）** ⇒ 需**合并为一个**：保留**蓝点视觉**、加**呼吸**、**去掉"您"字**，并使其**随用户移动**（当前 `mepin` 不动、`UserDotLayer` 在 riding 锁牌时还会消失，这是"乘车中不跟随"的直接原因）。
  - `TrackLayer` 负责"已驶过＝灰实线"。
  - 纵轴 `NavStrip.tsx` 渲染文字 **"您在这里"**（`NavStrip.tsx:115`）与"骑线节点"（`anchorIdx`：atIdx→passedIdx→首站前）；当前"停靠中"用户点会落在两个空心站点之间。
- **业界参照（M3/M4）**：单一蓝点 + 呼吸/精度圈；行进中蓝点随位置；已走过向后"吃掉"。谷歌蓝点在**乘车中沿路线推进**。
- **修改方向**：
  1. 地图**只保留一个用户标点**（蓝点），**加呼吸闪烁动效**，**去掉"您"字**。
  2. 蓝点**随用户移动而移动**；**乘车过程中沿线路轨迹移动**（即"用户经过的地方变灰"），与 `TrackLayer` 灰实线**同步推进**（像谷歌导航）。
  3. 纵轴**不再显示"您在这里"文字**；**只用一个"用户位置圆点"在轴上移动**：**进站时把空心节点变为用户点**；**行驶中把用户点放在两个空心节点之间**（与现状"行驶中在两空心站之间"一致）。

### 4.6 需求 6：导航中只显示当前乘坐车辆；车图标不刷新；点击巴士/站点图标不中断导航

- **现状（读码）**：`VehicleLayer.tsx` / `useRouteVehicles.ts` 管车辆图层（z130）；`StationCard.tsx` / `VehicleCard.tsx` 为站点/车辆信息卡。用户观察：① 导航中**多辆车图标**（应只留"当前乘坐的那班"）；② **巴士实时位置图标不更新、留在原地**；③ **点巴士/站点图标 → 弹卡 → 导航中断回到首页地图**。
- **业界参照**：导航态只高亮当前乘车；点击信息卡不应导致导航态丢栈/回退（Google 导航点 POI 卡片不中断导航）。
- **修改方向**：
  1. 乘车开始后**地图只显示当前乘坐的那班车图标**（其余隐藏）。
  2. 修复**车图标位置不更新**（轮询/图层 setPosition 未生效或重建异常）。
  3. **点击巴士/站点图标 → 打开信息卡但保持导航态**（不退出、不丢方案）；`body[data-nav="riding"]` 不被清除。

### 4.7 需求 7：换乘用时（含等车 + 能赶上 + 算法优化）

- **现状（读码，关键）**：`src/lib/recommend/model.ts` 头部明确：
  - `T_total = walkOut + Σ_k [wait_k + ride_k + transfer_k] + walkIn`；
  - `wait_1`＝DSAT 实时下限；无在途车 → 整条剔除；
  - **`wait_2+`＝按"到达换乘站的时刻"取班次**（轻轨查时刻表；**巴士按间隔 ÷ 2 估**）；
  - `transfer`：**同场（站码相同且非轻轨）＝ 0**；轻轨站内换乘读 `transfer_walks`；
  - `catch-up.ts` 有"赶车 5 档"（仅用于**首段赶车**的档位/文案），**换乘段无等效可行性闸门**。
- **偏差诊断（供架构师）**：
  - ① 换乘等车用"**班距 ÷ 2**"＝**平均等待**，未按"到达换乘站时刻的真实下一班"（业界 M6/乘换案内口径）→ 偏差可达数分钟；
  - ② **无"能否赶上"判定** → 会给出"看着能接上、实则赶不上"的方案；
  - ③ **同场换乘步行记 0 + 无安全余量** → 换乘方案总时长被**系统性低估**，于是"换乘方案普遍比直达方案更快"（与用户体感一致）。
- **修改方向**：
  1. 换乘等车**改为"到达换乘站的时刻 → 真实下一班"**（巴士用 `route_frequency`/在途车；轻轨用 `lrt_timetables` 逐班匹配）。
  2. 引入**换乘可行性闸门 + 安全余量（min-safe-transfer，建议 ≥2~3 分钟）**：赶不上 → **顺延到下一班并计入等待**（或该方案降级/剔除，口径待拍板）。
  3. **总时长必须含换乘等车**（保持并强化；修掉"班距÷2"的乐观近似）。
  4. 换乘段视情况计入**换乘惩罚 α**（与需求 8 的模型参数联动）。

### 4.8 需求 8：用户偏好模型（少换乘/少步行/默认综合推荐）

- **现状（读码）**：`src/lib/nav/rank.ts` 排序**主判据＝`totalMin` 升序**；tie-break 依次为 **换乘次数↑ → 总步行量↑ → 来源（高德优先）→ planId**。即"**时间优先，换乘/步行仅作同分裁决**"，**无可切换偏好档**。
- **业界参照（M7）**：高德/百度＝"默认综合 + 少换乘/少步行快捷档"；默认＝广义成本最小。
- **修改方向**：
  1. **默认＝综合模型**：`cost = totalMin + α×换乘次数 + (β−1)×步行分钟`（α/β 待定，见 §3.3），按 `cost` 升序。
  2. 提供**三档快捷偏好**：**综合（默认）/ 少换乘 / 少步行**（澳门无地铁，不设地铁档）。
  3. 偏好切换**即时生效**，且**不改变 `data-*` 契约**（仅排序结果变化）。

### 4.9 需求 9：下车判断全自动 + 上车判定更灵敏

- **现状（读码）**：`boarding-detect.ts` **上车判定已是全自动**（R1 车辆侧 / R2 GPS 侧 + 轻轨收紧档 + 安全网 A1/A2 + 冷却 20s）；上轮 Spec §4.3 已"全自动上车"落地。**用户反馈"上车判断不太灵敏"** → 偏向 R2 阈值/采样偏保守（`R2_MIN_SAMPLES_ALONE=3`，投影≤80m，速度 8~80km/h，沿线位移≥150m，45s 窗口）。**下车判断**：Spec 中"下车后（GPS）"为阶段⑦，但用户体感仍是**手动** → 说明"下车"缺**自动触发**（当前主要靠手动/安全网纠错）。
- **修改方向**：
  1. **下车自动化**：以"**车辆通道抵达/驶离下车站**"为主判据（权威链），GPS 仅作佐证（沿用铁律：站序进度只认官方车辆）；触发即进入"下车后"，给一次反馈。
  2. **上车灵敏度优化**：在"宁可晚判、不误判"前提下，放宽/校准 R2（如采样数、投影容差、速度下限），并**用实测数据回归**（避免误判回潮）。
  3. 安全网（疑似未上车/提前下车 + 一键纠正 + 可回退）**保留**。

### 4.10 需求 10：隐藏高德底图自带站点

- **现状（读码 + 既有文档，关键）**：**代码已接通** —— `src/app/page.tsx:47` 读 `AMAP_MAP_STYLE_ID` → `NavShell`（line 69/79/311）→ `NavMap.tsx:110/194/358`（`...(mapStyleId ? { mapStyle: 'amap://styles/<id>' } : {})`）。即 **v3.0.0 已具备能力**，**只需用户在控制台建"关公交站"样式并回填样式 ID**。
- **既有方案文档**：`docs/技术方案-隐藏底图公交站点方案-20260923.md`（架构师 高见远）已给出完整路径与风险（含 R1"编辑器能否细到只关公交站"待实测）。
- **⚠ 反面清单（严禁采信）**：`setFeatures(['bg','road','point:none','text:none'])`＝**幻觉接口**（`setFeatures` 只接受 `bg|point|road|building`）；`showLabel:false`＝连街道名一起关（过度）；JS API 2.0 **不支持**内联 `styleJson`。
- **修改方向**：**无需开发**。① 用户在控制台创建并发布"隐藏公交站"自定义样式 → 取样式 ID；② 配置 `AMAP_MAP_STYLE_ID`（Vercel env）；③ 验收底图无公交站图标、其余 POI/文字不变、我方站点图层正常、未配置时降级默认样式。

## 5. 验收标准草案（EARS · AC-25 ~ AC-57）

> 格式：`When <触发/条件>, the <系统> shall <可观察响应>`；均给**可机器断言的观测点**（既有钩子优先，新增钩子标 ★新增，由架构师 Phase 2 冻结）。
> 既有钩子：`data-sheet-state` / `data-detent` / `data-phase` / `data-live` / `data-map` / `data-overview-legs` / `body[data-nav]` / `data-nav-phase` / `data-dragging` / `data-open`。
> ★新增（建议）钩子：`data-map-follow="follow|free"`、`data-map-zoom`（数值）、`data-station-layer="all|route"`、`data-userdot="blue|none"`、`data-nav-leg="bus|lrt|transfer"`、`data-track-state="idle|riding|alighted"`、`data-pref="balanced|fewer-transfer|less-walk"`、`data-transfer-feasible="yes|tight|no"`、`data-vehicle-shown`（数量）。

### 5.1 需求 1 · 取景与抖动（AC-25 ~ AC-28）

| 编号 | EARS 验收标准 | 观测点 |
|------|----------------|--------|
| AC-25 | **When** 用户在导航/详情态对地图执行平移或缩放，**the** 地图 shall 进入 `free`（`data-map-follow="free"`）且此后**相机中心与缩放级别保持用户设定值不变**。 | `data-map-follow` + `data-map-zoom`（手势前后一致） |
| AC-26 | **When** 后台数据刷新（12s 轮询 / 报站更新 / 面板开合）发生，**the** 地图 shall **不改变**当前 zoom/center（无论处于 `follow` 还是 `free`）。 | `data-map-zoom` 与 center 在刷新前后**逐帧不变**；`pageerror=0` |
| AC-27 | **When** 处于 `free` 态，**the** 界面 shall 显示「重新居中」入口（可见）；**When** 点击之，**the** 地图 shall 回到 `follow`（`data-map-follow="follow"`）并重新贴住用户位置。 | `data-map-follow` 变化 + 按钮可见性 |
| AC-28 | **When** 用户开合/拖动底部面板（`data-dragging` 变化）期间，**the** 地图 shall **不出现**由程序触发的相机位移（无抖动），且 `console.error=0`。 | `data-dragging` 与相机不变断言；`console.error` 计数 |

### 5.2 需求 2 · 站点按线路过滤（AC-29 ~ AC-31）

| 编号 | EARS 验收标准 | 观测点 |
|------|----------------|--------|
| AC-29 | **When** 进入路线查看模式并选中某线路，**the** 地图 shall 只渲染该线路的站点，**其余站点不显示**。 | `data-station-layer="route"` ★新增 + 站点计数域（我方图层） |
| AC-30 | **When** 处于导航模式，**the** 地图 shall 只渲染**当前方案所涉线路**（含换乘的多条）的站点；**非本方案**站点不显示。 | `data-station-layer="route"` + `data-overview-legs`（在乘腿数） |
| AC-31 | **When** 方案不发生换乘（单腿），**the** 地图 shall 只显示该单腿线路站点；**When** 发生换乘，**the** 站点集合 shall 为**各腿线路站点之并集**（去重）。 | 站点集合与 legs 对齐（动态比对，禁硬编码） |

### 5.3 需求 3 · 导航界面稳定与文案（AC-32 ~ AC-37）

| 编号 | EARS 验收标准 | 观测点 |
|------|----------------|--------|
| AC-32 | **When** 导航阶段在「候车 → 车来了 → 乘车中 → 临近下车」之间切换，**the** "车辆信息/出发"窗格 shall **保持固定位置**（不位移、不遮挡其他内容）。 | 窗格 `getBoundingClientRect()` 跨阶段稳定（≤阈值抖动） |
| AC-33 | **the** 顶部时间区 shall **无灰色边框**；**总用时**显示在**左上**、**线路标签总览**显示在其**同一行的右上**，且**单行完整显示**（无折行、无省略号）。 | DOM 结构 + 文本不裁剪断言 |
| AC-34 | **When** 渲染导航界面，**the** 界面 shall **不出现**"估算"标签（全链路 0 命中）。 | 文案扫描：`估算` 命中数 = 0（沿用 AC-21 禁用词口径） |
| AC-35 | **When** 渲染车辆信息窗格，**the** 窗格 shall **不重复显示"下一站"**（纵轴已表达下一站）。 | 文案扫描：窗格内"下一站"副本数 ≤ 1（仅纵轴） |
| AC-36 | **When** 触发下车提醒，**the** 横幅文案 shall 为**简化短句**，且**站号 + 站名保持原样**（格式/繁简一致）。 | 横幅文本 = 规则化短句 + `destLabel` 原样 |
| AC-37 | **When** 横幅渲染（含最长站名），**the** 文本 shall **单行不溢出**（无折行/无截断/无横向滚动）。 | `scrollWidth ≤ clientWidth`；390×844 无横滚 |

### 5.4 需求 4 · 线路标签统一（AC-38 ~ AC-39）

## 10. 附录 · P2 复核门终稿（A1 ~ A4，2026-10-30 定稿）

> **用途**：`scripts/compare-slack-impact.ts` 的验收判据。对应改动 = P2「巴士第 2 段 `slackMin` 由 `null` 改为保守余量 `max(0, 2·lo − hi)`」。
> **效力**：以本节为准，主理人 2026-10-30 定稿。
> ⚠ **已作废两条**：原提交的「θ≥3 判 `no`」与「不换乘无解不算 `no`」。原因：`no` 分支**代码不可达**（轻轨 `gapMin` 与 P2 后巴士 `slackMin` 均 ≥ 0），验证一个永远进不去的分支会产生 **「假绿」——比缺一道门更危险**。

### 10.1 四条判据

**A1 · 逐位相等（不设容差）**
同一 OD、同一输入，改前/改后**每个方案**的下列值必须逐位相等：
`totalMin`、换乘数、`walkMinutesOf(card)`、**每段乘车分钟**、**每段等车分钟**。
**唯一允许的差异只出现在 risk / cost 分量。**
理由：只验 `totalMin` 挡不住「顺手改了顺延逻辑」这种隐蔽回归，逐位相等能挡住。

**A2 · 方案集不缩水**
改前有解 → 改后必须有解；方案数、线路组合集合完全相同（防「顺手筛掉了某方案」）。

**A3 · 排序翻转必须可解释（三条件须同时满足）**
若 top1 发生变化：
1. 同规则下 `cost_new(新 top1) < cost_new(旧 top1)`（**严格**小于）；
2. **新 top1 的 `totalMin` 增量 ≤ 旧 top1 的 risk 增量**；
3. 差额**完全**由 risk 分量解释（A1 已保证其余分量逐位相等，此项可机器验）。

> ⚠ **原表述「新 top1 的 `totalMin` 不得高于旧 top1」是错的，已撤回。** 该表述会禁止一切「用时间换稳定」的合法翻转，而那恰恰是本次改动的**目标结果**。反例见 §10.2。

**A4 · `tight` 分布（替换原 `no` 断言）**
P2 后 `tight` 占比上升，且**新增的 `tight` 必须全部来自巴士段**——来源须可归入下列两类**之一**，否则判红：
- (a) **时段行命中**且 `2·lo − hi < 3`（保守余量不足）；
- (b) **只剩 `headwayMedian`** ⇒ `slackMin = 0` 兜底判 `tight`（不确定性未知，按最不确定处理）。

⚠ **(c) 档 3（连中位数都没有 ⇒ `null`）＝⏳待定（测量中）**：测量期按「**不产生 `tight`**」预期验；**若最终定稿改为判 `tight`，必须先把 (c) 补为合法来源**，否则 A4 会把**合法新增**判成跨模式污染——这是本门最容易误伤的一处，改口径时务必同步本条。

**轻轨同场换乘的 `tight` 数不得增加**（`SAME_FIELD_TRANSFER_MIN = 0` 仍须判 `yes`）。
✅ 出现「轻轨新增 `tight`」即判红 —— 那是**跨模式语义污染**（巴士的余量口径渗到了轻轨）。
⚠ **隐含前提须在断言里显式写死**：`slackMin === undefined ⇒ yes`，且实现用**宽松等号** `== null` 覆盖 `null`/`undefined`；**不得收窄成 `=== null`**（收窄后 `undefined` 漏进 `< 3` 分支，同场换乘立刻变 `tight`）。不写死则 A4 验的是未定义行为；红了将无法区分「映射变了」还是「逻辑错了」。

### 10.2 A3 的 B/C 反例（存档，供将来判红时直接对照）

设两方案，`α·transfers` 与步行项相同（A1 已保证两次运行逐位相等）：

| 方案 | 改前 totalMin | 改前 risk | 改后 risk | 改前 cost | 改后 cost |
|------|---------------|-----------|-----------|-----------|-----------|
| **B**（巴士宽桶 `lo=8, hi=25`） | 30 | 0（`slackMin=null`，无风险项） | **1.5**（`slack=0`） | 30 | **31.5** |
| **C**（轻轨 `gap=3`） | 31 | 0（`slack=3`） | 0 | 31 | **31** |

- 改前：B(30) < C(31) ⇒ top1 = **B**
- 改后：C(31) < B(31.5) ⇒ top1 = **C**
- 此时**新 top1 的 `totalMin`（31）高于旧 top1（30）** ⇒ 按原 A3 表述**直接判红**；但按终稿三条件：`totalMin` 增量 1 ≤ 旧 top1 risk 增量 1.5 ✅、`cost_new(C) < cost_new(B)` ✅、差额全由 risk 解释 ✅ ⇒ **合法翻转，不判红**。
- 这正是「更稳 → 更优」：宽桶巴士被罚，换乘更确定的轻轨胜出，代价 1 分钟。

### 10.3 推导（为何三条件 ≡「只由 risk 解释」）

```
cost = totalMin + α·transfers + (β−1)·walk + risk
```
A1 保证除 `risk` 外各项在两次运行中逐位相等 ⇒ 两次运行的 `cost` 差**只可能**来自 `risk`
⇒ 排序翻转的**充要条件** = 「施加在**旧** top1 上的 risk 增量 > 施加在**新** top1 上的 risk 增量」。
**「赢家不许更慢」不是这个条件**，它只是把合法翻转误判为回归。

### 10.4 相关口径（与本门配套，勿单独立项）

- **PRD 与任何告警均不得依赖 `no`**（该分支不可达）。
- 判红归因顺序：先查 **A4**（跨模式污染 / 映射变更）→ 再查 **A1**（顺延逻辑是否被动过）→ 最后看 **A3**（排序解释性）。
- 量级依据：`risk ≤ riskFactor(0.5) × safetyMin(3) = 1.5 分/换乘`，恒小于换乘次数惩罚 `PREF_ALPHA = 10` 的 **15%**，故 risk 不可能淹没 cost。
- **调参红线**：`riskFactor ≤ α/2 = 5`（当前 0.5，10 倍余量）；超过即让「可行性」盖过「换乘次数」这一更硬判据，须重新评审。

### 10.6 验收基线 · `data-nav-phase` 的 CSS 依赖（2026-10-30 补）

> ⚠ **本基线不因当前全绿而失效。** 它是**「下次有人改 `NavPhase` 取值域时的参照物」**，不是「缺陷登记」——删掉本节即失去参照物，而缺失参照物的那次改动将**无任何报错**（CSS 选择器静默失配）。与「注释删了、防御就没了」属同一类脆弱点。

- `globals.css` 中依赖 `data-nav-phase` 的规则**只有 3 条**：`:6862`（`riding` 隐藏底栏）· `:6868`（非 `off` 隐藏品牌栏按钮组）· `:7864`（**`walk`** 隐藏底栏）。
- 其中 **`walk` 值只被 `:7864` 一处依赖** ⇒ 这是「`walk` 被删除或改名」的**唯一外部证据**。
- **验收口径**：凡改动 `NavPhase` 取值域（新增 / 删除 / 改名），须按上述 3 条**逐条核 CSS 命中**；**不得以"控制台没报错"作为通过依据** —— CSS 选择器失配是**静默失败**，浏览器不会报任何错。
- 具体风险：若 `walk` 被移除或改名而 `:7864` 未同步，该规则即成死代码（步行态底栏不再隐藏），**全程无报错、无告警**，只能靠本条基线人工比对发现。
