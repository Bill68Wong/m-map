## 1.1 定位澄清：我们是后处理器，不是路线引擎

设计文档把现行架构压成一句话：**「候选主要来自高德，时间由我们算，顺序由我们排；我们自己枚举出的更优方案也一并出给用户」**【实测】（`docs/设计-全澳导航-v1-20260918.md:15`）。这句话在实现里落得很实：一次「出发」= **1 次**高德 `transit/integrated` 往返（`src/lib/nav/nav-service.ts:259`），拿到高德**已经枚举好的方案骨架**（含上/下车站、完整站序、首末步行段），随后我们做的三件事全部是**对既有方案的再加工**：

| 我们的动作 | 不是我们做的 |
|---|---|
| 把高德站码桥接到我们的站码 | 不是我们枚举候选起终点组合 |
| 用自有 `segment_stats` 逐跳重算车程 | 不是我们推导线路连通关系 |
| 用 `T_ours` 重排序、并对高德漏掉的组合补漏 | 不是我们掌握全量换乘关系 |

这个定位决定了本章的全部讨论口径：**我们存在的「路线规划模型」实际上是「候选后处理 + 时间计算 + 排序」模型**，它的输入质量上限由高德给定，它的差异化来自自有数据。后文凡提「自建」，指的都不是重写这句话的前半句。

## 1.2 三层可分离视角：为什么这是全篇的分析主轴

把整条链路按「能力来源」而不是「代码文件」切开，会得到三个彼此正交的层：

| 层 | 职责 | 我们的状态 | 决定性约束 |
|---|---|---|---|
| ① 几何/步行路由层 | 两点之间的**道路几何与步行路径距离** | **依赖高德** | 唯一真正「缺基础数据」的一层；高德短距失真 6~12× |
| ② 候选寻路层 | 从路网中**枚举出可选乘车组合**（含换乘） | 高德为主源，本地有界 BFS 为补漏/降级 | 本地枚举漏线率高、换乘上限 ≤2 |
| ③ 时间计算与排序层 | 把方案折成**门到门分钟数**并排序 | **早已自建**（`lookupHop` + `T_ours`） | 无 ground truth |

之所以这个切法要当主轴：**三层的数据依赖、失败模式、可替换性完全不同**。①层失败表现为「距离不对」，②层失败表现为「方案没给」，③层失败表现为「排序不可验证」。任何笼统的「要不要自建路线规划」问题，在三层上会得出不同答案——把三层混在一起谈，结论必然含糊。本章按此视角解剖现状，第 2 章用它对标高德/谷歌，第 3 章按层盘点资产，第 4 章按层判定可行性。

## 1.3 九步链路逐段解剖

主流程 `planNav()` 定义在 `src/lib/nav/nav-service.ts:217`，链路注释见同文件 `:2-13`。

| # | 环节（代码位置） | 输入 → 输出 | 算法本质 | 失败时的降级行为 |
|---|---|---|---|---|
| ① | `loadStatics()` `nav-service.ts:229` | DB → 站序索引 / 段统计 / 步行 / 换乘 / 轻轨预载 | 全量装载 + 内存索引（只读一次库） | 抛错即整链路失败（无降级） |
| ② | `loadStationMap()` `nav-service.ts:232` | `station_amap_map` 表 → 站码映射 | **人工维护映射表**（自动生成 + 人工复核，`verified_by_human` 优先） | 表缺失 → 映射全失败 → 下游退化为「回落高德时长」 |
| ③ | `fetchTransitPlans()` `nav-service.ts:259` · `transit.ts:41` | OD 坐标 → 高德原始 `transits[]` | 单次 HTTP；`AlternativeRoute=10`（**驼峰，小写被静默忽略**）· `strategy=0` · `transit_cache` TTL 60s | 超时(1.5s)/限流/`infocode` 异常/**0 方案** → `ok:false` → **进入降级路径** |
| ④ | `parseAndBridge()` `nav-service.ts:274` · `parse-amap-plan.ts:42` | 高德 JSON → `AmapPlanSeed[]`（含桥接结果） | 纯函数：结构解析 → **方案级过滤**（赌场穿梭巴士黑名单 + 在建轻轨 ES1–ES6）→ 站码桥接 → **全段映射失败则剔整方案** | 单方案被剔 → 只减少候选数（`dropped` 记账）；全部被剔 → 等价于无高德候选 |
| ⑤ | 本地图枚举 `nav-service.ts:283-292` | 图 + 站点地理 → `StationPath[]` | **有界 BFS**（见 1.6） | 两种用途：**补漏**（主路径，只读离线 `shadow_diff_report`）/ **降级引擎**（高德不可用时现场跑，不受 `allowInlineLocal` 约束） |
| ⑥ | `fetchLive()` `nav-service.ts:311` | 全部种子 → DSAT 实时 + 轻轨时刻表 | 两来源**共用一次**批量查询 | 实时不可用 → 复用旧版 `liveDegraded` 文案（估值为准） |
| ⑦ | `modelOption()` + `patchAmapFallback()` `nav-service.ts:332,334` · `recompute.ts:180` | 种子 + 上下文 → 卡片 + `provenance` | 复用旧推荐引擎；注入 `walkResolver`（首末步行）+ 方案级换乘索引；**映射失败段回落高德时长**（纯加法补正） | 单段失败 → 该段用高德值并标「高德」；整方案差异 >50% → `suspect` |
| ⑧ | `mergeSources()` + `rankItems()` `nav-service.ts:373-374` · `merge-sources.ts:105` · `rank.ts:45` | 两来源条目 → 合并 + 排序 | 本地候选过 **5 道质量闸门** + **最多 2 张**（高德 <3 张时放宽到 3）→ 统一排序 | 本地候选不过闸 → 丢弃（实测常态：`localKept=0`，见验收报告④） |
| ⑨ | `slice(limit)` `nav-service.ts:375` | 排序结果 → 前 N 张卡片 | 截断 | 0 张时按 `too_close` / `amap_unavailable` / `no_live` / `no_candidate` 给空状态原因 |

三条值得单独记录的链路事实：

- **③ 的 `AlternativeRoute` 是承重参数**：不传时默认返回 4~5 条，驼峰 `=10` 时该 OD 只有 7 个可行解（上限截断但**不报错**）【实测】（`docs/调研…:83-94`）。
- **④ 的过滤只能靠线路名黑名单**：高德把赌场免费穿梭巴士当公交，而 `buslines[].type` 只有「普通公交线路 / 地铁线路」两种取值，穿梭巴士也落在前者 ⇒ 只能按线路名子串过滤【实测+推断】（`transit.ts:63-99`；`docs/调研…:241`）。
- **⑧ 的来源标注是刻意的**：本地方案对用户用中性文案（如「另一種走法」）【实测】（设计 §B.5；`nav-service.ts:427`）。

## 1.4 时间轴：`T_ours` 与取值层级

门到门总时长由我们逐段拼装（设计 `:302`）：

```
T_ours = walkOut + wait₁ + ride₁ + Σ_{k≥2}(transferₖ + waitₖ + rideₖ) + walkIn
```

各段的算法本质与可信度来源如下：

| 段 | 取值来源 | 算法本质 | 档位 |
|---|---|---|---|
| `walkOut` / `walkIn` | 高德方案的 `walking.distance` → 短距修正 → `÷84` | 直线距离 × 修正系数 / 常速基准 | 高德几何（非实测） |
| `ride` | **逐跳累加** `lookupHop(route, from, to, weekday)` | 邻接对查表（**禁止「站数 × 常数」**） | L1~L4 实测 / L5~L6 估算 |
| `transfer` | 轻轨相关 → 高德换乘 `duration`；巴士-巴士 → 高德距离 `÷84`（缺则回落 `transfer_walks`） | 按载具二分口径 | 高德 / 实测 / 估算 |
| `wait₁` | DSAT 实时报站（巴士）/ 轻轨时刻表 | 实时到站 | 实时 |
| `wait₂₊` | 巴士按班距 `÷2` 估；轻轨查时刻表 | 班距假设 | 估算 |

`lookupHop`（`segment-lookup.ts:123`）是一条 **6 级回退链**，这是本系统最核心的「自建」部件：

| 层级 | 判据 | 性质 |
|---|---|---|
| L1 | 本线 · 今天 · `arrive_kind=stop` | **实测** |
| L2 | 本线 · 全周 · `stop` | **实测** |
| L3 | 本线 · 全周 · `all` | **实测** |
| L4 | **跨线邻接共享**（同一物理邻接对，任一线路样本皆可用） | **实测** |
| L5 | 该线单站均值 × 1 跳 | **估算**（UI 标「估算」） |
| L6 | 全局单站均值 × 1 跳 | **估算** |

其中 L4 是设计上的关键判断：**覆盖率按「物理有向邻接对」评估而非「每线 × 邻接对」**，因为同一段马路（如 `C653→C654`）26 路要开、50 路也要开，物理时长同源。这一口径把逐跳命中率从 52.8% 抬到 76.8%【实测】（`segment-lookup.ts:8-15`）——口径之争的完整陈述留给第 3 章。

## 1.5 排序规则及其隐含的价值判断

排序实现是 `rank.ts:45` 的 `rankItems()`，键序为【实测】（`rank.ts:46-59`）：

```
① T_ours 升序  →  ② 换乘次数升序  →  ③ 总步行量升序  →  ④ 来源（高德优先）  →  ⑤ planId 升序
```

**注意 ③ 只统计首末步行**（`walkMetersOf`，`rank.ts:38-42`）——换乘步行无统一距离口径，不计入。

这套键序隐含三条价值判断，它们是「模型选择」而不是「自然规律」：

1. **「我们算出的分钟数 = 可比真值」被当作公理**。主判据不用高德原始排序，产品口径是「我们有数据优势，算出更准确的结果」【实测】（设计 §C.6）。但这意味着：**排序的正确性完全继承自 `T_ours` 的正确性**，而 `T_ours` 没有 ground truth（见 1.7-⑤）。排序合理与否只能靠代理指标（与高德最优的偏差分布）间接观察。
2. **「少换乘」优先于「少走路」**。②先于③，即 26 分钟 1 换乘排在 26 分钟 0 换乘之后、排在 25 分钟 2 换乘之前——这里的权衡是「换乘的心理成本 > 走路的体力成本」，属产品取舍。
3. **「来源背书」优先于「我们自己的解」**。④把 `amap` 排在 `local` 之前，等价于承认：**同分情况下，第三方背书的方案更值得信任**。与之配套的是 ⑤ 的稳定化（`planId`）。这条判断与 ⑧ 的「本地补漏最多 2 张」是同一取向的两个侧面。

⚠️ 一个容易被忽略的口径事实：`patchAmapFallback` 会在映射失败段把卡片时间轴**改成高德值**（纯加法补正）。因此同一张卡内部可能同时混有「我们的实测车程」与「高德车程」两个口径——系统用 `provenance` 记账 + 差异告警来标记，但**不能根除**（设计 §C.7 / `recompute.ts:225-228`）。

## 1.6 本地枚举的算法本质：换乘 ≤2 的有界 BFS

本地候选由 `searchStationPaths()` 产出（`graph-search.ts:156`），默认参数见 `graph-search.ts:62-68`：**`k=8` 最近站 · `radiusM=700` · `maxTransfers=2` · `maxCandidates=200` · `hubLimit=25`**。

其算法结构：

1. **起终点各取最近 K 站**（≤700m，WGS 球面）；
2. 沿站序索引算出「起点站集合单程可达的 hub」与「能单程到达终点站的 hub」；
3. 按换乘数分层组合：0 换乘（任一线顺向可解）→ 1 换乘（同一 hub 兼可达）→ 2 换乘（两 hub 之间有共有线路作中段）；
4. 按「线路@上→下」链去重，并以硬上限截断（防请求期超时）。

从算法族谱看，这**正是 RAPTOR 的退化雏形**：同为轮次式扩张、同样以「到达」与「换乘次数」为状态；差别在于我们没有轮次收敛判据、换乘数被**硬编码为 2**、且候选枚举是**有界截断**而非全量 Pareto 输出。完整的 RAPTOR / CSA / Transfer Patterns 对照留给第 2 章，此处只点出**一个结构性事实**：`graph-search.ts:19-21` 自述「换乘按同一主码处理 ⇒ 换乘步行计 0，真实的跨街换乘不建模」——这使本地候选在时间上**系统性偏乐观**，也是本地候选必须过质量闸门的原因。

## 1.7 六大已知局限

| # | 局限 | 量化证据 | 直接后果 |
|---|---|---|---|
| ① | **高德候选被框定** | `AlternativeRoute=10` 实测上限 **7 条**，且该 OD 的 7 条中约 **4 条是赌场穿梭巴士**（`#4 新濠天地 / #5 美高梅 / #6 新濠影汇 / #7 银河`）⇒ 过滤后真候选常仅 **3 条**【实测】（`docs/调研…:83-94,230-239`） | 候选池上限不由我们决定；短途/跨境/异常点还会退化（实测跨境只给 2 条、异常点只给 1 条） |
| ② | **本地枚举漏线率高** | 两套实测：工程侧 K=8 约 **57%**、K=16 约 **41%**【实测】（`docs/已知取舍…:45-48`）；QA 扩样 32 OD 得 A(k8,cap80)=**72.9%**、B(k8,cap2000)=**53.5%**、C(k16)=**34.1%**、D(k40/3km)=**26.4%**，且 32/32 OD **全部触顶**【实测】（`docs/验收…:62-67`） | 远高于设计「>10% 告警」阈值；**40% 量级的数字部分是 cap 假象**，且即便把高德选中站并入候选（D 配置）仍 26.4% > 10% ⇒ 该缓解不足 |
| ③ | **换乘上限 ≤2** | `maxTransfers: 2` 硬编码（`graph-search.ts:65`） | 3 换乘方案在本地层**结构性不可达**；2 换乘还叠加 hub 限量 25 与「中段=两 hub 共有线」约束 |
| ④ | **真实换乘关系几乎为空** | `transfer_walks` 实测仅 **2 条**【实测】（`docs/调研…:520,723`） | 巴士-巴士换乘步行只能改用「高德距离 `÷84`」（`recompute.ts:160-163`）⇒ 换乘段口径被高德接管，削弱了本层自主性 |
| ⑤ | **无 ground truth** | 审查明确列为 P1-8「三段式计时输出无从校验」【实测】（`docs/审查…:42,142`） | 任何「我们更准」的主张只能建立在代理指标上，**结论强度必须降级**；排序合理性无法直接证明 |
| ⑥ | **短距步行失真** | QA 真机 8 组：`T417→T429` 直线 **41m → 高德 492m（11.9×）**、`C652→C653` 20m → 126m（6.30×）；而**首末段典型正是 50~300m**【实测】（`docs/审查…:28`；`walk-fix.ts:7`） | 首末步行是**唯一依赖高德几何**的段；若不修正会把「赶得上」算成「赶不上」，**整条最优方案被剔除** |

> **补充观察**：短距修正规则存在**文档/实现口径漂移**——设计 §C.2 写「直线 <200m → 直线×1.5」，实现为 `min(高德, 直线×2.5)`，且短距下 `ratio ≤ 3.0` 时**直接采用高德值**【实测】（`walk-fix.ts:117-189` vs 设计 `:318`；QA 记为 P1-3）。

## 本章结论

1. **我们的「路线规划模型」在架构上不是路线引擎，而是「候选后处理器」**：候选集合由高德一次 `transit/integrated` 给定（`nav-service.ts:259`），我们只做站码桥接、逐跳重算、重排序与有限补漏。⇒ 第 4 章讨论「自建」时，**默认讨论的是②候选寻路层与①几何层，而不是③时间层**——③层已经在我们手里。

2. **应当把整条链路按「几何/步行路由、候选寻路、时间计算与排序」三层切开分析**（1.2）。三层的失败模式互不重叠（距离不对 / 方案没给 / 排序不可验证），因此可行性判定必须分层给出，否则结论无法落地。这是全篇主轴。

3. **第③层（时间计算与排序）是本系统真正的自研内核，也是最成熟的一层**：`lookupHop` 6 级回退链 + L4 跨线共享把逐跳命中率抬到 76.8%（`segment-lookup.ts:14`）。⇒ 任何自建方案都不应重写这一层。

4. **排序键序承载了三条价值判断而非事实**（1.5）：把 `T_ours` 当可比真值、「少换乘」优先于「少走路」、「来源背书」优先于自有解。其中第一条最脆弱——**无 ground truth**（1.7-⑤）使排序正确性无法直接验证；第 4~5 章须为它配可执行的代理验收，并保持结论强度降级。

5. **六大局限中，②与⑥是自建决策的分水岭**：本地枚举漏线率即使放宽到 K=40/3km 仍有 26.4%（`docs/验收…:67`）⇒ **②层的关键不在算法（RAPTOR 现成）而在图质量与站码映射**；而①层高德短距步行失真 11.9×（`docs/审查…:28`）是**唯一「缺基础数据」的硬证据**。这两条直接决定第 4 章方案 B（只自建寻路）与方案 C（全自建）的可行性边界。
