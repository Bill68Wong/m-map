## 引言

### 一、为什么做这个研究：一次升级撞到的一堵墙

「MUST登校」当前是一个**澳科大门到门通勤** PWA（Next.js + Vercel Serverless + Supabase，已上线 v2.0.1）。现在的目标是把定位从「校园通勤」升级为「**全澳导航**」。

这个升级在工程上撞到的不是算法难题，而是一个更朴素的问题：**我们的候选方案池，宽度不由我们决定。**

现行链路的实际形态是——候选主要来自高德一次 `transit/integrated` 调用，我们只做站码桥接、逐跳重算、重排序与有限补漏（`src/lib/nav/nav-service.ts:217`；`docs/设计-全澳导航-v1-20260918.md:15`）。而高德给的候选是**被框定**的：`AlternativeRoute=10` 实测返回上限 **7 条**，其中约 **4 条是赌场免费穿梭巴士**（须按线路名黑名单过滤，因为高德把它当普通公交）⇒ 过滤后**真候选常仅 3 条**【实测】（`docs/调研-全澳导航-高德API能力-20260918.md:83-94,230-239`）。

一堵墙引出四个问题——**该不该自建路线规划能力，以及如果建，建哪一层。**

### 二、本报告要回答的四个问题

以下为需求方的四个原始问题（逐字保留，见 `docs/研究-参数卡.md` §一）：

1. 梳理并解释我们当前的路线规划模型算法（核心原理 / 关键模块 / 输入输出 / 主要局限）——对应**第 1 章**。
2. 调研高德与谷歌在路线方案规划上的实现思路，重点比较**数据来源 / 算法策略 / 实时路况处理 / 多方案生成 / 偏好设置**（五个维度，一个不能少）——对应**第 2 章**。
3. 评估我们现有的能力和资源（已具备什么 / 尚缺什么 / 能支撑哪些功能）——对应**第 3 章**。
4. 从**技术可行性 / 数据 / 算力 / 成本**多角度分析能否自建，给可选方案对比与建议——对应**第 4 章**，结论落在**第 5 章**。

### 三、研究方法与边界

### 四、全文的核心论点（一句话）

> **真正的决策不是「要不要自建路线规划」，而是「只把 ② 候选寻路层的枚举与输出形态拿回来，几何层继续外包、时间层不动」。**

这条论点的完整推导见第 5 章 §5.1 与 §5.3：①几何/步行层**不自建**（唯一真缺基础数据的一层）、②候选寻路层**有条件自建**（技术成熟、算力无忧，但缺时刻表与 ground truth）、③时间计算与排序层**无需再自建**（早已自建，且是产品差异化所在）。推荐路径为 **D（混合）为主线 · B（只自建寻路层）为其完整形态 · E（外部采购）有条件 · C（全自建）排除 · A（维持现状）作回退基线**。

### 五、三条必须前置说明的限定（否则会误读全文）

**限定一 · 「自建」是【三层可分离能力】，不是布尔问题。**
全篇主轴是把整条链路按「能力来源」而非「代码文件」切开：**① 几何/步行路由层**（失败表现为「距离不对」）、**② 候选寻路层**（「方案没给」）、**③ 时间计算与排序层**（「排序说不清对不对」）。三层的数据依赖、失败模式、可替换性完全不同——**任何笼统的「要不要自建路线规划」，在三层上会得出不同答案**（第 1 章 §1.2、第 4 章 §4.1）。
⇒ 读者若把本报告结论读成「一句话回答」，等于放弃它唯一的有效信息。

**限定二 · 漏线率归因里的 pp 是【下界】，且【不可跨时段/跨样本直接比较】。**
第 4 章 §4.6 的百分数是**下界估计**——最宽配置（首轮 `cap=200,000`、复核 `cap=1,000,000`）在 **全部 OD 上仍然触顶**，说明残余未测尽、真实可达漏线率**可能更低**（首轮补充 §4S.2.5、独立复核 §复核局限）。同时，`20.5%` / `26.4%` / `38.46%` **不可直接比较**（样本与运行时段不同：QA 原始记录为凌晨 01:29，首轮复核为 16:21）⇒ **只可比归因结构，不可比绝对值**。此外 **只有第 1 名稳定**（cap 截断在三套口径下恒为第 1），**第 2 名及以后强依赖样本与口径**（第 4 章 §4.6.2）。

**限定三 · 无 ground truth ⇒ 涉及「我们更准」的主张只能建立在【代理指标】上。**
我们**没有独立真值集**（审查列为 P1-8「三段式计时输出无从校验」）。现有五个代理手段——模型测算 vs 实测对拍（档 3 平均绝对偏差 **0.58 分**）、双来源对拍（比值中位 **0.989**）、追踪式计时定点车对照、阴影对照（漏线率）、Scientific Data 2025 外部数据集对照——**都只能支撑相对性结论，不能支撑「我们比高德更准」**（第 4 章 §4.7）。
⇒ 本报告凡涉及精度主张，结论强度**一律降级表述**；候选指标只给建议区间。

### 1.1 定位澄清：我们是后处理器，不是路线引擎

设计文档把现行架构压成一句话：**「候选主要来自高德，时间由我们算，顺序由我们排；我们自己枚举出的更优方案也一并出给用户」**【实测】（`docs/设计-全澳导航-v1-20260918.md:15`）。这句话在实现里落得很实：一次「出发」= **1 次**高德 `transit/integrated` 往返（`src/lib/nav/nav-service.ts:259`），拿到高德**已经枚举好的方案骨架**（含上/下车站、完整站序、首末步行段），随后我们做的三件事全部是**对既有方案的再加工**：

| 我们的动作 | 不是我们做的 |
|---|---|
| 把高德站码桥接到我们的站码 | 不是我们枚举候选起终点组合 |
| 用自有 `segment_stats` 逐跳重算车程 | 不是我们推导线路连通关系 |
| 用 `T_ours` 重排序、并对高德漏掉的组合补漏 | 不是我们掌握全量换乘关系 |

这个定位决定了本章的全部讨论口径：**我们存在的「路线规划模型」实际上是「候选后处理 + 时间计算 + 排序」模型**，它的输入质量上限由高德给定，它的差异化来自自有数据。后文凡提「自建」，指的都不是重写这句话的前半句。

### 1.2 三层可分离视角：为什么这是全篇的分析主轴

把整条链路按「能力来源」而不是「代码文件」切开，会得到三个彼此正交的层：

| 层 | 职责 | 我们的状态 | 决定性约束 |
|---|---|---|---|
| ① 几何/步行路由层 | 两点之间的**道路几何与步行路径距离** | **依赖高德** | 唯一真正「缺基础数据」的一层；高德短距失真 6~12× |
| ② 候选寻路层 | 从路网中**枚举出可选乘车组合**（含换乘） | 高德为主源，本地有界 BFS 为补漏/降级 | 本地枚举漏线率高、换乘上限 ≤2 |
| ③ 时间计算与排序层 | 把方案折成**门到门分钟数**并排序 | **早已自建**（`lookupHop` + `T_ours`） | 无 ground truth |

之所以这个切法要当主轴：**三层的数据依赖、失败模式、可替换性完全不同**。①层失败表现为「距离不对」，②层失败表现为「方案没给」，③层失败表现为「排序不可验证」。任何笼统的「要不要自建路线规划」问题，在三层上会得出不同答案——把三层混在一起谈，结论必然含糊。本章按此视角解剖现状，第 2 章用它对标高德/谷歌，第 3 章按层盘点资产，第 4 章按层判定可行性。

### 1.3 九步链路逐段解剖

主流程 `planNav()` 定义在 `src/lib/nav/nav-service.ts:217`，链路注释见同文件 `:2-13`。

| # | 环节（代码位置） | 输入 → 输出 | 算法本质 | 失败时的降级行为 |
|---|---|---|---|---|
| ① | `loadStatics()` `nav-service.ts:229` | DB → 站序索引 / 段统计 / 步行 / 换乘 / 轻轨预载 | 全量装载 + 内存索引（只读一次库） | 抛错即整链路失败（无降级） |
| ② | `loadStationMap()` `nav-service.ts:232` | `station_amap_map` 表 → 站码映射 | **人工维护映射表**（自动生成 + 人工复核，`verified_by_human` 优先） | 表缺失 → 映射全失败 → 下游退化为「回落高德时长」 |

| ⑨ | `slice(limit)` `nav-service.ts:375` | 排序结果 → 前 N 张卡片 | 截断 | 0 张时按 `too_close` / `amap_unavailable` / `no_live` / `no_candidate` 给空状态原因 |

三条值得单独记录的链路事实：

- **③ 的 `AlternativeRoute` 是承重参数**：不传时默认返回 4~5 条，驼峰 `=10` 时该 OD 只有 7 个可行解（上限截断但**不报错**）【实测】（`docs/调研…:83-94`）。
- **④ 的过滤只能靠线路名黑名单**：高德把赌场免费穿梭巴士当公交，而 `buslines[].type` 只有「普通公交线路 / 地铁线路」两种取值，穿梭巴士也落在前者 ⇒ 只能按线路名子串过滤【实测+推断】（`transit.ts:63-99`；`docs/调研…:241`）。
- **⑧ 的来源标注是刻意的**：本地方案对用户用中性文案（如「另一種走法」）【实测】（设计 §B.5；`nav-service.ts:427`）。

### 1.4 时间轴：`T_ours` 与取值层级

门到门总时长由我们逐段拼装（设计 `:302`）：

```
T_ours = walkOut + wait₁ + ride₁ + Σ_{k≥2}(transferₖ + waitₖ + rideₖ) + walkIn
```

各段的算法本质与可信度来源如下：

| 段 | 取值来源 | 算法本质 | 档位 |
|---|---|---|---|
| `walkOut` / `walkIn` | 高德方案的 `walking.distance` → 短距修正 → `÷84` | 直线距离 × 修正系数 / 常速基准 | 高德几何（非实测） |
| `ride` | **逐跳累加** `lookupHop(route, from, to, weekday)` | 邻接对查表（**禁止「站数 × 常数」**） | L1~L4 实测 / L5~L6 估算 |
| `transfer` | 轻轨相关 → 高德换乘 `duration`；巴士-巴士 → 高德距离 `÷84`（缺则回落 `transfer_walks`） | 按载具二分口径 | 高德 / 实测 / 估算 |
| `wait₁` | DSAT 实时报站（巴士）/ 轻轨时刻表 | 实时到站 | 实时 |
| `wait₂₊` | 巴士按班距 `÷2` 估；轻轨查时刻表 | 班距假设 | 估算 |

`lookupHop`（`segment-lookup.ts:123`）是一条 **6 级回退链**，这是本系统最核心的「自建」部件：

| 层级 | 判据 | 性质 |
|---|---|---|
| L1 | 本线 · 今天 · `arrive_kind=stop` | **实测** |
| L2 | 本线 · 全周 · `stop` | **实测** |
| L3 | 本线 · 全周 · `all` | **实测** |
| L4 | **跨线邻接共享**（同一物理邻接对，任一线路样本皆可用） | **实测** |
| L5 | 该线单站均值 × 1 跳 | **估算**（UI 标「估算」） |
| L6 | 全局单站均值 × 1 跳 | **估算** |

其中 L4 是设计上的关键判断：**覆盖率按「物理有向邻接对」评估而非「每线 × 邻接对」**，因为同一段马路（如 `C653→C654`）26 路要开、50 路也要开，物理时长同源。这一口径把逐跳命中率从 52.8% 抬到 76.8%【实测】（`segment-lookup.ts:8-15`）——口径之争的完整陈述留给第 3 章。

### 1.5 排序规则及其隐含的价值判断

排序实现是 `rank.ts:45` 的 `rankItems()`，键序为【实测】（`rank.ts:46-59`）：

```
① T_ours 升序  →  ② 换乘次数升序  →  ③ 总步行量升序  →  ④ 来源（高德优先）  →  ⑤ planId 升序
```

**注意 ③ 只统计首末步行**（`walkMetersOf`，`rank.ts:38-42`）——换乘步行无统一距离口径，不计入。

这套键序隐含三条价值判断，它们是「模型选择」而不是「自然规律」：

1. **「我们算出的分钟数 = 可比真值」被当作公理**。主判据不用高德原始排序，产品口径是「我们有数据优势，算出更准确的结果」【实测】（设计 §C.6）。但这意味着：**排序的正确性完全继承自 `T_ours` 的正确性**，而 `T_ours` 没有 ground truth（见 1.7-⑤）。排序合理与否只能靠代理指标（与高德最优的偏差分布）间接观察。
2. **「少换乘」优先于「少走路」**。②先于③，即 26 分钟 1 换乘排在 26 分钟 0 换乘之后、排在 25 分钟 2 换乘之前——这里的权衡是「换乘的心理成本 > 走路的体力成本」，属产品取舍。
3. **「来源背书」优先于「我们自己的解」**。④把 `amap` 排在 `local` 之前，等价于承认：**同分情况下，第三方背书的方案更值得信任**。与之配套的是 ⑤ 的稳定化（`planId`）。这条判断与 ⑧ 的「本地补漏最多 2 张」是同一取向的两个侧面。

⚠️ 一个容易被忽略的口径事实：`patchAmapFallback` 会在映射失败段把卡片时间轴**改成高德值**（纯加法补正）。因此同一张卡内部可能同时混有「我们的实测车程」与「高德车程」两个口径——系统用 `provenance` 记账 + 差异告警来标记，但**不能根除**（设计 §C.7 / `recompute.ts:225-228`）。

### 1.6 本地枚举的算法本质：换乘 ≤2 的有界 BFS

本地候选由 `searchStationPaths()` 产出（`graph-search.ts:156`），默认参数见 `graph-search.ts:62-68`：**`k=8` 最近站 · `radiusM=700` · `maxTransfers=2` · `maxCandidates=200` · `hubLimit=25`**。

其算法结构：

1. **起终点各取最近 K 站**（≤700m，WGS 球面）；
2. 沿站序索引算出「起点站集合单程可达的 hub」与「能单程到达终点站的 hub」；
3. 按换乘数分层组合：0 换乘（任一线顺向可解）→ 1 换乘（同一 hub 兼可达）→ 2 换乘（两 hub 之间有共有线路作中段）；
4. 按「线路@上→下」链去重，并以硬上限截断（防请求期超时）。

从算法族谱看，这**正是 RAPTOR 的退化雏形**：同为轮次式扩张、同样以「到达」与「换乘次数」为状态；差别在于我们没有轮次收敛判据、换乘数被**硬编码为 2**、且候选枚举是**有界截断**而非全量 Pareto 输出。完整的 RAPTOR / CSA / Transfer Patterns 对照留给第 2 章，此处只点出**一个结构性事实**：`graph-search.ts:19-21` 自述「换乘按同一主码处理 ⇒ 换乘步行计 0，真实的跨街换乘不建模」——这使本地候选在时间上**系统性偏乐观**，也是本地候选必须过质量闸门的原因。

| # | 局限 | 量化证据 | 直接后果 |
|---|---|---|---|

### 本章结论

1. **我们的「路线规划模型」在架构上不是路线引擎，而是「候选后处理器」**：候选集合由高德一次 `transit/integrated` 给定（`nav-service.ts:259`），我们只做站码桥接、逐跳重算、重排序与有限补漏。⇒ 第 4 章讨论「自建」时，**默认讨论的是②候选寻路层与①几何层，而不是③时间层**——③层已经在我们手里。

2. **应当把整条链路按「几何/步行路由、候选寻路、时间计算与排序」三层切开分析**（1.2）。三层的失败模式互不重叠（距离不对 / 方案没给 / 排序不可验证），因此可行性判定必须分层给出，否则结论无法落地。这是全篇主轴。

3. **第③层（时间计算与排序）是本系统真正的自研内核，也是最成熟的一层**：`lookupHop` 6 级回退链 + L4 跨线共享把逐跳命中率抬到 76.8%（`segment-lookup.ts:14`）。⇒ 任何自建方案都不应重写这一层。

4. **排序键序承载了三条价值判断而非事实**（1.5）：把 `T_ours` 当可比真值、「少换乘」优先于「少走路」、「来源背书」优先于自有解。其中第一条最脆弱——**无 ground truth**（1.7-⑤）使排序正确性无法直接验证；第 4~5 章须为它配可执行的代理验收，并保持结论强度降级。

5. **六大局限中，②与⑥是自建决策的分水岭**：本地枚举漏线率即使放宽到 K=40/3km 仍有 26.4%（`docs/验收…:67`）⇒ **②层的关键不在算法（RAPTOR 现成）而在图质量与站码映射**；而①层高德短距步行失真 11.9×（`docs/审查…:28`）是**唯一「缺基础数据」的硬证据**。这两条直接决定第 4 章方案 B（只自建寻路）与方案 C（全自建）的可行性边界。

### 2.2 逐维结论

#### 2.2.1 数据来源：GTFS 范式 vs 自有采集范式（第 4 章的前置命题）

谷歌侧证据链完整：`developers.google.com/transit` 把公交数据分为 **GTFS Static**（预定路线的静态 Feed）与 **GTFS Realtime**（服务提醒、行程更新、车辆位置）【官方】；Transit 帮助页说明机构「share their static transit data (routes, stops, schedules)」后「integrated with Google Maps」【官方】；GTFS-Realtime 规范开篇即定义它**由公交机构发布**，且「always defined with relation to an existing GTFS feed」【官方】。

必须修正 Phase 1 的一句表述：**「谷歌只做校验与归一化、不改数据」未获官方确认**【未查到】。官方只确认「线路与时刻由机构提供、谷歌负责整合」。反而有反向线索：第三方 GTFS 服务商文档称 Google Maps 对换乘施加平台默认规则——「站点间步行时间 + 4 分钟」为换乘可行门槛，机构可用 `transfers.txt` 的 timed transfer 覆盖【第三方】。⇒ **更准确的说法是：谷歌不改机构发布的线路与时刻本身，但「换乘是否可行」由平台规则裁定。**

**这对我们是一记关键定性**：谷歌范式证明**公交寻路层不需要私有几何数据**——其输入是站点、线路、时刻、换乘关系，全是结构化数据，不含底图。我们的 `route_stations`（DSAT 官方站序/方向）恰属同类资产。⇒ **寻路层自建不卡在数据所有权上**（第 4 章第 ② 层判定的前置）。

高德相反：数据由自己采集生产，我们只买到「授权范围内的使用权」（协议 7.2），且超限即静默失效（见 2.4）。

#### 2.2.2 算法策略：两家都不公开，可借的是学术方案而非厂商实现

高德算法名**未公开**【未查到】；官方 Web 服务指南（更新至 2026-02-02）仍以 v3 为准，参数表中**不存在方案数控制项**【官方】。

谷歌的算法层并非空白，但要分清证据强度：谷歌工程师博客（Maps Directions 团队）写 2010 年公交方向提速「The technique behind that speed-up is the Transfer Patterns algorithm」，该算法在谷歌苏黎世办公室由访问学者 Hannah Bast 与谷歌工程师共同完成；ESA 2010 原文亦自述「We have accelerated public transportation routing on Google Maps with a system based on our ideas」【论文】。**这是关于「谷歌公交寻路用什么」迄今最强的公开证据**，但它是 2010 年陈述，**2026 年 Routes API 背后的当前算法仍【未查到】**。⇒ 「学谷歌」的对象应是它所用的那一类**公开算法**，而非它的实现。

#### 2.2.3 实时路况处理：公交的「实时」是班次流

谷歌把路况偏好严格限定在驾车，且 `TRAFFIC_AWARE` / `TRAFFIC_AWARE_OPTIMAL` 按更高费率结算【官方】；公交请求的「请求差异」第一条即是**无法指定是否包含路况数据**【官方】；公交实时能力改由 GTFS-Realtime 承担（`TripUpdate` 给行程进度与延误预测）【官方】。高德 Web 服务的公交接口同样无路况参数【官方】。

⇒ 两家都没把「路况」接入公交寻路入口。我们 `fetchLive` 的定位是对的，粒度甚至更细（我们要回答「下一班能否赶上」这种门到门问题，`TripUpdate` 只给延误秒数）。**这一维不需要向外部学习。**

#### 2.2.4 多方案生成：数量差是表象，「生成机制」差才是实质

三家数量为 10 / 4 / 2，但更值得注意的是机制：高德的方案集合由**同一引擎的不同目标函数**（`strategy`）产出；谷歌把备选定义为「额外」路线，说明其默认输出是**单一最优 + 少量有意义的分歧**；而我们 `mergeSources` 的闸门 4b 规定**本地候选必须严格快于高德最优才保留**【实测·代码】⇒ 我们的第二来源**只被允许「赢」，不被允许「不一样」**：一个略慢但步行更少或换乘更少的方案，即便产品上有价值，也会被直接丢弃。

⇒ **差距不在数量，而在「多样性目标」**：另外两家能为「更快/更少换乘/更少步行」这类冲突目标各出一案，我们只认「更快」。这是方案 B 的直接改造点。

#### 2.2.5 偏好设置：三家都停在粗粒度开关

高德是策略枚举（0~8），谷歌是「交通方式白名单 + 少步行/少换乘」二选一，我们是固定排序键、零开关。**没有一家提供连续偏好调节**，属行业现状；但**我们连粗粒度开关都没有**——把 `rank.ts:45` 的次要键提升为可选策略（映射高德 `strategy=3/2/5` 或本地权重）成本极低。

### 2.3 学术参照：我们的有界 BFS 是 RAPTOR 的退化雏形

| 算法 | 类型 / 关键性质 | 公开性能数据 | 与我们的关系 |
|---|---|---|---|
| **RAPTOR**（Delling/Pajor/Werneck, ALENEX 2012；期刊版 Transportation Science 2014）【论文】 | **round-based**：一轮 = 一次换乘；**每轮每条线路最多扫一次**；**不依赖预处理**，可完全动态（延误/取消/线路变更）；天然输出「到达时间 × 换乘次数」**Pareto 集**；可并行（线路分配到多核） | 伦敦网络：求全部 Pareto 最优行程比既有方法**快一个数量级**，「easily enables interactive applications」 | **`maxTransfers=2` 的有界 BFS ≈ 只跑 3 轮的 RAPTOR**，同样不依赖预处理。差别在不做 Pareto 输出、上限被写死 |
| **McRAPTOR / rRAPTOR**（同篇扩展）【论文】 | McRAPTOR 支持更多准则（论文示例：票价分区）；rRAPTOR 输出时间范围内全部出发时刻的完整 Pareto 集 | — | rRAPTOR 的「时间范围批量」与我们「按出发时刻给多张卡」的产品形态同构 |
| **CSA**（Dibbelt/Pajor/Strasser/Wagner, JEA 2018）【论文】 | 全部基本连接按出发时间排成**单数组、每查询线性扫一次**；不建图、无优先队列、数据局部性极好；**不用重预处理**，可直接吸收已知延误；已扩展至含随机延误的 MEAT | 伦敦：最早到达查询 **<2ms**；多准则 profile 221ms；MEAT 272ms | 实现复杂度最低的备选；代价是基础版需扫大量无关连接 |
| **Transfer Patterns**（Bast 等, ESA 2010）【论文】 | **预计算型**：存「换乘点序列」，查询时只看少数线路，代价是**放弃一小部分最优性** | 德国平均查询 **0.3ms**（无 hub），约为 Trip-Based（40ms）的 1/100；但常规 TP 预计算 **德国 372 小时 / 140GB**（无 hub）、350 小时（有 hub，少量次优），**全球估 140,000 小时 / 50TB**；Scalable TP 降至德国 16.5h / 1.16GB、全球 2,050h / 30GB【论文】 | **反面对照**：以海量预计算换查询速度，与澳门规模完全不成比例 |

★ 对 Phase 1 两处表述的修正：
1. 「Transfer Patterns 预计算需**数千 CPU 小时**」——方向正确但**需分尺度**：德国尺度是 **372 小时**（常规、无 hub），全球尺度才是数万至十几万小时；本项目不应引用「数千小时」这一中间值【论文】。
2. 「查询**微秒级**」——原始论文实测德国平均 **0.3ms**（约数百微秒），宜表述为「**亚毫秒级**」【论文】。

**从 BFS 升到 RAPTOR：增量在哪里、不在哪里**

- **不在**：不需重建图模型（「线路 × 站序」图已是 RAPTOR 所需的 line network）；不需预处理（RAPTOR 的核心卖点恰是**不依赖预处理**）。澳门 33km² 也远小于公开实验的伦敦/德国量级——**算力不是这条升级的约束**（算力结论归第 4 章）。
- **在**：① **换乘上限从硬编码 2 放开为「按轮自然增长 + Pareto 剪枝」**，直接对准漏线率根因之一；② **输出从「单目标最快若干」变为「到达时间 × 换乘次数」Pareto 集**，正好补上 2.2.4 / 2.2.5 指出的「无多样性目标、无偏好开关」；③ 复杂度由**轮数 × 线路数**决定，而非「K 个近站的两两组合」——**这提示：漏线率 57% 中由「近站 K 截断」贡献的部分，调大 K 只是把截断点后移，治标不治本**（根因量化归第 4 章）。

### 2.4 对「自建」的可移植性小结（为第 4 章埋线）

1. **公交寻路层不依赖私有几何数据**（论证见「本章结论」2），但**几何/步行段仍依赖地图底图**——「站点间步行图」是学术上独立且公认难做的子问题：ATRF 2024 指出，主流算法为使步行图**传递闭包**而引入的大量补充步行边，会让最优解出现**不切实际的超长步行换乘**，同时显著拖慢运行时间，故需专门改进版本【论文】。这从学术侧独立印证「步行/几何层是分离的一层，且是薄弱环节」（我们侧的短距步行 11.9× 失真见第 1 章）。
2. **高德侧的风险是「静默失败」**：协议 3.7 规定「若每秒并发请求量（QPS）超限或调用量超限，**超出的请求将返回无效结果或不返回结果**」【官方】，内部调研亦记录该超限「不是 infocode 报错」【实测】⇒ 我们**无法从单次响应状态区分「澳门确实无公交方案」与「配额/并发超限」**。既有抵御是本地图枚举降级（`nav-service` 的 `degraded` 路径）与 `transit_cache`——能保证「仍出结果」，但**不能保证「结果未被截断」**。
3. **合规边界独立于技术**：协议 14.1 规定本服务原则上仅面向**中国大陆地区且服务器在中国大陆**的开发者，以及中国大陆地区的最终用户，跨境使用需书面通知【官方】。本项目的 Vercel Serverless 与澳门最终用户均在该表述之外——`docs/合规-高德API使用-20260917.md` 已记录 14.1，但未展开**服务器地域**这一层。★ DSAT 侧存在同类门槛，见第 4 章。

### 2.5 澳门本地数据源的可得性（已外迁 · 见第 4 章）

澳门属于**我们自己的环境**而非「外部对照」对象，故其数据源核查（**无官方 GTFS · 时刻表缺口 · DSAT「依申請開放」资格门槛**）移至第 4 章使用，底稿留档于 `附录 A`。★ 该核查**修正了本章结论 4 的前提**：我们缺的不只是算法，还缺**时刻表**这一层输入。

### 本章结论

1. **五维中真正落后的是「数据来源范式」与「多方案生成机制」，不是「实时路况」。** 数据来源上，谷歌是机构发布的 GTFS、我们已有 DSAT 官方站序（同类资产），高德是自有采集（不可复制）；多方案上，`merge-sources.ts:64-68` 的「必须严格快于高德最优」把第二来源限制成「更快的重复」而非「不同的选择」。谷歌的公交同样不吃路况，我们方向正确。
2. **公交寻路层不依赖私有几何数据——这是自建可行性的第一个支撑点，也是第 4 章第 ② 层判定的前置。** 谷歌用机构 GTFS 输入 + 公开算法完成全公交寻路；RAPTOR/CSA 的输入同样不含底图；而**几何/步行层仍须依赖底图**，且该层另有独立难点。
3. **「换乘 ≤2 有界 BFS ≈ 只跑 3 轮的 RAPTOR」，升级增量在输出形态而非算法骨架。** 要改三处：放开换乘轮次、输出「到达时间 × 换乘次数」Pareto 集、以该集补上多样性目标与偏好开关。**调大近站 K 不能替代这一步**——它只移动截断点，不改变轮次与线路覆盖。
4. **Transfer Patterns 路线应明确排除。** 其定义即「用预计算换查询速度、并放弃少量最优性」：德国常规预计算 372 小时 / 140GB，全球估 140,000 小时；对 95 线 / 610 站的澳门规模，亚毫秒查询的收益远不足以抵成本。RAPTOR 才具备「零预处理、规模无关」的匹配性。**★ 但收益估算须与第 4 章合读**：澳门数据源核查表明我们**还缺「时刻表」这一层输入** ⇒ RAPTOR 只能按「按期望时长求最快」形态落地，而非教科书式的「按时刻表最早到达」。
5. **外部依赖侧共识别出三条须独立立项的风险**：高德的「静默失效」（协议 3.7）、高德协议 14.1 的服务器/用户地域限制、以及 **DSAT「依申请开放」的资格门槛（服务器须在澳门本地 + 须在澳门设立服务机构，见第 4 章）**——后者意味着官方实时数据渠道对本项目当前形态大概率不可得。完整推演在第 4 章承接。

> **本章遗留缺口（供第 5 章风险清单承接）**：① 谷歌 2026 年当前生产算法**【未查到】**（仅有 2010 年 Transfer Patterns 的论文级陈述）；② 谷歌对机构数据的「校验与归一化」流程**【未查到】**官方说明；③ 高德公交寻路的算法名与数据来源**【未查到】**官方说明，正文相关判断已全部标【推断】或【第三方】。★ 澳门本地数据源（GTFS / 时刻表 / 换乘 / DSAT 授权关系）的四项缺口属**我们自身环境**，已随 2.5 外迁，见第 4 章及其补遗底稿。

| 分子 | 105 个站对（重算前线上 `segment_stats`） | **886 个物理有向邻接对** |

| 结果 | **105 / 2,750 = 3.8%**（`数据盘点-有什么缺什么-20260918.md:59` 记 3.9%，分母取 ~2,660） | **886 / 996 = 89.0%**（`审查-全澳导航方案-批判性-20260918.md:29`） |
| 本章复核 | —— | **88.96%**，与 89.0% 一致【实测】探针 §3 |

**差异来源**：不是谁算错，而是**分子分母两处口径都不同**。① 分母：旧口径把「A 段被 25、25AX、26 三条线共用」记 3 次，新口径只记 1 次；② 分子：旧口径逐条清点，新口径按物理段归并。

**各自适用范围**：旧口径回答「**每条线自身样本够不够**」——运维采集进度视角；新口径回答「**该物理段有没有可复用实测样本**」——取数视角。

**本报告采用新口径（89.0%）**，理由有二：① 线上取数函数本身要求按「邻接站对」评估并**跨线共享**（`审查-全澳导航方案-批判性-20260918.md:29` 引 `segment-lookup.ts:8-14` 明文要求）；② 若沿用旧口径，会得出「全澳大部分车程必须估算」的错误前提，从而在「DSAT 实测」与「站均估算」之外再插入第三个「高德路网时长」口径，破坏单一口径不变量。

**★ 第二处同类陷阱**：`station_amap_map` 的 93.2% 同样**口径依赖**——主码归一后按行算 93.3%、按站点行 93.6%；**不归一则仅 360/610 = 59.0%**【实测】。⇒ 本章所有覆盖率数字**必须带口径**。

**★ 第三处口径差（行级 vs 物理段级）**：`segment_stats` **行级** `samples ≥ 30` 的仅 **1,590 / 24,161 = 6.6%**（中位 `samples = 3`）；**物理段级**聚合后才是 **819 / 886 = 92.4%**。⇒「92% n≥30」说的是后者，**不能拿它去说行级**：车程数据「够用」靠**跨行聚合**，不是单行厚实。

### 3.6 结论性判断：差异化在数据层，不在算法层

**图（996 段）与车程（886 段有实测）是齐的，算法层的「换乘≤2 有界 BFS」只是 RAPTOR 的退化雏形、可升级；真正稀缺的是数据层三样**——

- **`T_ours` 可解释性**：每一跳能追到 `segment_stats` 的具体行（线路 × 周几 × 时段桶 × `arrive_kind`），外部引擎给不出；
- **逐跳实测来源**：181,713 段样本 + 60,544 行原始样本，两条采集链**无系统性偏差**（比值中位 0.989）；
- **澳门本地细节**：穿梭巴士过滤、轻轨在建站桥接、`lrt_timetables` 时刻表——高德/谷歌都不会替我们做的脏活。

反过来：**算法替换（BFS → RAPTOR）不解决任何数据缺口；几何层缺口靠换算法也补不上。**

### 本章结论

1. **资产是「结构齐、车程密、几何空」的三段式**：图 2,870 行 / 95 线 / 119 方向 / 610 站**无缺口**（seq 零断裂），`segment_stats` 181,713 样本覆盖 996 个物理有向邻接对中的 886 个；而**步行几何、票价、无障碍三项结构性缺失**（票价/无障碍为全库零表零列）。★ 换乘关系**已移出「结构缺失」档**（见第 4 条）。
2. **覆盖率必须双口径并列陈述，本报告采用 89.0%**：旧口径 105/2,750 = 3.8%（每线×邻接对）与 QA 口径 886/996 = 89.0%（物理有向邻接对）分子分母定义均不同；采用后者的理由是它与 `lookupHop` 的 L4 跨线共享取数语义一致。**同一陷阱在 `station_amap_map` 上重现**（主码归一 93.3% vs 原始码 59.0%）。
3. **「92% 样本 n≥30」是物理段级口径，行级只有 6.6%（1,590/24,161，中位 `samples=3`）**：车程数据「够用」靠的是跨行聚合，不是单行厚实——这直接决定了第 4 章算力与预计算量的估算基线。
4. **最薄弱两环 = 【跨主码换乘不建模】+ 无 ground truth**：澳门换乘以「同主码站群」为主流（86.1% 主码多线共用，站内跨度中位 33 m），`transfer_walks` 2 条是**设计收窄**而非缺口；真问题是本地 BFS 不建模跨主码换乘（量级**样本依赖**：独立复核 22.5% / 首轮 5.6%）+ 换乘段**已事实依赖高德**。无真值 ⇒ 一切「更准」主张只能靠代理指标（档 3 平均绝对偏差 0.58 分、双来源比值中位 0.989）。★ **漏线率 57%/41%/26.4% 是第三短板，根因是「候选数上限截断（cap）」（生产口径 59.6%）而非初稿所写的「K 太小」（21.3%）**。
5. **差异化落在数据层**：可解释的 `T_ours`、逐跳实测来源、澳门本地细节（穿梭巴士过滤 / 桥接站码 / 轻轨时刻表）是本项目真正的护城河；⇒ 第 4 章三层判定的预判方向：**时间计算与排序层无需再自建，几何层补不上，候选寻路层才是最有增量的那一层**。

### 4.1 ★ 前置命题：「自建」不是布尔问题

「要不要自建路线规划」在本项目里**无法回答**，因为「路线规划」是三件彼此正交的事【实测】（第 1 章 §1.2）：① **几何/步行路由层**（失败表现为「距离不对」）② **候选寻路层**（「方案没给」）③ **时间计算与排序层**（「排序说不清对不对」）。三层的数据依赖、失败模式、可替换性完全不同；压成一句「自建还是不自建」，必然得到半对半错的答案。

展开前须先接受**两条来自前三章的前提修正**：

- **修正一 · 时刻表缺口**：澳门**没有官方 GTFS**，DSAT 数据目录中【無班次/時刻表 · 無換乘 · 無票價】【官方】；我们的 `segment_stats` 是**站间时长统计**而非时刻表。而 RAPTOR/CSA 的经典形态需要「线路 + 时刻」⇒ **即便自建 RAPTOR，也做不了「按时刻表求最早到达」，只能做「按期望时长求最快」**（第 2 章补遗 §2.5）。⇒ 方案 B 的收益上限必须按后者估。
- **修正二 · 换乘风险转移**：`transfer_walks` 仅 2 条**不是缺口**——该表只服务「轻轨站内换乘」，澳门全域仅 2 处；同站换乘才是主流（467 主码中 402 个、86.1% 被 ≥2 线共用；站内跨度中位 33 m ≈ 24 秒）【实测】。**风险已转移到算法层与几何层**：① **【跨主码换乘不建模】**（`graph-search.ts:19-21` 代码自认，量级见 §4.2② / §4.6.2）；② `recompute.ts:161-162` 的巴士↔巴士换乘**线上已用「高德距离 ÷ 84」**。★ 这两点与第 3 章补充 §3A.5 所述为**同一组风险**，不是新增风险。

**逐层要点补充：**

- **①层最硬的论据是短距失真**：直线 41 m → 高德 492 m（**11.9×**），而首末段典型恰为 50~300 m【实测】（第 1 章 §1.7⑥）。偏差会推高 `baseMin` ⇒ `pickCatchTier` 压档 ⇒ **把本可赶上的最优方案整条剔除**。学术侧独立印证该层是公认薄弱环节（ATRF 2024，第 2 章 §2.4）。
- ★ **①层「无合法来源」须改为「有免费来源但质量不足」**（补充 §4S.1.3）：**OSM（ODbL 1.0）是免费合法的澳门几何来源**（`macau.pbf` 3.48 MB · 日更）。★ **关键区别是「许可方向」而非「有 / 无」**——**DSCC 禁止**复制/改编/分发（参数卡 §三），**OSM 附条件允许**（署名 + 衍生库 share-alike），二者结论相反；把二者混为「都不可用」会漏掉 OSM。
- ⚠️ **证据等级**：OSM 澳门维基的覆盖判断是**社区自评**（`osm.wiki/wiki/Macau`）【第三方·社区自评，**非官方测绘**】：`行人路徑` 在路氹城「繪製完成」，但 **澳門半島「有待完善」、澳門大學（橫琴島）「有待完善」**。
- ⇒ **对①层的影响**：这两处正是核心走廊（home/school + 澳大横琴）⇒ **方案 C 由「底图从零建」降级为「在免费底图上自采补强」，成本「极高」→「高」，但 ❌ 判定不变**。
- **②层的升级增量不在算法骨架，在输出形态**：**不在**图模型（已是 line network）、**不在**预处理、**不在**算力；**在** ① 放开硬编码换乘 ≤2、② 输出「到达时间 × 换乘次数」Pareto 集。②项还有直接产品收益：`merge-sources.ts:64-68` 规定**本地候选必须严格快于高德最优才保留**⇒ 第二来源**只被允许「赢」，不被允许「不一样」**（第 2 章 §2.2.4）——略慢但少步行/少换乘的方案被丢弃。★ 边界：复杂度由「轮数 × 线路数」决定，**不是**「K 个近站的两两组合」⇒ **调大 K 只是把截断点后移，治标不治本**。
- **③层才是差异化所在**：`T_ours` 的逐跳可解释性、逐跳实测来源、澳门本地脏活（穿梭巴士过滤/在建站桥接/轻轨时刻表）（第 3 章 §3.6）⇒ 任何自建方案都不应重写③层。
- ★★ **②层还有一个算法层缺口，且现已能量化：【跨主码换乘不建模】**——`graph-search.ts:19-21` 自认「换乘按同一主码处理 ⇒ 换乘步行计 0；真实的跨街换乘不建模 ⇒ 本地候选取时偏乐观」。**在独立复核样本中它占漏线的 22.5%（第 2 大项）**，首轮样本以「换乘点本库不共站」为代理指标测得 5.6% ⇒ **幅度样本依赖**（见 §4.6.2）。⚠️ **它与第 3 章补充 §3A.5 的「算法层」是同一项风险，不是两条独立风险**；亦**不是**「换乘数据缺失」——`transfer_walks` 仅 2 条属设计收窄（第 3 章补充 §3A.1）。

### 4.3 算力测算：RAPTOR 在澳门的量级

以库内实测规模（95 线 / 119 方向 / 610 站 / 2,870 行 ⇒ 平均 24.1 站/方向；467 主码）套 RAPTOR 公开复杂度 `O(轮数 × 线路数 × 平均站/方向)`，按每站点事件 20~100 ns 估算【推断·方法见 `.verify/ch4-compute-estimate.ts`】：

| 场景 | 计算量 | 量级结论 |
|---|---|---|
| **单次查询** R=3（换乘 ≤2）/ R=4 / R=5 | 285 / 380 / 475 次线路扫描，≈6.9k / 9.2k / 11.5k 站点事件 | **0.14~0.69 / 0.18~0.92 / 0.23~1.15 ms** |
| **全量预计算**（全源最早到达矩阵） | 467 主码 × 35 情景（7 周几 × 5 时段桶）= **16,345 次**单源运行 | **16 s ~ 82 s**；Pareto 多标签按 2~4× 放大后仍约 **5 分钟** |

三条读法：① **单次查询落在「亚毫秒~1 毫秒」**，与 CSA 在伦敦的 `<2 ms` 同量级（第 2 章 §2.3）——澳门规模小约两个数量级，**算力完全不是约束**；② **全量预计算是分钟级**，可离线按情景整表刷新，不需要 TP 式重度预计算（德国常规 TP 372 小时 / 140 GB，差四个数量级以上 ⇒ **TP 路线明确排除**）；③ **算力充裕不改变数据缺口**——缺时刻表就只能求「期望时长最快」，缺 ground truth 就无法证明算得对，**算力结论只解除一个维度，不构成自建理由**。

### 4.4 成本维度

**(1) 高德配额与超额行为。** 配额 **基础 LBS 150,000 次/月 · 基础搜索 5,000 次/月 · QPS 3/s**，每次「出发」消耗 1 次 `transit/integrated` ⇒ 折合**日均约 5,000 次出发**。风险不在钱：协议 3.7 规定超限请求「**返回无效结果或不返回结果**」【官方】⇒ **无法从单次响应区分「澳门确实无方案」与「配额/并发超限」**；既有抵御（本地降级 + `transit_cache`）保证「仍出结果」，**不保证「结果未被截断」**。协议 14.1 的地域限制（Vercel 海外部署 + 澳门用户均在其表述之外）是「维持现状」也躲不掉的合规成本。

**(2) DSCC 地理资讯库的硬边界。** `mapapi.gis.gov.mo` 为 Token + 免费额度/付费计费，但条款写明「**未经书面许可严禁复制/改编/分发/向公众提供，不得商业用途**」「只供参考，不具法律效力」【官方】⇒ 可用边界是**「查询时调用」而非「批量抓取入库」**。★ 须与 OSM 区分（§4.2 要点）：**这是「许可方向」差异——DSCC 禁止，OSM（ODbL）附条件允许**；把二者都读成「不可用」会漏掉 OSM。

**(3) DSAT 依申请开放的资格门槛。** 「巴士定位數據」为**依申請開放**且当前状态「否」，要求**服务器设在澳门本地** + **在澳门设立服务机构** + 资格审查 + 保密协议【官方】⇒ 本项目当前形态**大概率不符合资格**；现用 `macauweb` 接口属 App 后端，其与该目录的授权关系**【未查到】** ⇒ **须单列合规确认项**。

**(4) 自研与维护成本的口径。** 按参数卡拍板，**不提供工时/排期估算**，只给性质：维护成本是**持续型而非一次性**——采集链连续运行（18 轮 / 16 天）· 站码映射人工复核（935 行 / 436 主码）· 每次算法改动都需代理指标回归 · 外部条款跟踪（高德 3.7/14.1、DSCC、DSAT）。⇒ 「成本量级」按此口径标注。

**(5) ★ 覆盖率天花板可突破，但不是低成本改进。** 第 3 章补充已推翻「110 段不可测」：**0 段不可测**，且离线样本早已入库（`segment_samples` 60,544 行），**入库后覆盖仍是 886** ⇒ 继续灌库不是提升路径；补齐需**夜线夜采（44 段）+ 轻轨专用通道（氹仔线 18 段 + 横琴线 2 段）+ 扩轮次**三条路径。⇒ **本章不写「覆盖率可提到 ~100%」这类无成本结论**。

### 本章结论

1. **「自建」必须分层判定——方法论核心。** 三层四维得三种答案：① 几何/步行层 **❌ 不自建**（唯一真正缺基础数据的一层；短距失真 11.9× 命中首末段典型 50~300 m；★ **OSM 是免费合法来源但核心走廊自评不足，DSCC 则是禁止——属「许可方向」差异**）；② 候选寻路层 **⚠️ 有条件自建**（技术成熟、算力无忧、站序官方无条件开放，但缺时刻表与 ground truth）；③ 时间与排序层 **✅ 无需再自建**（早已自建，且是差异化所在）。
2. **算力不构成约束，且这一条不构成自建理由。** 单次 RAPTOR 查询 **0.14~1.15 ms**（R=3~5）；全源最早到达矩阵全量预计算 **16 s ~ 82 s**、含 Pareto 放大后约 5 分钟 ⇒ 与 Transfer Patterns 的德国 372 小时差四个数量级，**TP 应排除**。
3. **方案推荐：以 D（混合）为主线、B 为其完整形态、E 先询价 + 先确认授权；C 排除；A 作回退基线。** 理由：`recompute.ts:161-162` 证明「几何外包」在换乘段**事实上就依赖高德**，故只需显式记账、不必额外付代价。★ E 的市场扫描已找到候选（**Moovit** 澳门覆盖明确、API 含 schedule、**需询价**；Ito 覆盖未证实；MapKing 仅路况），且 **E 的前置条件第 1 条不是价格，而是「授权范围是否允许公开可访问的 PWA 使用」**——`license=Commercial` 多附品牌展示/禁缓存/限用途条款，可能与本项目「个人非商业」定位直接冲突。
4. **方案 B/D 的收益上限只被一条约束封顶，另一条已被实测解除（并经独立复核 · 三批 OD）**：① **仍封顶的是「无时刻表」** ⇒ 只能按「**期望时长求最快**」落地，做不了按时刻表最早到达的教科书 Pareto 集；② ★ **「漏线率硬地板」已被解除**——残余主因是**候选数上限截断而非数据缺口**（合并三批口径 cap 占 **46.1%**、为第 2 名的 **2.4 倍**，且是**唯一三批都进前 2** 的项；`__amap_` 线路级映射**三批全为 0**）⇒ **单修「候选上限按阶段分配（重点：1 换乘阶段的同线路链多变体去重）」即可 20.5% → 8.6%（达标 <10%）**，RAPTOR 化的价值因此**回到「输出形态（换乘轮次 + Pareto 多样性）」而非补漏**。⚠️ 该 pp 为**下界**（最宽配置仍触顶）；⚠️ ★★ **「单项达标」为样本条件性**（b3 半島腹地样本单修 cap 仅到 **20.13%**，未达标 —— 见 §4.6.2(a′)）；★ **第 2 名三项并列、不可排序**（cap 之外的占比随 OD 区域在 2.5%~28.6% 间摆动，**按修复成本而非占比排序**）；★ hub 限量**不再写作「恒为 0」**（第三批首现 2 条 4.1%，b2 的结构性证明随之收窄为样本性质）。详见 §4.6.2。
5. **成本与验证两类的实际约束都不是「精度」**：高德超额**静默失效**（协议 3.7）使故障不可观测、14.1 地域条款连「维持现状」也躲不掉；**几何层须区分许可方向**（DSCC 禁止 vs OSM 附条件允许）；DSAT「依申請開放」要求**服务器在澳门本地 + 设服务机构**，本项目大概率不符合资格、现用 `macauweb` 接口授权关系**【未查到】**；覆盖率**结构上可突破 89%** 但代价是**夜采 + 轻轨专用通道 + 扩轮次**，非低成本改进。验证只能用**代理指标**（档 3 偏差 0.58 分 / 比值中位 0.989 / 追踪式定点车对照 / 阴影对照 / Scientific Data 2025 外部数据集共**五个**），**不能支撑「我们更准」**；外部数据集仅 4 线 / 2024 且源同为 DSAT App ⇒ **独立推导而非独立真值**。

|---|---|---|
| 1 | 候选上限按阶段分配（打在 **1 换乘阶段变体去重**） | 阴影对照漏线率 **≤10%** 且主路径候选数未降 |
| 2 | 站码映射覆盖补齐（**首修站名异体字/写法折叠**，如「荷兰园栢蕙/柏蕙」；含 LRT 跨线）· **并列**近站集覆盖 · **并列**跨主码换乘不建模（★ 三者按**成本**升序推进，不按占比） | 映射失败归零；近站集含高德选中站；跨主码换乘不再计 0 |
| 3 | RAPTOR 化**只改输出形态** + 修 `merge-sources.ts:64-68`「只许赢不许不同」 | 「少步行 / 少换乘」能产出不同方案 |
| 4 | **并行**：E 发一轮询价（Moovit 优先） | **先确认授权范围是否允许公开 PWA 提供** |

**止损**：① 步骤 1 后仍 >10% 且残余为**数据缺口** ⇒ 停投 B/D；② 达标后不再以「补漏」为由 RAPTOR 化；③ **E 若授权范围不通过 ⇒ 直接否掉，无论价格**。

### 5.4 风险与不确定性

| 风险 | 要点 |
|---|---|
| **无 ground truth** | 决定**结论上限**：五类代理（档 3 偏差 0.58 分 · 比值 0.989 · 定点车 · 阴影对照 · Scientific Data 2025）**只能支撑相对性结论**；外部集仅 4 线 / 2024，源同为 DSAT App ⇒ **独立推导 ≠ 独立真值** |
| **缺口与条款变更** | 谷歌 2026 生产算法【未查到】；澳门境外地图服务法规【未查到】⇒ 单列确认；高德 **3.7 静默失效** + **14.1 地域条款**；DSCC 禁止复制 / 改编 / 分发 / 向公众提供；DSAT「依申請開放」须**服务器在澳门本地 + 设服务机构** ⇒ 大概率不合资格 |
| **三处须降级** | ① 四配置**不完全正交**（C→D 同改 k 与 radius ⇒ 7.7 pp 非纯半径贡献；★ **cap 合并三批仍第 1——抬 K 修不掉大部分漏线；但单批 b3 为三项并列**）② 算力测算是**量级推导非真基准**（20~100 ns 系 JS 外推【推断】）③ 33 km² 未独立核实 |
| **B/D 上限** | **无时刻表** ⇒ 收益只能按「期望时长最快」估 |

### 5.5 不建议做的事项

| 不建议 | 论证 |
|---|---|
| ① 为几何层自建 | OSM 核心走廊不足 · DSCC 禁止 · 自采贵 ⇒ 解在**修短距修正规则并统一口径**（实现 `min(高德, 直线×2.5)` vs 设计 ×1.5） |
| ② 上 Transfer Patterns 或为「补漏」而 RAPTOR 化 | 德国预计算 372 小时 / 140 GB（差四个数量级）；达标只需候选上限一项 |
| ③ 继续「灌库」提覆盖率 | 60,544 行已入库、覆盖仍 886；须**夜采 + 轻轨通道 + 扩轮次** |
| ④ 用高德距离补换乘步行 | 站内 33 m 被读成 200~400 m ⇒ 多算 **2.4~4.8 分**（真值 ≈0.4），**比「计 0」更差** |
| ⑤ 重写③层 / 把 E 当优先项 | ③ 层是护城河；E 的第 1 前置是**授权范围**，且无公开报价 |

### 本章结论

1. **分层立场：② 有条件自建 · ① 不自建 · ③ 无需再自建。** 决策是「**只把②层的枚举与输出形态拿回来，几何继续外包、时间层不动**」。
2. **第 1 前置经独立复核三批 OD 复现为「唯一都进前 2」的项**：修枚举的候选数控制（首轮 −11.9 pp ⇒ 8.6%；复核 b2 38.46% → 8.65%；机制更正为「**1 换乘阶段的同线路链多变体去重**」；**合并 b2+b3 口径 cap 占 46.1%，为第 2 名 2.4 倍**）。⚠️ ★★ **但「单项即达标 <10%」是样本条件性的**：第三批 b3（半島腹地锚点）**30.82% → 20.13%，单修 cap 不达标** ⇒ 该结论只对「離島/口岸/路環起讫」的 OD 成立。★ **第 2 位三项并列且不排序**（占比在不同 OD 区域摆动 2.5%~28.6% ⇒ **按修复成本排序**）：① 站码映射覆盖补齐（b3 的 28.6% 全部来自「荷兰园**栢**蕙/柏蕙」**一个站名变体**）② 近站集覆盖 ③ 跨主码换乘不建模。
3. **推荐 D 为主线、B 为完整形态、E 有条件、C 排除、A 作回退基线；「达标 <10% 不需要先上 RAPTOR」** ⇒ RAPTOR 价值回到**输出形态**（换乘轮次 + Pareto 多样性）。⚠️ 「达标 <10%」需限定：**離島/口岸/路環起讫样本**下修 cap 单项即可；**半島腹地起讫样本**需 cap + 站名变体补齐 + 近站集覆盖（b3 单修 cap 为 20.13%）。
4. **两条硬约束封顶：无时刻表、无 ground truth；`transfer_walks` 不再是风险项**（设计收窄）⇒ ★ 但**换乘并未因此缓解**：风险已转移到**跨主码换乘不建模**（三批 5.6 / 22.5 / 10.2%，并列第 2 之一）与**换乘步行依赖高德**。
5. **一句话最终建议：先以「候选上限按阶段分配」（打在 1 换乘阶段变体去重）启动；第 2 位三项并列，按修复成本推进「站名映射补齐 → 近站集覆盖 → 跨主码换乘建模」；然后补②层输出形态；几何层继续外包、时间层不动；外部采购只做一轮询价且先确认授权范围。** ⚠️ hub 限量**不再写作「恒为 0」**（第三批首现 2 条 / 4.1%）。

## 结论

> 本节是**全报告的总括性结论**，不重复第 5 章 §5.1–§5.5 的分层结论、推进顺序与负面清单；需要展开时以第 5 章为准。

### 结论一 · 一句话总答案

**该自建——但只建一层：把 ② 候选寻路层的「枚举」与「输出形态」拿回来；① 几何/步行层继续外包给高德，③ 时间计算与排序层不动。**

理由一句话：`recompute.ts:161-162` 证明「几何外包」在换乘段**事实上已经在依赖高德**（巴士↔巴士换乘线上已用「高德距离 ÷ 84」），所以几何继续外包不必额外付代价、只需把依赖显式记账；而 ③ 层（`lookupHop` 6 级回退链 + `T_ours`）是**我们真正的护城河**，任何自建方案都不应重写它。

### 结论二 · 三层的最终判定

| 层 | 判定 | 最关键的一条理由 |
|---|---|---|
| **① 几何/步行路由** | ❌ **不自建** | 唯一真正缺基础数据的一层：高德短距步行失真 **11.9×**（直线 41 m → 高德 492 m），而首末段典型恰为 **50~300 m** ⇒ 会把本可赶上的最优方案整条剔除。★ 理由**不是**「无合法来源」——**OSM（ODbL）免费合法，但澳门半岛 / 澳大（横琴）行人路径自评不足**（正落在核心走廊），**DSCC 是禁止** ⇒ 属**许可方向**差异 |
| **② 候选寻路** | ⚠️ **有条件自建** | 技术成熟（换乘 ≤2 有界 BFS 已是 RAPTOR 退化雏形、RAPTOR 不依赖预处理）、算力无忧、站序数据官方**无条件开放**；但**缺时刻表、缺 ground truth** ⇒ 收益与结论强度双重封顶 |
| **③ 时间计算与排序** | ✅ **无需再自建** | 早已自建且是差异化所在（`lookupHop` L1~L4 实测 / L5~L6 估算，L4 跨线共享把逐跳命中率从 52.8% 抬到 76.8%）；物理有向邻接对覆盖 **886/996 = 89.0%**、其中 **92.4% `n≥30`** |

### 结论三 · 推荐路径

**D（混合）为主线 · B（只自建寻路层）为其完整形态 · E（外部采购/授权）有条件 · C（全自建）排除 · A（维持现状）作回退基线。**

- **B 与 D 是同一改造的两种边界**：D 是 B 的省钱版，代价是把几何依赖显式留在账单上。
- **C 因 ① 层无「低成本即可用」的数据路径而结构性不成立**（OSM 免费但核心走廊不足、DSCC 禁止、自采成本高）。
- **E 是唯一可能解开时刻表死结的方向**，但其**前置条件第 1 条不是价格，而是「授权范围是否允许公开可访问的 PWA 使用」**（商业 API 的 `license=Commercial` 多附品牌展示 / 禁缓存 / 限用途条款，可能与本项目「个人非商业」定位直接冲突）；候选已找到（**Moovit** 澳门覆盖明确、API 含 schedule，需询价；Ito World 覆盖未证实；MapKing 仅路况）。

### 结论四 · 最强的一条发现

**「达标 <10%」不需要先上 RAPTOR——单修「候选上限按阶段分配」即可。**

- 首轮实测：残余漏线率 **20.5%**，第 1 大主因是**候选数上限截断（cap）占 58.3% / 11.9 pp**；单项修复「**按阶段分配名额 · 重点是 1 换乘阶段的「同线路链多变体」去重**」后 ⇒ **20.5% → 8.6%，单项即达标 <10%**【首轮样本实测】。
- 独立复核以**另一套 30 个 OD · 另一套口径 · 另一个探针**复现了同一结论：**38.46% → 8.65%**（同样跨过 10% 线）。
- 被否证的旧归因：**线路级 `__amap_` 站码映射失败 = 0 条、hub 限量 = 0 条**（后者另有**结构性证明**——样本漏链全 ≤2 腿，而 `hubLimit` 只作用于 2 换乘阶段）。
- ⇒ **RAPTOR 化的价值因此回到它本来的位置：输出形态（放开换乘轮次 + 「到达时间 × 换乘次数」Pareto 多样性），而不是补漏。**

⚠️ 三条限定不可省：① pp 是**下界**；② 以上数字**不可跨样本外推**（首轮 `−11.9 pp` 与复核 `38.46% → 8.65%` 是两个样本各自的实测值）；③ **第 2 名及以后为样本依赖**。

### 结论五 · 两条硬约束

| 硬约束 | 内涵 | 后果 |
|---|---|---|
| **无时刻表** | 澳门**没有官方 GTFS**；DSAT 数据目录中**无班次/时刻表 · 无换乘 · 无票价**；我们的 `segment_stats` 是**站间时长统计**而非时刻表【官方】 | 即便自建 RAPTOR，也**做不了「按时刻表求最早到达」，只能做「按期望时长求最快」** ⇒ B/D 的收益上限按后者估 |
| **无 ground truth** | 无独立真值集；只能用五个代理手段（档 3 偏差 0.58 分 / 比值中位 0.989 / 定点车对照 / 阴影对照 / Scientific Data 2025 外部数据集） | 一切「我们更准」的主张**只能相对表述**；外部数据集仅 **4 条线 / 2024 年**且源同为 DSAT App ⇒ **独立推导 ≠ 独立真值** |

另有一条**合规硬边界**须单列确认：高德协议 **3.7 超限静默失效**（无法区分「澳门确实无方案」与「配额/并发超限」）与 **14.1 地域条款**、DSCC **禁止复制/改编/分发/向公众提供**、DSAT「依申請開放」要求**服务器在澳门本地 + 在澳门设立服务机构**（本项目当前形态大概率不符合资格）。

### 结论六 · 负面结论（不展开 · 论证见第 5 章 §5.5）

不建议做五件事：① 为几何层自建；② 上 Transfer Patterns、或为「补漏」而 RAPTOR 化；③ 继续「灌库」提覆盖率（60,544 行已入库、覆盖仍 886）；④ 用高德距离补换乘步行（站内 33 m 被读成 200~400 m ⇒ 多算 2.4~4.8 分，**比「计 0」更差**）；⑤ 重写 ③ 层、或把 E 当优先项。

### 结论七 · 第 2 前置的定稿口径：三项并列，按「修复成本」排序（不再按占比）

**第 2 位 = 三项并列**，★ **按修复成本升序推进，不按占比排序**：

| 第 2 位（并列） | 修复动作 | 成本 | 实测占比（三批） |
|---|---|---|---|
| ① 站码映射覆盖补齐 | 补 1 行映射 + `normalizeName` 折叠异体字（栢/柏）与「X/Y」「XY」写法 | **最低** | 19.4% / 2.5% / **28.6%** |
| ② 近站集覆盖 | 放宽 `k`（40 → 更大）或把高德选中的上/下车站**并入候选站集** | 1 个参数 | 13.9% / 7.5% / **28.6%** |
| ③ 跨主码换乘建模 | 需 `transfer_walks` 之外的**跨街步行**数据 | **最高** | 5.6% / **22.5%** / 10.2% |

★ **为什么不按占比排序**：三项占比由 **OD 锚点落在哪个区域**决定，而不是由问题严重程度决定——同一根因可摆动 **2.2~11 倍**（站码映射 2.5% → 28.6%；近站集 7.5% → 28.6%；跨主码换乘 22.5% → 10.2%）⇒ **用占比给第 2 名排序在方法上无效**（第 4 章 §4.6.2、附录 D §6）。

★ **第 1 前置（修枚举的候选数控制）仍是唯一三批都进前 2 名的归因**：合并 b2+b3（Σ漏 89）占 **46.1%**，为第 2 名（**19.1%**）的 **2.4 倍**。

★★ 但须连带更正一条口径：**「单修 cap 即单项达标 <10%」是【样本条件性】结论，不是无条件结论**——

- **成立**：首轮（離島 / 口岸样本）**20.5% → 8.6%** ✅；b2（離島站点锚点）**38.46% → 8.65%** ✅
- **反例**：b3（半島腹地锚点）**30.82% → 20.13%** ❌ ⇒ 该区域需 **cap + 站名变体补齐 + 近站集覆盖** 三者合力；即便把「站名变体补 1 行」算作同一批小改，b3 也只到 **约 11%**，仍略高于 10%。

★ **b3 那条「站码映射失败」的根因已定位到一个异体字**：库内为「荷兰园**柏**蕙」、高德 v5 实际返回「荷兰园**栢**蕙」，`normalizeName` 不折叠异体字 ⇒ 匹配 0 行；b3 该桶的 **14 条全部**源自这一个站名变体 ⇒ **补 1 行即解** —— 这正是「按修复成本排序」的由来。

> **留痕**：本节原标题为「一项明确留待复核（本报告不下定论）」，因第 2 前置当时仍在等第三批 OD 复核。**第三批（b3）已落盘并闭合该问题**，故按定稿口径改写；首轮 / b2 / b3 三批的完整对照见第 5 章 §5.2 与附录 D §5、§6。

#### 2.5 补充核查：澳门 GTFS 可得性（决定第 4 章方案 B）

> 本节为补查追加。来源：DSAT《交通數據開放管理（試行）辦法》PDF（`https://www.dsat.gov.mo/pdf/交通事務局交通數據開放管理（試行）辦法.pdf`，已下载至 `.verify/dsat-open-data-policy.pdf`）、[data.gov.mo 巴士路線資料](https://data.gov.mo/Detail?id=e7b2e84d-3333-42f0-b676-64ce95306f0d)、[Transitland](https://www.transit.land/search?q=Macau)、[澳門輕軌官网](https://www.mlm.com.mo/tc/route.html)。

**结论：澳门没有官方 GTFS / GTFS-Realtime。** 三路证据互不矛盾：

**(a)【官方】DSAT 的数据开放清单本身就否证了 GTFS。** 该办法附有完整「數據目錄」，逐项列明数据类型、描述、更新频率、开放方式与是否已开放。巴士类全部条目：

| 项 | 數據名稱 | 類型 | 數據描述（原文要点） | 開放方式 | 已開放 |
|---|---|---|---|---|---|
| 1.1 | 巴士定位數據 | **動態** | 車輛識別代號、日期時間、經度、緯度、海拔高度、速度、行車方向（10 秒） | **依申請開放**·接口訪問 | **否** |
| 1.2 | 巴士路線資料 | **靜態** | 站點序號、站點名稱、途經巴士路線、**路段序號、路線序號、方向**、巴士公司名稱、巴士路線編號 | **無條件開放**·網站下載 | **是** |
| 1.3–1.5 | 巴士數量 / 公共巴士站總數 / 巴士司機數量 | 靜態 | 統計類（年份、項目、總數、月份） | 無條件開放 | 是 |

⇒ 已见条目中**无 GTFS、无班次/時刻表、无换乘、无票价**项。另**依申請開放的资格门槛很硬**（第 4.1–4.2 条原文要点）：须通过资格审查、**平台服务器设置在澳门本地**、**在澳门设立服务机构**并有办公场所与技术与营运人员；审核通过须签**数据开放保密协议**，不得披露或出售数据。

**(b)【官方】data.gov.mo「巴士路線資料」**（DSAT 提供，**完全開放**）：文件为 `BUS_POLE.SHP`（巴士站）、`ROUTE_NETWORK.SHP`（路線數據）、`BUS_ROUTE_SEQ`（路線與站點對照表＝站序）；字段含 `POLE_ID`、`SID`、`P_NAME`/`P_NAME_POR`/`P_NAME_EN`（**中葡英三语站名**）、`ROUTE_NOS`；**格式为 SHAPEFILE / XLS，非 GTFS**；末次更新 2026-09-12。平台《用戶幫助》明确「对于完全开放数据，无须登入即可取得及使用」「**无须另行得到提供数据的公共部门或实体的书面授权**」【官方】。

**(c)【第三方】旁证**：Transitland（收录 55+ 国的 GTFS/GTFS-Realtime）检索 "Macau" 仅得 **1 个 feed：`f-getaround~macau~gbfs`，属 GBFS（共享单车/滑板车），非公交 GTFS**；其余命中均在澳大利亚、法国与香港（地名假阳性）。澳门轻轨官网有按站查询的「列車出發時刻表」，但**是网页内容，非机器可读 Feed**。Google Transit 以「机构自行发布静态数据」为前提，未见澳门机构参与的证据【未查到】。

**⇒ 对第 4 章方案 B 的影响：中性偏「风险升级」**

| 面 | 判定 | 依据 |
|---|---|---|
| 站序 / 线路拓扑 | ✅ **利好** | 官方**无条件开放**、含方向与路段序号、中葡英三语站名，且明确无需书面授权 ⇒ 站序依赖安全（葡/英站名对本地化关键词库是额外收获） |
| **班次 / 时刻表** | 🔴 **风险升级（新发现）** | 官方目录**无時刻表类数据**。RAPTOR/CSA 的经典形态需要「线路 + 时刻」，我们的 `segment_stats` 是**站间时长统计**而非时刻表 ⇒ **即便自建 RAPTOR，也做不了「按时刻表求最早到达」，只能做「按期望时长求最快」的变体**。这修正了「有 RAPTOR 就够了」的简化判断 |
| **换乘关系** | 🔴 **风险不变（未缓解）** | 目录无換乘项 ⇒ `transfer_walks` 仅 2 条的缺口**不会因官方开放而解决**，仍需自采或借助地图步行 API |
| **实时数据** | 🔴 **风险升级** | 巴士定位数据为「依申请开放」且当前「**否**」，资格要求服务器在澳门本地 + 在澳门设立服务机构 ⇒ 本项目（Vercel 海外部署、个人身份）**大概率不符合资格**。现用的 `bis.dsat.gov.mo:37812/macauweb` 属 App 后端接口，其与本目录的授权关系【未查到】，须在第 4 章合规章节单独确认 |
| 轻轨时刻表 | 🟡 维持自建 | 官网只有网页查询，无 Feed |

**一句话**：澳门**有官方「线路 + 站序」静态开放数据，但没有 GTFS、没有班次时刻表、没有换乘数据** ⇒ 方案 B 的「站序/拓扑」依赖安全，但**「时刻表 + 换乘关系」两项缺口不因官方开放而解决**，应新增前置条件：**在追求「按时刻表最优到达」前，先解决时刻表来源（自采班次，或明确改用 `segment_stats` 期望时长并声明口径差异）**。

#### 3A `transfer_walks` 的真实定位与影响面

##### 3A.1 它不是「换乘数据没采」，而是一张被设计收窄的窄表

库内 2 行的 `samples = 0`、`source = 'manual'`、`measured_at = NULL`——这是**人工常量**的指纹，不是缺失的实测。代码证据：

- `src/lib/recommend/model.ts:15` 明文定死口径：
  「`transfer`：**同场（站码相同且非轻轨）= 0**；**轻轨站内换乘读 `transfer_walks`** 」
- `src/lib/rebuild/transfer-walks.ts:152-155`（`MANUAL_TRANSFER_MIN`）逐个点名这两行：
  - `LRT-UH→LRT-UH` 3.0 分 =「協和醫院站內換乘（石排灣線↔氹仔線）」，**实测 2.9 分（n=9, 2026-09-15）取整**
  - `LRT-LOT→LRT-LOT` 4.0 分 =「蓮花站內換乘（氹仔線↔橫琴線）」，**无实测，按站台布局人工估算**
- 该表另有 timer 派生通道（`source='timer'`，`transfer-walks.ts:257-260`），**当前 0 行** —— 即采集链从未产出过换乘样本

⇒ `transfer_walks` 的设计用途只有「**同场但步行不可忽略**」这一种情形，而澳门全域**只有 2 处**满足（轻轨跨线站内换乘）。**2 条 = 场景全覆盖**，不是「2 / 应有几百」。

##### 3A.2 澳门是否普遍「同站换乘」——结论：是，且可量化

| # | 证据 | 数值 | 来源 |
|---|---|---|---|
| 1 | 主码被多线共用 | 467 主码中 **402 个（86.1%）被 ≥2 线共用**；86 个被 ≥10 线；最多 **38 线**（`M172 亞馬喇前地`） | 【实测】probe3 §S1 |

| 3 | ★ 站内实际要走多远 | 73 个多站位主码的**站内最大跨度**：中位 **33 m** / p90 **75 m** / 最大 **219 m** / **>300 m 的 0 个** | 【实测】probe4 §T5、§T7 |

⇒ **澳门巴士换乘以「同主码站群换乘」为绝对主流**，站内步行中位量级 **33 米（约 24 秒）**。初稿「换乘关系不完整」的说法在**结构上不成立**。

##### 3A.3 缺口的量级，以及「用高德补」是否可行

忽略站内步行的偏差量级（按 1.4 m/s，`步行速度五档-文献依据-20260918.md:15`）：

| 站内跨度分位 | 跨度 | 忽略步行的偏差 |
|---|---|---|
| p50 | 33 m | 24 秒 |
| p90 | 75 m | 54 秒 |
| max | 219 m（`T330 蘇利安圓形地`，19 线） | 2.6 分 |
| >100 m 的主码 | 仅 **4 个** | 1.2 ~ 2.6 分 |

**「用高德步行补换乘」= ❌ 不可行**，理由：

1. 站↔站短距**同样**失真：实测 `T417→T429` **直线 41 m → 高德 492 m（11.9×）**（`审查-全澳导航方案-批判性-20260918.md:28`）
2. 33 m 的站内换乘会被高德读成 **200~400 m** ⇒ 按 ÷84 换算 **2.4~4.8 分**，而真值 ≈0.4 分
3. 偏差方向是**推高 `baseMin`** ⇒ `pickCatchTier` 压档 ⇒ **整条方案被剔除**（传导链见 `审查:87`）
   ⇒ **「用高德补」比「计 0」更差**——计 0 只丢 24 秒，用高德会凭空多 2~4 分钟

**✅ 可行替代**：站内跨度 × 绕路系数（实测中位 1.6，`审查:52`）÷ 1.4 m/s，并对 <100 m 做 clamp（与 `审查:28` 建议同源）。

##### 4S.2.1 方法

★ **方法自纠（留痕）**：**首跑时本探针的「cap 判定条件写反了」**（把 `!setNoCap.has(chain)` 当成了 cap 成因），导致主桶被误标为「枚举约束」；经**微诊断**（`ch4-micro-probe.ts` 显示那些链在 cap=200,000 时**全部可枚举**）发现后修正条件并**重跑**。修正前后共运行 **3 次**（16:08 / 16:14 / 16:21），**归因结构稳定**（映射失败恒为 7 条量级、`__amap_` 与 hub 限量恒为 0、主桶恒为 cap），故本表结论不依赖单次运行。

##### 4S.2.3 ★★ 三条对初稿 §4.6 的推翻

**推翻一：`__amap_` 站码映射失败不是残余主因。** 线路级 `__amap_` 实测 **0 条**。QA 在 `验收…:72` 提出的「残余来自 ① 链中含 `__amap_`」是**假设，未经验证**；本次实测否证。⇒ 第 4 章 §4.6 引用该假设的表述须删除或改标为「已否证」。

**推翻二：hub 限量不是成因。** `hubLimit` 从 25 抬到 100,000 **未额外收回任何一条链**（在 cap=200,000 时，hubLimit 仍为默认 25 的配置就已把 21 条链全部枚举出来）⇒ **hubLimit=25 不是瓶颈**。

**推翻三：「先修 `station_amap_map`」的价值被高估。** 修映射的实测上限是 **−4.0 pp**（20.5% → **16.5%**），**单项到不了 <10% 的目标**；真正单项可达标的是**候选上限**：**−11.9 pp**（20.5% → **8.6%**）。

##### 4S.2.4 主因机制：为什么是「候选上限」而不是「算法不对」

微诊断（`。verify/ch4-micro-probe.ts`，`home→gate` 与 `school→M134` 两个 OD）给出决定性证据：把 cap 抬到 200,000 后，**此前全部被判「枚举不出」的 1 换乘链都被枚举出来了**：

```
── 链 [52→3X] · 本地枚举到? ✓ 是        （cap=5000 时判「漏」）
   腿0: 52  board=C703 alight=M172 hops=10   ↳ board∈SRC? ✓ · alight 前向可达? ✓
   腿1: 3X  board=M172 alight=M1   hops=6    ↳ alight∈DST? ✓ · hub=M172 反向前可达? ✓
── 链 [55→MT4] ✓ · [26A→51] ✓ · [51A→17] ✓（同构）
```

即：**这些链的每一腿都可解、换乘点共站、上下车站都在近站集合内——算法完全有能力生成，只是没轮到它们。**

★★ **根因（★ 本节曾写错一次，经独立复核修正）**：根因是 `graph-search.ts:174-200` 的**候选计数方式**——`add()` 用**全局** `results.length < maxCandidates` 作停止信号，**名额在「1 换乘阶段」被「同线路链的多上下车站（× 换乘点 × 下车站）变体」吃光**：`results.length` 计的是**路径变体**而非**链**，而同一线路链会产出大量变体。

❌ **被证伪的表述（保留留痕）**：本补充 §4S.2.4 首版曾写「**0 换乘阶段先跑满**（`95 线 × K × K`，k=40 时 **152,000 条候选**）⇒ 1/2 换乘阶段进不去」。**独立复核（`附录 D` · §机制检验）用 `stage0Stats` 自算四个量后证伪**：**152,000 是循环次数，不是有效候选数**——

| 量（Σ30 OD） | k=8 / r=700 | k=40 / r=3km |
|---|---:|---:|
| 循环次数 `95 线 × SRC × DST` | 182,400（6,080/OD） | 4,560,000（**152,000/OD**） |
| **有效 0 换乘路径（去重后）** | **224**（单 OD 最多 41） | **8,478**（单 OD 最多 **832**，均值 283） |

⇒ **0 换乘的有效候选比 cap 小一个数量级（k40：832 ≪ 5000；k8：41 ≪ 200）⇒ 「0 换乘吃满名额」不成立**；实测 `cap=200` 与 `cap=5000` 在 **30/30 OD 全部触顶** ⇒ 名额确实在**后续（1 换乘）阶段**被吃光。**结论方向不变（cap 是主因），但处方打错了阶段**：应从「0 换乘剪枝」改为「**1 换乘阶段的同线路链多变体去重**」。

1. **方案 E 从「条件式」升为「有条件式」，但推荐不变（维持 D）。** Moovit 是**唯一澳门覆盖明确、且公开售卖含 schedule 数据的商业标的**（需询价）；Ito 覆盖未证实、MapKing 仅路况、澳門通非数据商。⇒ 把 E 从「并行扫描」细化为「**先发一轮询价（Moovit 优先），并同步确认授权范围是否允许 PWA 对公众提供**」——后者比价格更可能否决。
