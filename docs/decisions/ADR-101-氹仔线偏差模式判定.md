# ADR-101：氹仔线「站间间隔模式」的判定与偏差取用

## Status

Accepted（2026-09-26 · Phase 1 技术调研产出；team-lead 裁定采纳「方案 C 全量」并追加刷新链路硬要求）

## Context

本轮（v3.2.0）需求 1 要求：氹仔线对「某站、某方向、下一班车」精确判定其属于哪一种**站间间隔模式**
（`52222222222` / `42322213132` / `22222232222` / `13222222222`），再取该模式下的**逐站偏差**做秒级读秒；
用户明确「不做方向合并」，并要求「趟次波动是可以被精确的」。

约束与事实（均有出处）：

1. **数据结构**：时刻表 `lrt_timetables` 的粒度是「站 × 线路 × 方向 × 班别」，每行只给出**本站**的发车时刻
   （`minutes` 为 `[{hour, minutes[]}]`，hour 可 >23），**没有任何「班次 / 趟次」标识**。
   因此「某一班属于哪个模式」不是库里现成字段，必须**由站间时序链式反推**得到。
2. **模式来自链条**：一条完整链覆盖 11 个站间区间（氹仔线 12 个有发车行的站，终点站无行）。
   原型算法（**修正版**）`.verify/lrt-tpl-chain2.mjs`：从起点站一趟发车 t0 出发，逐站取「首个满足
   `arr[i] − t ≥ minGap[hop]` 的发车时刻」（二分 `firstAfterIdx`），链到底 → 得到 11 位间隔序列，即模式编号。
   - **首跳 min-gap ≥ 4 分**（媽閣→海洋为跨海段，物理通行下限）；其余跳 min-gap ≥ 1（含真实存在的 1 分跳）。
   - 早期 naive 版 `.verify/lrt-tpl-chain.mjs`（下一站仅取「> 当前」的最小发车）在班距 ≤ 跨海时长时，
     首跳会接到**上邻车次的到达时刻** ⇒ 产生伪模式 `12322213132`（1 分钟跨海，物理不可能；现网约 7%）。
     该修正为 09-25 既有结论（见 `.verify/lrt-tpl-chain2.txt`）。
3. **主力模式覆盖率（现网全量统计，`.verify/lrt-tpl-stats.txt` + `14` 号 A2）**：
   正向 `52222222222` 62.8%~73.8% + `42322213132` 23.0%~29.7%；
   反向 `22222232222` 56.6%~73.8% + `13222222222` 20.3%~30.7%。四大模式合计约 98%，其余为深夜/早班变体。
4. **性能红线（事故记忆）**：Vercel 函数真身 **iad1（美东）**，主库 Supabase **sin1（新加坡）**，
   单次往返约 **230ms**。`next-departures.ts` 头注记录的「轻轨桶恒定超时、5 张卡掉到 4 张」事故，
   根因就是**跨洲往返被串行放大**；因此任何新增数据读取都**不得**增加串行往返，
   只能折进既有并行窗口（`loadStatics` / `buildLrtPreload`）。
5. **数据量**：氹仔线 12 站 × 2 方向 × 3 班别 = 72 行时刻表行；按「每站每班次」展开约 12,000~13,700 行
   （每班 ~180 趟 × 12 站 × 2 向 × 3 班别）。数据库侧极小，但**若整表灌进每请求的预载对象则偏重**
   （约 0.3~0.6MB 序列化负载）。
6. **维护耦合**：时刻表会在「现网刷新」（如 2026-09-25 全量刷新）时整体更换 ⇒ 模式映射是**派生数据**，
   必须能随刷新重算，且不得留下过期映射。
7. **降级要求（需求 1）**：四大主力模式（约 98%）秒级；其余深夜变体（约 2%）不读秒，保持分钟级。

## Considered Options

### 方案 A：离线预计算班次表（唯一真源表 + 运行时读表）

- 离线脚本按链式算法把 `lrt_timetables` 展开为 `lrt_station_patterns(api_station, route_no, direction, day_type, dep_min, pattern)`（每站每班一行）。
- 运行时**按站查表**得到「该站该班次的模式」，再查 `lrt_station_biases` 取逐站偏差。
- 优点：模式是**冻结的、可审计的、可复核的**数据（脚本可打分布报表，与 `14` 号 A2 对照）；
  运行时无算法风险（规避「沉默逻辑错误」——能编译、能跑、结果错），降级显式（查不到 → 分钟级）。
- 缺点：新增一张展开表（约 1.3 万行）+ 一个离线脚本 + 刷新后须重跑的运维耦合；
  若把整表折进每请求预载 → 负载偏重（约 0.3~0.6MB），逼近 230ms 红线。

### 方案 B：运行时内存链式反推（复用 `buildLrtPreload` 的 `tt` Map）

- 把原型算法抽成纯函数；`buildLrtPreload` 加载完 `tt` 后，**在内存**对已加载的 72 行时刻表跑链，
  得到「站班次 → 模式」映射；运行时 O(1) 内存查。直连路由（`/api/lrt/eta`、`/api/station/eta`）同法在内存反推。
- 优点：**零新增表、零迁移**；预载保持轻量（仍只有 72 行时刻表）；**自动跟随时刻表刷新**（无需重跑脚本）。
- 缺点：把链式算法放进请求路径（虽为纯函数、微秒级，但正确性风险从「离线可审」变成「运行时不可见」）；
  直连路由需多查「本方向同班别全部 12 站」的时刻行才能反推（数据本就要，可接受）；缺少可复核的中间产物。

### 方案 C：混合（离线表为权威 + 预载内存派生为投递方式，同一算法两处复用）

- **算法单一化**：抽 `src/lib/lrt/pattern.ts`（纯函数）——离线脚本、预载、直连路由**共用同一实现**。
- **权威产物落库**：离线脚本产出 `lrt_station_patterns`（审计 + 直连路由按站读表 + 运维复核 + 分布报表）。
- **预载路径保持轻量**：`buildLrtPreload` 用同一纯函数在内存派生（不加载 1.3 万行），从而不逼近负载红线。
- **防漂移**：加一条「表派生 == 内存派生」一致性测试（同一份时刻表快照下两者必须逐行相等）。
- 优点：兼具 A 的**可审计/显式降级**与 B 的**轻量/自动跟随**；算法只有一份，无三重实现。
- 缺点：两处调用同一函数（复杂度略高于单方案）；需要一条一致性测试守住两条投递路径。

### 方案 D（备选·已否决）：运行时全表灌入预载

把 1.3 万行模式映射直接折进每请求预载。**否决**：负载偏重，逼近 230ms 红线与轻轨超时事故的教训。

## Decision

**采用方案 C（混合）**，并以「分享同一纯函数 + 一致性测试」作为护栏。

具体形态：

1. **算法唯一实现**：`src/lib/lrt/pattern.ts`
   - `deriveStationPatterns(ttRows, routeNo) → Map<`${api_station}|${routeNo}|${direction}|${dayType}|${depMin}`, string>`
     （纯函数；输入仅时刻表行，无 DB、无 IO）。
   - 冲突/歧义（某站某班次被 0 条或多条链覆盖、链因收班截断不完整）→ **不入映射**（视为无模式）。
2. **离线权威产物**：`lrt_station_patterns`（每站每班一行）。
   - 由 `scripts/build-lrt-patterns.ts` 调用 `pattern.ts` 生成，经 `npm run`（db-guard）写入；默认 DRY-RUN。
   - 脚本同时打印分布报表（各模式占比），与 `14` 号 A2 的 62.8%~73.8% / 20.3%~30.7% 对照，作为验收。
3. **直连路由**（`/api/lrt/eta`、`/api/station/eta`）：按站读 `lrt_station_patterns` + `lrt_station_biases`（小查询）。
4. **预载路径**（推荐流程，`buildLrtPreload`）：内存派生（方案 B 的方式），预载**不加载**模式大表。
5. **偏差取用**：模式命中四大主力 → 取 `lrt_station_biases[route_code, direction, pattern, api_station].dep_bias_sec`
   叠到表定发车时刻；模式未命中（变体/截断/任一步缺失）→ `secPrecise = false` → 该班次退回**分钟级**。
6. **一致性护栏**：一条测试断言「`build-lrt-patterns` 输出 == `pattern.ts` 在同一快照上的内存派生」；
   时刻表刷新后两者必须同步，否则测试变红。
7. **刷新链路固化为 npm script**（team-lead 2026-09-26 裁定追加 · 硬要求）：
   把「时刻表刷新 → 重建 `lrt_station_patterns`」串成一条命令链，在 `lrt:fetch` 之后**自动**触发重建，
   纳入 `package.json`。原理：模式映射是时刻表的**派生数据**，刷新后必须同批重建，否则派生漂移
   （本项目既往事故类型）。链路示意（实现时以 db-guard 包装、参数以现网为准）：
   `"lrt:refresh": "npm run lrt:fetch -- cloud --allow-prod && npm run db:build-lrt-patterns -- cloud --allow-prod"`。
   文档记述见 `02-技术-调研与方案.md` §2.3。
8. **链式口径 = 逐段最小间隔（min-gap）**（team-lead 2026-09-26 追认 · 后端 Phase 3 发现口径冲突）：
   算法**不得**用 naive「下一站取 > 当前的最小发车」，必须用 `.verify/lrt-tpl-chain2.mjs` 的 min-gap 口径
   —— **首跳（媽閣→海洋跨海段）gap ≥ 4 分，其余各跳 gap ≥ 1 分**（常量 `LRT_TPL_MIN_GAP`，来源
   `.verify/lrt-tpl-stats.mjs` 的 `MIN`；方向专属：TFT `[4,1,…,1]` · BAR 全 `[1,…]`）。
   理由：naive 口径在班距 ≤ 跨海时长时首跳接到**上邻车次到达** ⇒ 伪模式 `12322213132`（现网约 7%）⇒
   该批被挤入「无模式」⇒ 正向读秒覆盖仅约 **89%**，违背需求 1 的 **98%** 目标。修正后分布与 `14` 号 A2
   **逐值吻合**（AC-63 断言通过）。实现记述见 `06-技术-实施规格.md` §1.1。

## Consequences

- **正面**
  - 需求 1 的「精确判定下一班属于哪种模式」有确定的、可审计的实现；错误模式不会静默进入读秒
    （降级路径明确：查不到就不读秒，而非猜一个模式）。
  - 不新增串行 DB 往返：直连路由是「按站小查询」，预载路径纯内存 ⇒ 守住 230ms 红线。
  - 预载负载保持与今日同量级（仅时刻表行），不引入新的事故面。
  - 算法唯一、可单测；表与内存两路一致性由测试守住，防派生数据漂移（本项目既往事故类型）。
- **负面 / 需接受的代价**
  - 新增一张派生表 + 一个离线脚本 + 一次刷新后重跑（运维耦合）。
  - 两处调用同一纯函数（离线脚本 + 预载）；若将来有人只改一处逻辑会破坏一致性——由一致性测试兜底。
  - 「无班次标识」这一根因未消除：判定仍依赖链式反推；收班末班（链被截断）天生不读秒（属预期）。
- **已裁定（2026-09-26 · team-lead / 用户）**
  - P1：采纳**方案 C 全量**（不降级为方案 B 单跑）；并追加第 7 条「刷新链路固化为 npm script」硬要求。
  - P3：区间用时取「手记换算优先」——東亞運→路氹東 **110s** · 科大→路氹東 **140s** · 東亞運→協和 **130s**；
    打点实测值（~80 / 138~139 / 102~111）**不采用**，但须记入偏差/用时表 `note` 供后续真机复核（见 02 文档 §5.4）。
  - P4：起点=「我的位置」时**也画起点红钉**（技术侧：`originArg` 不再因 `from=null` 而为 null；
    红钉与蓝点的组合形态由设计师定）。此项与模式判定无关，归 02 文档 §7 与 Phase 2 规格。
