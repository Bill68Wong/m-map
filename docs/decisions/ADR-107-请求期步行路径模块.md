# ADR-107：新增请求期步行路径模块 `lib/amap/walking.ts`，与"离线专用"的 `client.ts` 并存

## Status

Accepted（2026-10-29，主理人批准）

## Background

v3.6.0 要交付步行导航（分步指引 + 地图跟随）。现状是**完全没有**步行几何与分步数据：

- 有步行**距离**：离线落表 `station_walk_distance` / `walk_cache`，读端只取"米"；
- 有步行**时长**：由距离 ÷ 基准速度派生（`walk-fix.ts`、`catch-up.ts#requiredSec`）；
- **没有** polyline、**没有** instruction、**没有**跟随/偏航。

数据其实在高德响应里就有，缺的是"保留 + 暴露"。`src/lib/amap/client.ts:164` 与 `:231`：

```ts
const polyline = path.steps?.map((s) => s.polyline ?? "").join(";");
```

各 step 的 polyline 被 `join(";")` 拼成一个串，只用于算首末吸附距离（`snapStartM` / `snapEndM`），
**step 与 step 的边界在这一行被销毁** —— 事后无法还原"第 3 步从哪到哪"，`instruction` 也从未被解析。

障碍是 `client.ts` 文件头的硬规则 ①：

> **绝不在请求时调用** —— 本模块只允许被 `src/lib/rebuild/**` 与 Cron import。
> `src/lib/recommend/**` **禁止** import 本模块（推荐链路实时预算很紧，
> 任何同步外部调用都会直接吃掉它）。调用全部走离线批算 + 落表。

这条规则为"步行距离"而设，是对的（离线批算 + 落表把配额压到每天 ≈ 0）。但步行**导航**的 OD 是
「用户当前坐标 → 站点坐标」，用户坐标米级变化，走 50 米就换一个 OD ⇒ **无法预热到表**。
`walk_cache` 是「地点 ↔ 站点」的固定对（`nav-service.ts:180-201`，整表载入 `LIMIT 20000`），
覆盖不了任意起点。这条"为什么不能用离线预热"必须留档，否则后续会有人再提一次。

## Decision

### 为何"请求期调用"不违反 `client.ts` 的硬规则 ①（主理人要求写明）

硬规则 ① 的立法目的不是"禁止一切请求期外部调用"，而是三条具体约束：

1. **保护推荐链路的实时预算** —— `src/lib/recommend/**` 的请求预算很紧（`live.ts` 头部记录过
   11 个 DSAT 桶串行的实测教训），任何同步外部调用都会直接吃掉它；
2. **把可预热的量预热掉** —— 步行**距离**是「地点 ↔ 站点」的固定对，可以离线批算落表，
   请求期调用纯属浪费配额（稳态每天 ≈ 0 次调用）；
3. **控制并发** —— 个人认证开发者只有 3 QPS（按 Key 全局），批量并发会互相踩踏。

本 ADR 的请求期模块与这三条**不冲突**，逐条对应：

| 规则目的 | 本模块的处理 |
|---|---|
| 保护推荐预算 | 步行导航**不在** `/api/nav` 链路上，是独立端点 `/api/nav/walk`；`recommend/**` 与 `nav-service.ts` **不得** import `walking.ts`（禁引清单写进文件头） |
| 可预热的量已预热 | 步行**距离/时长**仍走 `walk_cache` / `station_walk_distance`，本模块**不接管**距离查询；只提供"任意起点"才可能拿到的几何与分步（规则 ① 恰恰无法覆盖的部分） |
| 控制并发 | 强制走 `acquireWithWait(RATE_BUCKET.walking, 600)` 跨实例令牌桶 + 4000ms 超时 + 单次请求 1~2 调用（首末段） |

⇒ 结论：规则 ① 的**适用域**是「推荐链路的步行距离查询」，本模块的**作用域**是「步行导航的用户实时路径」，
两者是不同问题。本 ADR 因此不是"破例"，而是**把规则的适用域写清**。`client.ts` 头部会追加一行指针：
「请求期步行路径请用 `walking.ts`，本文件仅离线（rebuild / Cron）」。

### 其余决策

**新增 `src/lib/amap/walking.ts` 作为请求期唯一入口**，`client.ts` 维持"离线专用"，两者并存，
靠**文件头互相指名 + 命名差异**防误用（`walkRoute*` 离线 / `fetchWalkingSteps` 请求期）。

接口与纪律：

1. 端点 `https://restapi.amap.com/v5/direction/walking`，`show_fields=cost,polyline`
   （`polyline` 需显式声明；`instruction` / `road_name` / `step_distance` / `orientation`
   是不受 `show_fields` 过滤的默认字段，无需追加）。
2. **按 step 保留边界**：返回
   `WalkStep { idx, turn, text, sub?, distM, cumStartM, polyline: LL[], cumM: number[] }`，
   逐 step `parsePolyline`，**服务端算好累计里程**（`cumM`）—— 客户端只做二分查找，
   不重复 `cumDistM()`，避免前后端各算一遍导致步界不一致。
3. `turn` 由服务端纯函数 `turnOf(step, prevStep)` 派生（`action` → `instruction` 文本匹配
   → `orientation` 方位差 → 回落 `straight`）；「向左前方 / 向右前方 / 靠左 / 靠右」
   统一映射 `straight`，不引入 `slight_*`。
4. **限流**：`acquireWithWait(RATE_BUCKET.walking, 600)` —— 该桶在 `rate-limit.ts` 早已定义
   但从未使用；高德基础 LBS 池并发 3 QPS 是**按 Key 全局**的，必须跨实例令牌桶。
5. **超时 4000ms**，与 ADR-103 的 `TRANSIT_TIMEOUT_MS` 一致（可用 `AMAP_WALK_TIMEOUT_MS` 覆盖）。
   依据：线上函数真身在 iad1、`preferredRegion="sin1"` 在 Hobby 下不生效，1500ms 对亚太服务必然超。
6. **不做服务端缓存**（不落库、不走 Data Cache）：路径几何在 30 分钟尺度稳定，但落库会引入
   "改了路网不更新"的第二次事故。改由客户端同 OD（坐标 4 位取整）5 分钟内存缓存。
7. **失败必须降级，不许空白**：`rate_limited` / 超时 / 无路径 ⇒ 前端显示「直线距离 + 固定步速估算」
   + 文字提示，**绝不显示假的分步**（沿用 `track.ts` 文件头"绝不猜测"的纪律）。
   固定步速沿用 `walk-fix.ts` 既有基准，不得另起一套。
8. **预取**：详情体 `detail-body` 到达后即并行预取**首末两段**步行路径，把高德 RTT 藏进用户
   阅读卡片的时间；展开步骤/开始步行时命中缓存 ⇒ 满足"命中 ≤200ms"。预取失败不得阻塞展开
   （走骨架 + 降级）。**默认 `both`（首段 + 末段）**，由主理人 2026-10-29 裁决。

   配额闸门五条（全部为验收项）：

   | # | 闸门 | 取值 / 做法 |
   |---|---|---|
   | G1 | 客户端同 OD 缓存 | 坐标 4 位取整为键，5 分钟内存缓存；反复进详情不重复取 |
   | G2 | 日计数 + 月告警 | 每 24h 计数，**`console.info` 结构化日志可查**（不为看账单才排查），阈值 10 万/月只告警不降级 |
   | G3 | 紧急降压开关 | `WALK_PREFETCH` ∈ `both`(默认) / `first` / `off` |
   | G4 | **开关纯环境变量生效** | 切换**不得要求改代码**、不得重新构建以外的任何操作；启动时读取一次并记录当前值到日志 |
   | G5 | **三态单测** | `npm run test:walk-prefetch` 覆盖 `both` / `first` / `off` 三种取值下的"实际发起哪些预取"（纯函数：`prefetchTargetsOf(mode, legs)`，不依赖网络） |

## Consequences

正面：

- 步行导航可交付，且延迟被预取吸收，用户感知只有"命中"路径。
- 与既有"离线距离链路"零冲突：`walk_cache` / `station_walk_distance` 仍服务推荐，不被改动。
- 令牌桶 + 4000ms 超时让配额与耗时都可观测（`RateDecision.tokensLeft`）。

负面（均已承接）：

- 出现**两条高德步行调用通道**（离线 `walkRoute*` / 请求期 `fetchWalkingSteps`）。
  防线：文件头双向指名 + 命名差异 + 本 ADR。若有人从 `recommend/**` import `walking.ts`，
  会把高德 RTT 塞进推荐预算 —— 代码评审必须拦。
- 配额模型从"每天 ≈ 0"变为"每用户每次导航 1~2 次"。**真实消耗以 G2 的日志计数为准；本 ADR 里
  的 DAU 估算（DAU 1000 × 人均 2 次导航/日 ≈ 12 万/月 ≈ 基础 LBS 池 15 万/月的 80%）仅作上限推演，
  不是事实。** 本项目为非商业个人项目、无宣传，真实日活远低于该值，故默认保留 `both` 体验，
  不为尚未发生的规模牺牲当下核心体验（主理人 2026-10-29 裁决）。
- `client.ts` 头部的硬规则 ① 需要补一句"请求期步行请用 `walking.ts`"，否则规则字面禁止一切
  请求期调用，与 ADR-107 冲突。
