## 一、立规依据：事故实测数据

封号前 20 天的提交节奏（本地 `git log` 统计，共 164 次提交）：

| 指标 | 实测值 | 判读 |
|---|---|---|
| 日均提交 | 8.2 次/天 | 偏高 |
| 中位提交间隔 | 22.9 分钟 | 正常 |
| 间隔 ≤30 秒 | **14 次** | 🔴 人类不可能 |
| 最短间隔 | **0 秒（同秒双提交）** | 🔴 纯自动化痕迹 |
| 间隔 ≤5 分钟 | 39 次 | 偏高 |
| 单小时峰值 | **9 次**（09-16 00:00）· 7 次（多次） | 🔴 深夜高频 |
| 公开期 PR 密度 | 5 天 30 个 PR（#50~#79） | 🔴 协同造假模型典型负样本 |

**归因结论（修正版）**：

> 公开可见（可被举报）＝ 点火源；AI 高频自动推送（秒级提交、深夜机器节奏、密集 PR）＝ 放大器。
> 两者缺一都不至于停号。行为侧约 **50%**，内容侧（公开鉴权算法逆向）约 **30%**。

⚠️ **诚实记录一个反证**：公开前的 09-03（17 次）、09-10（16 次）、09-16（19 次）同样是高频，但账号无事。**因此不能简化为「高频必封」**，规则设计要同时覆盖「节奏」与「可见面」。

## 二、核心原则

> **AI 是生产者，不是发布者。**
> commit 可以多，**对外动作一天最多一次**，**且必须人点头**。

三条派生原则：

0. **一天一次**：GitHub 推送与 Vercel 发版合并计算，**每天最多 1 次「发布窗口」**。窗口内 push 与 deploy 成对执行，算同一次；**同类动作第 2 次即超限**。
1. **可逆优先**：本地 commit 可随意，一旦离开本机就不可撤回。
2. **批量优先**：同一会话的改动合并推送，不逐条推。

> 已删除的原则：「人类作息 / 不在深夜推送」。理由：**无实证依据** —— 平台判自动化看的是提交间隔与频率，与钟点无关；凭空加限制反而会让规则失去可执行性。

## 三、规则

### §3.0 · GitHub 操作前政策自检【强制 · AI 每次必做】

> **这是本 SOP 的第一道闸。任何 GitHub 相关操作（push / tag / release / PR / 设置变更 / 调用 API）之前，AI 必须先逐条自问并给出结论，再动手。**
> 只要有一条答案是「可能」，**立即停止并告知主人**，不得「先试一下」。

| # | 自检问题 | 命中即停的典型情形 |
|---|---|---|
| **G1** | 这次推送/发布的内容，是否包含**绕过他人访问控制**的东西？（鉴权算法、密钥、签名复现、内部接口路径） | `token.ts`、`macauweb`、`getRouteData`、签名拼接逻辑 |
| **G2** | 是否涉及**未获授权的数据获取**，或公开描述其方法？ | 采集强度数据、逆向调研、抓包脚本 |
| **G3** | 是否**高频/批量/自动化**的操作形态？（短间隔多次提交、批量 issue/PR、脚本化评论） | 同秒提交、一小时多次 push、批量 `gh` 操作 |
| **G4** | 是否可能被误认为**冒充官方机构**或侵权使用他人标识？ | 使用政府机构名义、官方图标、近似官方命名 |
| **G5** | 是否包含**他人隐私或凭据**（真实连接串、token、手机号、住址） | `.env` 内容、JWT、`sbp_` 密钥 |
| **G6** | 是否**在冻结窗口内**（比赛/演示前 72h、事故处理期间、当日额度已用完）？ | L6 窗口、当日已发布过一次 |

**自检输出格式**（AI 在动手前必须写出，一行一条）：

```
[风控自检] G1 否 · G2 否 · G3 否 · G4 否 · G5 否 · G6 否 → 放行
[风控自检] G3 是（本日已 push 1 次）→ 停止，等待主人特别允许
```

**STOP 规则**：任何一条为「是」→ **不操作**，说明命中项与理由，等主人明确指令。**不得以「只推一点点」「先试试」为由绕过。**

### L0 · 权责边界【纪律 · 最高优先】

| 项 | 规定 |
|---|---|
| AI 可自主执行 | 本地读写、commit、lint/tsc/build、只读查询 |
| AI **必须**获明确许可 | `git push` · 打 tag · 发 Release · 合并 PR · **任何 Vercel 生产部署** · 任何 GitHub 设置变更 |
| **收尾默认动作** | 修复/优化做**完**只 commit、不推送；报告「已就绪，等你发版指令」后停下。**「改完」≠「可以发」**（2026-10-29 主人立） |
| 默认分支 | AI 只推 `vX.Y.Z-精要` 分支（如 `v3.5.6-风控基建`）；`main` 由 PR 合并进入 |
| `main` 直推 | 仅限「主人当次明确授权」 |

### L1 · 发布频率硬上限【强制 · 本次加严核心】

| 项 | 规定 |
|---|---|
| **GitHub push** | **每天最多 1 次**（自然日，澳门时间 00:00~24:00） |
| **Vercel 生产部署** | **每天最多 1 次**（含 CLI 直发、Git 集成自动部署） |
| **合并计算方式** | push 与 deploy 在同一窗口内成对执行，**只算 1 次**；分两次做则算 2 次（超限） |
| **突破条件** | **仅当主人当次明确说「允许再发一次」**；AI 不得自行判断「这次紧急」 |
| **紧急热修** | 同样占当天的 1 次额度；若当日已用完，需主人明确追加许可 |
| **计时口径** | 以澳门时间 GMT+8 的自然日为准，不按 24 小时滚动 |
| **超额处置** | 剩余 commit 留本地，次日窗口再发；本地 commit 数量不设限 |

> 说明：本限制**同时覆盖 push 与 deploy**，因为二者是同一个对外动作的两半。
> 若主人希望「push 与 deploy 各算 1 次、每天合计 2 次」，告我改回即可 —— 当前取更严的一档。

### L2 · 提交粒度闸【强制 · `check-commit-scope.mjs` 覆盖部分】

| 项 | 规定 |
|---|---|
| 同一会话的 commit 数 | 合并为 **1~3 个**语义完整提交（feat / fix / docs 各一） |
| 禁止 | WIP、`tmp`、`test`、`asdf` 类碎片提交进 `main` |
| 禁止 | **同秒内两次提交**（自动化铁证）；间隔 <60 秒连续 3 次即视为违规节奏 |
| 提交信息 | 必须写明「改了什么 + 为什么」，禁纯版本号堆砌 |

### L3 · 时段限制【已删除 · 2026-10-28 主人裁定】

> **本条作废。** 原规定「23:00~08:00 不做自动推送」，属**无实证依据的臆造规则**：
> 平台识别自动化针对的是提交间隔、频率、批量形态，与操作发生在几点无关。
> 保留此条仅为记录「曾立过、已撤销」，避免后续文档再引用。
>
> 仍有效的相关约束只剩两条：L1 的每日 1 次窗口、L2 的提交粒度。

### L4 · 平台减噪【纪律】

| 项 | 规定 |
|---|---|
| 批量操作 | 禁 `gh` 批量改 issue/PR、禁脚本批量评论 |
| 自动生成内容 | 禁自动生成 PR 描述轰炸、禁自动 assign/review 机器人式操作 |
| PAT | 最小权限；**90 天轮换一次**；禁长期不过期 token |
| 二次验证 | 账号必须开 2FA；恢复码离线保存 |

### L5 · 熔断与告警【部分强制】

| 触发条件 | 动作 |
|---|---|
| 本日已发布过 1 次，仍要 push/deploy | **硬停**（需主人追加许可） |
| 连续 3 次提交间隔 <60 秒 | 暂停提交，提示合并为 1 个 commit |
| 单日提交 >20 次 | 告警，提示检查是否陷入「改一点推一点」 |
| 收到平台邮件 / 推送失败异常 | **立即冻结全部远程操作 24 小时** + 取证（见 §六） |
| 仓库出现 404 / 账号异常 | 同上，且先查是否账号级问题（能否登录网页端） |

### L6 · 冻结窗口【纪律】

| 场景 | 冻结范围 | 时长 |
|---|---|---|
| 比赛 / 答辩 / 公开演示 | 全部 push、tag、部署 | 开始前 **72 小时** 至结束后 24 小时 |
| 期末 / 关键交付周 | 非必要 push | 按需 |
| 事故处理期间 | 全部远程操作 | 至事故关闭 |

## 六、事故响应 SOP（发现异常 → 关闭）

```
① 立即冻结
   停止一切远程操作（push/tag/部署/设置变更）。不做任何"先试试能不能推"的探测。

② 判级
   · 网页端能登录 → 仓库级问题
   · 网页端登录不了 → 账号级问题（本次属此类）

③ 取证（当天完成）
   截图/保存：报错原文、平台邮件全文、最后成功操作时间、近期操作清单。

④ 保线上
   切 Vercel CLI 直发通道（注意：仍受 L1 每日 1 次限制，需主人许可）。

⑤ 评估影响面
   未推送 commit 数、本地 tag 数、备份可用性、协作者是否受影响。

⑥ 申诉
   附：项目性质（个人非商业）、用途、整改承诺、已完成的自查动作。

⑦ 关闭
   解封后三件事：更新 remote → 核对远端状态 → 补推（严格顺序，禁 push --tags 一把梭）。
```

## 九、规范发版流程（2026-10-28 定稿 · 唯一标准动作）

> **设计目标：主人只需点两下确认，不需要手改任何名字。**
> 原理：Vercel 的部署名取「被部署提交的标题」。因此让**最后一个 commit 的标题**就是规范名，
> 并用 **Rebase and merge** 合并（不产生 `Merge pull request #N from ...` 这种默认标题），
> 名字自然正确。

### 9.1 命名规范（一次性设置好后全自动）

| 位置 | 格式 | 示例 | 谁生成 |
|---|---|---|---|
| **分支名** | `vX.Y.Z-<概述>` | `v3.5.6-新增风控脚本与发版流程` | `release-plan.mjs` |
| **PR 标题** | 同分支名 | `v3.5.6-新增风控脚本与发版流程` | GitHub 自动带入 |
| **最后一个 commit** | `vX.Y.Z <概述>` | `v3.5.6 新增风控脚本与发版流程` | **我必须在提交时就用这个标题** |
| **tag** | 纯 `vX.Y.Z` | `v3.5.6` | 合并后按需 |
| **Vercel 部署名** | 自动继承最后 commit 标题 | `v3.5.6 新增风控脚本与发版流程` | 自动 |

**`<概述>` 怎么写**（2026-10-28 主人补充）：

- **要「简洁概述修改」，不是极简标签**：写清这次改了什么，动宾短语，一般 **8~20 字**。
- 好例子：`新增风控脚本与发版流程` · `修复夜间到站倒计时偏差` · `导航界面改版与收藏两级` · `轻轨班次补前后邻班`
- 差例子：`风控` `优化` `修复` `杂项` `update`（信息量为零，三个月后自己都看不懂）
- 也别写成论文：超过 25 字会被 GitHub 列表和 Vercel 面板截断。

⚠️ 分支名必须带 `<概述>` 后缀，**不能只写 `v3.5.6`** —— 否则与同名 tag 构成 refname 歧义，git 会警告。

### 9.2 一次性前提设置（仓库 Settings）

`Settings → General → Pull Requests`：**只勾 `Allow rebase merging`**，关掉
`Allow merge commits` 与 `Allow squash merging`。

这样合并按钮只剩一个，不会手滑选成 Squash（Squash 会把整批 commit 压成 1 个，历史全毁）。

### 9.3 标准流程（9 步）

| # | 谁 | 动作 |
|---|---|---|
| 1 | AI | bump `package.json`（patch/minor 自动；major 须主人点头） |
| 2 | AI | `npx tsc --noEmit` + `npm run lint` + `npm run build`，三条全绿 |
| 3 | AI | `node scripts/check-commit-scope.mjs` 过提交门禁 |
| 4 | AI | commit：中间提交用语义式，**最后一个标题必须是 `vX.Y.Z 精要`** |
| 5 | AI | `git push origin HEAD:refs/heads/vX.Y.Z-精要` |
| 6 | **主人** | 点 `Create pull request` → 点 `Rebase and merge` → 确认（**仅两下**） |
| 7 | AI | 同步本地 main：`fetch` + `update-ref`（**禁 `reset --hard`**） |
| 8 | AI | 可选：打 `vX.Y.Z` tag 并推送（算当日第 2 次 push，需主人点头） |
| 9 | AI | `check-release-allowance.mjs --record push\|deploy` 记账 |

### 9.4 为什么用 Rebase 而不是 Merge / Squash

| 合并方式 | main 顶端提交 | Vercel 显示 | 历史 | 需手改名字 |
|---|---|---|---|---|
| Merge commit | `Merge pull request #85 from ...` | 丑默认名 | 保留 | ❌ 必须改 |
| Squash | PR 标题 + `(#85)` | 略有噪音 | **压成 1 个，全毁** | 不用改 |
| **Rebase** ✅ | 我们最后那个 commit | `v3.5.6 风控基建` | **完整保留且线性** | **不用改** |
