## 0. 结论摘要

| 项 | 结论 |
|---|---|
| 技术可行性 | 六个诉求**全部可实现**，无需新增依赖，**无 DB 表结构变更** |
| 最大技术障碍 | 步行导航需要**请求期**调高德步行路径 —— 与 `amap/client.ts` 头部的硬规则①（"绝不在请求时调用"）正面冲突，必须新开模块 + ADR 明确边界 |
| 最大行为风险 | 上车判定改为「定位主导」后，`e2e-v214.mjs` 的「自动上车」断言必然失败（Playwright 默认无定位）—— 必须同步注入 geolocation |
| 最大的"错觉" | 用户说的「刷新一秒冷却一次」不是冷却函数写错，而是**导航态根本没有有效冷却**（冷却条件退化成"请求往返耗时 ≈ 1 秒"），详见 §2.2 |
| 最大的缓存误解 | 「彻底去缓存」不可能全站成立：静态层（站序/段统计/线路色）全去会让每次冷启动重建 DB 连接 ≈ 2.3s（`query.ts` 文件头已记录实测反证链）。正确边界见 §5 |
| 交付顺序 | 去 speed → 清横幅 → 拆口令门 → 上车判定 → 刷新体系 → 步行导航 → 线路全景页（理由见 §7） |

## 2. 现状审计

### 2.1 诉求：上车判定（为什么"第一辆车到站就被判上车"）

#### 2.1.1 现状链路

```
useRideTracking (phase = "boarding")
  ├─ 首次 fetchFrame(null) + 每 12s 轮询        useRideTracking.ts:537-551
  ├─ 每个 GPS 帧（1.5~3s）再跑一次 tryAuto      useRideTracking.ts:554-557
  └─ tryAuto() → autoBoardOf()                  useRideTracking.ts:509-533
                   └─ 巴士分支：R1 strong ⇒ 立即 hit   boarding-detect.ts:227-230
```

#### 2.1.2 根因（三层叠加，缺一不会被骂）

**根因 1 —— `autoBoardOf` 里 R1（车辆）是"独立触发条件"，不是"佐证"。**

`boarding-detect.ts:226-230`：

```ts
// 巴士：R1 优先
const r1 = r1Of(input.vehicles, input.boardMain, input.boardPos);
if (r1.kind === "strong") {
  return { hit: true, plate: r1.plate, source: "vehicle", reason: "r1", streak: prevStreak + 1 };
}
```

这一句**在 `geomOk`（几何可用性）判定之前**返回（`geomOk` 在 `208` 行算好，但到 `231` 行才用来挡退化）。
即：**只要车辆侧命中，GPS 通道完全不参与**。`input.fixes`、`input.boardPos` 在这条路径上**没有任何约束力**（`boardPos` 只在 `rankBoardingVehicles` 里当次级排序项，见 `track.ts:117-121`）。

**根因 2 —— `r1Of` 的 "strong" 覆盖了一个**长达 1~3 分钟**的时间窗，而不是一个瞬间。**

`boarding-detect.ts:83-85`：

```ts
const strongs = ranked.filter(
  (v) => v.interval?.from?.code && mainOf(v.interval.from.code) === board,
);
```

而 `interval` 的来源是 `/api/route-vehicles` 的这段（`route-vehicles/route.ts:221-226`）：

```ts
} else if (m.status === "0") {
  // 已离挂载站、驶向下一站 ⇒ 区间 = 挂载站 → 下一站
  status = "moving";
  const next = stationBlocks[m.idx + 1];
  if (next?.staCode != null) interval = { from: stopRef(m.code), to: stopRef(String(next.staCode)) };
}
```

DSAT 的 `status=0` 表示"已离开挂载站、正驶向下一站"。⇒ **车辆从上车站开走后，直到抵达下一站为止，`interval.from` 恒等于上车站**。这段物理时间在市区常见 40~180 秒。

⇒ 用户点「开始导航」那一刻，只要**该方向任意一辆车**处在"已离上车站、未到下一站"的区间里，12 秒内的第一个车辆帧就会把他判成"已上车"。这正是"第一辆车到站（尤其刚走）就被判上车"的机制。

**根因 3 —— `tryAuto` 对 R1 免除多帧确认，且冷却被"开始导航"清零。**

`useRideTracking.ts:530-532`：

```ts
if (res.reason === "r1" || res.streak >= R2_STREAK) {
  switchToRiding(res.plate, res.source, res.reason);
}
```

- R2（GPS）需要连续 `R2_STREAK = 2` 帧（`boarding-detect.ts:50`）；**R1 一帧即切**。
- `start()` 把冷却基准清零（`useRideTracking.ts:729` `lastSwitchTsRef.current = 0`），于是 `nowMs - lastSwitchTs` 恒 > `SWITCH_COOLDOWN_MS(20s)`（`boarding-detect.ts:55`、`:206`），**冷却对首次判定完全不生效**。
- 每换一腿（`doAlight`）都重置 `autoUsedRef = false` 与 `lastSwitchTsRef = 0`（`useRideTracking.ts:852-853`），第二腿同样"立刻可判"。

**加重项（放大器，非根因）**：`useEffect([userFix, phase, tryAuto])`（`:554-557`）用**上一车辆帧**反复判定 —— 同一个 `strong` 的 `listRef.current` 会在每个 GPS 帧（1.5~3s）被重新评估一次。所以即使把轮询拉到 60s，判定频率仍由 GPS 决定。

#### 2.1.3 现阈值一览（改造时全部要重新审视）

| 常量 | 值 | 位置 |
|---|---|---|
| `R2_WINDOW_MS` | 45 000 | boarding-detect.ts:32 |
| `R2_TOL_M` / `R2_LRT_TOL_M` | 80 / 60 | :33-34 |
| `R2_SPEED_MIN_KMH` / `_FLEX` / LRT | 8 / 5.5 / 12 | :36, :46, :38 |
| `R2_DISPLACE_MIN_M` | 60 | :44 |
| `R2_STREAK` | 2 | :50 |
| `R2_FIX_MAX_ACC_M` | 150 | :52 |
| `SWITCH_COOLDOWN_MS` | 20 000 | :55 |
| `POLL_MS`（候车/乘车） | 12 000 | useRideTracking.ts:48 |

结论：`R2_*` 这套参数**本身是合理的**（自适应容差、位移门、帧确认都在），问题只在于**它被 R1 旁路了**。

### 2.2 诉求：刷新（为什么"一秒冷却一次"）

#### 2.2.1 现状：导航页有 **3 个刷新入口**，冷却语义各不相同

| 入口 | 组件 | 可见条件 | "忙碌/冷却"判据 | 实际效果 |
|---|---|---|---|---|
| A. 品牌栏圆键 | `RefreshButton` ← `NavBrandBar.tsx:79-81` | 仅 `picked.kind === "bus"`（**查看线路**模式） | `cooldownSec > 0`，来自 `useRouteVehicles.startCooldown()` 的 **10 秒**计时器（`useRouteVehicles.ts:96-108`，`RefreshButton.tsx:21`） | 唯一**真正有效**的冷却；但导航态该整列被 CSS 隐藏（`NavBrandBar.tsx:9-13` 注释 + `body[data-nav-phase]` 规则） |
| B. 面板顶栏刷新 | `RouteSheet.tsx:278-291` | recommend / detail 两态 | `refreshBusy = pane === "recommend" ? rec.phase === "loading" : detail?.phase === "loading"`（`:167`） | **导航态恒不忙**：`detail.phase` = `ov.phase`（`NavShell.tsx:547`），`ov.phase` 只在 `geomReady` 之前为 `loading`（`useRouteOverview.ts:176-182`）⇒ 详情体就绪后**永久 false** |
| C. 吸底操作条刷新 | `NavTrackBar.tsx:191-200` | 仅 `phase === "riding"` | `disabled={traveling}` | `traveling` 仅在 `fetchFrame` 执行期间为 true（`useRideTracking.ts:402/467`）⇒ 冷却窗口 = **一次 HTTP 往返，0.3~1 秒** |

#### 2.2.2 根因

> 用户说的「一秒冷却一次」，对应的是 **C（吸底条）**：`disabled={traveling}` 让"冷却时间"退化成了"网络往返时间"。点一次 → 转 1 秒 → 又能点。**连点即连发**。
> 而 **B（顶栏）** 在导航态**完全没有冷却**。
> 只有 **A** 存在真实冷却，但它在导航态不可见。

即：**导航全流程（候车 + 乘车）中，唯一能看到的两个刷新键，一个是 1 秒假冷却，一个零冷却。** 这与用户描述完全吻合。

量化后果：每次点刷新 = `getBusLocations` + `getBusPositions` 两个 DSAT 请求（`route-vehicles/route.ts:162-165`）＋（`?progress=1` 时）一次进度计算（`:248-254`）。连点 10 次 = 20 次 DSAT 调用，直接撞铁律 19 的风控面。

#### 2.2.3 附带发现：导航态"刷新了但地图上的车不动"

`NavShell.tsx:414`：

```tsx
vehicles={detailActive ? (ride.phase === "riding" ? ride.mapVehicles : ov.vehicles) : rv.vehicles}
```

- **riding**：`ride.mapVehicles` 随 12s 帧重算（`useRideTracking.ts:253-271`，依赖 `listTick`）⇒ 会动。
- **boarding（候车）**：用的是 `ov.vehicles` —— 来自 `useRouteOverview` 的一次性拉取（`useRouteOverview.ts:123-170`），该 effect 只在 `[open, card, detail.phase, legsInput, routeKey, extra]` 变化时重跑。**车辆列表此后永不更新**。
- 而刷新走的 `track.onRefresh`（`RouteSheet.tsx:171`）→ `fetchFrame`（`useRideTracking.ts:894-897`）只更新 `listRef` / `candidates` / `segProgress`，**不写 `ov.vehicles`**。

⇒ 候车态点刷新，只有"等车候选/文字"变，**地图上的车原地不动**。这是"刷新没反应"的第二个来源，必须一并解决。

#### 2.2.4 附带发现：`detail.reload` 是死代码路径

`RouteSheet.tsx:168-173`：

```ts
if (pane === "recommend") rec.reload();
else if (detail?.track?.onRefresh) detail.track.onRefresh();
else detail?.reload?.();
```

`NavShell` 恒传 `track: ride`（`NavShell.tsx:552`），`ride.onRefresh` 恒为函数 ⇒ **`detail.reload` 永不执行**。`detail-body`（站序/折叠栏）在导航中不会有任何刷新通道。

#### 2.2.5 附带发现：轻轨线路"查看线路"模式没有刷新键

`NavBrandBar.tsx:79` 的条件 `picked?.kind === "bus"` ⇒ 轻轨线路查看时品牌栏无刷新键。是否补，交产品决定（本文按"不补"处理，列入 §附录B 不做）。

### 2.3 诉求：推荐结果为什么可能陈旧（`unstable_cache` 到底缓存了什么）

**先纠正一个常见误判：`unstable_cache` 不含任何实时班次。**

`src/lib/recommend/query.ts:196-205`：

```ts
const getStaticRows = unstable_cache(
  async () => fetchStaticRowsUncached(getPool()),
  ["rec-static-rows-v1"],
  { revalidate: 60, tags: ["rec-static"] },
);
```

缓存的 `StaticRows`（`query.ts:80-99`）= `route_stops` / `stations` / `segment_stats` / `walk_times` / `station_walk_distance` / `transfer_walks` / `places` / `commute_plans` / `plan_legs` / `routes.color` / `lrt_*` 九个静态表。**全是派生静态数据**，`revalidate: 60`（60 秒）。
外加**进程内**第二层 `STATIC_TTL_MS = 60_000`（`query.ts:211-223`）。
⇒ 这两层只会让「站序/段时长/线路色」最多陈旧 60 秒，**用户不可感知**。

**真正让用户觉得"推荐一直是老样子"的，是下面四处（按影响排序）：**

| # | 机制 | 位置 | TTL / 键 | 用户感知 |
|---|---|---|---|---|
| 1 | **`transit_cache`（高德方案骨架）** | `amap/transit.ts:74-76`、`405-415`、`508-529` | 60 秒；键 = `坐标4位 + 澳门时间 15 分钟桶 + |s<策略>` | 15 分钟内「换乘方案集合/上下车站/站序」不变；刷新拿回同一批卡 ⇒ "怎么刷都一样" |
| 2 | **`useRecommend` 同一 query 只自动拉一次** | `useRecommend.ts:100-105` | 键 = `query + prefs + lrtFirst` | 关面板再开 = **秒显上次结果**，一个请求都不发 |
| 3 | **推荐刷新未带 `nocache`** | `useRecommend.ts:71-77`（`load` 只拼 `q`）、`:107`（`reload` 调 `load`） | — | 点"刷新推荐"仍可能命中 #1 的 60 秒缓存 |
| 4 | **`poi-search` 回车结果进程内缓存** | `nav/poi-search.ts`（`CACHE_TTL_MS = 10 * 60_000`） | 10 分钟，键 = `q + mode(enter)` | 只影响搜索下拉，不影响推荐 |

**实时层确实是每请求真调的**：`fetchLive`（`nav-service.ts:503-510`）无结果缓存（`live.ts` 文件头第 32-33 行明确"本模块不做结果缓存"），DSAT 客户端 `cache: "no-store"`（`dsat/client.ts:130`），`/api/nav` 响应头 `Cache-Control: no-store`（`api/nav/route.ts:131`）。
⇒ **数值（等车/到站/总时长）是新的；卡片集合与顺序是旧的。** 用户看到的"陈旧"= 结构不变，不是数字没更新。

**补充：`/api/nav/detail-body` 也无缓存**（`api/nav/detail-body/route.ts:189` 返回 `no-store`，客户端 `useDetailBody.ts:55` 亦 `no-store`）。

### 2.4 诉求：步行导航（现状：完全没有）

#### 2.4.1 现状

| 环节 | 现状 | 位置 |
|---|---|---|
| 步行**距离** | 有。高德步行距离离线落表 `station_walk_distance` / `walk_cache`，读端只取"米" | `query.ts:125-130`、`nav-service.ts:551` |
| 步行**时长** | 有，但是派生的：米 ÷ 基准速度（分档缩放） | `walk-fix.ts`、`catch-up.ts#requiredSec` |
| 步行**几何（polyline）** | **没有**。`walkRoute*` 只返回 `distanceM/durationS/snap*`，`steps[].polyline` 被合成后**仅用于算首末吸附距离**，随即丢弃 | `amap/client.ts:164-167`、`231-234` |
| 步行**分步指引** | **没有**。`steps[]` 的 `instruction` 字段从未被解析 | 同上 |
| 步行**跟随/偏航** | **没有** | — |
| 请求期能否调高德步行 | **明令禁止** | `amap/client.ts:10-12`（硬规则①）|

`client.ts:10-12` 原文（必须遵守的边界）：

```
① **绝不在请求时调用** —— 本模块只允许被 `src/lib/rebuild/**` 与 Cron import。
   `src/lib/recommend/**` **禁止** import 本模块（推荐链路实时预算很紧，
   任何同步外部调用都会直接吃掉它）。调用全部走离线批算 + 落表。
```

#### 2.4.2 结论

步行导航是**从零新增的子系统**，不是改造现有模块。它必须解决三个新问题：
1. 请求期调高德步行（配额/并发/超时）；
2. 分步指令的结构化（instruction + 折线 + 距离 + 转向点）；
3. 跟随的"已走/未走"切割与偏航重算（几何已有可复用的纯函数）。

### 2.5 诉求：搜索线路（现状：**线路被刻意排除在搜索之外**）

`nav/poi-search.ts:133-140`：

```ts
// 线路名（`route`）、已知地点（`place`，如校内部位/口岸）、泛 POI（`poi`）**一律不进下拉**。
// ① 线路名不是「想去的地点」，且造成「输入 25 就返回 25 路巴士」的困惑（产品实测）；
```

#### 判定模型（定位主导）

```
输入：fixes（GPS 采样，已过精度门）· colored（本腿上车站→下车站折线）
      vehicles（本帧车辆）· boardPos · boardMain

① 硬门（任一不满足 ⇒ 不判）
   G1 几何可用（colored.length ≥ 2 && !degraded）
   G2 有 ≥ 3 帧可信 GPS（accuracy ≤ 150m），窗口 ≤ 45s
   G3 冷却已过（SWITCH_COOLDOWN_MS）且本腿未自动触发过

② 定位三项（主判据，与 v3.5.5 的 R2 同源）
   P1 邻线：所有帧投影 distM ≤ tol（tol = max(80, accuracy×1.5)）
   P2 位移：沿线累积位移 ≥ max(60m, 5.5km/h × dt)
   P3 速度：平均速度 ∈ [5.5, 80] km/h

③ 车辆辅助项（只降门槛，不得单独触发）
   A1 = 存在车的 interval.from == 上车站（"刚从本站开走"）
   A2 = 存在车停在/挂靠上车站（status ∈ {stopping, terminal}）
   ⇒ A1 或 A2 成立时：位移门 × 0.6、所需帧数 3 → 2
   ⇒ A1/A2 均不成立时：位移门 × 1.0、所需帧数 3

④ 出结论
   hit = P1 ∧ P2 ∧ P3 ∧ (streak ≥ requiredFrames)
   plate = A1 的车牌（若存在且唯一）否则 null；progressSource = plate ? "vehicle" : "gps"
```

#### 定位不可用时的三件套（对应 PM AC-25a，必须逐条实现）

现状问题：候车态状态行右侧硬编码 `right = "正在检测车辆"`（`NavTrackBar.tsx:110`）。一旦 GPS 被拒权或长时间无帧，系统**事实上已停止判定**，但界面仍在说"正在检测" ⇒ 用户以为"车还没来"，实际是"我不再看"了。这正是 AC-25a 要禁的"把未判定渲染成正在判定"。

**判定 `paused` 的口径（纯函数，便于对拍）**：

```ts
// lib/nav/boarding-detect.ts 新增导出
export const GPS_PAUSE_MS = 60_000;
export function detectPausedOf(fixes: FixLite[], nowMs: number): boolean {
  const latest = fixes[fixes.length - 1];
  if (!latest) return true;                       // 一次定位都没拿到
  if (nowMs - latest.ts > GPS_PAUSE_MS) return true;  // 60s 无新帧 = 停了
  // 连续 2 帧精度超门限 ⇒ 视为不可用（与 trustedFixes 同门限）
  const tail = fixes.slice(-2);
  return tail.length === 2 && tail.every((f) => Number.isFinite(f.accuracy) && f.accuracy > R2_FIX_MAX_ACC_M);
}
```

> 注意：`paused` 只影响**自动判定**与**文案**，不影响地图蓝点（蓝点仍按 `youDot` 的冻结逻辑走，见 `useRideTracking.ts:681-695`）。两者不要合并成一个开关。

| 场景 | 冷却 | 理由 |
|---|---|---|
| 车辆位置（riding / boarding） | **5s** | DSAT 数据本身约 15s 更新一次；5s 足够让用户"再点一次"而不会空转。同时是**唯一**的连点防线 |

**实现要点（防"上一次那种假冷却"）**

```ts
// useCooldown.ts
export function useCooldown(totalSec: number) {
  const untilRef = useRef(0);
  const [sec, setSec] = useState(0);
  useEffect(() => {
    const t = window.setInterval(() => {
      const left = Math.max(0, Math.ceil((untilRef.current - Date.now()) / 1000));
      setSec((s) => (s === left ? s : left)); // ★ 值未变不 setState
    }, 250);                                   // ★ 250ms 轮询，显示粒度 1s，避免"卡秒"
    return () => window.clearInterval(t);
  }, []);
  const start = useCallback(() => { untilRef.current = Date.now() + totalSec * 1000; setSec(totalSec); }, [totalSec]);
  return { sec, cooling: sec > 0, start };
}
```

纪律：
1. **冷却状态必须来自"时间戳"，不是"请求状态"** —— 这是 2.2.2 根因（把 `disabled={traveling}` 当冷却）的直接纠正。
2. 计时器**挂在 hook 层**（`useCooldown` 由宿主持有），不挂在按钮上 ⇒ 按钮卸载/重挂不重置（现状 `RefreshButton` 是纯展示，OK；但要防止"宿主每次重渲染重建 timer"，故 `useEffect([])` + `useRef` 时间戳）。
3. 禁止在渲染期读写 `Date.now()` 作判据（`RouteSheet.tsx:222` 的 `macauHour` 是既有反例，本轮不动，只记录）。

### 3.3 诉求 R1：步行导航（分步指引 + 地图跟随）

#### 架构决策

诉求形态是「**详情页可预览，导航时跟随**」，且用户已排除语音/AR。

**架构决策（与 `03-设计-规格与Token.md` §2 对齐）**：步行跟随**不是独立全屏页面**，而是现有导航状态机的**第四态** —— `body[data-nav-phase]` 增加值 `"walk"`（现四值 `off|recommend|detail|riding`，`NavShell.tsx:272-278`）。理由三条：

1. 复用一个 `RouteSheet` 宿主，避免第二个全屏层与 bottom-sheet 手势打架（`RouteSheet.tsx:5-25` 已记录"两独立弹窗叠加"的历史教训）；
2. 阶段切换（步行结束 → 候车）由**同一条** `navPhase` 推导，不需要跨组件状态同步（PM `AC-06` 要求"阶段钩子由步行态切到候车/完成"）；
3. 设计稿的场景 A（详情页折叠预览）与场景 B（跟随）**共用同一份 steps 数据**，只是 `currentIdx` 一个为 `-1`、一个由定位驱动。

```
详情页（pane = "detail"）
  └─ 既有 .rc-row--walk 行（"步行 5 分 → 新馬路"，文案不动）
        └─ 行右侧新增 44×44 展开键 .walkseg__toggle
              └─ 展开 .rc-walklist（静态预览，currentIdx 恒 -1，全部按"未走"渲染）
                    └─ 点任一站点/上车站锚 ⇒ 进入跟随（nav-phase = "walk"）
                          ├─ .walknow（当前步大卡：指令 + 还有 N 米 + 约 N 分钟）
                          ├─ .walkseg（当前步 + 后续 2 步；已走压成一行"已完成 4 步"）
                          ├─ .walkoff（偏航提示，连续 2 帧才出）
                          └─ 地图：--map-walk-done（已走 69）/ --map-walk-ahead（未走 70）/ 当前步 73
                                       相机：按当前步 bounds + --map-fit-gap，animate ≤ 300ms
```

**互斥铁律**：`nav-phase === "walk"` 与 `nav-phase === "riding"` **互斥**。任一激活时另一入口隐藏（不是禁用，避免"看得见点不动"）。
**进入跟随的唯一入口 = 用户显式点击**（不自动进入）：`detailBody` 里步行段是首段（走到上车站）还是末段（下车站走到目的地），决定跟随结束后的下一态（→ `boarding` 或 `done`）。

**纪律**
1. **不做服务端缓存**：路径几何在 30 分钟内稳定，但落库/边缘缓存会引入"改了路网不更新"的第二次事故。改由客户端 5 分钟内存缓存（同 OD）。

3. **配额口径**：v5 walking 属"基础 LBS 服务"池（15 万/月，个人认证）。单次导航典型 1~2 次调用（首末段各一）。按人均 2 次/日、1000 DAU 估算 ≈ 6 万/月，需在 `/api/nav/walk` 之外**加日计数告警**（复用 `dsat_call_logs` 式记账思路，落 `amap_call_logs` 或直接 `console.warn` 阈值告警；**本轮不建表**，见 §4.3）。
4. **降级（必须有，不许空白）**：`rate_limited` / 超时 / 高德无路径 ⇒ 前端只显示**「直线距离 + 固定步速估算」+ 文字提示**（主理人 2026-10-29 裁决口径），**不显示假的分步**（宁可少，不可假 —— 沿用 `track.ts` 文件头"绝不猜测"的纪律）。固定步速沿用项目既有基准（`walk-fix.ts` 的常速基准，勿另起一套）。

#### 关于"数据本来就有，缺的是保留 + 暴露"（PM 第 2 问）

**结论：`show_fields` 不需要加字段，缺的是「step 边界」。**

- 现行 `walkRoute` / `walkRouteGcj` 已带 `show_fields: "cost,polyline"`（`amap/client.ts:130`、`:198`）—— 这是最小必要集：`polyline` 需显式声明，`cost` 给耗时；
- `steps[].instruction` / `road_name` / `step_distance` / `orientation` 是 v5 步行响应里**不受 `show_fields` 过滤的默认字段**，无需追加声明；
- **真正的缺口在 `client.ts:164` / `:231`**：

```ts
const polyline = path.steps?.map((s) => s.polyline ?? "").join(";");
```

这句把各 step 的 polyline **拼成一个串**，只用于算首末吸附距离（`snapStartM` / `snapEndM`）。**step 与 step 的边界在这一行被销毁** —— 事后无论怎么切都还原不出"第 3 步从哪到哪"。
⇒ 新模块 `walking.ts` 必须**按 step 保留** `{ instruction, road, distanceM, durationS, polyline: LL[] }` 数组（逐 step `parsePolyline`），并由服务端算好**累计里程 `cumM[]`** 一起下发 —— 客户端"当前第几步 / 还剩多少米"只需一次二分查找，不必在前端重复累加（也避免前后端口径分叉）。

#### 关于 AC-08「首次 ≤1.5s、命中 ≤200ms」的可行性（PM 第 1 问）

**必须先告知 PM 的一个事实**：线上函数真身在 **iad1（美东）**，`preferredRegion="sin1"` 在 Hobby 下不生效（`live.ts:26-32`，MEMORY「环境」节），而高德在亚太。`transit` 侧实测 1500ms 超时**必然超**，故 v3.3.0 上调到 4000ms（`transit.ts:52-63`，ADR-103）。
⇒ **单靠服务端同步取数，AC-08 的 1.5s 首屏大概率不达标**。不建议为此改指标，而是**把延迟藏到用户看不见的地方**：

| 手段 | 做法 | 效果 |
|---|---|---|
| **① 预取（主手段）** | 详情体 `detail-body` 一到（用户还在读卡片），**并行预取**首段与末段两条步行路径（`useWalkRoute` 在 `enabled=false` 时也能触发预取） | 用户点"展开步骤"时已命中 ⇒ 观测上 ≈ 0 网络时间，满足"命中 ≤200ms" |
| ② 客户端缓存 | 同 OD（坐标 4 位取整）5 分钟内存缓存 | 反复展开 / 退出重进 = 零请求 |
| ③ 骨架 + 渐进 | 展开瞬间即渲染卡片骨架（距离/时长来自 `detail-body` 的 `walkOut/walkIn`，已有），steps 到达后填入 | 首屏 LCP 不等网络 |
| ④ 失败降级 | 预取失败（429/超时）⇒ 展开时现取一次；再失败 ⇒ 直线示意 + 文案 | 满足 AC-08 的降级要求 |
| ⑤ 降压开关 | `WALK_PREFETCH` ∈ `both`（**默认**）/ `first` / `off`，**纯环境变量生效、不改代码**；三态由 `test:walk-prefetch` 覆盖（纯函数 `prefetchTargetsOf`） | 配额异常时 30 秒内可降级，无需发版 |
| ⑥ 日计数 | 每 24h 计数并 `console.info` 结构化日志（可查真实消耗曲线），月阈值 10 万只告警不降级 | 不为看账单才排查 |

**验收口径建议（给 PM）**："首次"定义为「用户**展开步骤或开始步行那一刻**到步骤可见」，而非"页面打开到步骤可见"。按此口径，预取命中 ≤200ms 可达；预取未命中时 p95 ≈ 高德 RTT + 200ms，**需实测**（本轮不给承诺值，先量再定；若实测 >2s，再讨论是否为 `walking` 单独走 `sin1` 区域函数）。

#### `follow.ts` 判定要点

```ts
// 已走切割：复用 route-overview 的 nearestOnPath + cumDistM（client-safe 纯函数）
export function progressOnPath(poly: LL[], fix: {lng,lat,accuracy,ts}, prevIdx: number) {
  const accOk = !(Number.isFinite(fix.accuracy) && fix.accuracy > 150);
  if (!accOk) return { walkedIdx: prevIdx, offRoute: false, frozen: true };
  const p = nearestOnPath(poly, fix);
  if (p.distM > 45) return { walkedIdx: prevIdx, offRoute: true };   // 偏航：不改已走，交给上层连续 2 帧判定
  const walkedIdx = Math.max(prevIdx, p.idx);                        // ★ 单调不回退
  return { walkedIdx, offRoute: false };
}
export const arrived = (remainM: number) => remainM <= 25;
```

**相机跟随（设计 §2.2）**：`NavMap` 已有唯一程序化相机入口 `applyCamera`（`NavMap.tsx:310` 附近注释"程序化相机调用唯一打标入口"）。跟随必须**走 `applyCamera`**，禁止直接 `map.setCenter`（否则手势/程序缩放状态机错乱 —— 该坑已在 `NavMap.tsx:655` 记录）。
跟随策略：视野 = **当前步折线 bounds + `--map-fit-gap`（24px）**；到步末 15% 提前把下一步并入视野；相机 `animate: true` 且 **≤ 300ms**。
★ 技术约束：`--map-fit-gap` 是 CSS 变量，而 `AMap` 相机只吃像素数 ⇒ 必须 `getComputedStyle(document.documentElement).getPropertyValue("--map-fit-gap")` 读取并 `parseFloat`，**禁止**在 JS 里硬编码 24（项目 P0 口径：颜色/间距一律从 token 读）。

#### 视觉（对齐 `03-设计-规格与Token.md` §1.1 / §2.3，token 名以设计为准）

| 元素 | Token | 折线参数 | zIndex |
|---|---|---|---|
| 已走（含当前步内已走过部分） | `--map-walk-done` | `strokeWeight: 5` · `strokeOpacity: 0.85` · `strokeDasharray: [0.5, 12]` · `strokeLineCap: "round"` | **69** |
| 未走（后续步） | `--map-walk-ahead` | `strokeWeight: 5` · `strokeOpacity: 0.55` · `strokeDasharray: [0.5, 12]` | **70** |
| 当前步（剩余行走部分） | `--map-walk-ahead` | `strokeWeight: 7` · `strokeOpacity: 1` · `strokeDasharray: [0.5, 12]` | **73** |

层级：三者严格插进既有 z 表（灰虚 68 < 69 / 70 / 73 < 灰实 74 < 站点 90/95 < pin 110/120 < 蓝点 128 < 车辆 130）。**不得插到蓝点或车辆之上**。

**★ 两组几何，而非"一条线切三段"（偏航重算决定的结构约束）**

偏航重算后路径几何整体改变。若按新路径重画"已走"，用户会看到**走过的路又变绿**。因此地图必须持有两组独立几何：

| 几何 | 来源 | 重算时 | z |
|---|---|---|---|
| `donePath: LL[]`（已走灰） | **累积追加**（每帧把当前位置并入） | **不清空** | 69 |
| `nowPath`（当前步剩余）+ `aheadPath`（后续步） | 当前 `steps` 按 `doneInStepM` 切分 | 整体替换 | 73 / 70 |

视觉上重算后灰线与新绿线自然接续，用户感知是"接着走"。这也意味着：**设计 §2.3 的三态参数表按"三段各自独立绘制"理解，而不是同一条折线切三份**。

`[0.5, 12]` + `lineCap:"round"` 为何画出圆点：`round` 在每段 dash 两端各补 `strokeWeight/2` 半圆 ⇒ 单点实长 6.5、高 6，肉眼即圆点。项目既有 `--map-dash-array: 2 14`（非乘车灰虚线）用同机制，已实证。
★ **必须 Playwright 截图验收**：若该 JS API 版本忽略 `strokeDasharray`，退化为"细实线底 + 上层 dashed"双层，并回报设计调整。

**★ `turn` 派生规则（服务端纯函数 `turnOf(step, prevStep)`，可单测）**

高德 v5 只给 `instruction` 文本与 `orientation` 方位，**无稳定语义枚举**。三级规则：
1. 响应含 `action` 字段 ⇒ 直取（「左转」「直行」…）；
2. 否则按 `instruction` 匹配：`左转/向左` → `left`；`右转/向右` → `right`；`掉头/向后` → `uturn`；末步 → `arrive`；
3. 否则用 `orientation` 与上一段方位差：|<30°| → `straight`；30~150° → `left/right`；>150° → `uturn`。
**映射约定**：「向左前方 / 向右前方 / 靠左 / 靠右」**统一映射为 `straight`**（不新增 `slight_*`，避免图标集膨胀与"图标说左转、实际斜走"的落差）。若要 `slight_*`，需设计同步加两个图标 —— 已交设计确认。

#### ★ 每站报站的配额风险（PM AC-42 要求"每站报站"）

一条线最长 90+ 站。若进入全景页对全部站点并发请求 `/api/station/eta?code=`，单次开页即 90 次 DSAT 调用 —— 直接撞风控面，且首屏必然超时。**架构约束（实现必须遵守）**：

#### ★ 关于 R8「快速滚动会把视口放大成整线遍历」（PM 提的风险，必须做机制而不是提醒）

PM 的判断是对的：`IntersectionObserver` 的天然行为是"扫过即触发"，用户从顶滑到底一次，90 个站点会全部进视口 ⇒ 事实上的整线遍历。**这不是配置问题，必须写机制**：

| # | 机制 | 具体取值 / 做法 |
|---|---|---|
| 1 | **滚动停止后才取（防抖）** | 监听 `scroll`，`setTimeout` 250ms 静默后才计算"当前视口内未取过的站"；滚动中只标记不请求 |
| 2 | **请求队列上限** | 待取队列 ≤ 8；超出时丢弃"离视口中心最远"的，**不是**先进先出（保证用户正在看的先到位） |
| 3 | **单页硬闸** | 单次页面生命周期内自动请求总数 **≤ 30**（约 1/3 条线）；达到上限后停止自动取，站点行显示「点此查看报站」手动键 |
| 4 | **并发上限 3** | 与 `BUCKET_CONCURRENCY` 同量级（`live.ts:74`），其余排队 |
| 5 | **可观测** | 每次自动请求累加计数，`console.info("[line-page] eta calls=", n)`；页面卸载时上报一次（首周观察指标，PM 要的日志） |
| 6 | **缓存命中优先** | 已取过的站（60s 内）不计入硬闸 —— 否则"来回滑两次"会白吃配额 |

> 纪律：这 6 条是**实现验收项**，不是建议。验收方法：Playwright 从顶滑到底来回 3 次，断言 `eta calls` 计数 ≤ 30 且不随滑动次数线性增长。

- **A4 与 B 不拒**（它们是产品功能本身，拒了等于拒用户）。这一点必须与 PM 对齐，否则 AC-50 会被理解成"全站要登录"，与本轮"拆除口令门 / 全站公开"直接矛盾；
- "不回显内部信息"对所有 **4xx/5xx** 一律生效：`error` 字段只允许固定枚举值（`unauthorized` / `gone` / `rate_limited` / `bad_request`），禁止把 `err.message`、SQL 片段、环境变量名回给客户端（现状 `api/nav/route.ts:136` 会回 `msg.slice(0,500)`，**需要收紧**）。

### 4.5 与设计的锁定契约（2026-10-29 定稿，开发照此实现，勿再改形）

#### 4.5.1 `WalkStep` 最终字段表（锁定版）

| 字段 | 类型 | 单位 | 可空 | 说明 |
|---|---|---|---|---|
| `idx` | `number` | — | 否 | 0 起；与服务端 `cumStartM` 对齐 |
| `turn` | `"straight" \| "left" \| "right" \| "uturn" \| "arrive"` | — | 否 | **服务端派生**（`turnOf`），前端不得从文本再猜 |
| `text` | `string` | — | 否 | 高德 `instruction` 原文（繁体/简体随高德，**不做转换**） |
| `sub` | `string` | — | **是** | 地标补充；缺失则不渲染该行，**不留空行** |
| `distM` | `number` | 米 | 否 | 本步距离（整数） |
| `cumStartM` | `number` | 米 | 否 | 本步起点在全程的累计里程 |
| `polyline` | `[number, number][]` | 经纬度（GCJ-02） | 否 | 本步折线，≥2 点 |
| `cumM` | `number[]` | 米 | 否 | 与 `polyline` **等长**，`cumM[0] === cumStartM` |

**明确不含的字段（不要再加，也不要预留位）**：

- 任何**震动/音频/语音**字段 —— 主理人 2026-10-29 裁决：偏航只做视觉提示（文案 + 颜色 + 「回到路线」按钮），
  全站至今无音频/振动能力，属新增面，本轮不做；
- `currentStepIdx` / `doneInStepM` / `offRoute` —— 这些是**运行时状态**，由 hook 输出，不进 API（见 §4.5.2）。

#### 4.5.2 当前步内已走米数（`doneInStepM`）：三项答复

| 问题 | 结论 |
|---|---|
| ① `nearestOnPath` / `cumDistM` 够不够用 | **够，但不足以单独定步**。两者只给"最近**顶点**"与顶点累计里程 ⇒ 顶点级分辨率（澳门步道顶点间距约 5~10m，直接切会有台阶感）。做法：`nearestOnPath` 定顶点 → 在**最后一段**做线性插值得到精确米数 → 再按 `step.cumStartM/cumM` 二分定位属第几步。三者都是 `route-overview.ts` 里现成的 client-safe 纯函数，**不新增几何库**。 |
| ② 放 API 还是纯客户端 | **纯客户端算**。API 只下发静态 `steps`（含 `cumM`/`cumStartM`）。理由：进度随 GPS 每 1.5~3s 变，放 API 等于把高频状态做成网络请求；而静态里程已由服务端算好，客户端只需"投影 + 二分"，无第二套口径。 |
| ③ 抖动导致比例回退 | **单调不减 + 1.5m 死区**（采纳主理人口径）。实现：`next = max(prev, raw)`；`if (raw < prev) 保持 prev`；仅当 `raw - prev > 1.5` 才推进。偏航/精度超门限（`accuracy > 150m`）时**冻结**，不清零。 |

输出给设计的两值：`ratio: number`（`0~1`，= `doneInStepM / step.distM`，用于切当前步折线）+ `doneInStepM: number`（整数米，用于文案「还有 N 米」的余量计算）。
⚠️ **判步唯一口径 = 服务端 `cumM` + 客户端投影**，禁止在别处（如按顶点数）另算一遍 —— AC-04「越过当前步终点自动推进」依赖唯一口径。

#### 4.5.3 冷却作用域（答复"会不会把步行推进一起冻住"）

**不会，但必须显式隔离**。现状 `RefreshButton` 的冷却只影响"点击刷新车辆"这一动作，不持有任何全局定时器，
也不阻塞 GPS 帧；步行推进由 `useUserFix` 帧驱动（1.5~3s），与冷却**完全无关**。
但存在一处真实耦合风险：若把冷却状态提升成"全局 busy"，会让步行进度看起来"卡住"。因此契约定为：

| 项 | 规则 |
|---|---|
| 冷却作用对象 | **仅**「巴士车辆数据刷新」（`fetchFrame`） |
| 不影响 | ① 用户定位刷新（`useUserFix` 自有 1.5/3/10s 节拍）② 步行进度推进（帧驱动）③ 步行路径重算（自有 3s 冷却，独立实例） |
| 实现纪律 | 冷却状态**只能**在 `RefreshButton` / `NavTrackBar` 的局部作用域使用；**禁止**进入任何"全局 loading/busy"变量 |
| 作用域判定 | `refreshScope: "bus" \| "lrt"` = **当前追踪腿的 `kind`**（无追踪取 `card.rides[0].kind`）；`"lrt"` ⇒ `data-cooldown="off"` |

#### 4.5.4 `CatchTier = 0` 的边界（主理人裁决 2026-10-29）

`CatchTier` 只影响**标签渲染**（`TierBadge`，数据源 `card.rides[].tier`，见 `lib/recommend/card.ts:220`）。
**禁止**据此改变任何按钮的可用性（含详情页主按钮"开始导航"）。用户口径是"只给这个标签，不做任何其他推荐"，
禁用主按钮属于额外行为，未经授权。
架构纪律：档位值是**展示字段**，不得作为任何 `disabled` / 交互分支的判据；代码评审必须拦。

#### 4.5.6 相机与地图适配（**禁 `setFitView`**，与设计建议的分歧在此）

设计师建议用 `map.setFitView(null, true, [g,g,g,g])`。**本项目不能用**，有两次实测证据（`NavMap.tsx:694-708`）：

> 「前一版用 `setFitView(overlays, …)` + 等 marker 就绪重试 —— **实测仍然失效**：取景后 zoom 掉到最小值 11（= 一屏 27.6km），中心跑到珠海斗门/黄杨山一带。`setFitView` 内部会参考 `setLimitBounds` 与遮罩范围，在这个「底图限制在澳门」的场景下把视野撑到了极限。」

因此步行跟随的相机**复用既有 `fit-box` 自算通路**，只做一处扩展：

| 项 | 现状 | 步行需要 | 改动 |
|---|---|---|---|
| `frame({mode:"fit-box", box, slotTopPx})` | 只处理"底部被面板占"（`availH = slotTop - 2gap`，`panBy` 抬到顶部槽中心） | 步行时**顶部有横幅、底部有面板**，两侧都占 | 扩为 `insetTopPx` + `insetBottomPx`：`availH = h - insetTop - insetBottom - 2gap`，`panBy` 把框中心抬到中带中心 |

- `gap` 继续走 `fitGapPx()`（已接 `--map-fit-gap`，回落 20）；
- 步行调用方传 `insetTopPx = safeTop + --walkturn-h`、`insetBottomPx = 面板顶边`（`topsPx[detentIndex]` 已有）；
- zoom 仍 clamp `[12,16]`，仍 `applyCamera(() => { setZoomAndCenter(z, c, true); panBy(0, dy) })`；
- **不得新增第二套相机数学**，也不得在组件里直接 `map.setCenter`（`NavMap.tsx:310` 的 `applyCamera` 是唯一程序化入口）。

#### 4.5.8 `donePath` 的规范语义（设计 §2.3 与本文必须字面一致）

**唯一定义（两份文档引这一条，不得各写一套）**：

```ts
// hook 输出（useWalkFollow），NOT in API
donePath: [number, number][]   // GCJ-02 顶点序列，已走过的整段（累积，单调增长）
```

规则四条：

1. **来源**：每帧把"当前位置投影点"追加到 `donePath` 末尾；重算（偏航）后**不清空、不重置**。
2. **增长性**：长度单调不减；已追加的顶点**永不删除、永不回退**（配合 `doneInStepM` 单调不减）。
3. **与当前路径的关系**：`donePath` 与 `nowPath`/`aheadPath` **可能几何不同源**（重算后路径变了），
   视觉上允许"灰线与新绿线接续但不完全共线"——这是正确行为，不是 bug。
4. **渲染**：`donePath` 用 `--map-walk-done`（z **69**），`nowPath` 用 `--map-walk-ahead` + `strokeWeight 7`（z **73**），
   `aheadPath` 用 `--map-walk-ahead` + `strokeWeight 5`（z **70**）。三者各自独立 `AMap.Polyline`，
   **不是同一条折线切三份**。

> 设计 §2.3 的表请按"三条独立折线"表述；字段名统一用 `donePath` / `nowPath` / `aheadPath`（不要用 `walked` / `remaining` 之类的别名），
> 终稿 Spec 只引用本文这一条。

### 5.2 「彻底去缓存」的精确边界

**可以彻底不缓存的（用户可感知的秒级实时数据）**

1. 车辆位置与状态（`/api/route-vehicles`）
2. 区间进度与"还剩 X 分钟"
3. 站点报站（`/api/station/eta`）
4. 步行跟随位置与其"已走/未走"
5. 推荐卡片里的**数值**（等车/到站/总时长）

**必须保留缓存的（否则是性能事故，不是"实时"问题）**

6. 静态派生行（站序、段统计、步行、换乘、轻轨时刻、线路色）：`unstable_cache` 60s + 进程内 60s。
   **理由（项目已有实测反证链，`query.ts:12-18`）**：函数真身在 iad1、主库在新加坡，**每次冷启动重建连接 ≈ 2.3s**；实测"提高连接池上限"与"压掉 9 成传输量"都无效 ⇒ **固定建连成本才是瓶颈**，只能靠跨实例 Data Cache 绕过。
7. 站点/线路/走向/站序：纯静态，`s-maxage=3600` + 客户端 `force-cache`。
8. 高德 POI 搜索：月配额 5,000 次且**超限静默返回空**，必须靠缓存与熔断。

**"刷新"的语义边界（写进实现注释，防止后人误解）**

- 刷新 = **旁路 `transit_cache`（高德方案骨架）+ 重取 DSAT 实时**；
- 刷新 **不**旁路静态索引、**不**清 Data Cache、**不**重查 `route_shapes`；
- ⇒ 用户点刷新后，**卡片集合仍可能不变**（因为高德方案 15 分钟桶内本就稳定），但**所有数值都是新的**。这符合"只刷数字不换路线"。
