## 0. 阅读须知

### 0.1 本文件的定位

这是**既有成熟项目的迭代规格**，不是从零立项。因此：

- 不重写整体 PRD，只把 6 项诉求拆成「可验收的子项」并划清边界；
- 所有「现状」结论都指向具体代码位置，供架构核对；凡属推测的根因，一律标注「待实证」，不得当作事实往下传；
- 验收标准统一写成 EARS 形式并编号（`AC-01` 起），测试用例直接引用编号，不再自造描述。

### 0.2 术语与口径

| 术语 | 含义 |
|---|---|
| 步行出行段（walk-out） | 出发地 → 上车站 |
| 步行到达段（walk-in） | 下车站 → 目的地 |
| 目标车 | 本次推荐方案指定的那一班车（有车牌或有班次时刻） |
| 在途车 | 同线路当前正在路上、尚未到本上车站的车辆 |
| 阶段机 | 候车 → 乘车 → 到达的阶段状态（现有 `data-nav-phase`，另有 `body[data-nav-phase]`） |
| 详情页 | 方案详情弹窗体（`RouteSheet` 的 detail pane） |
| 全景页 | 本次新建的「线路站点全景页」，按线路展示走向与全部站点 |
| 大概率赶不上 | 新增档位文案：连档 1（全力冲刺）都赶不上，判定结果为空 |
| 定位周期 | 系统自动取一次用户定位的间隔 |
| **「官方主表不列」** | **不等于**「已停运」。DSAT `getRouteData` 不再返回某线的站序（双向均返回 0 站、且对照组正常）时，只能判定「官方当期不提供」，**不能据此推断线路已取消** |

> **术语区分（2026-10-30 定，非 AC）**：本轮同步停用 6 条线路（`36 / 3AS / 17S1 / 17T / 26S / 52S`），原因各不相同，**处置也不同**：
> - **永久取消**：`36`（已并入 MT2）⇒ 应永久停用，属真实下线；
> - **时令/节假日专线当期未开行**：`3AS / 17S1 / 17T / 26S / 52S` ⇒ DSAT 只是暂不提供站序，**其停用不需要人工干预，DSAT 恢复列出即自动复活**；
> - 因此**不得**把「停用 6 条」写成「下线 6 条」，也不得据此在界面或文档里宣布线路已取消。
> - **同步守卫**：每次同步若停用 ≥2 条，必须在日志里告警待人工确认——单条多为专线当期未开行（可忽略），成批则更可能是接口结构变化而非官方真取消。

### 0.3 行业知识库取舍说明

专家包 `references/industries/` 下现有 5 份：SaaS/B2B、电商、企业管理、内容社区、AI 原生。**没有城市公共交通 / 导航出行类目**。

- 选取：`saas-b2b.md`（工具型产品，最接近"以数据正确性为核心的工具"这一形态）；
- 取舍：仅采用其「克制、专业、数据密度优先」「操作需可撤销」「状态必须可解释」的原则；其主色（Slate Blue / Indigo）、左侧导航布局、Dashboard 范式**全部不适用**，本项目是移动优先的地图类 PWA，视觉沿用项目现有绿主题与既有图标层级；
- 补充：步行导航的"成功标准"改以产品对标（Google 地图 / 高德地图的步行导航交互范式）为依据，联网核实要点见 §0.4。

### 0.4 步行导航对标基线（联网核实，2026-10-29）

对标结论（用于定义"做到什么程度算达标"，不作为功能清单）：

1. **两层认知分工**：先给「路线预览」（整条路径 + 起终点 + 周边关系），再给「逐步导航」（只回答"现在往哪走"）。二者是不同界面状态，不是同一张图放大。
2. **逐步导航的最小充分信息** = 当前位置（蓝点，带朝向）+ 下一个转向动作 + 到该转向点的距离；缺少任一项，用户就必须自己解释地图。
3. **已走过部分视觉降级**（变灰/变淡），剩余路径保持高对比，让"还剩多远"一眼可读。
4. **走错/偏离时给"回到路线"的动作**，而不是静默重算或静默不管。
5. **首次进入需原地确认方向**（指南针/朝向扇形），这是实际使用中最常见的失败点。

本项目的差异化取舍：不做 AR、不做语音（见 §3 不做清单），把"分步指引 + 地图跟随"做到与上述 5 点对齐即可。

## 2. 验收标准（EARS）

约定：
- 三种句式 —— **While**（状态持续期）、**When**（事件触发）、**If**（条件分支）；
- 「系统必须」后面必须是**可观察**的行为（界面上能看到、或日志/状态钩子上能取到），不得写"优化""更好"这类不可判定词；
- 验证方式列只写**取证手段**，实现细节由架构决定。

### 2.1 需求 1 · 步行导航（AC-01 ~ AC-14）

| 编号 | 类型 | 验收标准 | 验证方式 |
|---|---|---|---|
| AC-01 | While | 在方案详情页处于"可出发"态时，若首段步行距离大于 0，系统必须展示一个文字为「步行指引」的入口，点开后可看到完整步骤列表，每条含转向动作文字（如「右转进入……」）、路名、该步距离。 | 详情页截图 + 步骤条数与高德返回 steps 条数一致 |
| AC-02 | When | 当用户从步骤列表点「开始步行」，系统必须同时满足四项：地图居中并跟随用户位置；剩余步行路径以主题绿渲染且为「圆点虚线」样式；已走过部分渲染为灰色；地图上方显示当前步的转向文字与到该转向点的剩余距离。 | 导航态截图 + 逐步推进后"灰/绿分界"位置随定位前移 |
| AC-03 | While | 在步行导航进行期间，系统必须以不超过 5 秒的间隔自动更新用户位置，且更新不依赖用户点击任何刷新控件。 | 断网监测/日志时间戳，或断点观察定位请求间隔 |
| AC-04 | While | 在步行导航进行期间，当用户在地图上的投影点越过当前步的终点时，系统必须自动推进到下一步并把该段置灰；若越过的是最后一步，则进入到达态。判步口径唯一：`currentStepIdx` 由**服务端下发的累计里程** + 客户端对定位做投影后二分得出；前进量以"本步内已完成米数 ÷ 本步距离"表达（0~1），且必须单调不减并带 1.5 米死区；偏航或定位精度超过 150 米时**冻结当前步、不回退**（不得出现"走一步又退回上一步"的抖动）；**客户端不得重算累计里程**。 | **执行前置（缺了这条就触发不了偏航）**：① 固定 OD，按铁律 28 用 `VERIFY_OD` 指定有车方向的用例；② 用浏览器注入定位：先沿路线走 3 帧（建立已走几何），第 4 帧把坐标抖动到离线 60 米外并保持 2 帧（触发偏航，阈值 45 米 / 2 帧 / 精度门 150 米），第 5 帧回到路线。**断言两件**：① `currentStepIdx` 不回落；② `donePath` 顶点数单调不减（不得清空、不得变短）。后者专防"重算顺手重置 donePath"——编译能过、跑得动、零报错，只有用户看到走过的路复活变绿 |

| AC-06 | When | 当步行段结束（到达上车站或到达目的地），系统必须自动结束步行导航并切换到对应下一阶段（候车 / 完成），并给一次性的阶段切换提示。 | `body[data-nav-phase]` 由 `walk`（第四态）切到候车/完成；步行态不是独立全屏页，只是阶段机的一态 |
| AC-07 | While | 在随车导航（乘车）阶段期间，系统不得同时展示步行跟随态；两阶段互斥，任一时刻只有一个阶段在驱动地图。 | 两阶段切换过程截图，不出现双跟随/双路径 |
| AC-08 | If | 若高德步行路径规划失败或返回空步骤（含区域无路网数据），系统必须降级为「直线示意 + 距离 + 预计时间」，并以文字说明「暂无详细步行指引」；不得出现空白地图或永久加载态。延迟口径：**"首次可见"的起算点是「用户展开步骤或点开始步行的那一刻」**，不是页面打开时刻（页面打开时服务端在美东、高德在亚太，同步取数无法承诺秒级）。 | 构造失败（配额熔断/无路网 OD）后观察降级文案；首次可见时间以"展开→步骤可见"计 |

| AC-09 | If | 若某步行段距离超过 2500 米，系统必须（a）照常展示距离与预计时间；（b）不自动启动跟随导航；（c）给出「该段步行较远，请确认是否改乘」的提示（不推荐任何具体替代方案）。 | 构造长步行 OD 验证三条 |
| AC-10 | When | 当用户预览步骤后返回详情页，系统必须保持原面板档位与地图视野不变（不得重置为初始展开档或默认视角）。 | 返回前后截图对比 |
| AC-11 | If | 若用户定位不可用或被拒绝授权，系统必须（a）仍能展示步骤列表与路线；（b）以文字说明「定位不可用，无法跟随」；（c）提供手动「下一步 / 上一步」控件。 | 拒绝定位权限后走一遍流程 |
| AC-12 | When | 当应用从锁屏/后台返回，系统必须恢复到当前所处的那一步（不得从第一步重启，也不得丢失阶段）。 | 锁屏 60 秒后返回，步骤号与灰绿分界不回退 |
| AC-13 | When | 当最后一步完成，系统必须展示到达态（目的地名称 + 「已到达」），并停止持续定位请求。 | 到达后观察请求停止 |
| AC-14 | Ubiquitous | 系统必须为步行导航的当前步提供可供自动化观测的状态标记，使测试脚本能断言「当前第 N 步」而无需图像识别。 | 钩子已定稿：`body[data-walk-step]` = 当前步序号（1 起）；`.walkstep[data-walk-state]` = `now` / `done` / `ahead` |

### 2.3 需求 3 · 刷新（AC-26 ~ AC-37，含细分 AC-37a）

#### 断言 D-2：双源一致性（Given / When / Then）

> 总站集合在两处**各自计算**，这是有意的（同一份代码同一处写错，自己验证自己永远绿）：`src/lib/rebuild/segment-stats.ts`（内存版 `terminusMains()`）与 `scripts/build-hop-stats.ts`（SQL 版窗口函数子查询）。

- **Given**：两张派生表（`segment_stats` / `route_hop_stats`）的「总站集合」由上述两处独立实现各自算出，互不引用；
- **When**：用**同一份冻结快照**跑一致性断言（**禁止直读生产库**——否则红了不可复现，且分不清是「代码分叉」还是「数据在这两次之间变了」，这两种结论后面的处置完全相反）；
- **Then**：
  1. 两侧结果**逐条相等**；不等即红；
  2. 差集必须带**站码 + 方向 + 两侧各自的值**（只报「有差异」等于没报，定位不到哪个方向错了）；
  3. 差集按**三类分别计数**，不许合成一个总数（定义：**左** = `segment-stats.ts` 内存版；**右** = `build-hop-stats.ts` SQL 版）：

     | 类 | 机械含义 | 偏差性质 | 先查什么 |
     |---|---|---|---|
     | `仅左有` | 该站码**只**被内存版判为总站 | **漏算**：右少算一个总站 ⇒ `route_hop_stats` 侧**漏排**该站长停 | `route_stations` 的 seq 边界（`seq=0` / 重复 seq）、站台号后缀归一（`C690/3 → C690`）是否与 SQL 的 `regexp_replace` 等价 |
     | `仅右有` | 该站码**只**被 SQL 版判为总站 | **多算**：右多算一个总站 ⇒ `segment_stats` 侧**漏排**该站长停 | 同上反向；典型形态是「别线总站 / 本线中途」（实测此类 233 段，2.1%，全为真实总站待发） |
     | `两边都有但值不同` | 两处都判为总站，但归属方向或归一后站码不同 | **口径差**：两边都「有值」，看着都对，最危险 | 方向字段 `dsat_dir` 的取值口径；`mainCode()` 与 `regexp_replace` 是否逐字符等价 |

     > 为什么必须三类分开计数：合成一个总数时，「漏排 3 个站」与「多排 3 个站」会互相抵消，净差 0 看起来全绿——但两张表已经各自错在三处。
- **红时的处置纪律**：不许「以某一侧为准」直接合；先按上述三类定性，再定哪个是错的。**允许**两侧一起改判据，**不允许**把断言改成「忽略差异」。
- **门禁属性**：本条进脚本门禁（随重建脚本一起跑），不是一次性人工核对——一次性核对过的东西，下一次改 `route_stations` 就会静默失效。

> **实现现状（2026-10-30 已收口，三条缺口全补）**：对拍脚本独立成 `.verify/check-terminus-parity.mjs`（支持 `--snapshot=` 冻结对拍），三条缺口逐一闭合：
> 1. **第三类已显式打印**：`③ 两边都有但值不同=0（结构性为 0：比较键即归一后的码，值即键）` —— 按「**不许静默缺一项**」处理：比较键仍是站码，第三类结构上不可能非零，但**必须在日志里明说**，否则读者会以为三类都验过。
> 2. **差集已带方向**：输出形如 `25/dir=0/seq=12/C656`（线路 + 方向 + 序号 + 原始站码），重名站可定位。
> 3. **已进门禁**：`if (!ok) process.exitCode = 1` ⇒ 差集非空即非零退出，**不再「红了照样把表写完」**。
> 4. **归一已对齐**（本轮真缺陷，已修）：`TERMINUS_SQL` 改 `regexp_replace(rs.station_code, '(^[A-Za-z]+[0-9]+).*$', '\1')` ⇒ `C690/3 → C690`、`LRT-BAR → LRT-BAR`（不匹配原样），与 JS `mainOf` 同义。修前 JS 52 vs SQL 47（差 `LRT-*` 6 个 + 垃圾值 `LRT` 1 个），修后 **52 = 52，三类差集全 0，exit=0**。
>
> ⇒ **本条当前可直接作为门禁跑**，不再是「待补」。回归时若它变红，按上表三类定性，不要先怀疑数据。

#### 断言 D-3：判据判别力（**必须双向验，只验一侧等于没验**）

> 本条存在的理由：计数只能证明「排了多少」，证明不了「排对没排对」。一个写成 `if (dwell>=3) exclude()` 的粗暴实现也能让「排除样本数」看起来合理，甚至让 Then-1 变绿——只有 Then-2 能抓住它。

- **Given**：长停判据为「**2 个候选集定义 + 3 道运行期门**」——候选集定义①-1 `dwell≥3` / ②非总站；运行期门 `headway-sync` / B `insufficient`（逐格 n≥5）/ C `peak-crowded`（占比 ≥0.8）（见 `07` §h.7）；
- **When**：对全量 track 样本（分母 183,086）跑一次排除；
- **Then**：
  1. **必须排除** `(25, C654)`、`(26, C654)` —— C654 聯生圓形地是真**总站**，长停为**司机休息、昼夜均匀分布**，且逐格样本充分；
  2. **必须不排除** `(3A, M233)`、`(18A, M233)` —— `M233`（東北大馬路/東華）在 `3A`（seq 22/36）与 `18A`（seq 4/25）上都是**中途站（MID）而非总站** ⇒ 由「**候选集定义①-2（非总站）**」短路掉（**不写 `skipPairs`**）。中途站的长停是真实排队/拥堵，一律不排；
  3. **两侧任一侧不成立即红**。

> ⚠️ **归因必须写对（2026-10-30 经站序表核正）**：`M233` 对 `3A / 18A / 2A / 18 / 18B / 10B / 102 / 34` **全部是中途站**，没有任何一条线把它当总站。所以 Then-2 的实际拦截机制是「**候选集定义①-2（非总站）**」（前置短路，**不是运行期门**），**也不是**高峰判定。
> ⛔ **不得**写成「`peak-crowded` 判其高峰占比 ≥0.8 才没排」：该门**已落地**，但实测 `(3A,M233)` 高峰占比仅 **0.571** < 0.8 ⇒ **该门根本没拦它**；拦它的是**候选集定义①-2（非总站）**（`M233` 是 MID，`long-stop.ts:198` 直接 `continue`）。写错归因的后果是——给一道「挂着没用过」的门记功，而写反了方向的实现也能靠「M233 本来就不是总站」混过验收。

> ⚠️ **两道 0 命中的运行期门要如实标注**：门 `peak-crowded` 已落地但**一对也不命中**（全部候选站对高峰占比最高仅 **0.571**）；门 `headway-sync` 同样 0 命中（比值 0.13~0.44）。⇒ 二者都是「防将来」的防御性门，**本轮实际起作用的是「候选集定义①-2（非总站）」+「门 `insufficient`」**。行文时不要暗示这两道被真实数据检验过。

**为什么必须写死站码而不是只写数量**：数量（114 / 3 站对）一旦判据跑偏也可能凑出来；`(25,C654)` 与 `(3A,M233)` 这一对是**同一套判据给出相反判断**的实证——左边（总站 + 样本充分）删了、右边（中途站）留了，才说明判据有判别力，而不是「一律排除」或「一律保留」的阀门。

**红时的两种典型错法与各自含义**：

| 现象 | 说明 | 处置 |
|---|---|---|
| C654 两组未被排除 | 判据过度保守，或 `insufficient` 门把 C654 也判成样本不足 | 先查 C654 的**逐格** n 是否因分桶过细而 <5，**禁止**为让它「能判」而下调 `MIN_DWELL_SAMPLES` |
| M233 两组被排除 | 总站集合算错了（把中途站判成总站，或 SQL 侧归一缺陷把 `M233` 混进总站并集） | 查 `terminusMains()` 与 `TERMINUS_SQL` 的两侧差集；这是**最危险的一种**，会静默缩短 ETA |

**归一守卫（已修，仍要写在这里防复发）**：`TERMINUS_SQL` 的归一必须与 JS 侧 `mainOf` **同义**，否则对拍永远不可能相等、最终被人当成「常红」忽略。修前 `regexp_replace(station_code,'[^A-Za-z0-9].*$','')` 把 `LRT-BAR` 压成 `LRT`（JS 侧保留原值）⇒ JS 52 vs SQL 47。**现为** `regexp_replace(rs.station_code, '(^[A-Za-z]+[0-9]+).*$', '\1')` ⇒ `C690/3 → C690`、`LRT-BAR → LRT-BAR`，实测 **52 = 52 / 三类差集全 0 / exit=0**。⇒ 今后改任一侧的归一都必须同步另一侧并重跑对拍。

**回归守卫**：任何判据/阈值改动后重跑本条。若 Then-1 与 Then-2 同时绿但 M233 两组的样本数明显变化，说明站序或总站并集动了，须同步更新 `07` §h.6 的三代对照结论与算术恒等式。

#### 断言 D-4：时段口径（**禁止读 `time_bucket` 列**）

> 这是「同一批数据、两种算法、结论相反」的典型陷阱，且**不会报错**，只会让排除面悄悄变大。

- **Given**：`segment_samples.time_bucket` 列存的是**新旧桶混装** —— `am_peak` / `pm_peak` 是旧四桶（7-10 / 17-20），`pm` 是新五桶，而 `am_work` / `am_weekend` **一条都没有**；
- **When**：任何判据要做「高峰 / 非高峰」判定；
- **Then**：
  1. **必须**从 `observed_at` 现算，调用 `buckets.ts#bucketOfRoute`（唯一入口 `long-stop.ts#kindOfBucket`）；
  2. **禁止**读 `time_bucket` 列，也**禁止**手写小时区间；
  3. 违反即红——**读该列会让 07:00-09:00 的高峰样本整体漏掉一半**，高峰占比系统性低估 ⇒ 本该判「排队」的站被判成「休息」⇒ **排除面扩大、ETA 变短**，正是本轮要修的病的反向复发。

**小时集参考（由枚举反查 `bucketOfRoute` 得出，落地在 `long-stop.ts#KIND_HOURS`）**：`peak` = 整点 **7、8、16、17、18、19**（＝ `am_work` 工作日 7-9 ∪ `pm` 全周 16-20）；`nonpeak` = 其余 18 个小时。这组数字是**推导结果**，改 `buckets.ts` 桶边界后自动变——脚本里引用导出常量，**不要复制这 6 个数字**。

#### 断言 D-5：节假日口径必须与聚合侧**同源**（必填参数，不许有默认值）

> 「不读 `time_bucket`」只解决了**半个**口径问题。另一半是：同一份数据在**两处**做分桶，节假日判定必须一致——否则同一个样本在聚合侧和判据侧会落进不同的桶。

- **Given**：分桶有两处消费方 ——
  - 聚合侧 `segment-stats.ts`：`bucketOfRoute(mp.weekday, mp.hour, holidays.has(macauDayOf(t)))` ← **传了节假日**；
  - 判据侧 `long-stop.ts`：`kindOfBucket(mp.weekday, mp.hour, …)` ← 曾经**没传**；
- **When**：任何一处对样本分桶；
- **Then**：
  1. `loadLongStopPolicy(q, isHoliday)` 的第二参**必填、无默认值**（刻意不写 `= () => false`——一旦有默认值，下一个人漏传就又是静默漂移，编译期不报错）；
  2. 两个调用方都必须传 `(ms) => holidays.has(macauDayOf(ms))`（`segment-stats.ts` / `build-hop-stats.ts`）；
  3. 违反即红：节假日若是工作日，聚合侧算 `am_weekend`（非高峰）、判据侧算 `am_work`（高峰）⇒ **同一样本两处不同桶**，`peak-crowded` 的占比虚高或虚低。

**这为什么不是「保守 vs 精确」的取舍**：方向上看漏传会「节假日晨间被算成高峰 ⇒ 更少排除 ⇒ 不产生少算等待」，风险似乎可控；但**同一份数据出现两个口径**本身就是静默漂移，属于本项目明令禁止的那类问题——今天它无害，下一次改桶边界就会变成真缺陷，而且**不会报错**。

**实测影响面（修前量过，用于说明「当前数字为什么没变」）**：6 条节假日样本 / 4 个总站站对 / **0 个判定翻转**（`51|M9` 2 条 0.217→0.217、`50|T560` 2 条 0→0、`26|C654` 1 条 0.381→0.381、`11|M172` 1 条 0→0）。`lrt_holidays` 共 40 条，落到长停样本的只有 6 条 ⇒ **数字不变是运气，不是设计**。修复后复跑与修前逐位相同（114 / 3 / 8 / 31 / 183,086）。

### 3.1 Backlog（本轮不做、不排期、**不得写成 AC**）

> **起点快照口径（2026-10-30 定稿，替换此前「只冻一次」的模糊表述）**
> - **退出「可出发态」＝ 一次规划结束 ⇒ 起点按当前位置重新冻结。** 依据：不释放的话，起点行显示「我的位置」而红钉停在旧坐标，**标签与坐标不一致**，用户再出发会**从旧位置计算**。
> - **同一会话内（未退回可出发态）起点钉不变**：点定位、点刷新、切面板档位**都不变**。
> - **退回可出发态后再出发 ⇒ 按当前定位重冻。**
> - 事实前提：首页**没有**「把我的位置设为起点」的入口（`from` 只由 `pickPoint` 写入；`SearchSheet.tsx:511` 的「我的位置」是**未选起点时的显示文案**，不是可点选项）。
> - ⚠ 本条为**口径说明**，不设 AC、不排期。与 BL-01 的边界分工见下表。

| 编号 | 待办 | 背景与正确做法 |
|---|---|---|
| BL-01 | 提供**显式的**「从当前位置重新规划」动作 | 现无该能力。**不得靠在实现里自动覆盖起点快照来"顺手解决"**：若允许无条件覆盖，导航中点过定位、再回推荐点「出发」，就会静默变成「从半路重新规划」。**将来支持的正确做法**＝新增一个**显式按钮**（收藏页 `FavoritesClient.tsx:265-270` 已有同类先例），**只在该动作内**刷新快照；**禁止**让 `go()` 无条件覆盖。<br>**边界分工（防误读）**：本条只约束**同一会话内**（未退回可出发态）的替换；**退回可出发态时按上方口径自动重冻**，不属于本条范围、**也不需要按钮**。两条不冲突：会话内禁止静默改，会话结束才释放。 |
| BL-02 | 补齐少数线路的 `route_frequency` **班距区间**（`lo/hi`，目前只有中位数） | **⏳待测量结果确认后生效**：仅当「档 ③（无区间且无中位数）」的方案分布**集中在少数线路**时才立；若均匀散布全网，本条**不生效**（改按口径定 `tight`）。<br>**背景**：档 ③ 判 `tight` 是**临时兜底**，目的是**不静默乐观**，**不是**用罚分替代数据；**数据补齐后该罚应自然消失**。<br>**验收条件（三条须同时满足，缺一条不算完成）**：① 被列出的线路在 `route_frequency` 中均具备区间值 `lo/hi`（非仅 `median`）；② `compare-slack-impact` 跑出「档 ③ 因**真数据缺失**而落入」的方案数 = **0**；③ 这些线路的 `tight` 占比回落到全网均值区间、不再显著偏高。<br>**禁止**：为消除「某几条线老是被压」去调 `riskFactor`（调参红线 ≤ 5）。 |

## 4. 风险与依赖

### 4.1 风险

**R1（最高）· 拆口令门导致暴露面扩大，触发平台处罚**

- 事实基线：本项目 2026-10 曾因公开暴露被平台处罚一次（复盘 `docs/复盘-GitHub封号事故-20261028.md`；教训"公开可见=点火源"）。当前口令门是 fail-closed 的**唯一**总闸，`middleware.ts` 之外没有第二道通用防线。
- 具体暴露面（拆门后立刻成立，2026-10-29 架构全仓复核）：全仓 21 个 `route.ts` 中**只有 `/api/cron/rebuild` 自带 Bearer**，其余 20 个全靠中间件顺带保护。其中 `POST /api/dsat/grab` **完全无鉴权**（`api/dsat/grab/route.ts:44`，仅有一个风控开关判断），而它会写 `segment_samples` 等采集表并触发 DSAT 请求 —— 拆门当天即"任何人可污染采集库 + 刷 DSAT"。另有 `api/nav/route.ts:136` 在 500 时回 `msg.slice(0, 500)`，会把数据库/环境细节吐给前端。
- 对策（必须全部落地才算"拆干净"，逐条对应 AC-50 ~ AC-50d）：
  1. 按四类处置，不允许有"未处置"的接口：①令牌鉴权（`/api/dsat/grab` + `/api/cron/rebuild`）；②直接下线返回 410（`/api/timer/*`、`/api/free/*`，含单条读，防主键顺序扫描）；③公开加护栏（`/api/fav-routes`：同源 403 + body ≤16KB + 桶限流）；④只读全公开但走 DSAT 令牌桶（`/api/station/eta`、`/api/dsat/eta`）；
  2. 错误响应统一为固定枚举（6 个）：`unauthorized`/`forbidden`/`gone`/`rate_limited`/`bad_request`/`upstream_error`，细节只进日志。**漏掉 `forbidden` 的后果很具体**：收藏接口的跨站拒绝必须回 403，若无合法枚举，实现者只能回显原文或误用 `unauthorized`，两者都违规。**唯一豁免**：高德 JS 代理 `/api/amap-service/*` 的 `info` 字段属上游 SDK 协议，用于地图侧诊断，不在本条约束内（见 AC-50d）；
  3. 公开前逐页内容审查（AC-53）：无密钥、无连接串、无表结构、无 SQL 报错原文、无调试信息；
  4. 全站 `noindex`（robots）+ 不加 sitemap；
  5. 发布仍守每日一次窗口（铁律 34），不做连续多轮"试一下"。
- 残留风险（**已知、明确接受**）：
  1. 公开只读接口仍可能被高频抓取。可接受（数据本身来自公开接口），但需监控异常量级与 DSAT 调用曲线。
  2. **收藏数据仍可能被恶意写入**。`/api/fav-routes` 现状就是公开可写（`middleware.ts:46-49` 注释自认"接受此放宽"），本轮不关它 —— 它是收藏页的产品功能，无账号体系下硬造认证只会变成假安全。改为同源校验 + body ≤16KB + 限流与熔断三重护栏（AC-50c）。**残余后果：任何人都能往里塞垃圾收藏行**。影响面限于该表数据质量（可清理），不涉及用户隐私与生产库结构，故列为已知可接受风险，不做进一步加固。

**R2 · 彻底去缓存 + 每次真实消耗高德配额，可能撞配额断崖**

- 事实基线：搜索服务配额 **5,000 次/月**（超限静默返回空）；步行路径规划属基础 LBS 池（个人认证约 15 万次/月，控制台实测并发上限 3 QPS、串行最小间隔 400ms — `src/lib/amap/client.ts:44-52`）。
- 定量：5,000 次/月 ≈ 166 次/日。若去掉 10 分钟 TTL 缓存（`poi-search.ts:79`），一人一天搜 10 次、20 个活跃用户就触顶。触顶后表现为"搜索坏了"（虽然已有熔断文案 `HINT_AMAP_CIRCUIT`）。
- 对策：
  1. 打字阶段保持 0 配额（现行为不回退），只有"点搜索/回车"消耗；
  2. 保留熔断阈值与提示，并把熔断状态作为可见事实展示，不得用旧缓存冒充新结果（AC-34）；
  3. 步行步骤按"一次导航一次请求"，允许同一 OD 在**同一次会话内**复用（不跨会话、不跨用户），这不算"吃缓存"；
  4. 上线后观察 7 日的日消耗曲线后再决定是否恢复短 TTL（回到产品确认，不由工程私自加回）。
- 需用户知晓的取舍：**"彻底去缓存"与"配额安全"本质冲突**，本次按用户决策优先去缓存；一旦日消耗逼近上限，最先要动的就是这一条。

**R3 · 步行步骤的取数路径与现有工程硬规则的冲突（已定，残留延迟风险）**

- 事实基线：`src/lib/amap/client.ts` 文件头硬规则 ① —— 该模块**只允许**离线侧（`src/lib/rebuild/**`、Cron）import，禁止请求期实时链路 import；且内部串行 400ms 限速。
- 已定（2026-10-29 架构结论）：走**新建请求期取数路径**，否决"离线预热到表"。理由记录在案：步行 OD 是「用户当前坐标（任意、米级变化）→ 站点坐标」，走 50 米就换一个 OD，而 `walk_cache` 是「地点 ↔ 站点」固定对（`nav-service.ts:180-201`），覆盖不了任意起点。
- 残留风险（必须让用户知道）：线上函数真身在 **iad1（美东）**，`preferredRegion="sin1"` 在 Hobby 下不生效，高德在亚太；`transit` 侧实测 1500ms 必然超，v3.3.0 已上调到 4000ms。⇒ **服务端同步取数无法承诺 1.5 秒**。因此产品侧改用"把延迟藏起来"：详情体一到即并行预取首末两段（AC-08a），展开时命中 ≤200 毫秒，未命中先渲染骨架。**未命中场景的 p95 承诺值待实测定，不在规格里拍数字。**
- 另一个已确认的缺口（架构指出）：现有实现把各 step 的 polyline `join(";")` 成一个串（`client.ts:164`/`:231`），**step 边界被销毁**，事后无法还原"第 3 步从哪到哪"。⇒ 新模块必须按 step 保留（含 instruction / 路名 / 距离 / 时长 / 该步 polyline），并由服务端算好累计里程下发，客户端只做一次定位→步骤的判定，避免前后端各算一遍。

**R4 · 定位主导后的双面性：漏判与误判互换**

- 定位主导解决了"车辆数据延迟导致的误判"，但会把风险转移到定位质量上：隧道、地下站台、室内、冷启动首帧、accuracy 大于 150 米（现有精度门 `R2_FIX_MAX_ACC_M`）都会让判定要么迟到要么不判。
- 对策：判定必须**可撤销 + 可解释 + 可手动兜底**（AC-19/AC-21/AC-22/AC-23），且"不判定"必须给用户一条明确的手动路径（现有「我已上车」保留）。任何时刻不得出现"系统什么都不说、用户也不知道该点哪里"的状态。

**R5 · 去缓存推高服务端实时计算与函数执行时长**

- 推荐链路每次真实重算，会连带 DSAT 取数与派生计算；Vercel Hobby 有函数时长与并发限制，高峰期可能出现"转圈久"而非"结果旧"。对策：给推荐接口设超时与降级（现有 `degraded` 通道），并对超时给出可读文案而不是无限加载。

**R6 · 视觉层级冲突（新增绿路径 vs 现有地图层级）**

- 现有层级（记忆速查）：灰虚 68 < 彩段 72 < 灰实 74 < 站点 90/95 < 钉 110/120 < 蓝点 128 < 车辆 130。步行导航要新增"主题绿路径 + 已走过灰 + 蓝点跟随"，若层级插错，会出现"路径盖住站点"或"蓝点被路径盖住"。属设计 + 架构共同确认项，验收时以"蓝点始终可见、站点不被路径遮住、车辆标记仍最高"为准。

**R7 · 旧页处置（已由用户裁决，风险降为"执行完整性"）**

D-01（旧 `/routes` 删除）与 D-02（采集四页下线）已裁决完毕，不再是决策风险。**残余风险转为执行漏项**：漏删一个引用点或漏关一个子接口，就等于把真实数据继续公开。对策：AC-49a / AC-49b / AC-49c / AC-50b 联合验收，并按 §9 给出的引用点清单逐项勾销。

**R8 · 全景页的「每站报站」会制造一次高频 DSAT 调用（上线首周观察项）**

- 事实基线：单条线路最长 90 余站。若按字面实现"打开全景页就显示每站报站"，一次开页 = 90 余次 DSAT 调用，既撞风控面（铁律 19 熔断隔离、铁律 36 风控常驻），也必然首屏超时。
- 定稿口径：已选"懒加载"（AC-42a）—— 视口内 ±1 屏、并发不超过 3、按站 60 秒客户端缓存、`purpose=live_pos` 只记账不参与熔断、轻轨线零请求。
- 已落成机制（架构 2026-10-29，均为验收项）：① 滚动静默 250 毫秒后才计算视口（防抖）；② 待取队列 ≤8，超出时丢弃"离视口中心最远"的（不是先进先出，保证正在看的先到位）；③ **单页自动请求总数硬闸 ≤30**，达上限后停止自动取、站点行改为「点此查看报站」手动键；④ 并发 ≤3；⑤ 每次自动请求累加计数，页面卸载上报一次；⑥ 60 秒内已取过的站不计入硬闸（防止来回滑动白吃配额）。
- 验收方法：无头浏览器从顶滑到底再滑回，重复 3 次，断言计数 ≤30 且**不随滑动次数线性增长**。
- 观察口径：单页 DSAT 调用总数作为**上线首周观察项**，若普遍触顶 30，再回头谈是否放宽线路选点策略。

## 5. 用户旅程

### 5.1 旅程 A · 步行出发 → 上车 → 下车步行到达（本轮最核心）

1. 用户在首页输入出发地与目的地，点「搜索」。
2. 系统真实重算（不读上次结果），返回推荐卡片列表；卡片首行显示「步行 X 分」（常速基准）。
3. 用户点开第一张卡的详情页，看到分段：步行 → 上车 → 线路与总时长 → 下车 → 步行。
4. 用户点首段的「步行指引」，看到步骤列表：每条含转向动作、路名、距离；面板档位与地图视野不被重置。
5. 用户点「开始步行」。地图跟随居中，剩余路径为主题绿圆点虚线，已走过部分变灰，上方显示当前步转向文字与剩余距离。
6. 用户沿路线走。每越过一步终点，步骤自动推进，走过段变灰；若偏离超过 50 米，出现「已偏离路线」与「回到路线」。
7. 到达上车站。系统自动结束步行导航，切到候车阶段，并给一次性提示。
8. 候车期间，系统按 15 秒周期自动刷新报站；用户点刷新只刷巴士数据、可立即再点，不连带重新获取定位。
9. 目标车接近。若同线路另有一辆车先到站，系统不因此把用户判为已上车（场景 A 回归）。
10. 用户上车、定位开始快速移动。系统在 2 个定位周期内判为乘车，并标注「按你的定位判断已上车」。
11. 若系统误判，用户点「我没上车」，回到候车并在 20 秒内恢复自动判定。
12. 乘车期间，用户点刷新只更新车辆与报站，阶段与路线不变。
13. 到下车站，系统给出下车提示并切到步行到达段。
14. 用户点「步行指引」看下车后的走法，启动跟随；到达目的地后显示到达态并停止定位请求。

### 5.2 旅程 B · 详情页刷新（含"大概率赶不上"）

1. 用户在推荐列表点开某条线路的详情页，看到该班次档位文案（如「小跑能赶上」）。
2. 用户点右上刷新。
3. 300 毫秒内出现忙碌反馈（不再是"点了没反应"）。
4. 系统只更新三类数字：报站、报时、首段步行分档标签；卡片集合、排序、选中项、面板档位、地图视野全部不变。
5. 若刷新失败，出现可读失败提示与「重试」，上一次的数字仍在（不变 0）。
6. 若刷新后该班次已连冲刺都赶不上，该班次行原地变成「大概率赶不上」（与五档文案同位置，样式与绿/慢色区分，无备选推荐）。
7. 用户回到列表：列表里不出现任何「大概率赶不上」标签（该线路按原逻辑整条不进推荐）。

### 5.3 旅程 C · 线路搜索

1. 用户在搜索框输入 `25B`（或 `氹仔線`）。
2. 输入阶段即出现候选：结果区最顶部是线路分区，有分区标题「巴士线路」/「轻轨线路」，每行带该线主题色的徽章与副标题「查看全线站点」。
3. 下方是原地点/站点分区；两区各有标题、不互相覆盖。输入 `999` 时无线路区、不报错。
4. 用户点选线路结果，进入该线路站点全景页：线路名与主题色、全线站点按行驶顺序、当前方向、地图走向。
5. 站点报站随滚动加载：视口内与上下各一屏的站点在首屏后 2 秒内陆续到位，滚动到哪站显示哪站，不对全线并发请求。
6. 用户点换向，站点顺序反转，重新对齐该方向的报站；若是轻轨线路（无实时车辆数据），页面照常展示走向与站点，并说明「暂无实时车辆数据」，且不发起任何报站请求。
7. 用户返回，搜索框仍是 `25B`，结果列表仍在。
8. 用户可改输入地点继续原流程（线路不会被当作起终点填入）。
