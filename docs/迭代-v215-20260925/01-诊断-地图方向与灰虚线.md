- 复现方式：线上 API 只读复现（`https://musttoukou.vercel.app`）+ 库内只读核查

## 1. 结论速览

**一句话根因**：`route_shapes` 表里 **21A 的两个方向存了同一条几何**（都是「媽閣→九澳」，因为离线抓取脚本的繁简站名匹配失败、退化为「取第一条」，且从未按方向定向），而实际乘车方向是 `dsat_dir=1`（九澳→媽閣）；于是 `chooseShape` 只能选到「board 在 alight 之后」的反向折线，`cutColored` 对非环线反向切割**直接返回 `null`** 触发**降级**，前端 `drawOverview` 在降级态下**只画整线彩段、跳过灰虚线**，用户看到的就是「整条线都有颜色（含非乘车段）+ 方向反」。

即：**一个数据错配（方向几何重复）+ 一个渲染降级路径（反向切割不支持）叠加**，二者必须都修才彻底。

| 层 | 位置 | 问题 | 后果 |
|---|---|---|---|
| 数据 | `route_shapes` 表 / `scripts/fetch-route-shapes.ts` | 21A 两方向 polyline 完全相同（md5 一致） | 方向信息丢失，`dir` 不可信 |
| 渲染 | `src/lib/nav/route-overview.ts:192` `cutColored` | 非环线反向（`iBoard > iAlight`）返回 `null` | 触发 `degraded` |
| 渲染 | `src/components/nav/nav-map-overview.ts:34` | `degraded`（`colored===gray`）时跳过灰虚线 | 非乘车段也是实彩线 |

## 3. 逐层链路追踪

```
OD(澳科大→大三巴)
  └─ /api/nav  → card.rides = [ { bus 21A, board T306, alight M142 } ]        ← 正常
       └─ POST /api/nav/detail-body → legs[0]={board:T306(GSJ), alight:M142(GCJ)}  ← 正常
            └─ GET /api/route-shapes?code=21A → shapes[dir0,dir1]              ← 数据异常（同一条线）
                 └─ buildColoredLegs() : chooseShape → 反向 → cutColored=null → degraded  ← 缺陷点 A
                      └─ NavMap 绘制 drawOverview() : degraded ⇒ grayIsWhole=true ⇒ 跳过灰虚线 ← 缺陷点 B
```

### 3.1 OD → card → detail-body（正常）

`/api/nav` 返回含 21A 的卡，`card.rides[0] = { route:"21A", kind:"bus", board:"T306", alight:"M142" }`。
`/api/nav/detail-body` 把站码补成 GCJ-02 锚点（`board=T306 / alight=M142`），链路无异常。

### 3.2 route-shapes 选向（数据异常）

库内直查（`证据/02-库内-21A-shapes与站序.txt`）：

```
=== route_shapes 21A ===
  dir=0 amap_line_id=820000010104 pts=744 start=妈阁交通枢纽 end=九澳油库 md5=f5f13fa0...
  dir=1 amap_line_id=820000010104 pts=744 start=妈阁交通枢纽 end=九澳油库 md5=f5f13fa0...
  ⚑ 两方向 polyline 完全一致 = true

=== route_stations 21A ===
  dir=0: n=38 首站=M3/4(媽閣交通樞紐) 末站=C674(九澳油庫)
  dir=1: n=40 首站=C674(九澳油庫)   末站=M3/4(媽閣交通樞紐)   ← DSAT 方向本身是对的
  站 T306 的 seq：dir1=26
  站 M142 的 seq：dir1=34
```

- 站序（`route_stations`）**表明我们的 `dsat_dir=1` 是 九澳→媽閣**，本段 T306→M142 属 **dir=1**。
- 但 `route_shapes` 的 **dir=1 存的却是「媽閣→九澳」几何**（与 dir=0 完全相同，`amap_line_id` 也相同）。
  ⇒ **方向数据错配**：把「媽閣→九澳」这条高德线的几何塞给了两个方向。

**为什么会这样** —— 抓取脚本日志（`证据/06-抓取脚本日志-21A方向错配.txt`）：

```
[37/124] 21A（bus）dir=0 · 我方首「妈阁交通樞紐」末「九澳油庫」
   高德返回 2 条：21A路(妈阁交通枢纽--九澳油库) | 21A路(九澳油库--妈阁交通枢纽)   ← 高德两个方向都在
   ⚠️ 站名未匹配上（首尾「妈阁交通枢纽→九澳油库」），取第一条
   ✅ 入库：744 点 · 起「妈阁交通枢纽」终「九澳油库」

[38/124] 21A（bus）dir=1 · 我方首「九澳油庫」末「妈阁交通樞紐」
   高德返回 2 条：21A路(妈阁交通枢纽--九澳油库) | 21A路(九澳油库--妈阁交通枢纽)
   ⚠️ 站名未匹配上（首尾「妈阁交通枢纽→九澳油库」），取第一条                    ← dir=1 又取了第一条
   ✅ 入库：744 点 · 起「妈阁交通枢纽」终「九澳油库」
```

- 高德**两个方向都返回了**；但脚本的站名匹配**两次都失败**（`⚠️ 站名未匹配上`），退化为 `scored[0]`＝第一条「妈阁→九澳」。
- 匹配失败的根因是 `scripts/fetch-route-shapes.ts:77` 的 `toSimp()` **繁→简映射不全**：
  我方站名含 `樞紐`/`油庫`，映射表里**没有 `樞→枢`、`紐→纽`、`庫→库`**（同类缺失的还有 `廣/寧/廈/檢/樹/圓/聯` 等；注：`馬→马` 已在表内 `:87`，非本次致因）⇒ 归一后与高德 `枢纽/油库` 仍不等 ⇒ `score=0` ⇒ 退回「取第一条」。
  > 实测复核（本次定点核对 `scripts/fetch-route-shapes.ts:78-88`）：`樞 / 紐 / 庫 / 廣 / 寧 / 廈 / 檢 / 樹 / 圓 / 聯` 确缺；`馬` 已在表内。
- 脚本**从不校验**「两个方向的 polyline 是否相同」，也**从不按方向定向**（即使拿到对的线，也不会在必要时反转）。

### 3.3 cutColored → degraded（缺陷点 A）

`src/lib/nav/route-overview.ts:192-203`：

```ts
export function cutColored(pts: LL[], iBoard: number, iAlight: number, loop: boolean): LL[] | null {
  const n = pts.length;
  if (n < 2) return null;
  const ib = Math.max(0, Math.min(n - 1, iBoard));
  const ia = Math.max(0, Math.min(n - 1, iAlight));
  if (!loop) {
    if (ib > ia) return null;          // ← 非环线「反向」直接判失败（缺陷点 A）
    return pts.slice(ib, ia + 1);
  }
  ...
}
```

- 因为两个方向几何相同（都是媽閣→九澳），`chooseShape` 对 board(T306, idx268)/alight(M142, idx120) 只能得到 `iBoard > iAlight`（反向）。
- `cutColored` 对非环线反向**直接 `null`** ⇒ `buildColoredLegs`（`route-overview.ts:259-262`）落到降级分支：`colored = gray`、`degraded = true`。
- 这里的问题**不只是数据**：只要某段「行驶方向」与所存 polyline 的顶点顺序相反（数据只存一个物理走向时很常见），就应该**反向切片 + 反转**，而不是降级整线着色。

### 3.4 drawOverview 渲染（缺陷点 B）

`src/components/nav/nav-map-overview.ts:31-53`：

```ts
const grayIsWhole = leg.colored === leg.gray;          // degraded 时为 true
if (dim && !grayIsWhole && leg.gray.length >= 2) {     // ← 降级时灰虚线整条跳过（缺陷点 B）
  ... new AMap.Polyline({ strokeStyle: "dashed", strokeDasharray: [2,14], zIndex: 68 ... });
}
if (leg.colored.length >= 2) {                         // 降级时 colored=整线 ⇒ 整线实彩
  ... new AMap.Polyline({ ... zIndex: 72 });
}
```

- 降级态下 `colored===gray` ⇒ 灰虚线分支被跳过，只画一条**整线**彩实线（`showDir:true`）。
- 用户视角：**整条线（含非乘车段）都是线路色、没有灰虚线**，且线的方向箭头指向「媽閣→九澳」——与车辆实际行驶方向相反 ⇒ 「反向」。

## 4. 影响面

### 4.1 数据层（`route_shapes`）

全库统计（`证据/03-全库-方向重复统计.txt`）：

```
route_shapes 总计：93 条线路 / 117 行
多方向线路：24 条
  其中「两方向 polyline 完全相同」：3 条
  例如：2, 21A, 59          <-- 三个方向线被错误合并
单方向线路：69 条
```

- **确定错误**：`2`、`21A`、`59` 三条线路的 dir0/dir1 几何完全相同（同一 `amap_line_id` 塞给两个方向）。这三条线凡「反向乘坐」的行程都会触发本 bug。
- **匹配失败面更大**：抓取日志里 `站名未匹配上` 共 **37/117 行**——多数是单方向（首末同名）线路，退化无害；但多方向线路一旦两个方向都失配，就会退化成上面 3 条那样的重复几何。
- **潜在风险**：`toSimp` 缺字（`樞/紐/庫/馬/廣/寧/廈/檢/樹/圓/聯…`）会让更多线路的方向匹配处于「碰运气」状态，重抓时可能引入新的重复几何。

### 4.2 渲染层

- 任何「行驶方向与 polyline 顶点顺序相反」的乘车段（非环线）都会 `degraded`：
  - 非乘车段**不再显示灰虚线**，整线着彩；
  - 车辆层使用 `leg.dir`（本段错配为 dir=0，而正确方向是 dir=1）⇒ `/api/route-vehicles?code=21A&dir=0`（实测样例车 AA2509 在 T315 氹仔 CEM 貨倉）会把**反方向**的车画到本条行程上。
- 受影响入口：详情 pane 的路线总览（`NavShell.tsx:326` `overview={...ov.legs}`）——即用户「导航到大三巴」看到的那张图。轻轨段走同一 `buildColoredLegs`，同样受益/受损。

## 5. 修复方案

分两层，**建议 P0+P1 一起提**（P0 保证线上立刻恢复，P1 根治数据源）。

> **⚠️ 实施状态（2026-09-25 交接快照）**：本文件为**诊断定位性质**，**尚未改动任何 `src/` 源码**（`git status` 中 `src/` 仅有他人前端改动，`route-overview.ts` / `nav-map-overview.ts` 未动）。下方所有 P0/P1 方案均**仅经脚本级只读验证**（`scripts/diag-verify-fix.ts`、`scripts/diag-verify-dirfix.ts`），**未落盘生产代码**。详见第 8 节「待实施清单」。

### P0-1（渲染·立即恢复）`src/lib/nav/route-overview.ts:192` `cutColored`

非环线反向不再 `null`，改为「反向切片 + 反转」，使 `colored[0]≈board`、`colored[last]≈alight`：

```ts
if (!loop) {
  if (ib <= ia) return pts.slice(ib, ia + 1);
  return pts.slice(ia, ib + 1).reverse();   // 行驶方向与折线顺序相反 ⇒ 反转
}
```

- 效果：`degraded=false` ⇒ `drawOverview` 同时画「灰虚线整线(z68) + 彩实线段(z72)」，方向与行驶一致。
- 已用真实数据验证（`证据/04-验证-反向切片修复.txt`）：

```
现状 cutColored：null ⇒ 降级（整线着色，无灰虚线）
修复后 cutColored：149 点 · 起点距 board=23.5m · 终点距 alight=1.8m
  ⇒ gray(整线 744 点，虚线) + colored(149 点，彩实线)，degraded=false
```

- 环线逻辑（`ia>=ib` 正切 / 否则环绕）**保持不变**，`scripts/test-route-overview.ts` 用例 ⑤ 不受影响。
- 建议补一条用例：非环线 `ib>ia` ⇒ `colored[0]≈board` 且 `colored[last]≈alight`（替换现有用例 ④「反向 → null」的旧断言）。

### P0-2（数据·立即止血）修正 21A / 2 / 59 的方向几何

最快路径：对这三条线的 dir 行，**按 `route_stations` 该方向的首末站坐标定向**——若 polyline 起点更靠近「末站」而终点更靠近「首站」，反转 polyline 后写回（一次只读+定点更新脚本即可，不必重抓高德）。

### P1-1（数据·根治）`scripts/fetch-route-shapes.ts`

1. **补全繁→简映射**（`:77 toSimp`）：至少补 `樞→枢 / 紐→纽 / 庫→库 / 馬→马 / 廣→广 / 寧→宁 / 廈→厦 / 檢→检 / 樹→树 / 圓→圆 / 聯→联`；更稳妥的做法是改用**几何匹配**（见下）替代站名匹配。
2. **几何择向（推荐，免疫繁简）**：`:208-227` 打分改为——取该 `dsat_dir` 的**首站/末站坐标**（`route_stations` 已 JOIN 到 `stations`），在候选 polyline 上取最近顶点：
   - 若「线头≈首站 且 线尾≈末站」⇒ 采用；
   - 若「线头≈末站 且 线尾≈首站」⇒ **反转后采用**；
   - 都超容差才退化为「取第一条」，并打警告。
3. **入库前去重校验**（`:241` 前）：同一 `route_code` 两个方向的 polyline 若 `md5` 相同 ⇒ **不写第二行**（宁缺勿错）并记入报告。
4. **写库时定向**：保证 `route_shapes.polyline` 的顶点顺序 = 该 `dsat_dir` 的行驶顺序（首站→末站）。

### P1-2（渲染·健壮性，可选但强烈建议）`/api/route-shapes` 增加方向站序

`src/app/api/route-shapes/route.ts:49-67` 已在查 `route_stations`，可顺带按 `dsat_dir` 返回**有序站码**（+ 站点坐标）：

```jsonc
shapes: [{ dir, polyline, startStop, endStop, stops: ["M3/4","M25", ...] }]
```

`buildColoredLegs`（`route-overview.ts:238`）即可用**站序下标**精确取 `iBoard/iAlight`（与 `/api/nav/detail-body` 的 `mainCodeOf` 同口径），**彻底摆脱 `TOL_M=80m` 最近顶点误判**（本 bug 中 board 顶点距 23.5m、alight 1.8m，已接近容差边缘）。

> 说明：P1-2 是「更稳」而非「必需」。P0-1 + P0-2 已足以消除用户当前看到的两个现象；P1-1 保证重抓后不再复发。

## 8. 一句话交接
