## 1. ★1 路线收藏数据模型与融合迁移

### 1.1 新 Schema（在 PM §3.7 草案上落定）

键：`localStorage["must.favorites.v2"]`。

```ts
interface FavoritesFileV2 {
  schemaVersion: 2;
  updatedAt: number;
  /** 迁移来源标记（用于"仅迁移一次"，见 §1.3） */
  migratedFrom?: "v1";
  combos: Combo[];
}

interface Combo {
  id: string;                      // 尽量复用 v1 id
  type: "combo";
  name: string;                    // ≤24 字；默认「from.label → to.label」
  from: FavoriteEndpoint;          // ★ 复用 v2.2.0 `src/lib/favorites/types.ts` 的 FavoriteEndpoint（GCJ-02）
  to: FavoriteEndpoint;
  query: string;                   // = parseNavParams().query（不含 plan）——重算锚点
  chain?: ChainStep[];             // 空/缺省 = 自动选线
  walk?: WalkOverride;             // 两段步行覆盖
  tiers?: TierOverride;            // 五档覆盖
  plans: ComboPlan[];              // 0..N 条已保存方案
  isDefault?: boolean;             // 旧计时预设内置
  createdAt: number; updatedAt: number;
  pinned?: boolean; lastUsedAt?: number;
  /** 组合可改名后不再被默认名覆盖 */
  nameEdited?: boolean;
}

interface ComboPlan {              // ≈ v1 PlanFavorite 去 OD 化
  id: string;
  fingerprint: string;             // ★ 复用 planFingerprint（唯一真源，已存在）
  snapshot: PlanSnapshot;          // ★ 复用 v1 类型（含 capturedAt → 「保存于 MM-DD」）
  note?: string;                   // ≤40 字
  createdAt: number; updatedAt: number; pinned?: boolean;
}

type ChainStepKind = "board" | "transfer" | "alight";
interface ChainStep {              // 站链节点（PM §3.7）
  kind: ChainStepKind;
  code?: string; label: string; lng?: number; lat?: number;   // 站点（station）
  /** ★ 新增（回应 D1「段内并行」）：该"上车/换乘"节点容许的并行线路候选 */
  routes?: string[];
}

interface WalkOverride {
  seg1?: { distanceM?: number; minutes?: number; link?: boolean };  // 出发地→上车站（link=false 表示不联动）
  seg2?: { distanceM?: number; minutes?: number; link?: boolean };  // 下车站→目的地
}
interface TierOverride {
  speedMps?: Partial<Record<1|2|3|4|5, number>>;   // 覆盖 SPEED_RATIO 派生速度
  minutes?:  Partial<Record<1|2|3|4|5, number>>;
}
```

**落定要点（相对 PM 草案的增补）**：
- `Combo.nameEdited`：落实 §3.2「改后默认名不再覆盖」（否则编辑器保存时会被默认名重算覆盖）。
- `ChainStep.routes?`：D1「段内并行」在自定义链上需要**可声明多线**，否则编辑器无法表达 `A/B`。
- `WalkOverride.seg.link`：承载 §3.3「距离↔时长可否独立锁定」（默认 `true` 联动）。
- `ComboPlan` **不含 `from/to`/`query`**（已提到 Combo 层），与 v1 `PlanFavorite` 的差异在此。

**复用清单（不重写）**：`FavoriteEndpoint`、`PlanSnapshot`、`planFingerprint`、`legSummary`、`endpointOf`、`savedAtText`（均在 `src/lib/favorites/types.ts`，已存在）。

### 1.2 组合/组合下方案的语义边界

- **组合 = "去哪"**（一个 OD + 可选链/参数）；**组合下方案 = "怎么走"**（被显式保存的一条指纹+快照）。
- **「多方案」不是存储**：点组合卡 → 现场算出的**候选列表**（0~N）；`ComboPlan` 只是子集，命中指纹打「已保存」角标（PM FA-A.5/A.6）。
- **换乘段数上限**：`chain` 最多 **3 个换乘（4 段）**（PM §3.7 草案已如此，架构师同意）。
- **判重**：`Combo` 以 `query` 去重（同一 OD 一组合）；`ComboPlan` 以 `fingerprint` 去重。

### 1.3 融合迁移（v1 → v2）

**读优先 `must.favorites.v2`；缺失时迁移 v1；v1 键不删**（PM §3.5）。

```
readCombos():
  1) 若 must.favorites.v2 存在且 schemaVersion ≤ 2 → 校验后返回（不迁移）
  2) 否则读 must.favorites.v1（旧 FavoritesFile）：
     a) items 里 place 类 → Combo{ plans: [], name: note ?? "from → to" }
     b) items 里 plan 类  → 按 query 分组：
          · 已有同 query Combo（来自 a 或更早的 b）→ 复用，push ComboPlan{fingerprint, snapshot, note}
          · 无 → 新建 Combo（端点取该 plan 的 from/to），再 push
     c) 合并后写 must.favorites.v2（带 migratedFrom:"v1"）
  3) 注入默认组合（§1.4）后返回
```

**幂等保证**：
- 迁移**只在 v2 键缺失时发生** ⇒ 天然一次；`migratedFrom:"v1"` 仅作审计标记。
- 写入失败（隐私模式/配额）→ **不写、不删 v1**，本次会话**只读降级**（沿用 v1 视图或只读列表），下次再试（PM §5.3「不得因壳缓存读不到旧收藏」）。
- **「无丢失」校验（判据修正 2026-09-20，采前端 S1 实测结论）**：迁移后必须满足 **`#comboPlan === #plan` 且 `#combo ≥ #place`** —— 语义 = **任何一条 v1 收藏都不丢**。
  - `#comboPlan === #plan`：每条 `PlanFavorite` 必须落成一条 `ComboPlan`（**严格相等**）；
  - `#combo ≥ #place`：**plan-only 的 query 需新建 Combo** ⇒ `#combo` 可**大于** `#place`（多出的 Combo 只可能来自 plan 分组，不会丢任何一条）。
  - **任一条不满足 → 中止迁移、保留 v1**（防半迁移）。前端已实测 **34/0 夹具通过**（含**人为构造不守恒数据 → 中止保 v1**）。
  > ⚠️ 废弃原判据：`#place + #plan == #combo + #comboPlan` 在 **plan-only query** 场景**必不成立**（例：2 条 plan-only ⇒ `#comboPlan=2===#plan`，但 `#combo=2 > #place=0`，等式左侧 `2` ≠ 右侧 `3`）。

**数据校验（沿用 02 §2.6）**：逐条 `sanitize`（端点坐标范围 / `query` 非空 / `fingerprint` 非空）；坏条剔除后回写自愈；顶层 `schemaVersion > 2` → **只读不写**。

### 1.4 旧计时 4 预设 → 内置默认组合

**预设来源（已核实）**：`src/lib/home-plans-shared.ts` —— `PLACE_SHORT = { home: 擎天匯, school: 澳科大, hengqin: 橫琴口岸, gate: 關閘（拱北口岸） }`、`PAIR_ORDER = [school, hengqin, gate]`、`HOME_SLUG = "home"` ⇒ **3 对 ×（去/回）= 6 个组合**，`isDefault:true`：
- 擎天匯 ⇄ 澳科大 · 擎天匯 ⇄ 橫琴口岸 · 擎天匯 ⇄ 關閘（拱北口岸）。

**端点坐标来源（回填 PM §7-#2，已核实）**：表 **`place_coords` JOIN `places`**（`db/schema.sql:55`；`place_coords` 带 **`zone` 粒度**，坐标为 **WGS84**）。服务端取数 → `wgs84ToGcj02()` → 构造 `FavoriteEndpoint{kind:"place"|"gps", code:slug, label:PLACE_SHORT[slug]}`。

- ⚠️ 该取数**只能在服务端**（pg）；客户端不下发。

**注入方案（选型：代码常量 + 首次写入，幂等）**：

| 方案 | 机制 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| A 纯代码常量（每次读时合成，不入库） | 读时把预设组合"叠加"到列表 | 永不丢、零写入 | 用户**删不掉**（下次又出现），违反「可被用户删除」 | 否决 |
| **B 首次写入 + 幂等标记（推荐）** | 首读（v2 新建后）写入 6 条 `isDefault`；记 `seedVersion`；后续仅当 `seedVersion` 落后才补 | 可删、幂等、PWA 重复打开不重复注入（PM §5.3） | 需一次写入 | **采用** |
| C 独立常量文件 + 手动导入 | 用户点"恢复默认" | 可控 | 首屏无默认，体验差 | 否决 |

> B 的幂等键：`FavoritesFileV2.seedVersion`（整数）。仅当 `seedVersion < CURRENT` 时注入**尚不存在同名**的默认组合，然后置位。用户删除的默认组合**不再复活**（因为 seedVersion 已置位）。

## 2. ★2 实时计算引擎（点组合卡 → 现场算多方案）

### 2.1 选型：复用现有 nav 模型（不新建并行计算器）

**结论：扩展 `/api/nav`，复用 `planNav()` 全链路**，不新建"轻量计算器"。

理由：
1. **口径唯一**：车程/步行/五档/赶车分档/实时班次全在 `src/lib/nav/*` + `src/lib/recommend/*`（`planNav` = amap transit → `recompute`（我们口径重算）→ 排序 → 补漏 → `fetchLive`）。新建计算器必然**二次实现**，触发项目铁律里的**双重缩档 / 口径分叉**风险（`model.ts` 顶部已警示）。
2. **数据在服务端**：`segment_stats`（逐跳实测）、`walk_*`、`lrt_timetables`、DSAT 实时都只在服务端；前端重算不可行。
3. **`chain` 非空**是唯一新增能力：服务端在候选枚举阶段按用户链**约束/过滤**（见 §2.2）。

**接口形态（响应 PM §7-#1）**：`/api/nav` 追加**可选**参数（不破坏现有契约，缺省行为完全不变）：
```
GET /api/nav?fromLng=…&…&toCode=…            # 现状：自动选线（chain 缺省）
GET /api/nav?…&chain=<encoded>&walk=<encoded>&tiers=<encoded>   # 新增：自定义链/参数
```
- **编码约定（已定死，2026-09-20）**：三个参数 `chain` / `walk` / `tiers` **一律 `encodeURIComponent(JSON.stringify(<结构>))`**；结构分别对应 `ChainStep[]`（含 `routes?` 段内并行线、站台码 `board`/`alight`）/ `WalkOverride` / `TierOverride`（见 06 §3.7 + 07 §1.3）。此约定已随**收藏包服务端任务**下发给后端（贝洛奇）。
- ⚠️ **需修订 05-Spec §5「本期无新接口」**：本轮将"追加可选参数"记为**契约增量**（非新端点），并由 team-lead 同步 Spec。

**已保存角标**：**在前端比对**（沿用现成 `FavoritesClient.matchPlan` 的 `planFingerprint` 比对逻辑），服务端不需感知 `ComboPlan`。

### 2.2 数据流图

```
用户点组合卡 Combo{from,to,query,chain?,walk?,tiers?}
   │
   ├─ chain 为空（自动选线）
   │     └─ GET /api/nav?${query}                        ← 现有路径，零改动
   │
   ├─ chain 非空（自定义站链）
   │     └─ GET /api/nav?${query}&chain=…&walk=…&tiers=…  ← 新增可选参数
   │         服务端 planNav(pool, { origin, dest, chain?, walk?, tiers? })
   │           ① 候选枚举：本地图搜索/amap transit（按 chain 约束：段=用户指定 board/alight/routes）
   │           ② 重算：recompute（车程=我们 segment_stats 逐跳；步行=walk 覆盖 ?? 高德几何÷84；
   │                    五档=tiers 覆盖 ?? SPEED_RATIO）
   │           ③ fetchLive：DSAT 巴士 + 轻轨时刻表（一次批量）
   │           ④ 排序、补漏、组装 NavPlan[]（结构同现有 cards）
   │       ← 返回 { ok, cards[], degraded, emptyReason, … }（现有 NavOutput）
   │
   ▼
前端：cards 渲染（复用 RecommendCard）
   ├─ 对每张卡算 fingerprint → 命中某 ComboPlan → 打「已保存」角标
   └─ 无实时/整链无解 → 降级（§2.4）
```

### 2.3 实时请求口径与性能预算

| 项 | 值 / 口径 | 依据 |
|---|---|---|
| 单组合计算请求数 | **1 次 `/api/nav`**（内部：1 transit + N walking + 1 `fetchLive` 批量） | `/api/nav` 现有实现 |
| DSAT 并发 | 由 `fetchStationLive` 管理（每桶 ≤6 线，桶间并发）；`QPS 3/秒` 账号级 | 02 §A5 |
| **打卡即算的边界** | **打开收藏页不重算**（PM §7.6.1）；**仅点击某组合卡时**才 1 次请求 | 省 DSAT 配额 |
| 多组合并发保护 | 前端**串行化**（一个卡算完再算下一个）；或对同一时刻只允许 1 个 in-flight | 防连点打爆 |
| 超时 | 沿用 `/api/nav` 现有 `maxDuration=30` + `fetchLive` 内部超时 | — |
| 结果上限 | 复用 `limit`（默认 5，上限 20） | `/api/nav` 契约 |

> 结论：**单次点击成本 = 1 次 `/api/nav`**，与现状"点出发看结果"同量级，**不新增配额压力**。

### 2.4 无实时数据的降级（对应 PM §3.4 / FA-A.7/A.8）

| 场景 | 判定来源 | 表现 |
|---|---|---|
| 某段无实时班次 | `RideLegView.liveText` 空 / `waitMin` 兜底 | 该段标「暂无实时班次」，整链可算仍出卡 |
| 整链算不出 | `NavOutput.emptyReason`（`no_candidate`/`no_live`/`amap_unavailable`） | 展示该 `ComboPlan.snapshot`（标「历史记录，可能已变化」）+「重新规划」；无快照→空态 |
| 网络/接口失败 | fetch reject / `ok:false` | 行内错误 +「重试」，不崩不清空 |
| 高德降级 | `NavOutput.degraded=true` | 沿用「本地推算」细提示条 |

**与 `nav-notice` 机制的关系**：现有 `src/lib/nav/nav-notice.ts`（`sessionStorage["must.nav.notice"]`）是**跳转后一次性提示**。本引擎**复用同一机制**做**同页提示**的补充——但同页（收藏页内计算）不需要跳转，直接用**行内状态**（`FavoritesClient` 的 `notice` state）。仅在"计算后要跳 `/nav`"时用 `setNavNotice`（如未命中落 `/nav`）。**不新增机制**。

### 2.5 旧计时「五档速度 / 五档用时」的定义（回填 PM §3.3）

**位置：代码常量，不在 `walk_times` 表。**

| 常量 | 位置 | 原始数值 |
|---|---|---|
| `WALK_BASE_M_PER_MIN` | `src/lib/recommend/types.ts:93` | **84**（= 1.4 m/s × 60，档 3 基准） |
| `SPEED_RATIO`（**时间倍率**） | `types.ts:72` | 档1 **0.39** · 档2 **0.7** · 档3 **1.0** · 档4 **1.4** · 档5 **2.0** |
| 派生**速度**（= 84 ÷ ratio） | 由上式 | 档1 **3.6** · 档2 **2.0** · 档3 **1.4** · 档4 **1.0** · 档5 **0.7** m/s（与 PM FA-A.11 一致） |
| `TIER1_SEGMENTS`（档1 距离衰减） | `types.ts:120` | 8s→**3.8** · 22s→**3.58** · 90s→**2.68** · >120s→**2.24** m/s（`sprintWalkSec()` 分段累计） |

### 3.7 FIX-09 POI 目的地 → 「同名站吸附」（含 M70）【已复现，策略定稿】

**现象与根因（前端已复现）**：目的地是 **POI/地点**（无站码）时，落站由**"离目的地坐标最近的站"**决定。同类实测：POI「關閘(拱北口岸)」→ 下车 **M244 中心街**（而非同名站 `M1 關閘總站`）；M70 案例：POI「澳門理工大學」坐标经高德转换后**离 `M161 高美士/利港`（约 200m）比离同名站 `M70 澳門理工大學` 更近** ⇒ 落 M161，与用户预期（"理工大学"就应在 M70 下车）不符。

**机制定位（精确到函数）**：
- `src/lib/nav/graph-search.ts:92` `nearestMains(geo, point, k=8, radiusM=700)`：终点取**最近的 K=8 个站**（WGS 球面，按距离升序）；

- 高德种子路径同理：`amapAlight` 经 `map-stations.ts` 映射到"最近可映射站"，同样可能落 M161。
- ⇒ 结论：**名称重合的站（M70）本可满足，但被"纯最近站"逻辑挤掉**。

**裁定问题（吸附 vs 明示）与结论**：
> **采用「软吸附（偏好同名站）+ 卡片明示」，不做弹窗确认。**
- **软吸附**：把同名站**置入候选并前置**（不强制胜出）——最终仍由 `planNav` 的总时长模型排序。这样：同名站通常胜出（更贴用户意图），但若它导致明显绕路，会被更优方案自然取代（**不制造硬性错误**）。
- **明示**：卡片的下车段文案显式写「**在 M70 澳門理工大學 下车**」（现有 `walkIn.toLabel` 已承载站名，确认无误即可）；**不弹确认框**（打断流程，且用户未必理解站名）。
- 与 FIX-07.3 协同：**收藏站点/吸附后的终点存主码**，回放稳定命中 M70。

**吸附判据（三级，含防误吸附边界）**：

| 级别 | 条件 | 动作 |

| **L1 完全相等** | `norm(poiName) === norm(stationNameTc)`（`src/lib/shared/normalize.ts#normalizeQuery` 归一：繁简/异体/标点；两侧先**剥站码前缀**） | **吸附**：该主码置 DST/**SRC 首位**（即使超出 700m 半径也**额外纳入**） |

- 名称命中但**距离闸门不过** ⇒ 不吸附（宁可走"最近站"，也不跨区）。

**坐标真源与映射护栏（保留加固）**：坐标真源统一为**官方站坐标**（`stations`→`wgs84ToGcj02()`，`recompute.ts#geoOf`）；高德坐标只作映射比对；`station_amap_map` 中 `matchDistM > 150m` 或 `confidence='low'` 的行**不采用其高德坐标**，回落官方坐标（先例：`map-stations.ts:165 mainKindOk`、`:176` 注释记的"C651 误配"）。

**回归**：把「POI 名 = 站名」的吸附用例纳入回归集（M70 澳門理工大學、M1 關閘總站、以及"无同名站的任意 POI"作**反例**，确保不被误吸附）。

### 3.8 FIX-10 「搜索项不可点」（Bug②）【已复现，策略定稿】

**根因链（前端代码级，已核实）**：

## 5. 关键选型 ADR（MADR）

### ADR-004：收藏升级为「组合 → 组合下方案」两级模型，键 `must.favorites.v2`

**Status**: Accepted (2026-09-20)
**Context**: v2.2.0 的 `PlaceFavorite`/`PlanFavorite` 两类平级，无法表达"同一 OD 下多条已保存方案"；D2 要求与 v2.2.0 融合且旧数据无损。
**Decision**: 顶层 `Combo`（OD + 可选链/参数）+ `ComboPlan[]`；新键 `must.favorites.v2`；**读时一次性迁移 v1（v1 不删）**，`migratedFrom` 标记 + **「无丢失」校验**（`#comboPlan===#plan` 且 `#combo≥#place`）；默认组合用 `seedVersion` 幂等注入。
**Consequences**: 正面——模型表达力足、迁移无损可回滚、天然兼容"多方案"。负面——迁移代码需 fixture 回归；`useFavorites` 消费方一次性改。
**Related**: ADR-005

### ADR-005：自定义站链经 `/api/nav` 可选参数实现，不新建计算器/接口

**Status**: Accepted (2026-09-20)
**Context**: chain 非空需"按用户站链现场算"；05-Spec §5 曾锁"本期无新接口"（本轮可能修订）。
**Decision**: 复用 `planNav` 全链路，`/api/nav` **追加可选** `chain/walk/tiers`（缺省行为不变）；**不新建**并行计算器（防口径分叉/双重缩档）；已保存角标在**前端**按 `fingerprint` 比对。
**Consequences**: 正面——口径唯一、改动小、向后兼容。负面——**Spec §5 已由 team-lead 修订（2026-09-20，追加可选参数、不新增端点、缺省不变）**；`chain/walk/tiers` 编码已定死（`encodeURIComponent(JSON.stringify(…))`）。
**Related**: ADR-004

### ADR-006：五档速度与轻轨时长收口为「代码常量默认 + 组合级覆盖」

**Status**: Accepted (2026-09-20)
**Context**: 五档速度/用时现为代码常量（`SPEED_RATIO`/`WALK_BASE_M_PER_MIN`/`TIER1_SEGMENTS`），PM 要求编辑器"可修改"；轻轨石排湾/横琴需固定乘车秒数。
**Decision**: 全局默认**不动代码常量**；用户覆盖存 `Combo.tiers`（+ `WalkOverride`）；轻轨新增逐线常量 `LRT_RIDE_SEC_FIXED`（石排湾 100s / 横琴 135s），氹仔保持 `跳数 × 120s`；`distanceM ↔ minutes` 默认联动、可解锁。
**Consequences**: 正面——全局基线不被污染、每组合可定制。负面——需两处派生逻辑保持一致（`requiredSec` 单一真源）。
**Related**: ADR-004
