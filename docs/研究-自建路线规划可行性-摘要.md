## 2. 已掌握的关键事实（内部，已实读）

### 2.1 现行算法：定位是「后处理器」，不是路线引擎

设计原话：**「候选主要来自高德，时间由我们算，顺序由我们排」**（`docs/设计-全澳导航-v1-20260918.md:15`）。实现落在 `src/lib/nav/nav-service.ts:217` `planNav()`，9 步链路：

```
① loadStatics（复用旧推荐域：站序/段统计/步行/换乘/轻轨）
② loadStationMap（高德站 ↔ 我们站码的人工维护映射表）
③ fetchTransitPlans（高德 transit/integrated，AlternativeRoute=10 驼峰，带 transit_cache）
④ parseAndBridge（解析 → 过滤穿梭巴士/在建轻轨 ES1-ES6 → 桥接站码 + 逐跳站序）
⑤ 本地图枚举（补漏来源；高德不可用时即降级引擎）——graph-search.ts:64 radiusM=700、最近 K=8、换乘≤2
⑥ fetchLive（DSAT 实时 + 本库轻轨时刻表，两来源共用一次）
⑦ modelOption（注入 walkResolver + 方案级换乘索引）→ patchAmapFallback（映射失败段回落高德）
⑧ mergeSources（补漏质量闸门 + 最多 2 张）→ rankItems（T_ours 升序）
⑨ slice(limit) → 与旧版完全一致的卡片
```

**时间轴**：`T_ours = walkOut + wait₁ + ride₁ + Σ(transfer + wait + ride) + walkIn`；乘车段**逐跳累加** `segment_stats`（`lookupHop` 6 级回退 L1~L4 实测 / L5~L6 估算）。**排序**：`T_ours` 升序 → 换乘次数 → 步行量 → 来源（高德优先）→ planId（`src/lib/nav/rank.ts:45`）。**降级**：高德失败/超时/限流/0 方案 → 只用本地图搜索 + `walk_cache` 出卡（`nav-service.ts:401` `degraded`）。

**输入**：起终点 GCJ-02 坐标 + 可选座区；**输出**：`NavOutput{cards, degraded, emptyReason, provenance, stats}`。

### 2.2 数据资产（`【内部盘点】`，来源：team-lead 交接 + 项目文档）

`route_stations` 95 线/610 站/119 方向/2,870 行 · `segment_stats` 24,161 行 / 181,713 段 / 覆盖 87 线（按「周几 × 时段桶」分层）· `segment_samples` 60,544 原始样本 · `stations` 610/613 有坐标（DSAT 官方 WGS84）· `station_amap_map` · `poi_aliases` 1,723 行 · `walk_cache`/`transit_cache`。
**QA 复核的覆盖率口径（权威度更高）**：按**物理有向邻接对**算，`segment_stats` 覆盖 **886/996 = 89.0%**，其中 92% 样本 n≥30（`docs/审查-全澳导航方案-批判性-20260918.md:29`）。

### 2.3 已知局限（自建与否的争议焦点）

- **高德候选被框定**：`AlternativeRoute=10` 实测上限 **7 条**，其中约 4 条是赌场免费穿梭巴士（须黑名单过滤）⇒ 真候选常仅 3 条（`docs/调研-全澳导航-高德API能力-20260918.md:81-95,228-241`）。
- **本地枚举漏线率高**：`shadow-diff` 实测 K=8 时约 **57%**、K=16 时约 **41%**，远高于设计「>10% 告警」阈值（`docs/已知取舍-全澳导航-20260918.md:45-48`）。
- **换乘上限 ≤2**；**步行排序**在补漏路径已改用 `walk_cache`，高德路径用其几何距离；**无 ground truth**（`docs/审查…:42` P1-8）。
- **短距步行失真**：直线 41m → 高德 492m（**11.9×**），而首末段典型正是 50~300m；旧自检规则（`snap>100m`）对全部异常样本**零命中**（`docs/审查…:28` P0-2）——**这是「自建几何/步行层」最硬的论据**。

## 3. 待补的关键信息（外部，本轮已查到的部分）

**高德侧（`【官方】`+`【实测】`）**：公交路径规划 v5 `transit/integrated`，`alternativeRoute` 取值 1-10、**默认 5**（iOS SDK 文档原文；与项目实测「默认给 4~5、上限 7」一致）；个人认证配额**基础 LBS 150,000/月 · 基础搜索 5,000/月**，QPS 3/s；配额超限是**静默返回无效结果**而非报错（协议 3.7）。来源 <https://lbs.amap.com/upgrade>、<https://a.amap.com/…interface_a_map_transit_route_search_request.html>。

**谷歌侧（`【官方】`）**：现行生产接口是 **Routes API**（`computeRoutes` / `computeRouteMatrix`，已取代 Legacy Directions / Distance Matrix）。要素：`travelMode=TRANSIT`、**transit preferences（less walking / fewer transfers）**、`routingPreference=TRAFFIC_AWARE`（实时路况）、Matrix 上限 625 元素、流式返回；**数据来源 = 各公交机构发布的 GTFS + GTFS-Realtime**（Google 只做校验与归一化，不改数据）；路线算法层公开细节少（`【未查到】`官方确认使用 RAPTOR/Transfer Patterns）。来源 <https://developers.google.cn/maps/documentation/routes>。

**学术侧（权威、可直接落地）**：
- **RAPTOR**（Delling / Pajor / Werneck, ALENEX 2012，微软研究院）——**round-based**，每轮每条线路最多扫一次，**不依赖预处理**（可完全动态），天然输出「到达时间 × 换乘次数」的 **Pareto 集**；扩展 **McRAPTOR**（多准则，如票价分区）与 **rRAPTOR**（时间范围内批量出发）。这正是我们本地枚举「换乘 ≤2 的有界 BFS」的理论原型。来源 <https://www.microsoft.com/en-us/research/publication/round-based-public-transit-routing/>（原文 PDF：`raptor_alenex.pdf`）。
- **CSA（Connection Scan Algorithm）**——把全部班次按出发时间排序后线性扫描，实现最简单，国家尺度毫秒级；**Transfer Patterns**（Bast et al., ESA 2010）查询微秒级但**预计算量极大**（数千 CPU 小时）、需舍弃最优性、难以应对动态（RAPTOR 论文原文即以此作对比基准）。

**澳门本地（本轮新发现，对「自建」很关键）**：澳门地图绘制暨地籍局（DSCC）官方 **地理资讯应用程式库** <https://mapapi.gis.gov.mo/>（含 Token 机制、免费额度 + 付费计费单位），但其使用条款明确「**未经书面许可严禁复制/改编/分发/向公众提供，不得作商业用途**」，且资料「**只供参考，不具法律效力**」（<https://mapapi.gis.gov.mo/admin/zh-hans/regulation.html>）。DSAT 官方 App《巴士報站》《澳門出行》已内建点对点查询与换乘排序（`docs/调研…:488-489`）。

**明确 `【未查到】`**：① 澳门是否有专门针对「境外地图服务」的合规限制条文（只查到 DSCC 自有平台版权条款，未查到禁止使用 Google/高德的法规）；② Google Maps 在澳门的公交数据质量权威评测（本轮检索到的资料互相矛盾：一说「Google Maps 在澳门公交不准/不能用于巴士」，一说覆盖率 98.7% ——后者来自内容农场，**判定为低可信、不采用**）；③ 谷歌公开确认的公交寻路算法名。

## 4. 建议的章节骨架（供「季要纲」规划，初步 5 章）

1. **我们现在的算法**：后处理器架构（候选 vs 时间 vs 排序三层）· 9 步链路 · 数据资产与覆盖口径（89% 邻接对 vs 3.8% 旧口径之争）· 已知局限（漏线率、换乘上限、短距步行失真）。
2. **高德 vs 谷歌的实现思路对比**（五维表：数据来源 / 算法策略 / 实时路况 / 多方案生成 / 偏好设置）· 补充学术参照（RAPTOR / CSA / Transfer Patterns）· 结论：两家都不是「我们可复制的形态」，但**算法层有成熟公开方案可借**。
3. **能力与资源评估**：已具备（全澳路网图 + 实测段时长 + 站码映射 + 实时报站 + 逐跳计时 + 补漏/降级引擎）/ 尚缺（几何/步行路由、真实换乘关系、ground truth、算力与配额）/ 能支撑的功能梯度。
4. **自建可行性四维分析**：技术可行性（分「寻路 / 几何 / 时间」三层分别判定）· 数据（缺口在哪、补采成本）· 算力（澳门 33km² 规模极小 ⇒ BFS/RAPTOR 完全够用；瓶颈不在算力而在数据）· 成本（配额/合规/维护）· **可选方案对比**（A 维持现状 / B 只自建寻路候选 / C 全自建 / D 混合：自建寻路 + 高德几何）。
5. **结论与建议**：分层结论 + 风险与前置条件（漏线率、ground truth、合规红线）。

## 6. 本轮最有价值的一个认知（提示下游）

**「自建」不是一个布尔问题，而是三层可分离的能力**：① 几何/步行路由（Geo API 层）、② 候选寻路（算法层）、③ 时间计算与排序（数据层）。**我们早已自建了 ③，且它才是产品差异化所在**；② 有成熟学术方案（RAPTOR）且澳门规模极小、算力无忧，但**受制于漏线率 41~57% 与无 ground truth**；① 是唯一真正「缺基础数据」的一层。⇒ 讨论「该不该自建」时若不分层，结论必然含糊。

## 7. 我认为最需补充的信息

1. **漏线率根因量化**：57%(K=8) 中，多少来自「近站 K 截断」、多少来自「换乘上限 2」、多少来自「站码/图错误」——**这直接决定自建寻路要改哪一处、值不值**。
2. **真实换乘关系缺口**：`transfer_walks` 实测仅 2 条；高德能给的换乘关系我们图里是否有——这是自建寻路最大的隐藏短板。
3. **澳门「境外地图服务」合规边界**：现有资料只覆盖高德协议（且协议 14.1「原则上仅面向中国大陆开发者及最终用户」）与 DSCC 自有条款，**未查到澳门本地法规层面的明确结论**。
