## 0. 本轮要回答什么（对上一轮批评的回应）

上一轮只给了「上车前手机定位、上车后跟车」的二分，没有回答用户最关心的**机制**问题：
- 竞品到底用**哪个数据源**做每个判定（用户手机 GPS / 车辆实时数据 / 二者融合）？
- 「上车」「到站」「该下车了」的**触发条件与阈值**具体是什么？
- 数据缺失、隧道、无实时数据时**具体怎么降级**？

## 一、谷歌地图（Google Maps）公交导航的机制

### 1.1 谷歌如何知道「用户已上车 / 在车上」

**结论：不以「自动上车检测」为主，而是「用户手动启动 + 手机 GPS 沿线路匹配」。**

- 官方机制（2011，Maps 5.7 Transit Navigation 发布）：公交导航是**用户主动开始**的——用户点「开始（Start）」后，Maps 用 **GPS 判定用户沿路线的当前位置**，并在该下车/换乘时提醒。原文（Google 工程师 Chris Van Der Westhuizen，经 GMA 转载）：
  > "Transit Navigation uses GPS to determine one's current location along your route and alerts one when it's time to get off or make a transfer."
  > "since Transit Navigation relies on GPS signals, we recommend using this feature for **above-ground transit**."
  （第三方转载，引述 Google 官方博客：https://www.gmanetwork.com/news/scitech/content/225638/google-maps-for-android-adds-transit-navigation/story）
- 没有任何 Google 官方文档说明 Maps 用加速度计/传感器**自动**判定「已上车」；车辆位置另有来源（GTFS-RT，见 1.2）。
- 相关专利（Google Patents 检索到，**受让人未核实**）：US9068844B2「integrated personal navigation system」含「user context logic ... identify a switch in context when **detecting the user exiting a vehicle**」，用**运动传感器 + GPS**推断「离开载具」并切换导航模式（https://patents.google.com/patent/US9068844B2/en）。⇒ **专利层面存在"传感器 + GPS 判上下车"的构想，但未见其用于 Maps 生产环境的公开证据** ⇒ 该点标「未查实（是否有产品落地）」。
- 结论（可用于设计）：**上车是用户主动或半自动的，不是全自动**。

### 1.2 乘车中的「进度」如何推断

**结论：双源并用——「用户自己的位置」来自手机 GPS 沿线匹配，「车辆位置」来自运营方 GTFS-RT。**

- 用户侧：2011 官方口径即「GPS 判定用户沿路线的位置」（见 1.1 引用）。
- 车辆侧：Google 通过**运营方 AVL（自动车辆定位）系统、以 GTFS-RT 标准**接收车辆实时位置，更新约 15–30s（第三方引述 GTFS-RT 与运营商口径）：
  - https://en.actualidadiphone.com/?p=263231 （马德里城际巴士：数据经 CRTM/FSS → GTFS-RT → Maps，图标实时移动）
  - https://theportugalpost.com/posts/live-bus-tracking-finally-arrives-for-portugals-smaller-cities （运营商口径：Google 的延迟阈值约 20 秒）
  - https://en.actualidadgadget.com/?p=148764 （马德里 EMT：GPS 每几秒上报，Maps 结合路况算到达预测）
- 二者关系（据公开资料的可推断语义）：**车辆实时位置回答"车在哪、还有几站到站"；用户 GPS 回答"你在哪、离下车还有多远"**；两者不互相替代。未找到 Google 官方对"二者如何互相校正"的明确说明 ⇒ 「相互校正的算法细节」标「未查实」。

### 1.3 「该下车了」提醒的触发机制

**结论：以手机 GPS 接近该站为触发，提前量约 1–2 站；带震动 + 通知，可在后台/锁屏（Android 持久通知）。**

- 触发（官方 2011 口径）：GPS 判定用户沿路线的位置 → 到该下车/换乘时提醒（1.1 引用）。
- 提前量：第三方实测口径为「快到换乘点时，提醒你在**接下来 1–2 站**下车（alight at which of the next 1–2 stops）」：
  - https://www.blognone.com/node/98467 （泰国上线实测："系统会提醒在接下来 1-2 个站牌的哪一站下车"）
- 通知形态（2017 上线，多来源）：通知栏 + **震动**；可在**另开 App / 锁屏**时持续显示（Android 锁屏持久交互通知）：
  - https://news.wirefly.com/2017/12/15/google-maps-tell-you-when-to-get-off-bus-train
  - https://www.androidheadlines.com/2017/12/google-maps-now-includes-get-off-the-bus-notifications.html
  - https://www.ithome.com.tw/news/119631
- 触发条件精确阈值（多少米/多少秒）**未公开** ⇒ 标「未查实（Google 未披露具体阈值）」。
- 另一路是**用户可选的 Stop Reminders / "提醒我下车"开关**（第三方操作指南）：
  - https://www.makeuseof.com/tag/never-miss-google-maps-feature
  - https://www.downloadsource.net/how-to-make-google-maps-remind-you-your-bus-tram-or-tube-stop-is-coming-up/n/11204
  ⇒ 提醒是可开关的**导航态功能**，不是常驻。

### 1.4 蓝点/精度圈，以及隧道/信号差/无实时数据的降级

- **蓝点与精度圈（官方）**：蓝点 = 你的位置；当无法确定时，蓝点周围出现**浅蓝色圆圈 = 误差可能范围**，「圆越小越确定」；若无蓝点或显示**灰点**，表示无法定位，改显示**上次记录的位置**；基站被高楼/室内停车场遮挡会导致不准。
  - 官方帮助：https://support.google.com/maps/answer/2839911 （繁中）
- **隧道 / 信号差（官方 2011 口径）**：因依赖 GPS，Google 明确"建议在地面以上（above-ground）的公共交通上使用" ⇒ **地下/隧道场景本就不保证**。
- **无实时数据**：Google 公交本身以**时刻表（static GTFS）**为底座，无实时车位置时按时刻表推算（第三方综述）：
  - https://glassandnote.com/food/google-transit （Google Transit 以 GTFS 时刻表 + GTFS-RT 实时扩展为两级数据）
  ⇒ 即「有实时用实时，无实时回落到时刻表」。

### 1.5 「已驶过路段」的视觉处理（上一轮标"待验证"，本轮尽力查实）

- **官方可查证的部分**：Google 官方帮助明确「最优/选中路线 = **蓝色**；其他备选 = **灰色**」（官方）：
  - https://support.google.com/maps/answer/144339
  - 第三方图标解说的同义表述：https://www.itechguides.com/google-maps-all-icons-and-symbols-explained-2026/
- **"已驶过段淡化/置灰、前方高亮"**：在**驾车/步行导航**中是普遍观察（导航中蓝线表示"接下来要走的"，走过部分被淡化）——但**仅见二手来源**（https://www.positioniseverything.net/what-do-the-road-colors-in-google-maps-mean/）。
- **对公交段"已驶过置灰"**：**未找到 Google 官方或权威来源** ⇒ 标「**未查实（无权威依据）**」。
- 对本项目的意义：**"已驶过路段变色"是自定视觉，不必也不能声称对齐 Google**。v2.13 用「已驶过 = 绿色覆层 z74」（`TrackLayer.tsx:122-139`）是自定语义，可保留，颜色/强弱由设计规范定（注意与 `--brand-green` 的品牌语义、与"用户蓝点"的区分）。

### 1.6 谷歌机制小结表

| 问题 | 机制 | 来源可信度 |
|---|---|---|
| 用户是否上车 | 用户手动开始 + GPS 沿线匹配；无官方"自动上车检测" | 官方（2011 引述） |
| 乘车进度 | 双源：用户 GPS（用户位置）+ GTFS-RT（车辆位置） | 官方（用户侧）+ 第三方（车辆侧） |
| 下车提醒 | GPS 接近该站触发；提前约 1–2 站；震动 + 通知 | 官方（触发）/ 第三方（提前量） |
| 蓝点/精度圈 | 蓝点=你的位置；浅蓝圆=误差范围，越小越确定；灰点=定位失败显示上次位置 | 官方 |
| 隧道/地下 | 明确"建议地面以上使用"（依赖 GPS） | 官方 |
| 无实时数据 | 回落时刻表（static GTFS） | 第三方 |
| 已驶过置灰 | 驾车/步行有观察；**公交段无权威依据** | 未查实 |

## 二、高德地图（AMap）公交导航的机制

### 2.1 「上车提醒（50m）→ 乘车中 → 到站提醒（1 站且 <500m）」的判定数据源

**结论：这是「换乘提醒」功能，官方口径明确「基于 GPS 定位功能实现」——即判定的是"用户手机的位置"，不是车辆数据。**

高德 6.60 版「换乘提醒」三段（第三方媒体稿，明确写"基于 GPS 定位功能实现"）：
- 来源：https://tech.it168.com/a2013/0427/1478/000001478134.shtml （2013-04 首发，IT168）
1. **上车提醒**：用户**距离公交上车站或地铁入口 50 米**时提示乘车信息（图面显示上车站名 + 顶部乘车信息）。
2. **乘车中提醒**：屏幕显示**途经站点名称 + 实时位置**（地图为罗盘视角），便于了解"当前位置、离目的地还有几站"。
3. **到站提醒**：用户**距离下车站还有 1 站、且距离小于 500 米**时提示下车信息 + 下一步骤；**前台震动 1 次，后台持续震动 1 分钟**，直到用户点击通知确认（超 1 分钟自动停）。
- 提示形态：**震动 + 铃声 + 桌面通知**三重。
- ⇒ 判定链：要用「还有 1 站」「<500m」判定，必须同时知道 ①用户在站序中的位置（**GPS 沿线匹配**）②到下车站的剩余距离（**GPS 距离**）。与 Google 2011 口径一致。

补充（第三方操作指南，2024/2025 版本）：下车提醒"在乘客**接近目的站点前两站**自动启动弹窗、震动与语音"，且锁屏可收；实时公交页可为线路设「公交闹钟」（下一班到站前 5 分钟）：
- https://www.oppozhijia.com/wz/1051641.html
- https://www.ufcn.cn/article/2188309.html

### 2.2 「蓝色小箭头」与「还有 14 分钟，6 站 4 公里」的数据来源

- **蓝色小箭头**：第三方操作稿描述其两个作用——①看公交车往哪个方向开 ②"知道咱们现在站的位置，和公交车的距离有多远"：
  - https://m.toutiao.com/article/7617033414679462451
  ⇒ 语义 = **"我（用户）相对这条线路/车辆的位置"**，即用户定位 + 线路几何；箭头方向取自线路走向。
- **双刻度「还有 14 分钟，6 站 4 公里」**：
  - **站数 / 公里**：来自**车辆实时位置**（车辆沿线路已到站/距本站距离）。
  - **分钟**：来自 ETA 模型（路况 + 历史）。
  - 第三方对实时公交数据链的描述：车载 GPS 每数秒上报调度中心 → API 推送；ETA 结合"交通大数据与路况"精度到分钟级（来源：https://m.cnr.cn/tech/20180801/t20180801_524318481.html）。
  - "关注车辆"：车还有一站时提醒（https://m.sohu.com/n/539337809/）。

### 2.3 高德的数据缺失降级与用户可见标注

- **地理围栏 + 平滑**（第三方技术分析，标注为**推测**）：高德为每个站点设半径约 **30–50m** 虚拟围栏，车辆 GPS 进圈触发"进站"；用**卡尔曼滤波**平滑轨迹；围栏边缘反复横跳会产生"进站-出站"抖动。
  - 来源（第三方分析，非官方）：https://tsight.io/articles/12843304
- **数据缺失 → 历史平均用时模拟**（同上，**推测**）：运营方未接入实时数据时，高德只能用**历史平均用时**模拟到站时间；雨高峰偏差可达 200% 以上。
- **用户可见标注**：该文未给出高德的具体 UI 标注文案 ⇒ 「高德如何在界面上标注'模拟/估算'」标「未查实」。本项目自有口径为弱化样式（`.rc-val--est`，`StationStrip.tsx:16-18`），可继续沿用。

### 2.4 高德机制小结表

| 问题 | 机制 | 来源可信度 |
|---|---|---|
| 上车/到站提醒数据源 | 「基于 GPS 定位功能实现」——判定**用户手机位置** | 第三方媒体稿（明确引述官方口径） |
| 上车提醒阈值 | 距上车站/站口 **50m** | 第三方媒体稿 |
| 到站提醒阈值 | 距下车站 **还有 1 站 且 <500m**；前台震动 1 次/后台持续 1 分钟 | 第三方媒体稿 |
| 蓝色小箭头 | 用户相对线路/车辆的位置（"我在哪，离车多远"） | 第三方操作稿 |
| 双刻度（站数/公里/分钟） | 站数/公里来自车辆实时；分钟来自 ETA 模型 | 第三方 |
| 车辆数据链 | 车载 GPS 数秒上报 → 调度中心 → API；站级用 30–50m 围栏触发 | 第三方分析（**推测**） |
| 无实时数据 | 历史平均用时模拟 | 第三方分析（**推测**） |

## 三、我方（MUST登校）分阶段 × 分场景设计

> 设计原则：**车辆数据判"车到哪"，手机 GPS 判"人在哪"，二者互证但不互相替代**；任何自动判定都要**可回退、不误切**（呼应项目铁律「对不上就冻结，不乱跳」，`docs/交接-HANDOVER-2026-09-23.md:179`）。
> 坐标系：GPS 为 WGS84 → 必须 `wgs84ToGcj02`（`src/lib/amap/coord.ts:66`）；DSAT 车辆坐标已是 GCJ-02（直接喂地图）。
> 频率：车辆沿用 12s（`useRideTracking.ts:31`）；GPS `watchPosition` 建议**候车 15s / 乘车 30s 节流**（iOS Safari 回调本就近 10s 量级，见 §一/§二引用；前台才生效）。

### 3.1 七阶段总表（数据来源 / 判定规则 / 用户可见 / 失败处理）

| # | 阶段 | 数据来源 | 判定规则（阈值） | 用户可见行为 | 失败处理 |
|---|---|---|---|---|---|
| ① | 走向车站 | **GPS 为主** | 用户 GPS 到上车站球面距离（`haversineM`）；< 50m 触发"到站"提示（对齐高德 50m） | 地图蓝点 + 步行引导线；顶部"距上车站 X m"；<50m 震动一次 | GPS 拒权/超差 → 不画蓝点，退回"按文字指引走向上车站"，不阻塞 |
| ② | 站台等车 | **车辆为主** + GPS 辅 | 车辆：`rankBoardingVehicles`（`track.ts:105-124`）排候选（停靠本站 > 刚离站 > 最近）；GPS：距站 < 50m 且低速 → 判"在站台" | 候选车列表（车牌/停靠站/区间）+ 每车"还有 N 站"；"您在此站台" | 无在途车 → "这条线暂时查不到在途车辆，可手动上车"（沿用 `useRideTracking.ts:216`） |
| ③ | 车来了（该不该上） | **车辆为主** | 候选车 `atStation == 上车站` 或 `interval.from == 上车站`（`track.ts:65-98`）→ 高亮该车"已到/刚离" | 该车行高亮 + 横幅"这辆是 51 路，停靠/刚离开 M1"；可"换一辆" | 车辆数据缺失 → 保留候选列表（不误报"已到"） |
| ④ | **上车判定**（用户最关心） | **车辆 + GPS 互证（半自动）** | 见 §3.2 规则 R1–R3；**系统预选 + 用户一键确认**，不自动切状态 | 弹"看起来您已上车（51 · 车牌 XX）"确认条 + 「是 / 不是这辆」；确认即进 ⑤ | 判据都不满足 → 保持 ②，用户仍可手动"我已上车"（沿用 `useRideTracking.ts:297-338`） |
| ⑤ | 乘车中（区间推进） | **车辆为主**（权威）；GPS 仅蓝点 | `progressOf`（`track.ts:65-98`）由挂靠站/区间推 passedIdx/nextIdx；`cutAt` 投影切"已驶过"（`track.ts:130-137`，容差 250m） | 站条：已过站变绿、下一站加粗、下车站橙色、"您在这里"锚点；地图：车辆图标 + 已驶过绿段 + 用户蓝点 | 对不上站序 → **冻结上次进度 + 提示**（`useRideTracking.ts:222-226`）；连续 3 次丢信号 → 提示 |
| ⑥ | 临近下车站 | **车辆为主** + GPS 交叉校验 | 下一站 == 下车站 ⇒ soon；到站 ⇒ now（`useRideTracking.ts:260-274`）。**加 GPS 佐证**：用户 GPS 距下车站 < 500m（对齐高德）⇒ 提升提醒置信 | 横幅 + 震动（soon 一次、now 一次）；到站红色脉动；下车站差异化色 | iOS 无 `vibrate` → 仅横幅（如实，沿用口径）；GPS 不可用 → 仍按车辆提醒（不降级） |
| ⑦ | 下车后 | **GPS 为主** + 车辆结束 | 车辆通道停止（`onAlight`→done，`useRideTracking.ts:348-366`）；GPS 接管末段步行 | "已下车 · 步行 X 分 → 目的地"；地图蓝点 + 步行引导 | GPS 不可用 → 显示静态步行指引文字 |

### 3.2 上车自动/半自动判定的具体规则（阶段 ④ 展开）

**为什么不做"全自动上车"**：隧道/桥/地下场景 GPS 会静止或漂移（§一.4、§二.3 已证非可靠）；车辆数据有 12s 延迟与丢帧（`useRideTracking.ts:31,222-226`）。若全自动切状态，一次误判会导致整段进度错位，违反「宁缺毋滥」。⇒ 采用**半自动：系统预选 + 用户一键确认**。

**判据（任一强信号即可预选，但不自动切状态）：**
- **R1（车辆强信号）**：上一帧候选车中，存在 `atStation == 上车站`（停靠本上车站）或 `interval.from == 上车站`（刚离开本上车站）的车辆 → 预选该车牌。依据：`track.ts:111-113` 打分函数已用同一判据排序，复用即可。
- **R2（GPS 强信号）**：最近 45s 内 GPS 采样点满足：① 沿线投影距离 `nearestOnPath` ≤ **80m**（`route-overview.ts:103`，比 `CUT_TOLERANCE_M=250` 更严，因上车判定要保守）② 沿线累计位移 ≥ **150m** ③ 平均速度 ∈ **[8, 80] km/h**（排除步行/静止）→ 判定"用户正随该线路移动"。
- **R3（二者互证 = 最高置信）**：R1 命中且 R2 命中 → 预选置信"高"，确认条文案从"看起来您已上车"升为"已检测到您正乘坐 51 路"。
- **不预选**（保持 ②）：仅 R2 命中但无车辆数据（如轻轨段，见 §3.4）；或 GPS 静止且离线路 > 250m（可能未上车 → 不提示，也不改状态）。

**确认交互**：预选后弹一次确认条（`role="status"`），「是，就是这辆」→ 进 ⑤ 并锁定车牌；「不是」→ 保持 ② 并记下排除车牌。确认条 30s 无响应自动收起（不自动确认）。

### 3.3 GPS 与车辆数据互证 / 融合规则（跨阶段）

| 观测 | 解释 | 建议行为 |
|---|---|---|
| GPS **沿线连续移动**（R2 满足）且车辆区间推进 | 用户很可能在车上 | 提高 ⑤ 进度置信；④ 预选；⑥ 提醒置信提升 |
| GPS **静止/低速** 且离线路 < 80m | 可能仍在站台等车，或车停站 | 保持 ②/⑤ 当前态，不切换 |
| GPS **静止** 且离线路 > 250m | 可能**未上车**或**提前下车** | **不自动改状态**；仅弱提示"看起来您已不在车上？（继续 / 已下车）"——因隧道/地下会误判，必须用户确认 |
| 车辆数据**丢失**但 GPS 沿线移动 | 车在隧道/信号差 | 冻结车辆进度（现状 `useRideTracking.ts:222-226`），GPS 蓝点继续显示；**不**用 GPS 冒充站序进度 |
| 车辆数据**恢复** | 信号回来 | 自动续上（现状已支持，`track.ts:96-97` 的 unknown → 冻结语义） |
| 二者**都不可用** | 极端降级 | 手动模式（现状 `useRideTracking.ts:301-306`），站条仅静态对照 |

### 3.4 轻轨段（无逐车数据）怎么设计

- 现状：轻轨/几何缺失段走手动模式，站条不显示实时位置（`useRideTracking.ts:189-194,301-306`）。
- 强化设计（可选，二选一）：
  - **方案 L1（推荐，稳）**：轻轨段**仍为手动**，但用 **GPS 沿线投影**给出"距离下车站约 X m / 可能在 A–B 站之间（估算）"的**弱提示**，文案标注弱化样式（`rc-val--est`），**不做站序自动推进**、不做自动上车/到站提醒（轻轨地下段 GPS 不可靠）。
  - **方案 L2（激进）**：用 GPS 投影 + 轻轨时刻表（`/api/station/eta` 的 `depMs`）+ 站间距时长做**估算推进**，全程强标注"估算"。风险：地下段失效、站间距漂移（铁律：轻轨逐站漂移禁常数偏移）⇒ 不推荐用于提醒，仅可做信息展示。
- 提醒：轻轨段的"该下车了"用**时刻表 + 站序手动**，或在有 GPS 的地面段用 GPS 距离辅助。

### 3.5 频率 / 阈值建议值汇总（含理由）

| 参数 | 建议值 | 理由 |
|---|---|---|
| 车辆轮询 | **12s**（沿用） | 与官网 15s 同量级（`useRideTracking.ts:30`），站级切换跟手 |
| GPS 采样（候车 ①–③） | **15s 节流** | iOS Safari 本就近 10s；节流省电，候车对实时性要求低 |
| GPS 采样（乘车 ⑤–⑥） | **30s 节流**（仅前台） | 蓝点为增强，不需要秒级；省电；后台本就暂停 |
| 上车判定 GPS 窗口 | **45s** | 覆盖 12s 车辆延迟 + 用户上车动作间隔 |
| 上车判定沿线位移 | **≥150m** | 排除原地抖动；约 1~2 个站距的量级 |
| 上车判定速度区间 | **8–80 km/h** | 排除步行（<8）与异常（>80，澳门无此限速） |
| 上车判定投影容差 | **80m**（严于 `CUT_TOLERANCE_M=250`） | 上车判定要保守，宁可不判 |
| 「在站台」判定 | 距站 **< 50m**（对齐高德） | 竞品口径 |
| 到站提醒（soon） | 下一站 == 下车站（车辆口径，主） | 现状 `useRideTracking.ts:266-268` |
| 到站提醒（GPS 佐证） | 距下车站 **< 500m**（对齐高德） | 提升置信，不单独触发 |
| 走向车站"到站"提示 | 距上车站 **< 50m**（对齐高德） | 竞品口径 |
| 近站地理围栏（可选优化） | 站点 **30–50m** 圆环触发"到站"铃 | 对齐高德围栏推测值；仅用于提示，不用于改状态 |
| 冻结判定 | 连续 **3 次**丢信号（沿用） | 现状 `MISS_LIMIT=3`（`useRideTracking.ts:33`） |
