## 0. 一句话结论

主流竞品（谷歌/高德/百度/Moovit/Transit）在「乘车进行中」的**进度展示与到站提醒**已相对成熟，但**「已驶过路段由线路主题色渐变为副色」这一主视觉**几乎无人做（它们多数只在"路线总览层"用灰/绿/红信标区分），**「同站台改乘方案一键切换导航」也基本缺失**。本次重修的差异化机会点正是这两处（对应需求 4 与需求 6/7），叠加本项目独有的**全澳 92 线 + 3 轻轨覆盖 + 澳门本地语境**与**站牌风视觉**（青花蓝 + 澳门绿），可做出本地最好用的乘车进行中体验。前提是：先把**用户实时位置的可靠度**（本次最大难点）做扎实——否则一切进度可视化都是空中楼阁。

### 1.3 竞品差评暴露的真实痛点（差评 > 好评）

调研竞品时**重点看差评**（差评暴露市场空白）。汇总如下（来源见 §6）：

| 竞品 | 主要差评 | 暴露的空白 / 我们的机会 |
|------|----------|--------------------------|
| DSAT「巴士报站」 | 3.6★；**崩溃、卡顿、拖垮设备**（Android 9+ 兼容性）；**耗电**；无深色模式；**更新不及时**（"你见过突然走了五个站会飞的巴士？"）；无拥挤度 | 澳门本地用户对"官方 App 体验差"普遍不满 → **Web PWA 免安装 + 稳定 + 轻量**是机会；但需保证**到站准确性**（否则重复同样槽点） |
| Citymapper | **路线质量下降**、**漏报整班车**、错误站点久不修、**无法跨区域规划**、无离线地图、无 interlining（同车不换乘）概念 | "改乘 / 同站台替代"需求真实存在（漏车、错站）；主流 App 对"同站台还能坐什么"处理很弱 |
| Moovit | **到站时间常不准**（约 30% 用户提及）、**广告过多**（约 70% 提及，高峰弹窗"差点坐过站"）、崩溃、位置/时刻不准 | 到站准确性 + 无干扰是刚需；Moovit 的"数据最后更新时间"是可借鉴的可信度做法 |
| 高德地图 | 二三线城市**实时数据缺失**，靠"历史平均用时"模拟，**雨天高峰偏差可达 200%+**（"幽灵车"）；数据延迟 | 数据新鲜度必须可见（否则用户无法判断可信度）；**估计值要标注为"预估"** |
| 百度地图 | 地图与列表联动弱、实时页**不可拖拽**（历史评价）；部分城市拥挤度缺失 | 地图应始终可交互、不被面板"锁死" |
| 谷歌地图 | 公交导航长期"二等公民"（2024–2025 才大改，支持不中断行程改目的地）；部分地区无实时数据 | "改乘不中断行程"是明确趋势 → 需求 6/7 方向正确 |
| 苹果地图 | 实时公交信息**覆盖城市有限**（2024 才到东京）；无"已过路段"可视化 | "已过路段"可视化全球领先者也不做 → 我们的差异化空间 |

**空白点归纳（4 条）**：
1. **「已驶过路段由主题色渐变为副主题色」这一主视觉，全球主流几乎无人做**——大家只在"路线总览层"用灰线/绿红信标区分。→ 需求 4 是本项目**真正的差异化**。
2. **「同站台改乘」多停留在静态到站列表**，极少有"没赶上车时，同站台还有哪条线 / 换乘方案也能到、快多少、一键切过去"。→ 需求 6/7 填补空白。
3. **到站时刻准确性是全行业最大槽点**——准确性 + 数据新鲜度（"上次信号时间"）必须做实、可见。
4. **到站提醒的可靠性**（后台/锁屏）是普遍痛点——网页端受限尤甚，需**如实告知 + 前台做强**。

### 1.4 用户点名的「实时位置」竞品实现方式（对应需求 2）

| 维度 | 谷歌地图 | 高德地图 | 对我们的启示 |
|------|----------|----------|--------------|
| 「车在哪」来源 | 运营商 **GTFS-RT 车辆 GPS**（地面公交持续上报） | 公交车载 GPS（约每 **6–15 秒**一次） | **官方车辆位置**我们已有（DSAT `/api/route-vehicles`），是"车到哪"的可靠来源 |
| 「我在哪」来源 | **用户手机 GPS** + 计划行程推断；触发到站/换乘提醒 | 用户手机 GPS；到站判定=**距下车站剩 1 站且 <500m** | 我们**缺的是"用户手机持续定位"**——v2.13 全仓 `watchPosition` 零命中，"您在这里"实为**官方车辆位置代理**（见 `2026-09-25.md` 代码侦查） |
| 数据不足时 | 显示"灰字"（无实时，用时刻表） | **历史平均用时模拟**（偏差可达 200%+，被吐槽） | 数据不足时**明确标注"预估/手动"**，不假装实时 |
| 提醒触发 | 系统通知 / 锁屏 Live Updates | 前台震动 + 铃声 + 桌面通知三重 | 我们网页端**后台/锁屏受限**，需如实说明，前台做强提醒 |

**结论（产品口径，技术选型由架构师定、用户拍板）**：行业通行的思路是**"车的位置用官方数据、我的位置用手机定位、两者结合触发提醒"**。我们已具备前者，缺口在后者；建议方向为**混合模式**（手机 GPS 判"我在车上/我在哪个区间" + 官方车辆位置判"车到哪"并互为佐证），但**是否让用户开持续定位（权限/耗电/后台限制）必须由用户拍板**。

## 2. 12 项需求逐条结构化

> 优先级：**P0 = 本次必须交付（影响导航可用性或用户明确列为"核心"）**；**P1 = 重要，可紧随其后**。
> 验收标准采用 **EARS** 风格（While / When / If + 系统应当…），为 QA 唯一依据草案；细化数值（轮询间隔、站数阈值等）由架构师锁定。

### 功能·导航界面

#### 需求 1 · 路线详情界面升级为导航界面
- **用户场景**：Bill 选好路线、准备出门/上车，希望"看手机就知道到哪站了"，而不是读一段纯文字叙述。
- **功能点拆解**：① 详情弹窗内提供「开始导航」入口；② 点击后**同屏替换**为导航界面（不叠加新页面、不跳转）；③ 导航界面为后续所有实时能力（进度/位置/提醒/改乘）的宿主。
- **验收标准（EARS）**：
  - When 用户在详情弹窗点击「开始导航」，系统应当将详情界面**同屏切换**为导航界面（无页面跳转、无遮罩叠层）。
  - While 处于导航界面，系统应当持续展示：当前所在站/区间、下一站、下车站、剩余站数、预计到达下车站时间、以及「本站台其他线路」入口。
  - If 退出导航（返回/关闭），系统应当回到进入前的界面状态（推荐列表或地图），且**不丢失已选方案**。
- **优先级**：**P0**

#### 需求 2 · 用户实时位置显示（本次最大难点）
- **用户场景**：Bill 在车上，需要系统知道"他上车并离开了上车站 / 到了哪个站 / 到了哪个区间"。
- **功能点拆解**：① 采用何种定位方案（手机 GPS 持续定位 / 官方车辆位置代理 / 混合）——**架构师出对比、用户拍板**；② 定位结果驱动站条与地图两处显示；③ 失败降级与"进度来源"透明化。
- **验收标准（EARS）**：
  - While 导航进行中且用户已授权定位，系统应当以稳定频率获取用户实时位置（频率由架构师定），并同步驱动站条与地图。
  - When 用户离开上车站，系统应当把上车站标记为"已过"（对应需求 3）。
  - If 定位失败 / 未授权 / 信号丢失（隧道、地下），系统应当降级为**官方车辆位置**或**手动模式**，并**明确标注当前进度来源**；**冻结不跳**（宁缺毋滥，符合"报站数必须符合物理常识"口径）。
  - 验收（真机）：从上车到下车全程，进度显示**不得出现"跳站"**；来源标注与实际一致。
- **优先级**：**P0**（技术前提，阻塞需求 3/4/5/6）

#### 需求 3 · 途经站纵条旁的实时位置
- **用户场景**：Bill 只想"扫一眼"知道自己到哪站。
- **功能点拆解**：① 纵条上新增「您在这里」行，随用户位置推进；② 四态视觉：已过站 / 当前（或当前区间）/ 下一站 / 下车站；③ 导航中站条**默认展开**（沿 v2.13 口径）。
- **验收标准（EARS）**：
  - While 乘车中，系统应当在途经站纵条旁显示「您在这里」，且位置随用户实际所在站/区间推进。
  - When 用户到达某站（或停在区间），系统应当将「您在这里」推进到对应站之后 / 区间中。
  - While 导航中，系统应当对**已过站 / 下一站 / 下车站**使用互不相同的视觉（颜色 + 字重 + 图标），并保证**不依赖颜色单一维度**（可访问性）。
- **优先级**：**P0**

#### 需求 4 · 地图上的用户位置 + 已驶过路段变副主题色
- **用户场景**：Bill 想在地图上直观看到"我走到哪了、走过哪些路"。
- **功能点拆解**：① 地图显示用户实时位置标记；② **已驶过路段由线路主题色（`routes.color`）变为副主题色（澳门绿 `--brand-green #0b6e4f`）**；③ **纵条上已过站的站名文字同步变副主题色**。
- **验收标准（EARS）**：
  - While 乘车中，系统应当在地图上显示用户位置标记，并随定位推进。
  - While 乘车中，系统应当将**已驶过路段**由线路主题色渲染为副主题色（澳门绿），**未驶过路段保持主题色**；换乘多段时逐段独立判定。
  - While 乘车中，系统应当将纵轴上**已过站的站名文字**同步渲染为副主题色。
  - If 用户位置不可得（降级为官方车辆位置或手动），系统应当（按架构师锁定口径）以车辆位置或手动进度驱动同一套"已驶过"渲染，并保持标注透明。
- **优先级**：**P0**（核心差异化）

#### 需求 5 · 下车提醒 + 下车站独立配色
- **用户场景**：Bill 在车上玩手机/闭目，需要被叫醒"该下车了"。
- **功能点拆解**：① 下一站=下车站时触发提醒（横幅 + 震动〔可用时〕）；② 到站二次提醒；③ 下车站使用**区别于已过站(绿)/下一站(蓝)的独立颜色与样式**（建议橙，与 v2.13 一致）。
- **验收标准（EARS）**：
  - When 下一站 = 下车站，系统应当触发下车提醒（**应用内横幅**；支持震动的设备叠加震动）。
  - While 导航中，下车站应当使用独立于"已过站/下一站"的颜色（橙）与图标样式。
  - When 到达下车站，系统应当触发**第二次**提醒。
  - If 运行环境不支持震动（如 iOS 浏览器）或页面处于后台/锁屏，系统应当**如实降级**（仅横幅），并在界面说明该限制。
- **优先级**：**P0**

#### 需求 6 · 底部「本站台其他线路」重构（含可改乘方案一键切换）
- **用户场景**：Bill 走到站台发现**没赶上本班车**，或想比较"同站台有没有别的车也能到目的地"。
- **口径（已确认）**：**站台 = 用户第一程的上车站**。
- **功能点拆解**：① 展开后列出该站台的**其他线路**；② 若存在"可切换方案"（坐某条线直达、或坐某条线再换乘也能到），在该行下方补充：**线路标签**（换乘显示「线路色标签 → 换乘线路色标签」）、**总用时**、**比当前快/慢多少分钟**、**该行右侧一个跳转按钮**；③ 点击跳转 → **直接进入新方案导航界面**；④ **切入新方案后旧弹窗关闭**。
- **验收标准（EARS）**：
  - Given 站台 = 用户第一程上车站，When 用户展开「本站台其他线路」，系统应当列出该站台的其他线路，并对每个**可切换到目的地**的方案显示：线路标签（换乘为「线路色标签 → 换乘线路色标签」）、总用时、比当前方案**快/慢 X 分钟**、以及右侧跳转按钮。
  - When 用户点击某方案的跳转按钮，系统应当**关闭当前弹窗**并**直接进入该方案的导航界面**。
  - While 新方案导航界面打开，系统应当**同屏替换**旧视图，且旧弹窗**不再存在**（无叠层残留）。
  - If 该站台不存在可切换到目的地的方案，系统应当只显示该站台的其他线路列表，并不显示方案区块。
- **优先级**：**P0**（用户明确要求）

#### 需求 7 · 「本站台其他线路」排序规则
- **功能点拆解**：正常态按**数字-字母顺序**一行一条；有可切换方案时，**全部方案置顶**，按「快多少分钟」**递减**、「慢多少分钟」**递增**排序，其余线路置下方。
- **验收标准（EARS）**：
  - While 「本站台其他线路」展开且存在可切换方案，系统应当将**全部可切换方案置于上方**，并按"快多少分钟递减、慢多少分钟递增"排序；其余线路置于下方。
  - While 无任何可切换方案，系统应当仅按**数字-字母顺序**、一行一条展示其他线路。
  - When 方案数据加载失败，系统应当仍展示其余线路列表（软降级，不空屏）。
- **优先级**：**P0**（与需求 6 耦合）

#### 需求 8 · 导航界面美观 / 操作舒适（本次 UI/UX 核心）
- **用户场景**：Bill 对 v2.13 的尝试"不满意：界面不美观"。
- **功能点拆解**：① 延续**站牌风**（青花蓝 `#1b4d8f` + 澳门绿 `#0b6e4f`），精细打磨、不换风格；② 信息层级清晰、留白舒适、动效克制；③ 与设计师产出（03 文档）联动的走查清单。
- **验收标准（EARS）**：
  - 定性验收（本阶段无法自动断言）：导航界面应当符合设计稿（03 文档）；视觉走查清单全部通过；无 emoji 作功能图标（统一 SVG 图标库）；无紫→粉渐变；无 AI 模板味文案。
  - When 在 390×844 主视口下浏览导航界面，系统应当**无横向滚动、无内容被安全区遮挡、无布局抖动（CLS）**。
- **优先级**：**P0**（本次核心）

### 优化项

#### 优化 1 · 地图缩放/取景按"可见区域"计算 + 拖面板不动地图
- **覆盖场景**：选中目的地后、选择出发地后、路线选择界面、导航界面（4 处）。
- **功能点拆解**：① 取景按**当前未被面板遮挡的地图区域**计算中心与缩放；② 检查并修复"**拖动调整弹窗大小时，后面的地图也跟着动**"。
- **验收标准（EARS）**：
  - When 选中目的地后 / 选择出发地后 / 打开路线选择界面 / 进入导航界面，系统应当按**未被面板遮挡的可见区域**计算取景，使目标落在可见区内。
  - While 用户拖动调整面板高度，系统应当**保持地图视野不动**（拖动过程中不触发取景）。
  - When 面板档位落定，系统应当**按落定后的可见区**重新取景一次（不抖动、不重复）。
- **优先级**：**P0**

#### 优化 2 · 文案去 AI 化
- **检查清单见 §5**。
- **验收标准（EARS）**：
  - 系统应当移除所有面向用户的**内部术语/注释型/空洞承诺**文案（清单逐项通过）。
  - When 展示估计值（时间/距离），系统应当使用"约 / 预估"等中性词，且术语全站统一。
- **优先级**：**P1**（低成本高收益，建议随版做）

#### 优化 3 · 轻轨读秒准确（设备时钟倒计时）
- **用户场景**：Bill 点轻轨站后，"延迟出报时"可接受，但**时间必须准**。
- **功能点拆解**：① 点击轻轨站后记住**发车绝对时刻**；② 用**设备时钟倒计时**；③ 归零自动滚动下一班；④ **核实 v2.13 已做的"绝对时刻 `depMs` + 设备时钟"是否真正解决问题**（架构师专项核查）。
- **验收标准（EARS）**：
  - When 用户点击轻轨站，系统应当在可接受延迟内显示到站倒计时，且倒计时基于**设备时钟**、相对官方发车时刻**误差在 ±1 秒**内。
  - When 倒计时归零，系统应当自动滚动到下一班。
  - If 设备时钟与真实时间偏差过大，系统应当（按架构师方案）给出偏差处理或提示。
- **优先级**：**P0**（"时间必须准"是用户硬口径）

#### 优化 4 · 路线推荐卡片底部「后续班车」信息恢复
- **口径**：符合条件的后续班次 = **总用时比最差一张推荐卡还短**的后续班次。
- **功能点拆解**：排查 v2.13 链路为何"最近看不到了"（`altBuses` 渲染在 `RecommendCard`，`hasAlts = length>0`），修复并加回归。
- **验收标准（EARS）**：
  - Given 存在符合条件的后续班次，When 推荐卡片渲染，系统应当在卡片底部显示该后续班车信息。
  - If 无符合条件的后续班次（如深夜时段性为空，属正常），系统应当不显示该区块（不显示空壳）。
- **优先级**：**P1**（回归修复）

## 3. 专项梳理

### 3.1 「导航界面」信息架构（按阶段）

导航界面应随行程阶段**动态重排信息优先级**，保证"第一眼"永远回答最关键的问题。

| 阶段 | 触发 | 第一眼（最大最显眼） | 次要信息 | 主操作 |
|------|------|----------------------|----------|--------|
| A 等车 / 上车前 | 点「开始导航」 | **目标线路 + 该线下一班车还有几站 / 约几分钟** + 我的上车站名 | 车辆在地图上的位置；「本站台其他线路」（改乘）；数据新鲜度 | 「我已上车」 |
| B 乘车中 | 用户上车并离开上车站 | **「您在这里」+ 还剩几站下车 + 下车站名** | 下一站；预计到达下车站时间；已驶过路段（地图变绿 + 站名变绿）；「本站台其他线路」 | 手动兜底（换一辆 / 我已下车） |
| C 临近下车 | 下一站 = 下车站 | **「下一站下车 · 站名」强提示（横幅 + 震动〔可用时〕）** | 下车站橙色高亮 | 确认 / 忽略 |
| D 到站 / 下车后 | 到达下车站 | **到站二次提醒** | 下一步：换乘指引 / 步行到目的地 | 结束导航 / 进入下一段 |

**设计原则**：
- 任何阶段，**"还剩几站"必须是最易读的数字**（大号、居中、无需滚动）。
- 进度来源（实时 GPS / 官方车辆 / 手动）**必须可见**，用中性小字标注（如"实时定位""依据车辆位置""手动"），不出现技术词。
- 地图与站条**同源同色**：已过=绿、下一站=蓝、下车站=橙，两处一致。

### 3.2 「本站台其他线路」交互流程（含切换后状态流转）

```
[导航界面 / 详情]
   │ 用户展开底部「本站台其他线路」
   ▼
[懒加载方案] ── 服务端 POST /api/nav/switch-plans（已有；零高德调用 / 20s 缓存 / 软降级）
   │
   ▼
[渲染]
   ├─ 方案区（置顶）：每条 = 线路标签（换乘双色「色标签 → 色标签」）· 总用时 · 快/慢 X 分钟 · [跳转按钮]
   └─ 其他线路区（置下）：按数字-字母顺序，一行一条
   │
   │ 用户点某方案 [跳转按钮]
   ▼
[关闭旧弹窗] ── 用户明确要求：切入新方案后旧弹窗关闭（同屏替换，无叠层残留）
   ▼
[进入新方案导航界面] ── 建议状态：**A 等车 / 上车前**（因为该场景本质是"没赶上车 / 想改乘"，
   │                        而非"已在新车上"）；新方案数据复用 detail-body / 导航引擎重新加载
   ▼
[可在新方案再次展开同一入口] ── 保留改乘能力（若仍没赶上）
```

**待确认（见 §4）**：
- 切换后新方案进入的状态（等车 vs 直接乘车），以及是否**自动带入**用户已输入的起终点（应带入）。
- 方案区是否包含"当前正在乘的这条线"（应排除自身）。

### 3.3 下车提醒策略建议

| 维度 | 建议 | 依据 |
|------|------|------|
| 提前量 | **默认提前 1 站**；预留"提前 2 站"可选项（Backlog） | 高德 / 百度 / De Lijn 均提前 1 站；澳门巴士站距短，1 站足够；TMAP 提前 2 站用于站距大的场景 |
| 方式 | **应用内横幅（主）+ 震动（可用时）**；到站**二次**提醒 | 高德三重提醒中我们网页端能做的前两项；百度/台北捷运同为"震动 + 通知" |
| 触发条件 | "用户到达下车站**前一站**"或"官方车辆到达下车站前一站"，**取更可信/更早者**（口径由架构师定） | 高德用"剩 1 站且 <500m"；我们需与定位/车辆方案绑定 |
| 后台 / 锁屏 | **如实告知受限**；本版不承诺系统级通知（独立小工程进 Backlog） | 网页/浏览器能力限制；谷歌用 Live Updates、TMAP 用锁屏，我们短期做不到 |
| 边界 | 坐过站 → 提供补救提示（文案引导下一站下车往回坐 / 重新规划）；轻轨段无逐车数据 → 手动模式提醒 | 已知限制（交接文档 §四.6） |

### 3.4 文案去 AI 化检查清单

**审查范围（逐界面过一遍）**：搜索框占位 / 出发地与目的地输入 / 推荐卡片（含底注与「后续班车」）/ 详情各段（步行·乘车·换乘）/ 本站台其他线路 / 导航界面 / 各类空态（too_close、no_live、no_candidate）/ 错误态与重试 / 按钮与文字链 / 悬浮提示 / 设置页 / 收藏组合页 / `/help`、`/about`。

**判断标准（出现任一即需修改）**：
1. **内部实现词外露**：接口、缓存、轮询、投影、数据源、高德、算法、兜底、熔断、后端、字段名等。
2. **注释型文案**：本应写给开发看的说明被渲染给用户（如"不掺高德方案"）。
3. **空洞承诺 / AI 腔**：智能、一键、极致、赋能、全新升级、Welcome、Lorem ipsum、机械翻译腔。
4. **估计值未标注**：估计的到达/等待时间未用"约 / 预估"。
5. **术语不统一**：上车/上车点、站台/站点、换乘/转乘、轻轨/地铁等混用。

**好 / 坏例子**：
| 坏（现状示例） | 好（建议） | 原因 |
|----------------|------------|------|
| 收藏组合「不掺高德方案」 | 删除；若需表达，用「纯本地线路」等对用户有意义的信息 | 注释外露 |
| 「本地推算」 | 「预估」 | 技术词外露 |
| 「接口暂无数据」 | 「暂无实时信息」 | 技术词外露 |
| 「Welcome to M Map」 | 「输入目的地，开始规划」 | AI 模板味 |
| 「智能为您推荐最佳路线」 | 「推荐路线」 | 空洞承诺 |
| 展示"车牌锁定""12s 轮询" | 不展示；如需可信度 → 「上次更新：12 秒前」 | 技术词外露；可借鉴 Moovit 的数据新鲜度表达 |

## 4. 待确认问题（请用户拍板）

1. **实时定位方案**：手机 GPS 持续定位 / 官方车辆位置代理 / 混合——架构师出三方案对比后，用户拍板（涉及**是否接受持续定位权限与耗电**）。
2. **「已驶过路段」的口径**：以**手机定位**为准，还是以**官方车辆位置**为准？若用户未上车（等车阶段）是否不显示"已驶过"？
3. **切换方案后的状态**：点「切过去」后，新方案导航进入**"等车/上车前"**状态（我的建议）还是直接进入乘车状态？
4. **方案区是否排除"当前正在乘的线路"**？（建议排除自身）
5. **下车提醒提前量**：默认**提前 1 站**是否可接受？是否需要"提前 2 站"可选项？
6. **后台/锁屏提醒**：接受"**仅前台横幅 + 震动（可用时）**"这一 Web 限制，还是需要额外方案（独立小工程）？
7. **取景**：4 个场景是否需要**统一动画**（面板落定后取景）？拖动面板时地图"完全不动"是否即为期望？

## 5. 边界与约束（产品侧）

- 主视口 390×844；iOS/Android 安全区避让。
- 地图失败/缺 Key **不阻塞**导航信息展示（沿用"地图失败不阻塞"铁律）。
- 数据新鲜度必须可见（借鉴 Moovit）——否则"实时"无从判断。
- 网络慢/弱网：进度与提醒的**降级链**必须清晰（实时 → 车辆位置 → 手动），且**来源标注**随降级变化。
- 轻轨段、几何缺失段：**手动模式**（已知限制）。
- 可访问性：已过/下一站/下车站**不依赖颜色单一维度**区分（配字重/图标）。WCAG 2.1 AA 基本合规。
- **⛔ P0 红线（本项目团队级）**：文档与实现中禁止 emoji 作功能图标（用统一 SVG 图标库，具体库由架构师锁定）；禁止紫→粉渐变配色建议；禁止 "Welcome to" / "Lorem ipsum" 类空洞占位文案。
