## A. 用户实时位置方案对比（核心难点）

### A.0 现状（v2.13 实为「车辆位置代理」）

- 现有「定位」= 单次定位：`AMap.Geolocation({ enableHighAccuracy: true, timeout: 10000, convert: true })` + `geo.getCurrentPosition(...)`（`src/components/nav/NavMap.tsx:387-413`），定位点存 `userPos`（`NavShell.tsx:84,139`），仅用于「我的位置」出发地。
- 导航追踪态的「您」标记**不是用户位置**，而是**锁定车辆的实时坐标**：`ride.traveled` 末点被当作「您」的位置（`NavShell.tsx:305-313` → `TrackLayer.tsx:99-120`）。这一点在 `src/lib/nav/track.ts:11-13` 的注释里已写明（「手机 GPS 仅作后续增强」）。
- 车辆通道：12s 轮询 `/api/route-vehicles`（`useRideTracking.ts:31`），车牌锁定（`useRideTracking.ts:297-338`），进度由「挂靠站 / 行驶区间」推导（`track.ts:65-98`），已驶过路段用投影切割（`track.ts:130-137`）。

> 结论：**当前系统没有任何「用户真实位置」数据流**。「实时定位不够好」的根因是这里——「您」= 车的位置，不是人的位置。

### A.1 A1 · 手机 GPS 持续定位

**两条可选实现：**

| 实现 | 坐标 | 说明 |
|---|---|---|
| `navigator.geolocation.watchPosition`（浏览器原生） | **WGS84**（原始 GPS） | 标准 API，需自行转 GCJ-02 才能喂高德 |
| `AMap.Geolocation` | `convert:true` 时**已是 GCJ-02** | 官方文档（更新至 2024-03-25）只示范 `getCurrentPosition` |

**关于 `AMap.Geolocation` 是否支持 `watchPosition`——存疑，标记「待验证」：**
- 高德官方「定位」指南只列 `getCurrentPosition`（https://lbs.amap.com/api/javascript-api-v2/guide/services/geolocation，2024-03-25）。
- 多篇社区实践明确指出「高德 Geolocation 插件仅适用于单次定位，连续定位/轨迹追踪用 `navigator.geolocation.watchPosition` 更合适」（https://blog.csdn.net/jackchen32795/article/details/149436999、https://blog.csdn.net/jackchen32795/article/details/149422448 用 `setInterval + getCurrentPosition` 模拟实时）。
- 另有社区示例出现 `geolocation.watchPosition(...)`（https://www.yisu.com/zixun/592052.html）——可能为部分版本可用。
- ⇒ 本方案**不依赖 `AMap.Geolocation.watchPosition`**，一律走 `navigator.geolocation.watchPosition`，规避版本不确定性。

**平台限制（联网核实）：**
- **后台/锁屏一律暂停**：Web 无「始终允许」定位权限；iOS Safari 页面切后台或锁屏即停 `watchPosition`，Android Chrome 后台标签 ~30s 后被冻结；Service Worker **不能**访问 Geolocation（https://www.xjavascript.com/blog/it-is-possible-to-watch-the-location-in-the-background-on-mobile-ios-android、https://dev.to/alex_truhniy/...-fieldkit-4-448g）。
- **iOS Safari 回调频率低**：`watchPosition` 在 iOS Safari 默认可能 ~10s 才回调一次（https://www.php.cn/faq/2496706.html）。
- **精度**：开阔地 10~30m；城市峡谷（澳门半岛高楼、桥面、隧道）多径误差放大、甚至丢星。
- **权限**：必须 HTTPS；**必须由用户手势触发**（不能在 `onload` 自动调）（https://juejin.cn/post/7653433755940634667）。
- **耗电**：`enableHighAccuracy:true` 明显耗电；必须配对 `clearWatch()`，且业务层自做节流。

**对澳门场景的判断：** 澳门路网密集、桥隧多，纯 GPS 做「公交站级进度」不可靠——GPS 无法区分「在第 3 站还是第 4 站」。**GPS 适合回答「人在哪」，不适合回答「车到哪一站」。**

### A.2 A2 · 官方车辆位置（现状主通道）

- 数据源：`/api/route-vehicles`（车牌 / 坐标 GCJ-02 / 挂靠站 / 状态 / 区间），12s 轮询（`useRideTracking.ts:31`）。
- 与 DSAT 报站同源，「站级」准确；车牌可稳定锁定；**无定位权限门槛**。
- 局限：**只覆盖巴士**——轻轨无逐车数据（`useRideTracking.ts:189-194`「该程暂无自动进度」）；丢信号时冻结（`track.ts:96-97`、`useRideTracking.ts:222-226`）。
- 这正是 v2.13 采用它的理由（用户 2026-09-24 拍板，见 `track.ts:11-13`）。

### A.3 A3 · 混合（推荐）

Google Maps 公交导航的公开实现方式与之同构：**车辆位置来自运营方 AVL（GTFS-RT）**，用户自身位置来自手机 GPS，二者是**两条并列数据层**，进度/到达判定以 AVL 为准，不用手机 GPS 去推公交进度（https://lifetips.alibaba.com/...、https://en.actualidadiphone.com/?p=263231）。

**位置融合策略：**

| 阶段 | 「人在哪」 | 「车到哪」 | 说明 |
|---|---|---|---|
| 候车（boarding） | 手机 GPS（watchPosition）→ 转 GCJ-02 → **snap 到出发步行段/线路 polyline** | 官方车辆（候车候选列表） | 告诉用户「离上车站还有多远」，GPS 有效 |
| 乘车（riding） | 手机 GPS 仅作**蓝点增强**（可关） | 官方车辆（权威） → 站序进度 + 已驶绿段 + 下车提醒 | 进度/提醒**只认车辆**，GPS 漂移不影响 |
| 下车后（done） | 手机 GPS | — | 末段步行引导 |

- **是否 snap-to-route**：是，但对两类坐标分开处理。GPS（WGS84）先 `wgs84ToGcj02`（`src/lib/amap/coord.ts:66-77`，已与高德官方转换逐点比对，最大差 0.32m，`coord.ts:122-124`），再用 `nearestOnPath`（`src/lib/nav/route-overview.ts:103`）投影；投影距离超容差（`CUT_TOLERANCE_M=250`，`track.ts:137`）**不吸附、不切线**，如实降级。
- **坐标系注意（铁律）**：`navigator.geolocation` 返回 **WGS84**，必须转 GCJ-02 才能画到高德底图；`AMap.Geolocation convert:true` 返回**已 GCJ-02，不得再转**（`amap-loader.ts:16-17`、`NavMap.tsx:28`）。两者**绝不能混用同一转换入口**。
- **UI 数据流（谁提供「您在这里」）**：
  - 地图「您」蓝点 ← **手机 GPS**（真身，独立于车辆）。
  - 车辆图标 ← 官方车辆位置（已有 `VehicleLayer`）。
  - 纵条「您在这里」锚点 + 「已过 N 站 / 下一站」 ← **车辆通道**（`StationStrip.tsx:62-72`、`RouteDetailBody.tsx:179-186`）。
  - ⇒ 地图上「您」（人）与车辆（车）**同时可见、可区分**，不再用车辆冒充用户。
- **失败与降级链**：GPS 拒权 / 超差 → 蓝点不画（或画精度圈），**站条与下车提醒不受影响**（走车辆通道）；车辆丢信号 → 冻结上次进度并提示（`useRideTracking.ts:222-226`）；两者皆失 → 手动模式（`useRideTracking.ts:301-306`）；页面前后台切换 → 恢复可见时重申请 Wake Lock（`useRideTracking.ts:176-183`）。
- **与 `useRideTracking` 状态机的整合草案**：新增一条 `userFix` 通道（`{ lng, lat, accuracy, ts } | null`）并保留现有 `RidePhase`；`boarding` 阶段消费 `userFix` 做「离站多远」，`riding` 阶段 `userFix` 只喂地图蓝点，**不参与 `progressOf`**（保证进度永远由车辆决定）。

### A.4 推荐方案

- **推荐：A3 混合**。理由：① 公交站级进度只有官方车辆数据能可靠给出（A2 权威）；② 用户真实位置（A1）是需求 2/4 明确要的「用户实时位置」，当前完全缺失；③ Google 的公开做法即「车辆 AVL 与用户 GPS 并列」，可复用同一心智模型。
- **代价**：多一条 GPS 数据流（权限、耗电、漂移处理），前端组件与状态机复杂度上升；需新增坐标转换调用（已有纯函数，无新依赖）。
- **备选**：若用户坚持「只做一个」——退 A2（现状增强：把「您」的语义从车辆改名为「本班车」，另加一个可选 GPS 蓝点），或退 A1（仅在候车阶段用 GPS，乘车阶段不做进度）。**不建议纯 A1**（隧道/高架下进度会错，违反「报站数必须符合物理常识」的口径）。
- **已知不可达项（如实标注）**：锁屏/后台不做定位与提醒（Web 平台限制，非本项目可解），交付文案需沿用现有「仅前台亮屏有效」的披露口径。

## C. 轻轨读秒准确性核查

### C.1 现状实现（v2.13）

**服务端 `src/app/api/station/eta/route.ts`：**
- 秒级选班：`nextDeparture` 用 `v*60 + biasSec > nowSec` 比较（`eta/route.ts:217-238`），避免偏差为负时把「该分钟内已开出」的班次错报为下一班。
- 绝对发车时刻：`dayStartMs + nextSec*1000`（`eta/route.ts:255,269-272`），`nextSec = 表定分钟*60 + biasSec`。
- 轻轨站**跳过 20s 内存缓存**（`eta/route.ts:306-316,377-378`），保证时刻滚动与 `depMs` 新鲜。

**前端 `src/components/nav/StationCard.tsx`：**
- 倒计时 = `depMs − 设备时钟`（`StationCard.tsx:98-107`）。
- 到点自动重拉下一班：`nowMs - depMs > 2000` 时触发，4s 护栏（`StationCard.tsx:185-194`）；静默重拉不闪加载态（`StationCard.tsx:196-224`）。

### C.2 判定：v2.13 方案**方向正确**，但仍有两处缺口

**已解决（确认）：** 旧口径 `etaSec` 是「服务端处理那一刻」的相对快照，命中 20s 缓存时会整体偏大；改下发 `depMs` 绝对时刻 + 客户端设备时钟倒计时后，**缓存/网络往返不再影响读数**（`eta/route.ts:80-86` 注释、`StationCard.tsx:91-96` 注释）。

**缺口 1（新增风险）· 设备时钟偏移：**
- `depMs` 由服务端 `Date.now()` 推出（`eta/route.ts:151,255`），客户端用**设备时钟** `Date.now()` 相减（`StationCard.tsx:103`）。两者都是绝对 epoch ms ⇒ **设备时钟若与真实时间有偏移，读数会同步偏移**。旧 `etaSec` 口径反而对设备时钟免疫（它是相对量）。
- 影响：手机时间被用户或系统误差调偏（常见几十秒）时，「还有 X 分 Y 秒」会整体偏移；「到点重拉」的触发（`nowMs - depMs > 2000`）也会随之提前/延后。
- 判定方法：真机改系统时间 ±60s，观察倒计时是否同步偏移。

**缺口 2（次要）· 到点重拉间隙：**
- 倒计时归零后到重拉返回前，界面停留在「即将开出」（`StationCard.tsx:104,107`），时长 = 重拉网络延迟 + 4s 护栏（`StationCard.tsx:191`）。间隙内显示的是**上一班已过去的时刻**，属可接受但不够干净。

**其它核查项（结论）：**
- 并发缓存：轻轨已跳过缓存（`eta/route.ts:310,377`）——**无问题**。
- 跨日滚班：`nowMin > lastMin` 收班返回 null（`eta/route.ts:236`）；过零点后 `nowMin` 重置 → `all.find(v*60+bias > nowSec)` 返回**当日首班**（凌晨验证：氹仔 06:30 / 横琴 06:33:40，含 +40s 偏差）。**行为正确**，但「收班到次日首班」之间的文案统一为「今日已收班」（`StationCard.tsx:99`），未预告次日首班时刻——是否补充由产品定（建议在「已收班」旁提示次日首班）。
- `dayStartMs` 用「+8h 取模」推当日零点（`eta/route.ts:255`），不依赖时区 API，澳门无夏令时——**正确**。
- 偏差应用：选班与展示**同一 `biasSec`**（`eta/route.ts:260,269`）——**一致**。

### C.3 修复设计

1. **服务端对时**：响应体增加 `serverNowMs`（或复用已有 `fetchedAt` 换算）。客户端在 fetch 成功时记录 `offset = serverNowMs − Date.now()`，倒计时用 `left = depMs − (Date.now() + offset)`。约 5 行改动，即可对设备时钟偏移免疫。降级：老接口无 `serverNowMs` → `offset=0`（现行为）。
2. **重拉间隙收敛**：把触发阈值提前（如 `nowMs >= depMs`）并把重拉期间的文案置为「正在获取下一班…」，避免显示已过期时刻；护栏从 4s 降到 1.5s（服务端已不缓存，可承受）。
3. 可选：收班态补充次日首班时刻（需服务端在收班时仍算出次日首班的 `depMs`）。

## D. altBuses（后续班车）回归排查

### D.1 机制（读码确认）

- 回填函数 `backfillAltBuses`（`nav-service.ts:641-661`）：**阈值 = 最后一张卡的 `totalMin`**，只保留 `totalMin ≤ 阈值` 的后续班次；只对**入选前 N 张**的卡回填（`topSet`）。
- 主链路：`planNav` 内 `backfillAltBuses(cards, modeled, siblingAlts)`（`nav-service.ts:567`）；并行线后续班次由 `siblingSeedsOf` 独立建模（`parallel-alts.ts:29-53`）后合并。
- 旧链路 `recommend/service.ts:142-150` 为同一口径（v1.1.5）。
- 渲染条件：`RecommendCard.tsx:91` `hasAlts = altBuses?.length > 0`；仅当非空才渲染卡底（`RecommendCard.tsx:237-253`）。
- 回归断言：`scripts/test-altbuses.ts`（8 断言，覆盖两卡/单卡/临界/topSet/sibling）。
- 首页推荐走 `/api/nav`（`useRecommend.ts:60` → `route.ts:102` → `planNav`），**非** `/api/recommend`。

### D.2 可能原因（区分「时段性空」与「代码回归」）

| 类别 | 原因 | 判据 |
|---|---|---|
| 时段性（正常） | 深夜/平峰发车间隔长 ⇒ 后车 `totalMin` > 阈值 | 白天高峰同 OD 复现则恢复 |
| 口径（正常） | **只剩 1 张卡** ⇒ 阈值=自身 ⇒ 后车（必然更晚）全被滤（`test-altbuses.ts:85-90` 已锁此口径） | `cards.length===1` 时**必然**空，非 bug |
| 口径（正常） | 无在途车 / 后车被 `excluded`（`nav-service.ts:159`） | 看 `excluded` / `missed` 列表 |
| 时段性 | 阈值随「最后一张卡」浮动 ⇒ 同一 OD 不同时刻保留集不同 | 分时采样对比 |
| 代码回归（需查） | 并行线 `parallelRoutes` 未填充 ⇒ sibling 缺失 ⇒ 只剩主干线后续 | 检查卡首段 `parallelRoutes` 与 `route_options` 数据 |
| 代码回归（需查） | `modelOption` 内 `alts` 生成被去重/排除逻辑吃空（v1.1.6 `loSec` 去重排本班） | 单测 + 线上探针看 `modeled[].alts` |
| 代码回归（需查） | 缓存命中旧结果（`transit_cache` / 10s rec 缓存 `service.ts:27`）不含 `altBuses` | 带 `nocache=1` 重跑 |
| 渲染（需查） | 新界面重写后卡片未渲染 `altBuses` 区块 | 静态核对 `RecommendCard` 渲染分支 |

### D.3 排查步骤与判定方法（本阶段只出步骤，不改代码）

1. **分时采样**：对同一 OD（如 home→school）在 08:00 / 14:00 / 22:00 / 00:30 各调 `/api/nav?...`，记录 `count`（卡片数）、每卡 `altBuses.length`、`excluded`、`missed`。
   - 判定：`count>1` 且白天有值、深夜无值 ⇒ **时段性**（正常，收尾）。
   - 判定：白天也恒空 ⇒ 进入 2。
2. **锁口径单测**：跑 `npm run test:altbuses`。
   - 8/8 ⇒ 回填逻辑本身未坏，问题在数据/渲染（进入 3、4）。
   - 有失败 ⇒ 回填逻辑回归（重点改 `nav-service.ts:641-661`）。
3. **查数据源**：只读查 `route_options` 中目标卡首段的 `parallelRoutes` 是否非空；查该时段线路在途车（`/api/route-vehicles`）。
   - `parallelRoutes` 空 ⇒ sibling 缺失类回归。
4. **查渲染**：静态核对 `RecommendCard` 的 `hasAlts` 分支在**新界面重写后**是否仍被挂载（重写时最易丢）。
5. **查缓存**：同 OD 带 `nocache=1` 复跑，对比是否出现 `altBuses`。
   - 出现 ⇒ 缓存类问题（旧缓存或 `transit_cache`）。

> 结合 `MEMORY.md`（两轮深查均证明功能正常、深夜为空属时段性），**最可能仍是时段性/口径**；但本次要求区分，故按上述 1→5 顺序定性。

### D.4 修复方向（待定性后执行）

- 若时段性：不改逻辑，考虑在卡片底注加入「当前时段无更晚且不更慢的班次」的**说明文案**（消除「以为坏了」的观感）。
- 若 sibling 缺失：修复首段 `parallelRoutes` 填充链路（`bridgeLeg` / `route_options`）。
- 若渲染丢失：在新卡片组件补回 `altBuses` 区块。
- 若缓存：校正缓存键或加 `altBuses` 失效条件。

## E. 地图取景（按真实可见区缩放）

### E.1 现状机制

**指令生成（`NavShell.tsx:261-278`）**：
- `rsOpen`（面板打开，推荐或详情）：`mode='fit-box'`，`box` = 详情用 `ov.box`（路线外包框）否则 OD 两点外包框；`slotTopPx` = `topsPx[DETENTS.indexOf(snap)]`（当前档顶边）。
- `stage==='panel'`：有 `from` ⇒ `fit-two`；仅 `to` ⇒ `dest-center-top`。
- 其余 ⇒ `none`。`tick` 变化即重新取景。

**执行（`NavMap.tsx:640-750`）**：
- 一律**自算**（禁 `setBounds` / `setFitView`，`NavMap.tsx:209-210`），反推 zoom + `setZoomAndCenter(..., immediately=true)` + `panBy` 把目标抬到「顶部槽中心」。
- `dest-center-top` / `fit-two` 用 `.rpanel` **真实顶边** `panelTopPx()`（`NavMap.tsx:159-171`），读不到回落 1/5 屏 / 半屏。
- `fit-box` 用 `slotTopPx` + 设计 Token `--map-fit-gap`（`NavMap.tsx:173-178,731`），`--map-fit-gap:24px`（`globals.css:158`）。

**档位几何（`sheet-detents.ts:21-25`）**：`full = clamp(max(safeTop+44, 12vh), 96, 128)` / `half = 50vh` / `peek = 80vh`。

### E.2 「拖面板时地图跟着动」根因分析

- 面板拖拽本身在 `RouteSheet` 内部，`NavShell` **不重渲染**（拖拽 state 在 `useSnapSheet`，`useSnapSheet.ts:70-72`）——**拖动过程中地图不动**，这部分符合预期。
- 冲突点在**释放吸附后**：`useSnapSheet` 释放时调用 `onDetentChange`（`useSnapSheet.ts:192-202`）→ `NavShell.setSnap` → `view` 因依赖 `snap` 重新计算（`NavShell.tsx:261-278`，依赖含 `snap`）→ `slotTopPx` 变化 → `NavMap` 取景 effect 依赖 `view`（对象 identity 变）→ **重新取景**。⇒ 每次换档都会把地图重设视野，观感即「拖完面板地图自己跳」。
- 加剧因素：
  1. `view` 由**响应式 state 派生**（`rsOpen`/`pane`/`snap`/`topsPx`/`ov.box`/`ovExtra`/`stage`/`from`/`to`/`viewTick` 任一变即重算），其中 `ov.box`（`useRouteOverview` 输出）与 `topsPx`（resize）会**非用户意图地**变化 ⇒ 触发意外取景。
  2. 取景 effect 依赖 `[view, dest, origin, phase]`（`NavMap.tsx:750`），`view` 为新对象即重跑，即使 `tick` 未变。
  3. 桌面端曾因「拖 handle 改档位 → 重取景」被专门加守卫忽略拖拽（`useSnapSheet.ts:89-96`）；移动端无此守卫，靠「释放才改档」减轻，但**换档重取景仍在**。
- 另一处邻近冲突：`.rpanel` 起拖区仅 `HANDLE_H`（`RoutePanel.tsx:24,66`）、面板拖拽区 `HANDLE_H=56`（`useSnapSheet.ts:25,108`），若命中区判定与地图拖动区重叠，可能误接管（需真机验证，标「待验证」）。

### E.3 「按真实可见区缩放」四场景设计

统一原则：**可见区 = 屏幕中「未被面板/搜索层遮挡」的矩形**；目标外包框适配进该矩形并留呼吸边距。取景**只由显式指令触发**（见 E.4）。

| 场景 | 可见区定义 | 取景定义 |
|---|---|---|
| 1 选目的地后（`stage='panel'`，仅 `to`） | `y ∈ [safeTop+chrome, panelTop]`，`panelTop = .rpanel` 真实顶边（`panelTopPx`，`NavMap.tsx:159-171`） | `dest-center-top`：目标居中于该矩形（现逻辑已用真实顶边，`NavMap.tsx:662-663`）；呼吸边距统一用 `--map-fit-gap` 替代硬编码 20px |
| 2 选出发地后（`stage='panel'`，`from`+`to`） | 同上 | `fit-two`：两点外包框适配进 `[safeTop, panelTop]`（现用 `panelTopPx`，`NavMap.tsx:693-707`）；同样接 Token 边距 |
| 3 路线选择界面（`rsOpen`，`pane='recommend'`） | `y ∈ [safeTop, `topsPx[snap]`]`（推荐默认 `full` ⇒ 仅 ~96~128px 高可视） | `fit-box`（OD 外包框，`NavShell.tsx:268`）。⚠️ **问题**：`full` 档可视高度仅约百 px，会强制 zoom 触底（下限 12，`NavMap.tsx:740`）；**建议路线选择界面默认取 `half` 档**（可视 50vh），或取景时对 `full` 档按「可视区下限」兜底 |
| 4 导航界面（`rsOpen`，`pane='detail'`，默认 `half`） | `y ∈ [safeTop, `topsPx['half']`]` = 上半屏 | `fit-box`（`ov.box` = 路线彩段 + 起终点外包框，`NavShell.tsx:265-266`）。导航中「已驶过绿段 / 您 / 车辆」应保持在可见区内；取景随段推进可考虑轻微跟随（新增需求，待产品确认） |

### E.4 设计要点（消除「拖面板地图跳」）

1. **取景与响应式 state 解耦**：`NavMap` 的取景 effect 改为**只在 `tick` 变化时执行**；`view` 内部携带 `tick`，effect 依赖收敛为 `[view.tick]`（或把取景改成命令式 API `ref.reFrame(spec)`）。这样 `snap`/`ov.box`/`topsPx` 变化**不自动**触发取景。
2. **只在明确意图时发指令**：卡开（`openDetail`）、进详情/回推荐（`contextClose`）、选点（`pickPoint`）、出发（`go`）已经 `setViewTick`（`NavShell.tsx:182,188,198,215`）——保留；**拖动换档不 `setViewTick`**（即换档后地图保持不动，符合需求）。
3. **换档后如需重取景**：只在「用户主动进入某档并停顿」时按需取景，或在换档后再单独补一次带防抖的取景（可选，默认不做）。
4. **呼吸边距统一 Token 化**：`dest-center-top` / `fit-two` 的硬编码 20px / 半屏口径改为读 `--map-fit-gap`（`globals.css:158`），与 `fit-box` 统一。
5. **`full` 档取景兜底**：场景 3 说明的可视区下限问题。

## ADR 提案（状态 = Proposed，待用户拍板后转 Accepted）

### ADR-001：用户实时位置采用「混合方案（A3）」

- **Status**: Proposed（2026-09-25）
- **Background**: 「您」标记当前实为车辆位置代理（`NavShell.tsx:305-313`），系统无用户真实位置数据流；用户反馈「实时定位不够好」。手机 GPS 无法可靠判定公交站级进度（隧道/高架漂移）；官方车辆数据覆盖巴士但不覆盖轻轨，且无定位权限门槛。
- **Decision**: 采用双通道——**候车阶段**用 `navigator.geolocation.watchPosition`（WGS84 → `wgs84ToGcj02` → snap 到步行/线路 polyline）给出「离上车站多远」与地图蓝点；**乘车阶段**进度 / 已驶绿段 / 下车提醒一律以官方车辆位置为准（12s 轮询），手机 GPS 仅作地图蓝点增强。不依赖 `AMap.Geolocation.watchPosition`（版本不确定，标「待验证」）。
- **Consequences**:
  - 正面：需求 2/4 的「用户实时位置」有了真实数据源；进度抗 GPS 漂移；与 Google 公交导航心智一致。
  - 负面：多一条 GPS 数据流（权限、耗电、漂移处理），前端状态机与组件复杂度上升；锁屏/后台仍不可用（Web 限制，需如实披露）。
- **Related ADRs**: ADR-002。

### ADR-002：界面「推翻重做」的边界 = 保留服务端与计算层，重写视图层

- **Status**: Proposed（2026-09-25）
- **Background**: 用户要求界面全部推翻重做，但 v2.13 的服务端接口与计算逻辑（planNav / 建模 / 追踪引擎 / 几何 / 折叠栏 / 坐标工具）经线上 E2E 验证正确，重写会丢正确性并引入回归。
- **Decision**: 保留 `app/api/**`（含 middleware 白名单，`middleware.ts:38-61`）、`lib/**`（引擎 / 几何 / 编排 / 坐标）、数据 hook（`useRouteOverview` / `useDetailBody` / `useRecommend` / `useRideTracking` 逻辑）与 UI 原子件；**重写**视图层（`RouteDetailBody` / `StationStrip` / `StationReachFold` / `RecommendCard` / 面板视觉 / `NavMap` 取景段）。重做时顺势拆分超 300 行的文件（`NavMap.tsx` / `NavShell.tsx`）。
- **Consequences**:
  - 正面：界面自由重做，同时保住已正确的数据/计算逻辑与线上契约；回归面收敛在视图层。
  - 负面：视图重写需逐一核对与数据 hook 的接口（尤其 `RideTrackView` 增加 `userFix` 后的类型变更）；存在「重写时漏挂功能」（如 D.3 的 `altBuses` 渲染）的风险，需靠 E2E 探针守住。
- **Related ADRs**: ADR-001。
