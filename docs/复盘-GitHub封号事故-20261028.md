# M Map · GitHub 账号封禁事故复盘报告

> 报告日期：**2026-10-28**
> 事故定性：**生产事故（P1）** —— 承载全部代码资产的账号被平台停权，持续约 **5 周**
> 当前状态：**已解封**（2026-10-28 确认）· 已完成仓库改名 `musttoukou` → `M-Map` · 已邀请协作者
> 证据边界：**本报告全部依据本地仓库、本地文档、线上站点与历史交接记录**；未对 GitHub 做任何读/写操作。
> ⚠️ 因此「成因」为**证据推断**，非平台官方结论。官方结论以 GitHub 停权通知邮件原文为准（见 §9 待补信息）。

---

## 1. 一句话结论

事故最可能的成因是**「仓库转公开 + 新协作者账号 5 天内提交 30 个 PR」触发了 GitHub 的反滥用/协同造假（Coordinated Inauthentic Behavior）风控**，而**仓库公开内容中包含政府系统鉴权算法的逆向实现 + 大规模自动采集证据**构成了第二重（也是更长尾的）合规风险。两者都会导致**账号级停权**而非单仓库处置 —— 与本次实际现象一致。

## 4. 成因假设（按置信度排序）

> 置信度为**主观概率估计**，用于排序与决策，不代表事实。多条假设可同时成立（叠加触发）。

### H1 · 协作行为触发反滥用风控 —— 置信度 **高（约 55%）**

- **假设**：仓库公开后，一个新协作者账号在 5 天内密集产生 30 个 PR，并以极短间隔被 merge；GitHub 的反协同造假/刷量模型将其判定为 inauthentic activity，处置**账号**而非仓库。
- **依据**：
  - F6/F7 —— 平台侧看到「同一账号 5 天合入 30 个 PR」，这正是刷量模型的典型负样本特征；
  - 时间点吻合：PR 高峰（#77/#79，09-20~21）与封号同窗口；
  - **处置形态吻合**：内容类投诉通常只处置仓库（DMCA/ToS takedown，仓库变 404 但账号仍在）；**账号停权**是反滥用体系的典型输出；
  - 解封耗时约 5 周 —— 与「自动风控 → 人工复核 → 申诉排队」的节奏一致，而非「误报秒解」。
- **反证/弱点**：GitHub 一般允许正常开源协作，30 个 PR 不算天文数字；若真是纯刷量，申诉通常更快恢复。
- **验证方式**：看停权邮件是否出现 `spam`、`inauthentic`、`multiple accounts`、`automation` 等字样。

### H2 · 公开的鉴权算法逆向实现被举报 —— 置信度 **中高（约 40%）**

- **假设**：权利人（DSAT）或第三方发现公开仓库内含其系统 token 算法的完整实现 + 大规模采集证据，向 GitHub 举报「未授权访问 / 规避技术措施」；GitHub 依 AUP 处置。
- **依据**：
  - F1/F2/F3 —— 内容确实存在且可运行、可检索；
  - F4 —— 官方政策明示该类数据个人不可申请，我们无授权依据；
  - F5 —— 采集强度构成「异常使用」的旁证；
  - 公开化（09-19）与封号（09-20/21）时间高度重合，公开是内容被发现的**必要条件**。
- **反证/弱点**：GitHub 对「逆向第三方 API」的常规做法是先发仓库级通知，账号级停权较少见；除非举报方援引法律条款或内容被判定违法。
- **验证方式**：检查账号是否收到 `DMCA`、`legal`、`terms of service` 类邮件；GitHub 通知中心是否有仓库级 takedown 记录（解封后应可查）。

### H3 · 采集流量被 DSAT 侧识别并投诉 —— 置信度 **中低（约 15%）**

- **假设**：22.6 次/秒 的轮询被目标侧 WAF 标记，DSAT 通过渠道投诉至平台或直接封 IP；封 IP 本身不影响 GitHub，但**若投诉同时指向仓库内容**则与 H2 合流。
- **依据**：F5；合规备忘自述「单一 IP 18.4 次/秒是明显异常特征」。
- **反证**：合规备忘实测「速率提速 11 倍、对方 p50 延迟纹丝不动（12~16ms）」、失败率 0.065%，对方服务端**无可观测劣化**；且封 IP 不会导致 GitHub 停号。
- **验证方式**：解封后首次采集试探，看是否立刻 403/超时（可判定 IP 是否被记）。

### H4 · 机构混淆/冒充误判 —— 置信度 **低（约 10%）**

- **假设**：早期产品名「MUST登校」、采集 UA 含 `MUSTDengxiao`、内容大量涉及「交通事务局」，被模型或人工误判为冒充官方机构。
- **依据**：UA 自报身份串（铁律 32 冻结项）；早期仓库名 `musttoukou`。
- **反证**：UA 明确写 `personal non-commercial`；站点 `/help` 有来源声明；已改名 M Map 去官方化。

### H5 · 账号凭据泄露 / 异常登录 —— 置信度 **低（约 5%）**

- **依据**：F8（`.env` 从未入库）→ 无常见泄露路径；但 09-17 起 commit 邮箱由 `noreply` 切为真实 Gmail（`bill070608@gmail.com`），真实邮箱暴露会增加钓鱼/撞库面。
- **反证**：若是盗号，通常表现为仓库被改/被删/被加陌生协作者，而非整号停权。
- **验证方式**：解封后核对 Security log（登录地点、PAT 创建记录）。

## 8. 改进与预防措施

### 8.0 决策 D1（2026-10-28 主人定）：**提交面白名单化 —— 今后的 GitHub 只提交必要文件**

**决策原意**：不再把「全部资料」往仓库里堆。仓库只承载「跑起来需要的东西」，调研/复盘/过程文档留在本地。

#### 8.0.1 提交范围白名单（建议边界）

| 归属 | 内容 | 入 git | 理由 |
|---|---|---|---|
| ✅ 必要 | `src/` `public/` `scripts/` `db/` | 是 | 产品本体，缺了就跑不起来 |
| ✅ 必要 | `package.json` / `package-lock.json` / `tsconfig.json` / `next.config.ts` / `eslint.config.mjs` / `vercel.json` / `.gitignore` / `.env.example` | 是 | 构建与部署配置 |
| ✅ 必要 | `README.md` | 是 | 对外唯一门面（只留定位、上手、合规声明） |
| ⚠️ 慎入 | `docs/`（387 个已跟踪文件） | **否**（建议移出索引） | 含鉴权逆向、采集强度、内部复盘；是本事故的最大暴露面 |
| ⚠️ 慎入 | `.verify/` `data/` `backups/` `tools/` | 否 | 已在 `.gitignore`，保持 |
| ⚠️ 慎入 | `.workbuddy/` | 否 | 已在 `.gitignore`，保持 |
| ❌ 不入 | `*.pptx` `*.mp4`（路演材料） | 否 | 二进制大文件，且属对外发布物，不属于代码资产 |

#### 8.0.2 这条决策能解决什么 / 不能解决什么

| 能解决 | 不能解决 |
|---|---|
| 未来新增的敏感内容**不再进入公开面**（从源头切断复发） | **历史里的旧内容仍在** —— 已推送过的 commit 里 `token.ts` 与调研文档仍可被 `git log -p` 翻出 |
| 仓库体积与检索噪音下降，协作方看到的范围收窄 | 若本次主因是 H2（内容举报），**仅靠「今后不提交」不足以消除已存在的暴露** |
| 明确「什么算必要」，减少每次提交时的判断成本 | 不能替代「是否转 private」这个开关 |

> ⚠️ 因此 D1 与「仓库可见性」是**两个独立开关**：D1 管未来，可见性管历史。两者可以叠加，但不能互相替代。

#### 8.0.3 三个执行力度（待主人选定，风险依次递增）

| 力度 | 动作 | 影响 | 风险 |
|---|---|---|---|
| **L1 只约束未来** | 只改 `.gitignore` + 加提交前检查脚本；已跟踪的 387 个 docs **原样保留** | 未来干净，历史不动 | 最低。但公开面仍含全部旧内容 |
| **L2 移出索引** | 在 L1 基础上 `git rm --cached -r docs/` 并提交一次 | 今后 clone 看不到 docs（本地文件**不删**，仍在磁盘） | 中。一次提交删除 387 个文件，历史仍保留旧版本；且未推送的 49 个 commit 顺序需重新核对 |
| **L3 重写历史** | `git filter-repo` 彻底抹掉历史中的敏感文件 | 公开面**真正归零** | 🔴 极高。全部 commit hash 改变 → **137 个本地 tag 全部失效**、49 个待推送 commit 需重建、与 Vercel/文档里所有旧 hash 引用脱节 |

**建议**：先做 **L1**（零风险、立刻生效），L2 等补推完成、远端状态理清后再做，**L3 不建议做**（代价远大于收益，等价效果可由「转 private」以零风险获得）。

### 8.2 P1 · 需主人授权后执行的 GitHub 操作（逐条最小化，一次只做一件）

## 10. 复盘结论（三句话）

1. **主因大概率是行为侧（H1）而非内容侧（H2）** —— 证据是「公开化 1~2 天内出事」+「账号级停权而非仓库级 takedown」+「5 天 30 个 PR 的异常协作密度」。
2. **但内容侧才是长期风险** —— 即使这次侥幸不是它，`token.ts` 与调研文档仍是一份公开的「绕过访问控制」说明书；不解掉，同类事故只是时间问题。
3. **本次真正暴露的不是技术问题，是「无备份、无护栏、无预案」** —— 5 周里唯一撑住项目的是 Vercel CLI 这条旁路，属于运气好而非设计好。
