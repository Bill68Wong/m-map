## 2. 五大机制竞品调研

### 2.1 Google「定位按钮点击即聚焦」机制（需求 4a）

**机制还原**
- 移动端定位按钮（右下角，2025-10 起 Android 改为**罗盘图标 + 圆角方形**）**单击 = 立刻把相机移到当前位置并恢复「跟随」**；拖动地图会退出跟随，按钮进入「未居中」态，再点一次恢复。[来源](https://9to5google.com/2025/10/01/google-maps-location-button/) · [来源](https://www.positioniseverything.net/how-to-use-the-compass-on-google-maps-to-find-north-more)
- 谷歌 Android SDK 的定位按钮行为：点击后**相机恢复跟随当前位置**（`setMyLocationButtonEnabled`）——即**按钮控制相机，而位置由系统持续提供**；用户在远离路线处拖动后，点按钮「跳回蓝点并继续随移动更新」。[来源](https://www.positioniseverything.net/how-to-use-the-compass-on-google-maps-to-find-north-more)
- 关键点：聚焦动作**不等待一次新的 GPS fix**；它使用「**最近一次已知位置**」立即定位，随后由后台的定位流（watchPosition 类）异步刷新蓝点。若**首次进入且无任何历史位置**，则无「已知位置」可聚焦——此时才是唯一必须等首帧 fix 的断点。[来源](https://www.positioniseverything.net/a-step-by-step-guide-on-how-to-change-location-on-google)

**对本项目的启示**：需求 4a「点击后立刻聚焦（不等新 GPS fix，用最近一次定位先聚焦、后台刷新）」= **把「相机聚焦」与「定位获取」解耦**，正是行业做法。断点 = **会话内尚无任何 location（冷启动首帧）**，此时应显示轻量加载态而非无响应。

### 2.2 公共交通「偏好开关」范式（需求 6 轻轨优先）

**竞品做法**

| 竞品 | 偏好形态 | 单选 / 多选 | 「优先某模式」如何定义 |
|---|---|---|---|
| Google Maps | Trip options：最佳路线 / **最少换乘** / **最少步行** / 无障碍 / 最低价；Preferred Modes：勾选公交 / 地铁 / 火车 / 渡轮 | 路线选项＝**单选**；模式偏好＝**多选** | 偏好**重塑排序**，但**不硬性排除**其它可行方案（"preferences reshape the routes it suggests"）[来源](https://www.howtogeek.com/google-maps-features-that-make-public-transit-less-confusing/) · [API](https://googleapis.dev/dotnet/Google.Maps.Routing.V2/latest/api/Google.Maps.Routing.V2.TransitPreferences.Types.TransitRoutingPreference.html) |
| 高德地图 | 公交策略参数（服务端 `strategy`）：0 推荐 / 1 最经济 / 2 最少换乘 / 3 最少步行 / 4 最舒适 / 5 不乘地铁 / 6 地铁图 / **7 地铁优先** / 8 时间短 | 单一策略 | **7＝「地铁优先模式，步行距离不超过 4KM」**——与「轻轨优先」最接近的现成定义 [来源](https://lbs.amap.com/api/webservice/guide/api/newroute) |
| Citymapper | Routing Powers：BUS ONLY / TRAIN ONLY / **SIMPLE（最少换乘）** / MIXED / STEP-FREE；另有 Turbo（时间）/ PRICE（票价）/ Walk Less | **多选过滤器** | 以「过滤器」形态生效；官方说明「**偏好会重新生成路线**」[来源](https://citymapper.com/news/2293) · [来源](https://ridewithvia.com/news/citymapper-the-ultimate-journey-planning-app-unlocks-features-that-make-it-easier-to-prioritize-safety-convenience-and-speed-on-every-trip) |

**对本项目的启示**
- 「轻轨优先」本质是**「软优先 + 容忍阈值」**（`轻轨 totalMin ≤ 当批最慢方案 + 15min`），**不是硬过滤器**——比竞品的「过滤器」更保守、更不易误伤更优方案，方向合理。
- **高德的「地铁优先」有量化门槛（步行 ≤ 4km）**，本项目以「时间容忍 ≤ +15min」为门槛，属同类但更贴合「赶时间」诉求。
- 建议：开关生效时**给用户可感知的标记**（如置顶卡带「轻轨优先」小标），并**保留其它方案**（禁硬隐藏），避免「为什么我的首选方案没了」的困惑。

### 2.3 「赶车提示」类产品（附加需求 · 动态提速提示）

**竞品做法**
- **高德「通勤助手」（成都，与公交集团合作）——最贴合的范式**：进入实时公交后，系统显示最近班次车辆的到站时间；同时**根据距离与步行速度预估用户到站用时**；两者结合后，「**提示用户应该多少分钟后出发，或者是否应该加快脚步**；如果实在赶不上，则推荐用户耐心等待下一辆车」。[来源](https://news.qq.com/rain/a/20230824A09B1900)
- **Citymapper**：「More trips in the next hour」列出未来一小时各班次，可「**Hurry up to catch the previous departure or stay put**」；并给**Tight transfer 标记**（换乘时间基于平均步行速度，「我们步速各不相同」）。[来源](https://www1.citymapper.com/news/2571/pick-the-best-time-to-leave-and-spend-less-time-waiting)
- **Google Maps**：可设「Remind you to leave on time」；支持 `Depart at / Arrive by / Last available`；发车 / 到站时间**分钟级**且官方提示**可能有误差**（「take its advice with a pinch of salt」）。[来源](https://www.makeuseof.com/tag/never-miss-google-maps-feature) · [来源](https://www.techradar.com/features/5-more-things-you-didnt-know-google-maps-could-do/)
- **百度地图**：实时公交含**车厢拥挤度（红黄绿）**与**末班车提醒**。[来源](https://www.toutiao.com/article/7665376051370951203)

**核心计算式（行业共识）**：`能否赶上 = 车辆预计到站时刻 ≥ 当前时刻 + 步行到站用时`，其中 `步行到站用时 = 距离 ÷ 走行速度`（速度按分档）。**只有当「正常速度赶不上、提速能赶上」时才出现提速提示**——正是本次附加需求的场景。

**对本项目的启示**：方向与高德「通勤助手」一致；**可靠性边界是产品红线**——见 §5 R3。

### 2.4 收藏体系范式（收藏大改 0~10）

**竞品做法（Google Maps 为主）**

| 类型 | 对象 | 说明 | 来源 |
|---|---|---|---|
| **地点收藏** | 单个地点 | 三个默认类目：**Starred places（黄星，通用）/ Want to go（绿旗，未来计划）/ Favorites（粉心，常去）**；另有 **Labels（私人命名）** 与 **自定义列表**；一个地点可属多个列表 | [来源](https://geekchamp.com/how-to-save-a-location-on-google-maps) |
| **行程收藏** | 起终点（OD） | **Saved trips（已保存的行程）**：仅**移动端**；仅支持**驾车 / 公交 / 两轮**；是**「常用行程的快捷方式」**，打开后**按当前路况 / 班次重新规划**，**不冻结**具体方案 | [来源](https://support.google.com/maps/answer/7565193?hl=zh-Hans) · [来源](https://geekchamp.com/how-to-save-a-route-on-google-maps-on-android-iphone-and-computer?__v=US-win) |
| 通勤 | 固定 OD | Google「已保存的行程」即为通勤场景；Citymapper 保存 Home / Work / 常去站点 | [来源](https://econsultancy.com/six-features-to-appreciate-about-citymappers-ux/) |

**对本项目的启示**
- 本项目「**组合（OD）+ 地点（单点）**」两类收藏 = 行业「Saved trips + Saved places」的**同构简化**，方向正确。
- **分组（组合在上 / 地点在下）**：Google 把两类放在**不同入口**（Saved trips vs Saved lists），本项目放在**同一页分两段**——都是「按对象类型分组」，可接受；建议**段标题清晰**（如「收藏组合」「收藏地点」）。
- **「点组合即实时规划」= Google Saved trips 行为**（打开即用实时数据重算，不冻结方案）——**完全对齐**，是正解，可放心采纳。
- **「编辑起点 / 终点」**：Google Saved trip 支持改起终点、可删可移；建议组合卡编辑沿用「起终点字段」交互。
- **迁移**：「预设退出历史」时，Google 从不静默删除用户数据——见 §5 R1。

### 2.5 地铁 / 轻轨「进出站步行时间」行业处理（附加需求 · 步行距离化）

**竞品 / 学术做法**
- **通行建模 = 距离 ÷ 速度**：巴黎区域研究把轨道出行的进 / 出站步行拆为「站外距离 + **站内均值距离 c≈250m**」，再除以分年龄段平均步速 **4.3~4.8 km/h**；换乘时间 = 换乘步行 + 站台等待。[来源](https://www.mdpi.com/2673-7590/2/4/49)
- 西安「公交—地铁」换乘研究：取普通步速 **1 m/s**，**可接受的换乘步行时间 5~10 分钟**（对应 300~600m）。[来源](https://ieeexplore.ieee.org/document/9300199/metrics)
- 厦门出行链研究：平均步速 **1.2 m/s**，轨道站 500~800m 集散范围；「800m ÷ 1.2 m/s ≈ 15 分钟」作同一出行链判据。[来源](https://www.mdpi.com/2079-8954/13/11/951/htm)
- Citymapper：明确说明换乘时间**基于平均步行速度**，并提供 `Walk Less` 让用户减少步行。[来源](https://ridewithvia.com/news/citymapper-the-ultimate-journey-planning-app-unlocks-features-that-make-it-easier-to-prioritize-safety-convenience-and-speed-on-every-trip)

**对本项目的启示**：本次「进 / 出站步行**距离化**（正常速度 2 分钟对应的距离）、换乘步行同样距离化（協和醫院 4 分钟 / 蓮花 5 分钟对应距离）、用户可在速度分档内走快」——**与行业标准建模完全一致**；「写死时间」才是反模式。速度分档的设计也与 Citymapper「步速因人而异」的产品主张吻合。

## 4. 21 项需求逐项建议

> 格式：**行业最佳实践** → **用户真实期望** → **取舍建议** → **风险 / 验收点**

### 一、普通功能（1~10）

**需求 1 · 后续班车（altBuses）多线排查**
- **最佳实践**：主流 App 对同一站台的「后车 / 备选线路」按**实际可乘**排序，同一 OD 的多条线并列展示（如「25 / 26」），并各自带 ETA。
- **用户期望**：**「同一上下车站的多条线，我要看到全部，且标签别错」**——不是要新功能，是要「25/26 别只显示一条、别贴错标签」。
- **取舍建议**：数据侧排查 `backfillAltBuses` 非幂等（可能重复 / 漏写）；渲染侧核对 `RecommendCard:261` / `CardDetailClient:239` 的 `hasAlts` 判据；**归因优先看数据生成，再看渲染**。
- **风险 / 验收**：非幂等重建可能反复覆盖。**验收**：选一个「25/26 同上下车站」的 OD，线上实测应同时出现两条且标签正确。

**需求 2 · 多线标签一致性**
- **最佳实践**：顶部总览栏用**线路组**（与本项目推荐界面同款「25/26」）；行程条用**即将乘坐的那一班**的线路（因最终只坐一条）；轨道线路**必须写方向**（Google / 港铁均标终点方向）。
- **用户期望**：**「顶栏是我规划时的样子，行程条告诉我现在该坐哪一班」**——两者语义不同，需分别正确。
- **取舍建议**：① 导航顶栏 = 推荐界面模样（线路组）；② 纵轴流程图旁 = **即将乘坐那班车**的线路标签（能赶上 25 显示 25，能赶上 26 显示 26）；③ 轻轨写**方向**（如「氹仔碼頭方向」）；④ 末尾结构 = 步行 → 终点，并排查「下车站点错误出现在流程图末尾」。
- **风险 / 验收**：当后车切换时标签需同步刷新，避免「标签滞后」。**验收**：25/26 场景 + 轻轨场景各跑一次，标签与方向正确。

**需求 3 · 高德搜索显示**
- **最佳实践**：搜索结果以**地点名 / 站名**为主，弱化行政区划（用户搜的是「聖方濟各堂」而不是「聖方濟各堂區」）。
- **用户期望**：**「别把区名糊在结果里；来源就说『高德』，别写『来自高德』」**——去噪 + 文案自然。
- **取舍建议**：结果去区名（行政区划）；来源文案「来自高德」→「**高德**」；须过文案门禁 `.verify/check-ui-copy.mjs`。
- **风险 / 验收**：去区名后同名地点可能歧义，保留足够的地址信息。**验收**：搜索含区名的地点，结果无区名且来源为「高德」。

**需求 4a · 定位按钮响应慢**
- **最佳实践（见 §2.1）**：按钮＝相机动作，**解耦 GPS fix**；立刻聚焦「最近一次已知位置」+ 恢复跟随，新 fix 异步刷新。
- **用户期望**：**「点下去要有反应」**——不是要更准，是要**即时反馈**（对齐谷歌手感）。
- **取舍建议**：**采纳台账口径**——点击立刻聚焦缓存位置，后台刷新；无缓存（冷启动首帧）时显示轻量加载态。
- **风险 / 验收**：无缓存时的断点要可感知，不能「点了没反应」。**验收**：① 有缓存 → 点击瞬时聚焦；② 冷启动无缓存 → 有加载反馈；③ 后台新 fix 到达后蓝点平滑更新。

**需求 4b · 首页模式定位按钮位置**
- **最佳实践**：控件位置稳定、不重叠（Google 用 map padding 精算控件事位）。
- **用户期望**：**「首页那个按钮回到原位（查看路线下面），别压着 M Map 标」**——这是上轮避让改造的**回归缺陷**。
- **取舍建议**：首页模式定位按钮回到**右边栏「查看路线」图标下方**（品牌栏右列原位）；与需求 11 的「随弹窗避让」区分**模式**（首页默认地图 ≠ 导航模式）。
- **风险 / 验收**：修复不得回退导航模式的避让（需求 11）。**验收**：首页模式按钮在「查看路线」正下方、与 logo 不重叠；导航模式仍随面板避让。

**需求 5 · 底栏帮助图标**
- **最佳实践**：底导图标语义直白（问号 / 信息类图标），同组图标风格统一。
- **用户期望**：**「现在那个 help 图标看着怪」**——图标与项目 Icon 体系不一致。
- **取舍建议**：在**项目既有 Icon 体系内**换一个语义清晰、风格一致的图标（如问号圆标），**禁 emoji**、禁硬编码色。
- **风险 / 验收**：换图标后底导三项视觉权重需平衡。**验收**：底导截图，三项图标风格统一。

**需求 6 · 轻轨优先开关**
- **最佳实践（见 §2.2）**：偏好以「软优先 / 过滤」重塑排序但不硬排除；高德「地铁优先」有量化门槛。
- **用户期望**：**「我想优先坐轻轨，但别为了轻轨让我绕到离谱」**——即「优先」要带容忍上限。
- **取舍建议**：**采纳台账口径**——轻轨优先开关置于导航偏好旁；满足 `轻轨 totalMin ≤ 当批五张卡最慢方案 + 15min` 且**轻轨在营运时间**（时刻表判定、有班次可赶）时，把轻轨方案置顶（三种偏好下均适用）；「含轻轨段的方案」视为轻轨方案；**保留其它方案**并加「轻轨优先」标记。
- **风险 / 验收**：营运时间误判 → 置顶不可乘方案（见 §5 R2）。**验收**：① 可乘场景置顶正确；② 收班后不置顶；③ 无轻轨方案时不报错。

**需求 7 · 轻轨方向文案 + 流程图结构**
- 同需求 2（③ 轻轨写方向、④ 末尾步行 → 终点）；文案格式由设计师出，须过文案门禁。

**需求 8 · 「路网数据暂时不可用」根因**
- **最佳实践**：降级提示应**面向用户可读**、给出下一步（重试），不暴露技术细节；能自动重试则自动重试。
- **用户期望**：**「别老是跳这个、刷新才好」**——要的是**少出现**，不是换文案。
- **取舍建议**：根因归架构师（配额 10044 / 风控 / AMap 代理时段性超时）；产品侧约束：**提示不得外泄技术语言**（禁「开发语言外泄」铁律 33），提供重试；能自动恢复的优先自动。
- **风险 / 验收**：若为配额问题，需容量 / 缓存方案。**验收**：连续规划多次，成功率显著提升、失败时有可重试提示。

**需求 9 · 删除「仅有 X 条路线可用」**
- **最佳实践**：不向用户展示内部处理量的「解释性噪音」。
- **用户期望**：**「这句话没用、还让我怀疑数据」**——删除。
- **取舍建议**：删除 `RecommendCards:83` 文案。**风险 / 验收**：确认删除后无空状态裸露。**验收**：单一方案场景不出现该文案。

**需求 10 · 钉不可见（P0 · 持续）**
- **最佳实践**：地图标记应**不依赖外部资源 + CSS** 的高兼容实现（内联 SVG marker）。
- **用户期望**：**「起点终点两个钉都看不见」**（Android Chrome + 微信双环境）——**功能缺失级**问题。
- **取舍建议**：**采纳台账兜底方向** —— marker content **直接内联 SVG**（不依赖外部文件 + CSS 变量 + filter）；配合 `?diag=pin` 类诊断参数 + Playwright 移动视口复现；**必须真机取证**（桌面正常不等于移动可用）。
- **风险 / 验收**：这是 v3.2.0 已判 P0 的遗留，本批须闭环。**验收**：Android Chrome + 微信真机「选起终点 → 选路线 → 导航全程」双钉均可见。

### 二、收藏大改（0~10）

**需求 0 · 「路线收藏」→「收藏」**
- **最佳实践**：入口名反映内容（含地点 + 组合），用上位词「收藏」。
- **取舍建议**：底导 label 改名「收藏」；文案过门禁。**验收**：底导显示「收藏」。

**需求 1 · 取消预设 + 只收藏组合**
- **最佳实践（见 §2.4）**：收藏对象分「地点 / 行程」两类；系统**不预置**用户收藏（预置易与用户数据混淆）。
- **用户期望**：**「只要我自己的组合和地点，不要系统塞给我的预设」**。
- **取舍建议**：收藏 = 组合（OD）+ 地点（单点）；**系统预置路线全删**（走迁移备份，见需求存量处理）。**风险 / 验收**：删除前**必须备份**（§5 R1）。**验收**：预置清空、用户自建收藏完好。

**需求 2 · 组合卡右侧工具（编辑起终点）**
- **最佳实践**：收藏项可编辑（Google Saved trip 可改起终点）。**取舍建议**：组合卡右侧提供编辑起点 / 终点；沿用以字段编辑的交互。**验收**：改起终点后组合更新且可再次规划。

**需求 3 · 预设退出历史 + 点组合即实时规划**
- **最佳实践**：Saved trip = 快捷方式，**打开即用实时数据重算**（§2.4）。**取舍建议**：**采纳**；「预设」概念整体退役。**验收**：点组合触发与首页同理的实时规划。

**需求 4 · 点组合 = 首页式界面**
- **最佳实践**：进入收藏后的规划界面与主流程**一致**（降低认知成本）。**取舍建议**：地图 + 推荐弹窗；点方案进导航弹窗。**验收**：交互链路与首页一致。

**需求 5 · 组合卡「扁」**
- **最佳实践**：列表密度优化（一屏多放）。**取舍建议**：降低卡高。**验收**：一屏可见组合数提升且信息不丢。

**需求 6 · 分组（组合在上 / 地点在下）**
- **最佳实践**：按对象类型分组（Google 分入口，本项目分段）。**取舍建议**：**采纳**；**段标题清晰**（「收藏组合」「收藏地点」）。**验收**：两段分组正确。

**需求 7 · 地点收藏入口**
- **最佳实践**：从「地点详情 / 已选」处收藏（Google 在地点卡点 Save）。**取舍建议**：搜索结果**确认点击后**，地图顶部搜索框右上角「已选」→「收藏地点」。**验收**：「已选」处可收藏地点且进入地点收藏段。

**需求 8 · 按钮文案统一**
- **最佳实践**：同一动作同一措辞。**取舍建议**：起点终点页 + 推荐弹窗顶部 = 「**收藏组合**」；**导航弹窗内删除收藏键**（导航态不设收藏）。**风险 / 验收**：导航弹窗删除收藏键后确认无遗留入口。**验收**：三处措辞一致、导航弹窗无收藏键。

**需求 9 · 回放交互**
- **最佳实践**：点地点 → 以该地点为目的地进入规划 / 选点（Google 点已保存地点即给方向选项）。**取舍建议**：点组合 → 首页式规划；点地点 → 首页式选点（目的地 = 该地点，「我的位置」为默认起点、可改）。**验收**：两类点击行为分别正确。

**需求 10 · UI/UX（精美清爽舒适）**
- **最佳实践**：延续既有设计 Token 与品牌体系。**取舍建议**：全程走 Token、禁硬编码色、禁紫粉渐变、禁 emoji 图标；配色 / 间距沿用 v3.2.0 体系。**验收**：视觉一致性 + 可读性。

### 三、附加需求（步行模型细化）

**附加 A · 轻轨站进出站步行「距离化」**
- **最佳实践（见 §2.5）**：步行时间 = 距离 ÷ 速度。**取舍建议**：进站→站台、站台→出站统一为「**正常步行 2 分钟对应的距离**」（不写死时间），用户可在速度分档内走快；**不含换乘**。**验收**：速度分档切换时，步行用时随之变化（同一距离）。

**附加 B · 换乘步行距离化**
- **最佳实践**：换乘时间 = 换乘步行 + 等待（§2.5）。**取舍建议**：協和醫院 **4 分钟**、蓮花 **5 分钟**对应距离，同样距离化。**验收**：两处换乘距离随速度分档变化。

**附加 C · 动态提速提示**
- **最佳实践（见 §2.3）**：`能否赶上 = 车辆预计到站 ≥ 现在 + 距离÷速度`；仅「正常赶不上、提速能赶上」时出现；高德语式「是否应该加快脚步」。
- **用户期望**：**「告诉我走快一点能不能赶上这班」**——一个决策，不是一堆数字。
- **取舍建议**：文案「**走快一点可赶上 XX:XX 那班**」（格式由设计师出）；**仅在存在明确提速窗口时出现**；措辞用「可赶上 / 有望」而非「一定」。**风险 / 验收**：见 §5 R3（不可误导）。**验收**：构造「正常赶不上 / 提速能赶上」场景，提示出现且时刻正确。

## 5. 风险清单

| # | 风险 | 影响 | 缓解建议 |
|---|---|---|---|
| **R1** | **收藏迁移数据安全（预设留备份后全删）** | 用户既有收藏丢失 = 严重信任事故 | **双层备份**（导出 JSON 文件 + 本地隐藏备份键，架构师定）；**迁移前先读旧存储（`must.favorites.v2`）并兼容映射**；删除仅针对**系统预置**，**用户自建一律保留**；删除操作**二次确认 + 可回滚** |
| **R2** | **轻轨优先误判**（营运时间判定错 / 收班 / 临时调整） | 置顶**不可乘**方案，用户白等 | 营运时间判定以时刻表为准 + **班次可赶**双条件；**保留其它方案**并在置顶卡标「轻轨优先」；判定边界（末班 / 首班）专项复验；不确定时**不置顶**（fail-safe） |
| **R3** | **赶车提示可靠性边界** | 误导致用户跑着赶不上 / 安全风险 | **只做保守提示**：仅在有明确窗口时出现，措辞「可赶上 / 有望」，**禁止「一定赶得上」**；考虑步行速度分档的低估（用较慢档估算更安全）；误差大时不提示 |
| **R4** | **钉不可见（P0）复现依赖真机** | 桌面 / 仿真通过但移动仍坏 | 内联 SVG 兜底（不依赖外部资源）+ Android Chrome / 微信**双真机取证** + `?diag=pin` 诊断 |
| **R5** | **路网不可用若为配额** | 时段性不可用反复出现 | 架构师做触发统计 + 重试 / 缓存 / 代理加固；产品侧**不暴露技术细节** |
| **R6** | **定位按钮聚焦「无缓存」断点** | 冷启动点击无反应 | 无缓存时显示轻量加载态；有缓存则瞬时聚焦 |
| **R7** | **altBuses 非幂等** | 重建反复污染数据 | 先修数据生成（幂等）再验证渲染；避免重复写入 |
| **R8** | **多线标签切换滞后** | 显示错误班次 | 标签随「即将乘坐班次」实时刷新；切换瞬间去抖 |
| **R9** | **视觉硬编码色值 / emoji**（P0 红线） | 违反 Token 体系与规范 | 一律走 Token（唯一例外 `#fff`/`#000`）；禁 emoji 图标；文案过门禁 |

**明确「不做」（行业有、但个人项目 / 数据受限不适合）**
- 不做「Lock Screen / 通知栏级」赶车与下车提醒（PWA 能力受限，用页面内提示替代）。
- 不做「云端账号同步收藏」（Google Saved 全云同步）——本项目为本地存储（`localStorage`），继续本地 + 备份即可。
- 不做「车厢拥挤度 / 最佳车厢 / 最佳出口」（百度 / Citymapper 级）——无对应数据源。
- 不做「多模式联程（公交+骑行+网约车）」——超出本项目范围。

## 6. 待澄清 / 需裁决

1. **轻轨优先的「营运时间」判定口径**：以「首末班时刻表」为准，还是叠加「末班车已过但仍可赶」的宽限？建议**区间 + 可赶班次**双条件，边界（首班前 / 末班后）由架构师与用户确认。
2. **提速提示的出现窗口阈值**：多远 / 多久内才提示（避免刷屏）？建议由设计师 + 架构师定一个保守窗口。
3. **收藏迁移备份的「双层」具体形态**：导出 JSON（用户可见）+ 本地隐藏键（用户不可见）——由架构师定，产品侧要求「可恢复、不丢用户数据」。
4. **首页模式 vs 导航模式 FAB 的两套位置规则**：需与设计师、架构师对齐（首页=右列原位；导航=随面板避让）。
5. **「地点收藏入口」的触发时机**：搜索结果「确认点击后」才出现「收藏地点」，需与设计师确认「已选」态的表现。
