## 1. 【P0】钉不可见

### 1.1 现状复盘（「修复为何未生效」）

- v3.2.0 已把两个 SVG 的颜色改为**字面量**（`public/pin-destination.svg` 第 25 行 `fill="#0b6e4f"`、`pin-origin.svg` 第 18 行 `fill="#B4342A"`）——**确已生效**，但用户移动端仍不可见。
- 钉的渲染链（两钉同构）：`NavMap` 建 marker（`content: '<div class="nav-map__destpin">'`，`NavMap.tsx` L581-591 / L624-634）→ CSS class（`globals.css` L2115 `.nav-map__destpin` / L4096 `.nav-map__originpin`）→ `background: url("/pin-*.svg") center/contain no-repeat` + `filter: drop-shadow(var(--destpin-shadow))`。
- 结论：颜色修复只解掉了「`var()` 不穿透」这一环；**外链文件 + CSS `background` + `drop-shadow filter` 三段仍在**。桌面（Chrome/Blink）能画，移动端不可见 ⇒ 失败点在**这三段在 Android WebView / WKWebView 的兼容性**，或 marker 未落位。

### 1.2 移动端特有路径分析（候选根因，按可能性排序）

| # | 假设 | 机理 | 与「桌面正常、移动双环境不可见」的吻合度 |
|---|---|---|---|
| H1（**首选**） | **外链 SVG 经 CSS `background` 在移动 WebView 未加载/未合成** | `background: url(...) center / contain no-repeat` 与 `filter: drop-shadow()` 叠加；部分 Android WebView 对「异步加载背景 + GPU filter」的层合成返回空绘制 ⇒ div 无内容（**该 div 无背景色兜底**）⇒ 不可见 | 高：与内核/合成器相关，桌面不受影响 |
| H2 | **`filter: drop-shadow()` 致整层透明** | `filter` 建立新合成层，个别 WebView 对 `filter` + 背景图的层返回透明 | 高 |
| H3 | marker **未创建 / 被移除**（时序） | 移动端首屏 `phase` 就绪时序、resize/orientation 重建、或 `origin` 为 null（起点用「我的位置」） | 中：可用 `?diag=pin` 计数直接判定 |
| H4 | **取景不含钉**（off-screen） | 移动端视口窄、`fit-box`/`dest-center-top` 计算差异致钉落屏外 | 中 |
| H5 | marker `offset` 在移动端被裁剪 | `offset:(-10,-26)`；若容器尺寸测量异步，钉尖锚点偏差（仍应可见，不太可能「完全不可见」） | 低 |

> 判据：H1/H2 是「画得出但看不到」；H3/H4 是「根本没画/画在屏外」。`?diag=pin`（§1.4）能一次区分。

### 1.3 修复兜底：**内联 SVG**（ADR-102）

**目标**：marker `content` 直接内联 SVG 字符串，**彻底摆脱**「外部文件 + CSS background + drop-shadow filter」三段。

**两钉 SVG 字符串**（几何沿用现有文件：`viewBox 0 0 32 42`，钉头圆心 (16,19) r9.5，钉尖 (16,40)，切点 (7.53,23.3)/(24.47,23.3)）：

- 终点（绿 `#0b6e4f`）：
```
<svg viewBox="0 0 32 42" width="20" height="26" xmlns="http://www.w3.org/2000/svg" aria-hidden="true"><path d="M7.53 23.3 L16 40 L24.47 23.3 A9.5 9.5 0 1 0 7.53 23.3 Z" fill="none" stroke="#fff" stroke-width="2" stroke-linejoin="round"/><path d="M7.53 23.3 L16 40 L24.47 23.3 A9.5 9.5 0 1 0 7.53 23.3 Z" fill="#0b6e4f"/><circle cx="16" cy="19" r="3.8" fill="#fff"/></svg>
```
- 起点（红 `#B4342A`）：同上，仅 `fill="#B4342A"`。

**接入形态**（保留 `.nav-map__destpin/.nav-map__originpin` 类 → QA 选择器与既有断言不失效）：
```
content: '<div class="nav-map__destpin" aria-hidden="true">' + INLINE_SVG_DEST + '</div>'
```
- `INLINE_SVG_DEST/ORIGIN` 定义在 `NavMap.tsx` 顶部（或新 `src/lib/nav/pin-svg.ts` 纯字符串模块）——**单一真源**。
- **CSS 调整**：`.nav-map__destpin/.nav-map__originpin` 去掉 `background: url(...)`；改 `display:flex`（或 `.nav-map__destpin svg{display:block}`）；**保留** `width/height: var(--destpin-w/h)`；`filter` **改为可选**（可保留 `drop-shadow` 作增强，但**不得成为可见性的必要条件** —— 故 SVG 自带白色描边外圈，无 filter 也清晰）。
- **与 offset 配合**：裁到 `width=20 height=26`（= `--destpin-w/h`）⇒ **offset 仍为 `new AMap.Pixel(-10, -26)`**（钉尖=底边中点）；zIndex 不变（起点 110 / 终点 120）。
- **回退**：两钉类名与钩子保留，若内联 SVG 仍异常，可按 §1.4 取证后调整（如把 `filter` 整体删除、或改用 `AMap.Icon` image）。

### 1.4 实机诊断路径：`?diag=pin`

**目标**：用户在手机上打开带参链接 → 页面渲染诊断浮层 → 截图即可定位根因。

**实现规格**（新增 `src/components/nav/PinDiag.tsx`，`"use client"`）：
- **入口**：`NavShell` 读 `new URLSearchParams(location.search)`；含 `diag=pin` → 渲染 `<PinDiag/>`（`position:fixed; left/right:8px; bottom:8px; z-index:9999`，等宽字体、可滚动、`pointer-events:auto`）。**生产默认不渲染**（仅带参触发，零性能影响）。
- **采集项**：
  1. `document.querySelectorAll(".nav-map__destpin").length` / `.nav-map__originpin` 计数；
  2. 每钉 `getBoundingClientRect()`（x/y/w/h）+ `getComputedStyle(el)` 的 `width/height/backgroundImage/filter/display`；
  3. 首个子节点标签（应为 `svg`）与其 `getBBox()`；
  4. 地图状态：`[data-map]`、`[data-nav-z]`（既有钩子读实际 zoom）；若能取到 map 实例，读 `getCenter()/getZoom()`；
  5. marker 创建日志：`NavMap` 在创建/移除两钉时 `window.__pinLog?.push({t, which, ok, err})`（可选，`?diag=pin` 时才采）；
  6. 环境：`innerWidth/innerHeight`、`devicePixelRatio`、`window.visualViewport?.scale`、`navigator.userAgent`。
- **判读**：
  - 计数=0 → H3（未创建）；计数>0 但 rect 为 0×0 / `backgroundImage` 为空或 svg 无 bbox → H1/H2（未绘制）；rect 在视口外 → H4（取景）。
- **文案**：中文、无 emoji、`prefers-reduced-motion` 不涉动效；仅在诊断浮层出现，不进用户主界面。

### 1.5 回归与真机清单

- Playwright 移动视口（iPhone/Pixel 设备仿真）跑：显式选起点+终点 → 断言 `.nav-map__originpin/.nav-map__destpin` 计数=1 且其内部存在 `<svg>`；截图人工核对。
- Android 真机（Chrome + 微信各一次）：`?diag=pin` 截图 → 按 §1.4 判读 → 修复后复验「起点红钉 + 终点绿钉全程可见」。

## 2. 【P0】「路网数据暂时不可用」

### 2.1 触发口径（代码链，5 个返回点）

`fetchTransitPlans`（`src/lib/amap/transit.ts`）**任何失败都收敛为 `{ok:false, degraded:true}`**，触发点：
1. `acquireToken(RATE_BUCKET.transit)` 抛错 → `限流器不可用`（L520）；
2. 取不到令牌 → `rate_limited`（L523）—— 3 QPS 全 Key 共享桶；
3. `fetch` 抛错 / **超时**（`TRANSIT_TIMEOUT_MS=1500`，L533）→ `请求失败`；
4. `json.status !== "1"` → 带 `infocode`（L545；如 **10044 日配额** / **20003 无路网**）；
5. `route.transits.length === 0` → `no_plan`（L557）。
上层 `nav-service.ts`：`transitOk=false` ⇒ `degraded=true` 且 `emptyReason='amap_unavailable'`（L596/L613）→ 前端 `RouteResultPane` 显示「路网数据暂时不可用，以下为估算结果」（L62）/ 空态标题（L19）。另 `ComboPlans:215` 同文案。

**已有缓解**：`nav-service` L416-419 对**首次失败自动重试一次**（`TRANSIT_RETRY_DELAY_MS=350`）。

### 2.2 线上实测（本次探针）

**A. 直连高德 transit（本地，绕开我们的桶）** — `.verify/probe-v330-amap-transit.mjs`，N=12：
- 成功 11/12（`infocode=10000`，方案数 7）；**超时 1/12（1503ms，恰卡在 1500ms 预算）**；**配额 10044 = 0 次**；**无路网 20003 = 0 次**；延迟 p50 **246ms**、max 1503ms。
- ⇒ 直连（亚洲→中国）**根因不是配额**，是**边界超时**。

**B. 生产 `/api/nav`（prod 真身 iad1 → 高德）** — 6 次 `nocache=1`：

| # | ok | degraded | transitMs | transitOk | amapPlans | 总 ms |
|---|---|---|---|---|---|---|
| 1 | true | false | 2973 | true | 7 | 7860 |
| 2 | true | **true** | **7092** | **false** | **0** | 8270 |
| 3 | true | false | 3508 | true | 7 | 4854 |
| 4 | true | false | 7081 | true | 7 | 9209 |
| 5 | true | false | 3739 | true | 7 | 5101 |
| 6 | true | false | 3855 | true | 7 | 5189 |

- 生产 `transitMs` = **2.97~7.09 秒**，是本地（246ms）的 **12~28 倍** ⇒ 印证「函数真身 iad1（美东）→ 高德（中国）」的跨洲 RTT。
- `transitMs ≈ 3000` 的结构 = **首次超时（~1500ms）+ 重试成功（~1500ms）**；`transitMs ≈ 7000` 且 `transitOk=false` = **两次都超时 → 降级**（#2）。
- ⇒ **根因判定：`TRANSIT_TIMEOUT_MS=1500ms` 与生产真实 RTT 不匹配**；绝大多数调用的第一次尝试都超时（靠重试侥幸兜住），偶发两次都超时即降级 → 用户体感「经常出现、刷新后才好」（刷新=再触发一轮，通常能过）。**与配额无关，与 JS 代理无关**（transit 走服务端 `AMAP_KEY` 直连，不经 `/_AMapService` 代理）。

### 2.3 修复方案（ADR-103）

| 项 | 现状 | 建议 |
|---|---|---|
| 超时预算 | `TRANSIT_TIMEOUT_MS=1500` | 上调至 **4000ms**（可配 `AMAP_TRANSIT_TIMEOUT_MS`）；`maxDuration=30`，余量充足。使**首次即成功**，去「超时+重试」的翻倍耗时 |
| 重试 | 一次，延迟 350ms | 保留一次；延迟可到 250ms；**两次仍失败才降级**（现状已够，配合上调后降级率大降） |
| 限流取令牌 | `acquireToken`（不等待） | **主调用改 `acquireWithWait(transit, 800ms)`**：把「瞬时桶空」从「降级」改为「短等 ≤0.8s」；补查（s=7/8）仍用 `acquireToken` |
| 缓存 | `transit_cache` TTL 60s | 保持；可对**热 OD** 用 cron 预暖（可选，非必需） |
| 降级文案 | 「路网数据暂时不可用，以下为估算结果」 | 保留功能（估算卡仍在），文案**软化**为刷新提示（文案门禁核查）；`amap_unavailable` 空态标题同理 |
| 观测 | 无 | 探针保留 `.verify/probe-v330-amap-transit.mjs`；建议在 `stats` 暴露 `infocode` 分布（仅诊断） |

### 2.4 验证

- 修复后重跑 §2.2-A（应 0 超时）与 §2.2-B（`transitMs` 应落到 ~1500~3500ms、`degraded` 显著下降；连续 20 次统计降级率）。
- 断言用观测钩子/契约（禁硬编码条数）。

## 3. 后续班车多线（altBuses / parallelRoutes）

### 3.1 线上实测（复现）

- OD：石排灣郊野公園 → 連貫公路/新濠天地（25/26 共同走廊；DB 实测 **25∩26 = 17 个共同站**）。**线上 `/api/nav` 结果**：
  ```
  count 5  degraded true  empty null
  card 900002 本地补充 | rides: 25[-] | alts: (none)
  card 900003 本地补充 | rides: 25[-] | alts: (none)
  card 900004 本地补充 | rides: 26[-] | alts: (none)
  card 900006 本地补充 | rides: 26[-] | alts: (none)
  card 900007 本地补充 | rides: 26[-] | alts: (none)
  ```
  ⇒ **25 与 26 各成独立卡**（未合成「25/26」并行组）、`parallelRoutes` **全为 undefined**、`altBuses` **全空**。**用户投诉可复现。**

### 3.2 数据链排查

```
高德腿 bls.length > 1 → leg.parallelNames（transit.ts L266-274）
  → bridgeLeg: routeCodeOf(name) → parallelRoutes（map-stations.ts L211-215）
  → siblingSeedsOf（parallel-alts.ts）→ 服务端建模各并行线 → siblingAlts（nav-service L510-529）
  → backfillAltBuses 合并主干线 + 并行线 alts（nav-service L654-674）
```
- **关键事实**：`parallelRoutes` **只在「高德腿」生成**（来源 `AmapPlanLeg.parallelNames`）。**本地枚举**（`searchStationPaths`）按线路**各出一卡**，**不做**「同 OD 并行线合并」。
- 本 OD 线上 `degraded=true`（高德超时，§2）⇒ 候选**全部来自本地枚举** ⇒ 25、26 各成一张卡；`parallelRoutes` 恒空 ⇒ `siblingAlts` 无从产生 ⇒ **无「25/26」并行标签、无跨线 altBuses**。
- 即便高德不降级：也只在**同一 segment 含多条 busline**时才生 `parallelNames`；此 OD 该条件未必满足 ⇒ 并行合并仍可能不触发。
- `backfillAltBuses` 已知**非幂等**（Spec 标注），且以「第 N 张卡最慢 `totalMin`」为阈值、**仅覆盖首段** ⇒ 换乘卡的第 2 段不会有 altBuses、空实时池时 `alts` 缺（本 OD 即 `(none)`）。

### 3.3 修复方向（Q2 裁定：先①；②后置）

1. **本地候选补 `parallelRoutes`（Q2 采纳·先做）**：枚举出 `board→alight` 后，用 `routeIdx.adjOwners`/同邻接对求「同 board/alight 的其他线路」，填入 `RideSegment.parallelRoutes` ⇒ 卡片标签得以渲染 `25/26`（对齐台账 #2「推荐界面模样」）。
2. **同 OD 并行线合并成一张卡（Phase 2 评估）**：在 `mergeSources` 后对「首段 board/alight 相同、其余段相同」的卡做归并（主干线 + `parallelRoutes`），并合并各自 alts。
3. **修 `backfillAltBuses` + 覆盖组合内每条线（team-lead 硬要求）**：
   - **硬要求（合并为一组验收项）**：用户报告场景是「25/26 组合卡上的**后续班车只出单线**」⇒ `altBuses` 生成**必须覆盖组合内每条线的后续班车**（非只算主干线一条）；
     - 实现：`backfillAltBuses` 的 groups = 主干线 alts **+** 各 `parallelRoutes` 的 sibling alts（`siblingSeedsOf` 已能造 sibling，需确保**在本地候选路径也走同一逻辑**，而非仅高德路径）；
     - 验收：25/26 组合卡应列出 25 与 26 **各自的**后续班车（按线分组、标签正确、无重复/无串线）。
   - **幂等**：改「每次重建」而非累加；明确**空实时池**（该线无实时 ⇒ 该线不列，不影响他线）与**换乘卡仅首段**口径。
- 边界：并行判定**以我们站序为准**（不迷信高德名），`routeCodeOf` 只作高德侧补充。

## 4. FAB 首页模式位置（需求 4b）/ 顺带 4a

### 4.1 根因

- `.nav-locate-fab`（`globals.css` L2558）**无条件渲染**（`NavShell.tsx` L449-458）。
- 首页模式无面板 ⇒ `--sheet-y-anim` 未设/为 `100dvh` ⇒ `bottom: max(100dvh - 100dvh + space3, tabbar+safe+space3)` = `tabbar+safe+space3`；`right: space3`。
- 而 `.nav-brandbar`（L2449）也固定在 `bottom: calc(tabbar+safe+space3)`、右列 `.nav-brandbar__acts` 亦右对齐（含「查看路线」/「M Map」标）⇒ **同坐标重叠** = 用户所见「FAB 与 M Map 标重叠」。

### 4.2 修法（台账 #4b 指定）

## 5. 轻轨步行「距离化」+ 动态提速提示

### 5.1 现状

- 速度五档：`SPEED_RATIO`（`types.ts`）：档1 冲刺 3.6 · 档2 小跑 2.0 · 档3 正常 1.4 m/s · 档4 慢 1.0 · 档5 极慢 0.7；**常速基准 `WALK_BASE_M_PER_MIN=84`**。
- 距离→分钟**只用一个基准**（`walk-fix.ts#walkMinutes = 距离 ÷ 84`）；分档缩放**只在读端** `catch-up.ts#requiredSec`（乘 `SPEED_RATIO` / 档1 用 `tier1EffRatio`）。铁律：**禁止双重缩档**。
- 进/出站与换乘步行：当前多为「时间口径」——LRT 站内换乘读 `transfer_walks`（`transfer_walks` 无样本时 `TRANSFER_FALLBACK_MIN=3` 兜底）；进出站步行多随高德几何/实测，**时间已被固定** ⇒ 用户无法在分档内走快。

### 5.2 「距离化」设计

- **口径**：把「进站→站台 / 站台→出站」与「换乘步行」统一改为**距离（米）**；分钟 = 距离 ÷ 84（读端再按档缩放）。
- **折算基准（2/4/5 分 × 84 m/min）**：
  - 进站→站台 = **168 m**；站台→出站 = **168 m**（正常步行 2 分对应距离）；
  - 協和醫院换乘 = **336 m**（4 分）；蓮花换乘 = **420 m**（5 分）。
- **数据落点**（二选一，建议 A）：
  - A（Q4 采纳·先落）. 常量表（`src/lib/recommend/types.ts`）：`LRT_STATION_WALK_M = { in:168, out:168, transfer: { "LRT-UH":336, "LRT-LOT":420 } }`；**预留「表化接口」**（读取走单一取值函数，日后表化不改调用方）；
  - B（后置）. 表 `transfer_walks` / `station_walk_distance`：把上述距离登记为对应行（走 db-guard；一致性由脚本校验）。换乘既有 `transfer_walks` 已按 `(下车站|上车站)` 建键，故 B 更贴既有结构。
- **落入点**：`model.ts` 的 LRT 段 walkOut/walkIn/换乘分钟由「距离 ÷ 84」产出；**不写死分钟** ⇒ 分档自然生效。

### 5.3 动态提速提示（「正常走赶不上、走快能赶上」）

- **算法**（纯复用既有档位判定，零新模型）：
  ```
  对候选发车 dep：
    t3 = pickCatchTier(walkMin, depSec, distM)          // 正常速（档3方向）能否赶上
    tFast = pickCatchTier(walkMin, depSec, distM, 强制档1/2 覆盖) // 提速能否赶上
    若 t3 === null 且 tFast ∈ {1,2} → 提示「走快一点可赶上 HH:MM 那班」
  ```
  注：`pickCatchTier` 从慢到快返回**首个满足**的档；「正常赶不上」= 返回 null；「提速能赶上」= 档 1/2 的 `requiredSec ≤ depSec`。等价实现：比较 `requiredSec(walkMin, 3, distM)` 与 `requiredSec(walkMin, 1|2, distM)` 对 `depSec` 的关系。
- **触发面**：轻轨首段（有明确 `depMs`）最自然；巴士首段可选（有 `loSec` 时）。
- **文案**：设计师出（格式如「走快一点可赶上 15:32 那班」），过 `.verify/check-ui-copy.mjs`。
- **边界**：仅在**已能走到站台**（不然提示无意义）且该班为「可赶候选」时给；`distM` 未知时档1 退回线性（既有行为）。

## 6. 轻轨优先开关

### 6.1 目标（台账 #6）

勾选后**在三种偏好下**，把满足阈值的**轻轨方案**置顶。阈值：`轻轨 totalMin ≤ 当批五张卡里最慢方案 totalMin + 15min`；且轻轨**须在营运时间**（时刻表有可赶班次）。「含轻轨段」即轻轨方案。

### 6.2 注入点与实现

- **注入点 = 排序之后、`limit` 之前**（`nav-service.ts` 的 `ranked` 已排 → 取前 N 之前）：
  ```
  const ranked = rankItems(merged.items, prefs);
  const withLrtTop = applyLrtPriority(ranked, cards-limit, prefs); // 新纯函数
  const cards = withLrtTop.slice(0, limit).map(r => r.card);
  ```
  作为**独立后置**（不污染 `score.ts#cmpByPref` 三档主判据，避免「偏好语义被轻轨开关改写」）。
- **`applyLrtPriority(items, limit, enabled)`**：
  1. 取**当前前 `limit` 张**（= 当批面板要展示的卡）的最慢 `totalMin` 作基线；
  2. 候选 = **含轻轨段**的 items；
  3. 过滤：`card.totalMin ≤ 基线 + 15` **且** 营运时间（见 6.3）；
  4. 命中的轻轨方案按 `totalMin` 升序**提到最前**，其余相对序不变（稳定）。
- **参数传递**：`/api/nav` 新增可选 `lrtFirst=1`（照 `prefs` 模式，非法回落关闭）；前端偏好区旁新增开关（设计师出 UI）。`switch-plans` **不适用**（组内维持 `totalMin`，与本开关无冲突）。

### 6.3 营运时间判定（数据）

- 轻轨「有班次可赶」= 该方案轻轨段的下一班 `state==='running'`（复用 `LrtLive.state` / `next-departures` 的 `before_first|after_last|no_data`）。**不新增时刻判断逻辑**。
- 边界：跨午夜续班（`hour>23`）由既有单轴口径覆盖；无轻轨数据的方案不进候选。

### 6.4 边界与回归

- 基线依赖「当批五张卡」，故必须在 `ranked` 已定、`slice(limit)` 之前算；
- 开启开关**不得**改变非轻轨卡相对序、不得新增/删除卡片（只重排）；
- 回归：固定 OD 对拍「开/关」两态，断言「命中轻轨卡被提到最前、其余相对序不变、张数不变」（禁硬编码条数）。

## 10. 【新增排查 · 高优先】石排灣 → 科大 路由漏洞（石排湾线换乘缺失）

> 用户发现：导航「石排灣→科大」推荐「**步行到協和醫院上车**（氹仔线）」，而正确解应含「**石排灣上车（石排湾线）→ 協和醫院换乘（氹仔线）→ 科大**」。归因用户「研究这个问题，以及它反映的模型漏洞」。

### 10.1 线上实测（显式 OD，GCJ-02）

| OD | 结果 | `localCand` | `localKept` | 关键卡 |
|---|---|---|---|---|
| **石排灣→科大** | 6 卡（全 Amap） | **131** | **0** | card2 = `walkOut 12.6 → 協和醫院` + `氹仔线 協和→科大`；**无石排湾线卡** |
| 石排灣→協和（分段） | 3 卡 | 101 | **1** | **[LOCAL] 900018 = `lrt:石排湾线`（walkOut 0）** ⇒ 石排湾线本地枚举/实时**正常** |
| 協和→科大（分段） | 6 卡 | 67 | 0 | card1 = `氹仔线`（Amap）⇒ 氹仔线正常 |
| 石排灣→科大（Amap 降级态，`amapPlans:0`） | **0 卡** | 131 | **0** | **本地兜底全部落空 ⇒ 空结果** |

- 结论：**石排湾线作为首段、氹仔线做末段，单独都成立**；**组合（跨线换乘）的本地候选被系统性丢弃**——`localCandidates=131` 而 `localKept=0`（跨 3 次复现稳定，含 Amap 降级态）。

### 10.2 根因：本地候选「覆盖度 ≥0.5」质量闸门系统性误杀（仅作用于本地）

- 合并闸门 `src/lib/nav/merge-sources.ts#applyLocalGates` 五闸门，其中**闸门 3 = 覆盖度 ≥0.5**（仅对**本地**候选生效；**Amap 候选不过闸门**）。
- 覆盖度定义 `src/lib/nav/recompute.ts#ourDataCoverage = 我们数据分钟 ÷ 门到门总时长`——**分子只含「乘车段 + 非估算换乘」，不含步行（walkOut/walkIn）与任何等待**（`totalMin` 含它们）。
- ⇒ 对「**步行/等待占比高**」的方案，覆盖度天然偏低：本 OD 的「石排灣→協和(102s)→協和换乘(4min)→氹仔线→科大」全轻轨方案，**乘车+换乘 ≈ 11.8min，而两次轻轨等待（班次稀疏）可能 >10min** ⇒ 覆盖度 ≈ 0.4 < 0.5 ⇒ **被闸门丢弃**。
- 而 Amap 的「步行到協和 + 氹仔线」卡**不过闸门** ⇒ 幸存并显示 ⇒ 正是用户所见。（分段 OD「石排灣→協和」因等待短而覆盖度达标 ⇒ 本地卡保留，反证机制。）
- 其余闸门已排除：闸门 5 `suspect` 对本地**硬编码 false**（`nav-service.ts` L556）；Amap 降级态无重复（闸门 4a 不适用）；LRT/巴士段均可解（闸门 2 不适用）。

### 10.3 高德解析复查（历史「石排灣→大三巴 轻轨+打车」）

- 本次 OD：`amapPlans 8 / bridged 8 / dropped []` ⇒ **高德解析无异常**；但高德**根本没给「石排湾线」组合**（Amap 把轻轨标「地铁」，且不含石排湾线支线）⇒ 该组合**只能由本地枚举提供**，而本地被闸门丢弃。
- 历史「轻轨+打车未正确解析」与本条**同族**：**轻轨组合的候选来源脆弱**（Amap 侧缺/乱 + 本地侧被闸门杀）。

### 10.4 归纳的模型漏洞（用户所求）

1. **质量闸门口径偏差**：`ourDataCoverage` 把「步行 + 等待」排除在分子外，又**只对本地候选**施加 ⇒ 系统性**压制本地来源**、**优待 Amap**；对**轻轨（班次稀疏、等待长）**尤甚 ⇒ 全轻轨 / 轻轨换乘方案被误杀。
2. **轻轨换乘候选被误杀**：跨线轻轨换乘（石排湾线→氹仔线@協和）**只能靠本地枚举**，却恰是被覆盖度闸门杀掉的一类 ⇒ 「轻轨换乘」在结果里系统性缺席。
3. **短支线首段无保护**：石排湾线（1 区间支线）作为首段时，其短乘车时长 + 长等待 + 换乘 **拉低覆盖度**，无任何豁免 ⇒ 支线首段方案易被淘汰。
4. **降级脆弱性**：Amap 降级时，本地兜底因闸门全灭 ⇒ **该 OD 直接空结果**（用户体验塌方）。
5. **观测盲区**：`/api/nav` 的 `stats.dropped` **只记 Amap 解析丢弃，不记合并闸门丢弃** ⇒ 本类问题长期不可见（本次靠分段对拍才定位）。

### 10.5 修法（建议）

1. **覆盖度口径修正（核心）**：把「**由时刻表/间隔推导的等待**」与「**步行（有实测/几何依据）**」纳入「我们的数据」分子；或分母改为「**本可由我们数据覆盖的时段**」。最小改动：`ourDataCoverage` 中 `if (r.kind==='lrt') ours += r.minutes + (r.waitMin ?? 0)`（轻轨等待来自时刻表 = 我们的数据），并对 `walkOut/walkIn` 按来源（level≤2 视为实测）计入。
2. **轻轨方案豁免闸门 3**：全轻轨或「首/末段含轻轨」的本地候选豁免覆盖度闸门（LRT 段本就是我们的数据，等待是真实信息非估算）。
3. **观测补齐**：把 `mergeSources` 的 `dropped`（含 `low_coverage(x)` 等）并入 `stats`，长期可见。
4. **验收项（并入 Spec）**：给定 OD「石排灣→科大」，**必须**出现「石排湾线→協和换乘氹仔线→科大」候选，且 `totalMin` 与他卡并列前位；Amap 降级态**不得**空结果（本地兜底应至少出该方案）。
5. **历史同族**：一并回归「石排灣→大三巴」——确认轻轨组合不再因解析/闸门缺席。
